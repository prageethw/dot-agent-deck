# Concurrent orchestrations and the shared-clone model — design record

> **Developer / maintainer reference.** This page documents internal rationale and is intentionally excluded from the published documentation site (CLAUDE.md rule 11). It exists so a future contributor doesn't have to rediscover Model A/B/C's divergence, or the ownership-attribution mechanism's two-attempt history, the hard way — the way [PRD fork#325](../../prds/fork-325-shared-clone-architecture.md)'s own investigation had to.

## The incident this all exists to prevent

Two orchestrations running concurrently against **one root checkout** — one `.git` object store, one worktree registry — is not automatically safe. On 2026-08-14, on one deck running three-plus concurrent orchestrations, this happened twice in one evening:

1. An orchestration deleted five worktrees it did not own, mid-use — one vanished while a reviewer was actively working in it.
2. An orchestration ran a shallow fetch. `.git/shallow` lives in the **common dir**, shared by every linked worktree — so one orchestration's fetch broke merge/rebase for every orchestration on the box, silently. Symptoms looked like a corrupt or wrong remote, not a truncated one; the tell was a branch measured hours apart going from "78 behind / 7 ahead" to "1 behind / 1122 ahead" — an absurd enough number to investigate.

Neither failure left a trace of who did it. Both are what [issue #325](https://github.com/prageethw/dot-agent-deck/issues/325) reports, and what this whole line of work closes.

## Three provisioning models, and why they diverged

Before this PRD, the repo had three call sites that provision a worktree/clone for a new orchestration or task, and they'd quietly diverged onto different clone strategies without anyone deciding that on purpose:

| Model | Call site | Historically |
|---|---|---|
| **A** — TUI-initiated orchestration | `src/ui.rs`'s `Action::SpawnPane` (PRD fork#166) | Every orchestration provisioned as a `git worktree add` sibling of the deck's own already-open root checkout — intended, not a bug, per fork#166's own text. |
| **B** — the `dispatch` CLI | `src/dispatch.rs`'s `handle_dispatch` (PRD #220) | Identical pattern: worktrees as siblings of the caller's own checkout. |
| **C** — scheduled issue-dispatch | `src/issue_dispatch_run.rs`'s `provision_repo` (PRD #120) | Already a **one-clone-per-task-name** model: a fresh clone under `workspace.join(crate::issue_dispatch::sanitize_clone_segment(task_name))` if absent, otherwise fetch/fast-forward — with every issue *that same scheduled task* dispatches sharing that one clone via `.worktrees/issue-<n>` worktrees off it. A **different** task name gets a **different, fully separate clone**, automatically, with zero additional code.

So "should concurrent orchestrations share one clone" was never really a single yes/no question — Model C had already answered it (no) for its own case, years before Models A and B's answer (yes, unconditionally) caused the 2026-08-14 incident. The real question fork#325 (M3) had to settle was whether A and B should adopt something closer to C's already-working per-scope isolation. They did — but only for the **Nth-concurrent** case, not unconditionally, which is the next section.

Correcting the framing further: the disk/build-cache tradeoff the original issue named for "many clones" doesn't actually hold for build cache. Nothing sets `CARGO_TARGET_DIR` for ordinary builds — the only two setters anywhere in this codebase are `scripts/windows-cross-check.sh` and `tests/e2e_version_injection.rs`'s own child build (`.config/nextest.toml` documents the latter's isolation requirement), neither on the normal development path — so every worktree still gets its own independent `target/` today, purely from cargo's own per-directory default (CLAUDE.md rule 1 already treats this as a *feature*: switching branches doesn't force a rebuild). The real, remaining cost of N clones instead of one is git object-store duplication only — deferred, not measured, and out of scope for this PRD.

## The gate: Nth-concurrent, not "always isolate" — with a narrower refusal on the default path

**The decision (M1, approved 2026-08-18, corrected same day):** the trigger is not "human vs. automated" (the originally-approved framing, which matched no actual code signal) — it's **whether a live orchestration already shares the target root checkout's git object store**. That comparison is not one universal rule, though — it has two different granularities depending on which caller is asking, a correction added *after* M3 first shipped by [issue #489](https://github.com/prageethw/dot-agent-deck/issues/489)/[PR #506](https://github.com/prageethw/dot-agent-deck/pull/506), described next.

`root_checkout_has_live_sibling(target_dir, scope)` (`src/ui.rs`) takes a `SiblingScope`:

- **`AnySharedCommonDir`** — a live orchestration collides if it shares `target_dir`'s `--git-common-dir`, whether its own cwd IS `target_dir` or a linked worktree carved off it (two orchestrations can each have their own worktree sibling and still share one underlying object store). This is the **typed-slug** arm — the caller names an explicit Worktree field — and its remedy is to isolate: provision a fresh clone instead of a `git worktree add` sibling that would race the shared object store, issue #325's original incident shape.
- **`ExactCwdOnly`** — a live orchestration collides only if its own cwd literally equals `target_dir`; a live orchestration running in a linked worktree of `target_dir` does **not** count. This is the **blank-slug** arm — the default path most orchestrations use. Its remedy was originally an outright **refusal** (issue #489/PR #506, pinned by `orchestration/worktree/017`), on the reasoning that "a blank slug has nothing to isolate *into*." [Issue #521](https://github.com/prageethw/dot-agent-deck/issues/521) reclassified that as a defect rather than a design tradeoff — CLAUDE.md rule 1's every-fix-gets-its-own-worktree model expects a worktree with zero manual naming, and the refusal violated that for the common (blank-slug) case — so the remedy is now the same as the typed-slug arm's: `auto_generate_worktree_slug` (`src/ui.rs`) picks the next free `orchestrator-N` slug (mirroring `NewPaneFormState::suggest_orchestration_name`'s `<foldername>-orchestrator-N` naming) and provisions an isolated clone via the same `provision_isolated_clone_or_status` helper the typed-slug arm uses, pinned by `orchestration/worktree/018` (which replaced `017`, since the two scenarios' assertions could not coexist). The narrower `ExactCwdOnly` *comparison* itself is unaffected by #521 and is still deliberate for the reason below: treating a linked-worktree sibling as a collision for this arm blocked a brand-new, unrelated blank-slug orchestration in the root checkout for as long as *any* worker orchestration held a worktree — this repo's own everyday one-worktree-per-fix model (CLAUDE.md rule 1) — a real regression caught by `orchestration_dispatch_001`'s e2e failure.

So the gate has **three** outcomes, and the third was added after M3's initial ship:

- **1st orchestration against any root checkout**: unaffected. Shares the checkout exactly as before creation — `create_worktree_sync` (Model A) / `create_worktree` (Model B), a plain `git worktree add` sibling.
- **Nth (2nd, 3rd, …) orchestration, typed-slug, against a root checkout a live one already shares** (`AnySharedCommonDir`): isolated into its own fresh clone instead — `provision_isolated_clone_sync` (`src/issue_dispatch_run.rs`), generalized from Model C's clone-if-absent pattern.
- **Nth orchestration, blank-slug, whose cwd exactly equals a live orchestration's own cwd** (`ExactCwdOnly`): **auto-isolated** — a slug is auto-generated and an isolated clone is provisioned automatically, the same outcome as the typed-slug arm above (issue #521; previously refused outright, asking the user to re-submit with a typed Worktree slug — see the previous paragraph for why that changed). A live orchestration in a *linked worktree* of the target does not trigger this collision at all, by design (previous paragraph).
- **The daemon query fails, or answers in a shape that can't be trusted to mean "no live sibling"** (an error response, or the older-daemon shape omitting per-agent tab membership): **fail closed** regardless of scope — refuse to provision at all. This was a deliberate M3 design decision (Design step 4), not inherited silently from the existing `live_orchestration_in_same_cwd` hint path it was repurposed from, which fails *open* on a down daemon (fine for a cosmetic warning, wrong for a correctness gate — failing open there would let the exact "a down/wedged daemon hides a live sibling" race recur). Model A's fail-closed decision is pinned by `orchestration/worktree/015`; Model B's own equivalent gate re-applies the *same* decision rather than re-litigating it.

  **One tracked exception to "fail closed," not yet fixed:** the guarantee above doesn't extend to a single *live orchestration's own record* arriving with `tab_membership: None` — that record silently falls through the per-record loop as if it were absent, rather than making the whole query untrustworthy. Two routes produce it (an older client whose record predates this field; a same-uid peer sending a malformed `orchestration_cwd` that gets the whole field clamped to `None`), neither a boundary crossing in this same-uid threat model, both tracked as [issue #496](https://github.com/prageethw/dot-agent-deck/issues/496) rather than fixed here. See `root_checkout_has_live_sibling`'s own `KNOWN LIMITATION` doc comment (`src/ui.rs`) for the full account.

One consequence worth stating plainly, because the changelog's first wording of it was misleading: for `dispatch`'s **dominant caller** — a role pane inside a live orchestration issuing `dispatch` — the calling pane's cwd already equals that orchestration's own `orchestration_cwd`, and `dispatch` always supplies a typed slug, so it **always** self-matches the `AnySharedCommonDir` gate's fast path and is **always** isolated, including what would otherwise be "the first" dispatch against that specific target. Isolation is `dispatch`'s normal case, not its edge case.

**Shipped**: Model A's Nth-concurrent gate in [PR #481](https://github.com/prageethw/dot-agent-deck/pull/481); Model B's equivalent gate in [PR #504](https://github.com/prageethw/dot-agent-deck/pull/504) (issue #490) — which also needed isolated-clone-specific spawn-rollback, tab-close cleanup, and `origin_warning` surfacing that Model A didn't, because Model A never calls `record_worktree` for what it provisions; the blank-slug `ExactCwdOnly`/`AnySharedCommonDir` split added afterward by issue #489/PR #506 (originally refusing on `ExactCwdOnly`, pinned by the now-removed `orchestration/worktree/017`); the blank-slug arm's remedy changed from refusal to auto-isolation by issue #521, pinned by `orchestration/worktree/018`.

**Proven against the actual incident shape, not a reduced one**: `orchestration/worktree/016` (PRD fork#325 M5) reproduces **three-plus** concurrent orchestrations — not the simpler 2-orchestration case `014`/`015` already covered — and both of the incident's concrete original failures, asserting each is now structurally impossible: cross-repo `git worktree remove` fails outright (separate object stores, nothing to look up), and a shallow fetch in one orchestration's directory leaves the others' object stores untouched. Verified empirically during review that both assertions would have **failed** against the pre-M3 architecture — the test doesn't merely pass, it discriminates.

## Isolated clones are permanent until someone removes them

An isolated clone is a fully independent repository — its own `.git`, not a linked worktree of anything. That has two consequences neither Model matched at the outset:

- **Its `origin`** is repointed at the **source checkout's own origin URL** (or removed, if the source has none) — never left as a local filesystem path, which would otherwise make `git push origin HEAD:refs/heads/<branch>` (the exact command CLAUDE.md rule 1 tells every agent to run) land silently in the source checkout instead of reaching GitHub.
- **It is never automatically removed by the daemon-side removal path.** `RemovalPolicy::IsolatedClone` / `KeptReason::IsolatedClone` (`src/issue_dispatch_run.rs`, `src/event.rs`) always report `Kept`, regardless of cleanliness or PR state, with no removal probe attempted at all — a clean working tree proves nothing for an isolated clone the way it does for a linked worktree, since a linked worktree's commits remain in the shared object store even after the worktree directory is removed, while an isolated clone's local-only branch commits have no copy anywhere else. `worktree list`/`worktree reclaim` (`src/worktree_reclaim.rs`) are a separate surface with their own, much stricter M4c auto-reclaim rule — see below.

## Why `owned_git_dir` didn't need to change (and the PRD said it would)

The original design (M3 Design item 2) expected `owned_git_dir` and the attach-race lock to need to become "clone-aware… iterating a small registry of known clone roots." That concern **never materialized** in the shipped architecture, and correcting it cost nothing: every real call site of `owned_git_dir` (`src/worktree_reclaim.rs`, `src/issue_claim.rs`) and of the attach-lock path functions (`src/issue_dispatch_run.rs`) already receives the single, correct repo/clone root for the one specific thing it's checking — never a case needing to check one target against multiple candidate roots. `owned_git_dir`'s whole reasoning is containment: is this worktree's `.git` under *this* repo's common-dir `worktrees/`? An isolated clone is a separate top-level repository, so that question doesn't even apply to it — which is exactly why isolated-clone discovery (next section) needed a **parallel**, not a modified, mechanism.

## Discovering isolated clones: a second, unrelated enumeration

`worktree list`/`worktree reclaim` (`examine_worktrees`/`run_reclaim`, `src/worktree_reclaim.rs`) walk `git worktree list --porcelain` from one `repo_dir` — which structurally **cannot** see an isolated clone, since it's a separate repository, not a linked worktree of anything. Until **M4a** ([PR #510](https://github.com/prageethw/dot-agent-deck/pull/510)), an isolated clone that outlived its orchestration was invisible to every discovery surface, accumulating on disk with no way to find it short of knowing where to look.

`discover_isolated_clones` fixes this with a **structurally separate** scan: sibling directories of the (correctly root-checkout-resolved, not assumed-equal-to-`repo_dir`) root checkout, filtered to a `.git` present as a **directory**, not a **file** — the same test that already tells an isolated clone apart from a linked worktree's `.git` redirect. Reported via a new `kind` field (`"linked"` vs `"isolated_clone"`) and, as of this milestone (M4a), a fourth `verdict` value (`"isolated_clone"`, alongside the existing `remove`/`ask`/`keep`, bumping the `--json` document's `schema_version` 2 → 3) that never received an automatic-removal verdict — hardcoded to a value `run_reclaim`'s existing match fell through to its default `kept` arm for, with no new arm added, so a future contributor editing that match couldn't accidentally make an isolated clone reachable by `--yes` (this mirrors the daemon-side `RemovalPolicy::IsolatedClone` precedent more directly than routing through the existing `Ask` verdict would have, which would have let `--yes` reach `git worktree remove` against something that isn't a linked worktree at all — failing loudly rather than cleanly). **M4c** (below) later added a fifth `verdict` value, `"isolated_clone_reclaimable"`, and a dedicated `run_reclaim` match arm for it — the only isolated-clone row shape that can ever be auto-removed, and only under M4c's own tightened rule.

A candidate directory is untrusted input, and every `git` invocation `discover_isolated_clones` makes against one — `check_cleanliness`, `derive_repo_slug`, `resolve_isolated_clone_branch` — routes through `git_in_untrusted_dir`, which adds `-c core.fsmonitor=` to block RCE via a forged `.git/config`. **That closes one vector, not every vector**: `git_in_untrusted_dir`'s own doc comment records that the audit's final round reproduced arbitrary code execution through a *different* config key, `filter.<driver>.clean` declared via a candidate's own `.gitattributes`, reachable through the very `git status` this helper exists to protect — an accepted, still-open residual, not confined to a subcommand this module avoids issuing. Closing it would mean not running `git status` in an untrusted directory at all, which is its own design question, tracked as [issue #519](https://github.com/prageethw/dot-agent-deck/issues/519) rather than decided here.

## Ownership attribution: a two-attempt history worth reading before touching this code

**This is the part of M4 most likely to bite a future change**, because the wrong-looking answer passed code review twice before the right one shipped, and both times looked plausible.

The question `owned`/`owner`/`owner_kind` answer for a discovered isolated clone: *did this deck genuinely create this directory, and who owns it?* Three shapes were tried, in this order:

1. **`candidate_shares_history_with`** (M4a's original, [PR #510](https://github.com/prageethw/dot-agent-deck/pull/510)) — bound ownership to the candidate's current `HEAD` naming a commit the root checkout already has. **Broken two ways**, found by two different review rounds: (a) *functional* — a genuine clone's `HEAD` moves the moment the dispatched agent makes its first real commit, silently dropping the clone out of discovery the moment it holds the local-only work this whole milestone exists to protect; (b) *security* — a same-uid actor could forge acceptance with 4 files, no `git` invocation, no real objects at all (a `.git/HEAD` containing a real, public SHA as plain text is enough).

2. **A dedicated provenance artifact inside each candidate's own `.git`** (M4b's first attempt, [PR #515](https://github.com/prageethw/dot-agent-deck/pull/515) round 1) — closed (1) cleanly. **Reopened the ORIGINAL forgery this whole line of work started from** (auditor A1/B1, M4a's very first review round), at the cost of one `touch` — because a same-uid attacker who can plant a sibling directory at all already controls everything inside that directory's `.git`, including any filename the deck might check for there. Caught by both reviewer and auditor independently, each with a working exploit, before merge.

3. **`state_dir()`, keyed by a path hash, outside every candidate** (M4b's shipped fix) — the artifact lives in `crate::platform::paths::state_dir()` (the deck's own per-user state directory, owner-only permissions), keyed by `fnv1a64` of the candidate's canonical clone path — the exact same hashing scheme the attach-lock path already used, reused rather than reinvented. This closes the loop back to the actual reason `owned_git_dir` is trustworthy for linked worktrees: **the evidence has to live somewhere the *enumerating* party controls, never somewhere the *candidate* controls** — containment is one instance of that property, not the property itself. A same-uid attacker who can only plant a sibling directory cannot write into `state_dir()`; one who *can* write there already has the same access `owned_git_dir`'s own linked-worktree case assumes as its ceiling.

**The lesson, stated so it doesn't have to be relearned**: any future change to how ownership is decided for a discovered isolated clone must keep the evidence outside the candidate. An implementation that "just" writes something recognizable inside the clone's own `.git` — however specific the filename, however unlikely to collide by accident — is the shape that failed twice already, once in each direction (too fragile, then too forgeable).

`candidate_has_attach_lock`'s own doc comment records **M4a's two residuals, both closed here** by the shipped mechanism — reviewer P1's shared-namespace concern (a removed linked worktree's stale lock artifact could theoretically be inherited) is closed because the provenance artifact lives in a wholly separate namespace under `state_dir()` that `create_worktree_sync` never writes into under any circumstance, so there's nothing left for a forged occupant to inherit; auditor C1's lock-before-`exists()` ordering is deliberately preserved (moving the check earlier would reopen a TOCTOU auditor A3/fork #282 already closed), but its *attribution* consequence is closed too — the artifact is written only after the clone this call performed has actually succeeded, so a pre-planted directory fails visibly as `AlreadyClaimed` before that write is ever reached, and is never vouched for. Both are pinned by `worktree/reclaim/056`/`057`.

That doc comment also names honest limits that remain genuinely live, two of which bear directly on ownership correctness and are worth stating here rather than only there: the provenance artifact is never removed when a clone is deleted, so it **vouches for any later directory recreated at the same canonical path** (the closest live analogue to the forgery this whole section is about — a same-uid actor with no `state_dir()` write access at all gets `owned: true` for free by planting a sibling at a path the deck previously provisioned and abandoned); and attribution is **path-bound**, so a legitimately `mv`'d or `cp -r`'d clone reports `owned: false` even though nothing forged it. Neither is tracked as its own issue — both are properties of the mechanism as designed, not defects — but a future change to this code should know they exist before assuming the current scheme is airtight.

## Auto-reclaim eligibility: a five-condition rule redesigned around `headRefOid` (M4c), widened to six by fork issue #546 hazard 2

`worktree list`/`worktree reclaim` (unlike the daemon-side `RemovalPolicy::IsolatedClone` path above, which never auto-removes at all) can report an isolated clone as `"isolated_clone_reclaimable"` — a fifth `verdict` value, distinct from the permanently-conservative `"isolated_clone"` default — under a maintainer-decided rule (`isolated_clone_report`, `src/worktree_reclaim.rs`). This shipped in three rounds, and the first two rounds' gaps are worth recording because they show what "a clean tree isn't proof" actually looks like when the eligibility check itself doesn't yet cover it, and how close round 2's own fix came to being inert for the real clones this milestone exists to reclaim.

**Round 1** compared only the clone's `MERGED`-PR commit SHA (`gh pr list --json mergeCommit`'s `oid`) against the clone's own `git rev-parse HEAD`. An audit of that version found three blocker-severity gaps:

- **A2 — eligibility never consulted `has_attach_lock`.** A forged/unowned sibling directory — no genuine deck involvement, no `state_dir()` write access — could satisfy commit-SHA equality on its own (check out the right commit, plant a marker) and be auto-removed. Ownership evidence backs the `owned` **display** field but was never wired into the **deletion** decision at all.
- **A1 — eligibility never consulted cleanliness.** `remove_dir_all` has no equivalent of `git worktree remove`'s own refusal against a dirty tree, so a dirty-but-SHA-matching clone still reported reclaim-eligible.
- **A8 — commit-SHA equality is the wrong comparison on a squash-merge repo.** GitHub's squash merge creates a brand-new commit object; a genuine clone still on its own work branch essentially never has a `HEAD` equal to `mergeCommit.oid`. The rule was therefore inert for exactly the real, genuinely-merged clones this milestone exists to reclaim, while a planted candidate could satisfy it trivially with one `git checkout` to the (public) merge SHA.

**Round 2** required the AND of five conditions, each closing one of the above plus two more the audit surfaced along the way:

1. `has_attach_lock` — the deck's own `state_dir()` provenance artifact (closes A2).
2. `Cleanliness::Clean` (closes A1).
3. Exactly one local branch — the resolved current one, no others (`git for-each-ref refs/heads`). A second local branch may hold commits with no copy anywhere else; HEAD-equality proves only one ref safe to discard, never the whole clone `remove_dir_all` destroys.
4. An empty `git stash list` — the same local-only-content hazard as (3), through git's other local-only ref namespace.
5. The clone's HEAD **tree** SHA (`git rev-parse HEAD^{tree}`) equal to the merged PR's merge-commit **tree** SHA — not commit SHA (closes A8). The merge commit's tree is reached via a second `gh` subcommand, `gh api graphql -f query='query{repository(owner:"…",name:"…"){pullRequest(number:N){mergeCommit{oid tree{oid}}}}}'`, because `gh pr list --json`'s flat field selection cannot sub-select into `mergeCommit` at all — confirmed directly, there is no field name that reaches `mergeCommit.tree.oid` through that interface.

**Round 3 (the shipped rule, PR #526, reviewer B2)** found condition 5 above itself effectively inert: reviewer B2 measured live against this very repo that a genuine deck-provisioned clone's own HEAD is (almost) never equal to `mergeCommit.oid` under any GitHub merge strategy (PR #481 head `7339edd5f440` vs merge `1ceb919349ef`; PR #477 head `11d6327f2421` vs merge `5742ad1f93dd`), so round 2's tree comparison could (almost) never fire for a real clone — it closed A8 in theory while remaining inert in practice, the same failure shape A8 itself described for round 1. Round 3 drops the `mergeCommit`/tree machinery entirely, along with its second `gh api graphql` round trip, and replaces condition 5 with:

5. The clone's own current HEAD **commit** SHA (`git rev-parse HEAD`, no `^{tree}`) equal to the merged PR's own `headRefOid` — the PR BRANCH's own tip commit, not the merge commit GitHub creates on the base branch. `gh pr list --json headRefOid` exposes this directly as a flat field, so no second `gh` subcommand is needed at all. Conditions 1-4 are unchanged from round 2.

`None`/unresolvable at any point in the chain — an unresolvable branch listing, stash list, or HEAD SHA, or a `MERGED` PR whose `headRefOid` itself couldn't be resolved — fails closed to "not eligible," the same stance every earlier round already took for an unresolvable SHA: an ambiguous signal must never widen eligibility for a safety-relevant deletion decision.

`run_reclaim` gets a dedicated match arm for `"isolated_clone_reclaimable"`, removing via `remove_isolated_clone_dir` (`std::fs::remove_dir_all`) rather than `remove_worktree_dir`'s `git worktree remove` — the latter realpath/symlink-resolves its argument against the `git worktree list` registry and exits 128 against anything that isn't a linked worktree at all. Immediately before that `remove_dir_all`, `remove_isolated_clone_dir` re-checks that `.git` is still a directory (a structural sanity check) AND, as of round 3 (reviewer M1), re-derives what was then 4 of the 5 eligibility conditions fresh from disk — cleanliness, the local branch list, the stash list, and HEAD SHA vs. a freshly re-resolved `headRefOid` — refusing rather than deleting on any mismatch. This closes the TOCTOU window between `examine_worktrees`' examination pass and the actual removal, which can be seconds to minutes apart on a large reclaim batch, during which the clone could have been actively worked on. The `has_attach_lock` condition is deliberately not re-derived here: it is a provenance marker written once under `state_dir()` at provision time, keyed by the clone's own canonical path rather than anything inside its tree, and it documentedly never gets removed even once the clone it names has been deleted — nothing a live orchestration does inside the clone can make it change during this window the way an uncommitted file, a new commit, a new branch, or a stash push can, so re-deriving its *presence* immediately before deletion would answer the identical question already answered at examination time. (Fork issue #546 widens this re-derivation count to 5 of 6 — see below; the artifact's own *content* turns out not to share `has_attach_lock`'s presence-only stability.)

**Known residual (M2, round 3):** the five conditions above prove *provenance* (the deck created this clone) and *content safety* (nothing local-only would be lost), never *liveness* (whether the clone is currently in active use). Issue #325's original incident was exactly "an orchestration deleted another orchestration's actively-in-use worktree," and a clone can satisfy every condition above while a live orchestration is still working in it. The daemon tracks liveness for its own dispatched worktrees in-process (`crate::issue_dispatch_run::WorktreeRegistry` / `worktree_still_in_use`), but `worktree reclaim` is a plain CLI subprocess (`run_worktree_reclaim_cli`) that never connects to the daemon socket — that signal is not reachable from this call path. Round 3 does not invent a substitute (a heuristic liveness probe would be worse than none — a false "not live" reads as license to delete); this is accepted as a documented residual on `is_reclaim_eligible`'s own doc comment in `isolated_clone_report`, not gated, pending a future signal `worktree reclaim` can actually reach.

**A sixth condition (fork issue #546 hazard 2):** round 3's five-condition rule proved provenance and content safety, but had no way for a caller to say "keep this one regardless" — the liveness residual immediately above. `worker-agent-deck`'s pin/unpin mechanism (`pin_isolated_clone`/`unpin_isolated_clone`, `src/issue_dispatch_run.rs`, wired to the `dot-agent-deck worktree pin <path>` / `worktree unpin <path>` CLI subcommands in `src/main.rs` — fork issue #597; see [`orchestration.md`](../orchestration.md#listing-worktrees-by-owner) for the user-facing surface) closes that gap manually: it rewrites the same M4b provenance artifact in place, upgrading it to `schema=3` and adding a `pinned=` field, and `isolated_clone_report` ANDs `!is_pinned` in as a sixth, independent eligibility condition. Only a literal `pinned=true` counts; a missing field, an explicit `pinned=false`, or any other value all read as not pinned. Because the artifact's *content* — unlike its mere presence — can now legitimately change at any time via pin/unpin, `remove_isolated_clone_dir`'s TOCTOU re-verification re-derives the pin state too, as its fifth re-derived signal (of six total), so a pin applied during the examination-to-removal window still refuses the deletion rather than trusting a stale examination-time verdict. Both the examination-time read and the TOCTOU re-check share one helper (`isolated_clone_pin_state`) rather than each parsing the artifact independently. A review-findings fix round (reviewer/auditor) caught and closed a fail-*open* bug in the first cut of this: the examination-time read collapsed an I/O error reading the artifact (e.g. permission denied) to `None` via `.ok()`, which then read as "not pinned" — the one gate in this whole heuristic that inverted the "unresolvable fails closed" posture every other condition here takes. Fixed to distinguish "read failed" from "read succeeded, field absent": either an I/O error or a `pinned=true` field now makes the clone ineligible; only a successful read with the field absent or `false` clears the gate.

## Named, persistent orchestrator workspaces (PRD fork#544)

Fork#325's own M4c bullet (above, "Auto-reclaim eligibility") asked *"whether an isolated clone can ever become automatically reclaimable, and under what stricter safety condition"* — flagged as needing a maintainer decision and explicitly not bundled into an implementation PR. **PRD fork#544 was originally intended to answer that question, but discovered mid-implementation (M5's RED round) that M4c had already shipped**, independently, as `a8f37894`/PR #526 (the five-condition `headRefOid` rule described above) — before fork#544 itself even existed as a PRD. Fork#544's own status line and Predecessors section carry a 2026-08-22 correction recording this.

What fork#544 actually ships, unaffected by that discovery, is a different, **orthogonal** thing: not an answer to "can an isolated clone auto-reclaim," but a deliberate, **name-keyed reuse** mechanism for Model A's isolated clones, plus an explicit, confirmation-gated **retire** action as the only deliberate way to clear one. Reconciling the two mechanisms — the heuristic auto-reclaim above and fork#544's deliberate reuse/retire below — is tracked as [issue #546](https://github.com/prageethw/dot-agent-deck/issues/546), not settled here.

### Naming: the workspace directory's identity is the orchestration Name (M2)

Before fork#544, Model A's clone directory came from a separate "Worktree slug" form field (auto-generated as `<dir-basename>-orchestrator-N` when left blank), entirely disconnected from the orchestration's own required, unique-among-live **Name** (PRD fork#192) — the two fields looked related by naming convention only, producing exactly the `repo-orchestrator-1`, `repo-orchestrator-2` directory sprawl fork#544 was filed to fix. The "Worktree slug" field is retired outright. The workspace directory is now derived as `<root-checkout-basename>-<sanitize_clone_segment(name)>`, reusing the same `sanitize_clone_segment` (`src/issue_dispatch_run.rs`) Model B's `dispatch <name>` already sanitizes its own argument with — proving a single-field identity is sufficient, since Model B never had a separate slug to begin with.

### Resume arm: existence becomes a success case, not an automatic refusal (M3)

`provision_isolated_clone_sync` gained a third outcome alongside the pre-existing `Created`/`AlreadyClaimed`: `Resumed`. On the Name-derived path, an absent directory still creates exactly as before (M2 also verified/fixed creation-time freshness against `origin`). A **present** directory now runs a three-part eligibility check via `resume_existing_isolated_clone`, checked in an order that keeps a corrupt directory from being misdiagnosed as an ancestry mismatch:

1. **M4b ownership evidence** — the provenance artifact (below) exists for this canonical path. Pure presence (`is_file()`), not content — see the format-hardening note below for why that matters.
2. **Health** — `git rev-parse HEAD` succeeds, checked *before* the ancestry probe so a directory with no `.git` at all fails for the right reason.
3. **Ancestry** — `isolated_clone_ancestry_matches_source`: does the candidate's history genuinely derive from the root checkout being opened, closing the gap where M4b evidence alone only proves "the deck created *something* here," never *what* or *from which repo*.

A full pass resumes with a **read-only `git fetch`** — updates `origin/<default-branch>`'s remote-tracking ref only, touches no local branch, no working tree — and nothing else. Zero mutating git commands. This is the Decisions-table constraint that rules out Model C's fetch+fast-forward pattern here: a named workspace is meant to carry forward uncommitted changes and local-only commits across sessions, so integrating the branch stays fully manual. A failed check rejects with a named reason (`Stranger`/`Unhealthy`/`AncestryMismatch`) and **never** auto-deletes or auto-suffixes — refusal always points at the explicit retire action (M5) as the only way to clear a rejected directory.

The resume race this introduces — two near-simultaneous opens of the same Name both passing eligibility — is closed by reusing the existing attach-race lock (`worktree_attach_lock_path`, already keyed on canonical target path), acquired before the liveness check and held through registering the winner; a second racer sees the first's registration and is refused as `Contested`.

### Ownership evidence hardened into structured, backward-compatible data (M4)

The M4b provenance artifact (`isolated_clone_provenance_path`/`write_isolated_clone_provenance`) was content-free — literally the bytes `b"deck\n"`. Fork#544 replaces the content (not the path/keying scheme, which is unchanged) with plain `key=value` lines: `schema=2`, `root-hash=<fnv1a64 of the root checkout's canonical path>`, `name=<orchestration Name>`, `path=<clone's own canonical path>`. This is additive evidence for future tooling — a schema tag so a future format change can branch on it, and a root-checkout-path hash so evidence written under a future naming rule can't silently vouch for content created under today's rule.

**The read path never changed.** `resume_existing_isolated_clone`'s eligibility check (1) above only ever tested file presence via `is_file()` — never content, before or after M4 — so a pre-M4 `b"deck\n"` artifact keeps resuming exactly as it did before, pinned by `orchestration/workspace/012`. See "Rule 12 determination" below for why this makes the format change additive rather than breaking.

### Explicit "forget this workspace" retire action (M5) — shipped, no caller wired yet

`forget_isolated_workspace` (`src/issue_dispatch_run.rs`) atomically removes both the workspace directory and its provenance artifact, modeled on this repo's `issue claim --takeover --confirm-stopped` pattern: refuses by default, requires an explicit confirming flag. This is deliberately **not** built on `worktree_reclaim.rs`'s `remove_isolated_clone_dir` — that function's preconditions (clean tree, empty stash, HEAD matching a *merged PR's* `headRefOid`) all encode "this was already safely auto-reclaimed," which is precisely wrong for a workspace being explicitly forgotten on purpose, possibly mid-work, possibly with uncommitted changes the caller has every right to discard. As of this writing `forget_isolated_workspace` ships `#[allow(dead_code)]` — no CLI surface or UI action calls it yet; wiring one in is an open follow-up, not required by any M9 test.

### Registration: Model A becomes visible to `WorktreeRegistry` (M6)

Before fork#544, Model A never called `record_worktree` at all — its isolated clones were invisible to the daemon's own `WorktreeRegistry`, discoverable only via fork#325 M4a's separate sibling-directory scan (`discover_isolated_clones`, above). Fork#544 wires registration in via a new, additive `isolated_clone_origin: Option<String>` field on `AttachRequest::StartAgent` (`src/daemon_protocol.rs`): the TUI sets it to the root checkout the workspace was cloned from whenever it spawns a role pane into an isolated clone; the daemon-side handler uses its presence to call `record_worktree` under `RemovalPolicy::IsolatedClone`. A test pins that tab-close still never removes a named workspace (unchanged from the pre-fork#544 `RemovalPolicy::IsolatedClone`/`KeptReason::IsolatedClone` behavior described above) — this is a **registration** guarantee, not a new removal-policy decision.

### Post-merge sync (M7) — shipped, no caller wired yet

Two functions, tied conceptually to the existing merge phase (the orchestrator workflow's own merge step / `release`'s `/prd-done`) but **not yet called from either**: `fetch_other_live_workspace` (a proactive, read-only fetch for other live named workspaces when an unrelated branch merges) and `sync_merged_workspace_to_main` (for the just-merged workspace itself: checkout + fast-forward to updated `main`, conditional on the tree carrying nothing beyond what was just merged — otherwise leave untouched and surface a note). Both ship `#[allow(dead_code)]`, the same state M5's `forget_isolated_workspace` shipped in before this milestone; wiring either into a real caller is an open follow-up decision.

### Rule 12 determination (M8)

Two changes on this branch touch the daemon/wire/marker surface; CLAUDE.md rule 12 requires an explicit, written determination for each rather than leaving it implicit.

**1. `isolated_clone_origin: Option<String>` on `AttachRequest::StartAgent`.** Same-wire additive: `#[serde(default, skip_serializing_if = "Option::is_none")]`, matching the precedent already set by `display_name`/`tab_membership`/`agent_type`/`seed` on the same enum variant. No `#[serde(deny_unknown_fields)]` exists anywhere in `src/daemon_protocol.rs` (or anywhere in `src/`), so an older daemon that doesn't know the field silently ignores it via serde's default unknown-field tolerance, and a newer daemon talking to an older client simply sees `None`. **Verified empirically, not just on paper**: a raw `StartAgent` frame carrying `isolated_clone_origin` sent directly over the attach socket to a daemon built at `c34b03ab` — the commit immediately preceding this PRD's own work, same `PROTOCOL_VERSION` (10) — was accepted and spawned the pane normally; `list-agents` against that daemon shows the resulting `AgentRecord` with no trace of the unknown field, exactly as expected. **No `PROTOCOL_VERSION` bump, no `.breaking.md` fragment.**

**2. The M4 provenance-artifact format change** (content-free `b"deck\n"` → structured `schema=`/`root-hash=`/`name=`/`path=` lines). This is a marker on-disk-format change, which rule 12 also asks about explicitly. The read path (`resume_existing_isolated_clone`'s eligibility check) was verified to test file presence only, never content, both before and after this change — so an old-format marker keeps resuming exactly as before. `orchestration/workspace/012` pins this directly: it overwrites a freshly-written artifact with the literal pre-M4 `b"deck\n"` bytes (bypassing the writer entirely, not merely testing the current writer's own output) and asserts the next open still resumes. **Additive/backward-compatible, not breaking. No `PROTOCOL_VERSION` bump, no `.breaking.md` fragment.**

**Cross-version manual test (both changes), performed rather than assumed:** built this branch's binary and two comparison daemons — the actual previous release, `v0.41.0` (`PROTOCOL_VERSION` 9), and a same-protocol build at `c34b03ab` (`PROTOCOL_VERSION` 10, immediately pre-fork#544). Against `v0.41.0`, this branch's binary refused to attach outright with an explicit, actionable message naming the protocol skew (`"local daemon speaks attach protocol v9 but this binary speaks v10"`) — a clean, by-design refusal, not a silent break, and **caused by an unrelated prior change** (`c34b03ab`/PR #532, fork issue #201, landed on `main` after `v0.41.0` was tagged and before fork#544's own first commit) rather than by anything in this PRD. Because that refusal happens before any fork#544-specific behavior would run, the `c34b03ab` build (same protocol version, immediately pre-fork#544) is what actually isolates this PRD's own changes: against it, the `isolated_clone_origin` field round-tripped cleanly (verified above), and both `delegate` and `work-done` — driven from this branch's CLI against the older daemon over the separate hook socket, which carries no `PROTOCOL_VERSION` gate at all — routed and were accepted correctly end to end, once supplied with the resuming pane's actual `daemon_boot_id`/`registration_generation` (an unrelated, pre-existing staleness guard that correctly rejects a signal produced with the wrong values, which a bare shell invocation outside a real spawned pane doesn't inherit automatically). `delegate`/`work-done` were also confirmed to route/accept correctly against the actual `v0.41.0` daemon directly, independent of the attach-protocol refusal above, since those two commands use the hook socket rather than the attach socket. No silent breakage observed on any path.

## What's still open

- **Issue #516** — two Low-severity residuals found in M4b's final review round: `state_dir()` has no guard against an empty (not merely unset) `DOT_AGENT_DECK_STATE_DIR`, newly security-relevant now that path backs an ownership decision; and the fast-tier unit tests exercising the real provisioner don't sandbox that variable, writing real artifacts into the developer's/CI runner's actual state directory.
