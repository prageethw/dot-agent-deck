# A RED confirmation is only meaningful if it has exactly one cause

The harness's TDD loop treats a RED result from CI as proof that a test pins the intended defect (CLAUDE.md rule 5). That proof only holds if the test has exactly **one** way to fail. If it can fail for two independent reasons, RED tells you nothing about which one you fixed — this is the mirror image of a test that's green regardless of whether the fix is present (the vacuous-pass / "inconclusive run" failure mode already called out in `tests/CATALOG.md`, e.g. the `status/shell-activity/007` entry's "an inconclusive run is never reported as a pass"). The check to run before trusting a RED: **would this test still fail if the defect were fixed?** If the honest answer is "maybe, for an unrelated reason," the RED confirmation is worthless and needs isolating before implementation starts.

This bit a real branch: `orchestration/delegate/020` was written RED and CI confirmed it RED, but the test was red for two reasons at once — the real defect (the daemon clobbered a pre-existing report) and, independently, a tempdir lifetime bug in the test's own `run_two_work_done_calls` helper, which returned a `PathBuf` derived from a `tempfile::TempDir` guard that dropped (and recursively deleted the directory) at the function's closing brace. Pre-fix, both causes produced the same failure, so the RED confirmation couldn't distinguish them. Post-fix the test still failed, and the coder had to trace it, correctly decline to edit the tester's own test, and report back — a full extra cycle to diagnose what a single-cause check would have caught up front.

What to watch for:

- **A failure message that names the specific observed value**, not just "assertion failed." `020`'s message asserted the pre-fix wording and kept asserting that same wording after the fix — that's what made the mismatch visible instead of silently passing for the wrong reason.
- **A fixture that can escape its own scope.** Guards — `TempDir`, lock guards, spawned children — dropping earlier than the caller expects is a common second cause hiding behind the intended one. The structural tell in this case: a sibling test (`019`) kept its tempdir in its own scope and passed cleanly — same daemon, same archive logic, different lifetime shape.
- **A passing sibling test over the same production path** is a strong isolation signal — if it exercises the same code and passes, the RED you're looking at is more likely test-local than product-local.
