# CLAUDE.md — dot-agent-deck

## PERMANENT INSTRUCTIONS

1. **Every Fix Gets Its Own Worktree**: Any distinct piece of work — a PRD, a bugfix, a docs change, a review follow-up — gets its own dedicated git worktree, created up front. This is the default; do **not** ask whether the user wants a worktree or a plain branch, and do not reuse a worktree for a second, unrelated fix — one worktree per change. `/worktree-prd` remains the helper for PRD work. **Never work in the root checkout**: it is the long-lived checkout the running daemon and worker panes are attached to, and it routinely carries uncommitted state. The incident behind this rule (2026-08-07): the root checkout was sitting on `docs/prd-386-upstream-pr-record` with an uncommitted `.dot-agent-deck.toml` and an untracked `tests/snapshots/render_dashboard__pane_008_named_agent_badges.snap.new`, and a task told a worker to commit a documentation file "from the root checkout" — switching that checkout to `main` would have dragged the dirty `.dot-agent-deck.toml` along and risked committing the fork's local role-command config onto `main`. The worker refused and used a throwaway worktree instead; a dedicated worktree makes that class of mistake impossible rather than relying on each worker noticing. A worktree also keeps each branch's `target/` build state isolated, so switching work does not force a full rebuild. Remove the worktree once its branch is merged and dropped (`git worktree remove`) so they do not accumulate. This recurred on 2026-08-07/08 (fork issue #74) with a sharper root cause than the original filing assumed: two orchestrations worked the same issue concurrently because a second orchestration's task named no worktree path, so its worker found the first orchestration's existing branch and reasonably joined it — writing production code into a worktree it did not own, then pushing to it and cancelling the first orchestration's in-flight CI run. **The orchestrator creates the worktree and states its absolute path, exact expected commit SHA, and branch name in every task it delegates**; a task naming no path, SHA, or branch, or naming the root checkout, is itself the defect, not a judgement call the worker gets to make. **Unset the new branch's upstream immediately after creating it** (`git branch --unset-upstream` in that worktree, then push explicitly with `git push origin HEAD:refs/heads/<branch>`, substituting the task-named branch for `<branch>`) — `git worktree add -b <branch> <path> origin/main` sets the new branch to track `origin/main`, so a bare `git push` from that worktree lands on `main`; this happened for real on the #89 branch and was caught only because a worker noticed and pushed explicitly instead. **Before touching anything, a worker verifies the worktree is clean and `git rev-parse HEAD` equals the task-named SHA**; if either is wrong, report it through `work-done` and stop there — do not `git add -A`, do not stash, do not work around it to make progress anyway. **Never `git add -A` or `git add .` in a shared checkout — stage explicit paths.** This is the exact mechanism behind #74's original incident, where a live mutation-testing run was swept into a real commit and pushed to an open PR. **Mutation testing, and any other tool that rewrites source in place, runs against its own throwaway worktree or copy — never one an agent is actively editing.** **When delegating to a read-only role (`reviewer`, `auditor`), the task must also state the exact absolute path of the findings file under the root checkout's `.dot-agent-deck/` directory** — rule 15 requires the worker to refuse a relative or unnamed findings path rather than guess it from its worktree, so a task that omits the path produces the same deadlock a missing worktree path, SHA, or branch would. This exact defect happened three times in the #74 lineage before it happened a fourth time here (fork issue #114): a template requires something of the worker that nothing requires the orchestrator to supply.
2. **Run `cargo fmt --check` and `cargo clippy -- -D warnings` Before Committing**: Always run both `cargo fmt --check` and `cargo clippy -- -D warnings` before creating any git commit. If fmt reports issues, run `cargo fmt` to fix them. If clippy reports warnings, fix the code. Stage any fixes before committing.
3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (e.g. `tests/event_forwarding.rs`), not for the milestone or PRD that introduced them (e.g. `tests/m2_17_event_forwarding.rs`, `src/prd76_*.rs`). Milestone tags belong in commit messages and the PRD doc — long-lived filenames must outlive the branch. Existing `m*_` test files are scheduled for cleanup; do not create new ones in that pattern.
4. **Add or Update TUI Tests for Functional UI Changes**: When a change adds or modifies user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, embedded panes, hook delivery), add or update tests in the TUI harness. Use L1 (in-process `TestBackend` + `insta`) for pure widget/layout changes; use L2 (PTY + vt100, files named `e2e_*.rs`, gated by `#[cfg(feature = "e2e")]`) when the change touches the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change do not require new tests. **For a major user-facing feature, include at least one PTY-attached L2 test** (the vt100 harness that drives the real binary, e.g. mirroring `scheduler/live/*`) that exercises the user-visible surface — not only headless daemon-serve (`RunNow`) tests. Only PTY-attached tests record a `.cast`, but a cast alone is **not** enough to be demo-reel-eligible: a clip must genuinely spin up a **real agent** (spawn → agent → work) **and** be explicitly opted in with a trailing ` [reel]` marker on its `tests/CATALOG.md` entry (PRD #180/#20 — see `.claude/skills/demo-reel-adapter`). A synthetic/stand-in PTY test (cat, scripted echo, recorder stubs, terminal-probe, synthesized hook events) is left unmarked and never becomes a clip even though it has a cast; a feature whose entire e2e coverage is headless (or unmarked) ships with no reel clip. (PRD #120's `issue_dispatch` is the cautionary case: `scheduler/dispatch/001-010` are all headless, so the showcase clip required adding the PTY-attached `scheduler/dispatch/011`.) **A major user-facing feature should also have at least one REAL-scenario e2e test** that drives the genuine spawn→agent→work path with a *real* agent on a **cheap model** (Haiku for Claude, a mini model for OpenCode) through a cheap, deterministic-enough operation — e.g. "list the files and report a known sentinel filename" — rather than relying solely on a stand-in like `cat`. We have historically over-relied on stand-ins; a stand-in proves the plumbing but never that an agent genuinely runs against the cloned/worktree/target state. Real-agent tests live in the **pre-PR e2e tier** (flaky-tolerant, and not exercised by CI, which has no credentials configured — see rule 5); make them robust with a directive prompt plus a uniquely-named fixture **sentinel file** so the assertion survives LLM phrasing/tool variance. **The bar is: at least one test per major feature must validate it AS A USER ACTUALLY USES AND SEES IT** — the genuine, user-visible experience end to end, e.g. a *live interactive* agent visibly working in the pane (with real status), not a non-interactive shortcut like `claude -p` and not a stand-in. Print mode and stand-ins prove the wiring; they do not prove the user-facing reality. Interactive headless agents are achievable — seed claude's onboarding + per-folder trust into the test HOME (see `prepare_claude_home` / the `TuiDeck` claude-trust seeding hook) and pass `--allowedTools` so no permission prompt blocks; `scheduler/dispatch/013` is the reference (an interactive Haiku agent listing the freshly-cloned repo live in the pane). Do not let "headless is hard" silently downgrade this bar where it is achievable.
5. **Fast Tests Per Task, E2E Before PR**: `cargo test-fast` (alias for `cargo nextest run`) runs the fast tier — protocol/state tests plus L1 widget/render tests — and is the per-task gate. `cargo test-e2e` (alias for `cargo nextest run --features e2e`) additionally runs the L2 PTY/real-agent suite and is required to pass before the release flow. Do not run `cargo test-e2e` per task; it spawns binaries, hits LLM APIs, and is intentionally bounded to the pre-PR step.

    **Fork-only addendum — ALL test runs happen in CI, not locally.** This addendum **overrides the sentence above for this fork**: the upstream text is correct upstream, but here every test run belongs to CI — progression as well as regression, a single filtered test as well as a full tier. **All tests → CI; lint/build checks → local.**

    - **ALL tests → CI. No exceptions, including progression testing.** *(Superseded 2026-08-06: this previously kept progression testing local. It no longer does.)* Every test run — a filtered single test you are actively writing, a whole test binary, or a full tier — happens in CI, not on this machine. A tester writing `orchestration_010` **commits and pushes**, then reads the RED from CI; the coder implements, pushes, and reads the GREEN from CI. `cargo test-fast`, `cargo test-e2e`, `cargo nextest run …` — filtered or not — are **not** to be run locally.

        **Precondition, or the push produces nothing to read:** CI triggers on `pull_request` (opened/synchronize/reopened), on pushes to `main`, and on `workflow_dispatch` — a push to a feature branch with **no PR open fires no run at all**. So open the PR as a **draft** as soon as the branch has its first commit; every later push then re-runs CI via `synchronize`, and `/prd-done` marks it ready for review instead of creating it. `gh workflow run ci.yml --ref <branch>` is the fallback. "There was no CI to read" is never a reason to run the tests locally — it is a reason to open the PR.

        **Consequence, stated so nobody rediscovers it the hard way:** the TDD chain becomes push-and-wait. RED/GREEN confirmation costs a CI round trip (~1–2 min for the fast tier, ~9–12 min for e2e) instead of seconds. Batch your work accordingly — get a change to the point where a single push answers several questions, rather than pushing per-iteration. Expect more commits per branch; that is fine, and squashing is not required (this repo keeps review history legible).

        **Why:** local test runs — filtered ones included, because each PTY test spawns a binary, a daemon and panes — starved this machine repeatedly (load average 13–16 with concurrent worktrees, and a measured case where a test failed purely on a 10s startup wait it would otherwise have passed). Local runs were also producing *misleading* results: a test that fails from machine contention looks identical to a real failure, which cost real triage time. CI is the only environment where a red result means something.
    - **Regression testing → CI**, as before. A full-tier `cargo test-fast` (`cargo nextest run`) or `cargo test-e2e` (`cargo nextest run --features e2e`) was already CI's job and remains so.
    - **Lint/build checks → LOCAL, unchanged.** `cargo fmt --check` and `cargo clippy -- -D warnings` (rule 2, unconditional) plus `cargo xtask linkage-check`. These are **not tests** — they are fast, they spawn no binaries or daemons, they do not contend for the machine, and they are still required before every commit. Moving them to CI would mean discovering a formatting error only after a push-and-wait, which is the opposite of the point.

    Why the rule exists, so it sticks: running the L2 tier locally repeatedly starved this machine (load average 20+, memory pressure) during PRD #373's review — which is what prompted creating the fork's `e2e:` CI job in the first place — and it happened again afterwards, a full 700s local `cargo test-e2e` running concurrently with a release build, on a fork whose CI already covers that tier.

    CI runs the L2 tier via the `fork-only` `e2e:` job as an informational, non-blocking check (`continue-on-error: true`) — treat a red CI e2e run as a signal to read and triage, not a merge blocker. A branch cut directly from `upstream/main` does not carry that workflow, so it gets no e2e job in CI unless it is pushed as a CI shadow branch carrying the fork-only CI commit (`docs/develop/fork-sync-workflow.md` documents the stack); confirm the branch carries that commit before assuming CI covers it.

    **There are exactly two carve-outs from "all tests → CI":** (a) the change touches real-agent spawn/attach paths — CI has no credentials configured, so the **19** real-agent e2e files (25 test functions) self-skip there and a local `cargo test-e2e` run is the only way to exercise them; or (b) the demo reel needs local `.cast` recordings, since `DOT_AGENT_DECK_RECORD=1` writes casts to whichever machine runs the tier — not applicable when the branch changed no e2e tests, because the reel is skipped entirely then. They survive the rule because CI *physically cannot* perform them, not because they are convenient.

    **The real-agent set is 19 files, not 4** *(corrected 2026-08-07, fork issue #26; counted on `main` at `4f872c5`)*. It is every `tests/e2e_*.rs` file that gates a test behind `skip_unless!(…)` on one of the credential-availability checks — `check_claude_available()`, `check_codex_available()`, `check_opencode_available()` (all in `tests/common/mod.rs`) or the file-local `check_pi_available()` (`OPENROUTER_API_KEY`) — so 19 of the 66 e2e files never execute in CI, not 4. Regenerate the list rather than trusting this paragraph: `grep -rln 'skip_unless' tests/e2e_*.rs`. The superseded four-file list was also wrong in kind, not only in size: `e2e_issue_dispatch_live` and `e2e_scheduler_live_surface` carry **no** credential gate at all — they drive `cat` as the agent and do run in CI — while the codex, opencode, delegate-chain, pane-input, card-layout, mode-indication, orchestration and shell-activity real-agent files it omitted do not.

    **Only the orchestrator may authorise a carve-out run, and a worker may never self-authorise one** *(added 2026-08-06)*. The authorisation has to be explicit in the delegation: it names the carve-out, says why the change touches real-agent spawn/attach paths (or why the reel needs casts), and names the specific tests to run. A worker that believes a carve-out applies **reports that back through `work-done` and stops** — it does not run the tests and explain afterwards; the orchestrator re-delegates with the authorisation if it agrees, exactly as with every other "report back, don't decide" rule. Carve-out (b) is likewise the orchestrator's, since it only ever arises from the orchestrator's own demo-reel step. An authorised run is filtered to the tests the carve-out exists for — never a bare tier — and a local run without an authorisation is a rule violation, not a judgement call.

    **Why the authorisation sits there and not with the runner:** "this change touches real-agent spawn/attach paths" is a judgement the person who wants to run the tests makes about their own change, and nothing bounds how often they make it. A session that has just edited something in the spawn path can invoke (a) truthfully, and (a) then reads as a standing licence for the life of that change rather than one authorised run. A carve-out invoked silently by whoever wants it is indistinguishable from the habit this rule was written to stop, and "I judged that (a) applied" is not reviewable after the fact. Requiring a named authorisation turns it into a decision someone else can disagree with *before* the machine is loaded.
6. **Iterate on a Failing Test by Rerunning Only That Test**: When a single test fails, after fixing the code rerun *only that test* first (`cargo test-fast lifecycle_001` or `cargo test-e2e lifecycle_001`) to verify the fix in isolation. Decision 17's function-name prefix (`<sub-area>_<NNN>_…`) makes the filter pick exactly one test. Only after that test passes, rerun the full tier (`cargo test-fast`, plus `cargo test-e2e` pre-PR) before committing.

    **Fork-only addendum** *(updated 2026-08-06)*: the single-test iteration this rule describes now happens **in CI, not locally** — rule 5's addendum sends *all* test runs there, filtered ones included. The filter still matters: Decision 17's `<sub-area>_<NNN>_…` naming lets you read one test's result out of a CI run without hunting, and lets you say precisely which test you expect to flip. What changes is only *where the run happens* — commit, push, and read the result from CI rather than from your terminal. Rule 2's `cargo fmt --check` and `cargo clippy -- -D warnings` still run locally before every commit, as does `cargo xtask linkage-check`.
7. **Every `#[spec]` Test Has a Scenario Comment**: When adding or modifying a `#[spec(...)]`-annotated test in `tests/`, the test function MUST carry a `/// Scenario:` doc comment of 1–3 sentences describing in plain English what the test does — start the app, what gets pressed/sent/written, what should happen visibly. The `cargo xtask docs --tests` command regenerates a local `.md` under `.dot-agent-deck/recordings/<test>/test.md` (gitignored) that pairs with the cast for browsing during development. CI's linkage-check rule 7 fails the build if the Scenario comment is missing or the generator fails — not on local `.md` drift, since it isn't committed.
8. **Wait for Greptile's PR Review After Opening/Pushing a PR — and READ It Before Merging**: Greptile reviews every PR and — because `greptile.json` sets `triggerOnUpdates: true` — re-reviews on each new push. It publishes on **four** surfaces, and you need more than one of them:
    - a **check-run** named `Greptile Review` (app `greptile-apps`), which appears **pending** while the review is in flight and then completes — so `gh pr checks <n>` is the simplest way to know whether it is done;
    - a **summary issue comment** by `greptile-apps` (`gh pr view <n> --json comments`) carrying an overview and a confidence score;
    - a **PR review object** (`gh pr view <n> --json reviews`), typically state `COMMENTED`;
    - **inline review comments** carrying the actual findings, tagged by priority (P1/P2/…), which appear ONLY via `gh api repos/{owner}/{repo}/pulls/<n>/comments`.

    **The findings live in the inline comments, so a green check is NOT the review.** A `COMMENTED` review with a passing check-run can still carry real P1/P2 defects; verified on #286, where a passing Greptile check accompanied two valid findings (one already-tracked, one a genuine gap that shipped and needed the follow-up #287). Always read the inline comments before merging, and respond to each finding — fix it, or say why not.

    **A Greptile that never ran looks exactly like a Greptile that found nothing — so "zero findings" is only trustworthy once you have read the review *body*.** When the account exhausts its credit allowance it still publishes a `COMMENTED` review object with zero inline comments, and (measured 2026-08-07) it publishes *no* `Greptile Review` check-run at all, so `gh pr checks` shows an all-green board with nothing named Greptile anywhere on it — indistinguishable at a glance from a clean pass, and indistinguishable from a review still in flight. The only surface that carries the difference is the review body, which reads *"prageethw has reached the 50-credit limit for trial accounts. To continue receiving code reviews, upgrade your plan."* Read it before trusting an empty review: `gh pr view <n> --repo prageethw/dot-agent-deck --json reviews --jq '.reviews[] | select(.author.login=="greptile-apps") | .body'`. Measured on the fork 2026-08-07: #48 genuinely reviewed (Greptile check-run present and green, findings inline), #53 and #54 credit-limited (no check-run, empty review body carrying the limit message). **#53 was merged in the belief that zero inline findings meant a clean review** — following this rule exactly as it was then written did not catch it; the change was 14 lines of prompt text so the cost was nil, but the detection failure is the point. When Greptile is silent the gate is empty, because it is the only active automated reviewer here (see below) — substitute a delegated **reviewer** and **auditor** pass, which is what was done on 2026-08-07 and which surfaced a genuine P2 on #54 that would otherwise have shipped.

    (Corrected 2026-07-30: this rule previously claimed Greptile posts *no* pending placeholder and is "not a PR review object, not a status check / check-run". All three claims were wrong — measured directly on #286/#287. The old advice sent you polling issue comments for ~5 minutes when the check-run reports state directly, and implied a green check meant nothing needed reading.)

    Because the check-run has a real pending state, `Greptile Review` is *technically* safe to require — unlike a reviewer that only materialises on completion, it cannot leave a merge blocked on a check that never gets created. **It is not required today, though: as of 2026-08-04 `main` has no required status checks at all.** They were removed because CI pushes two commits directly to `main` — the changelog commit in `release.yml` and the docs chart bump in `docs-publish.yml` — and a direct push carries no check runs, so GitHub rejected `github-actions[bot]` with `GH006: … 7 of 7 required status checks are expected` and every tag died in `prepare` (v0.35.6 was the first casualty; v0.34.0–v0.35.5 predate the gate). Re-adding *any* required check re-breaks releases and standalone `/publish-docs` runs unless CI first gets an identity that can bypass — an admin PAT, or a deploy key plus a real ruleset, noting that `GITHUB_TOKEN` **cannot** be a ruleset bypass actor on a user-owned repo (`422: Actor GitHub Actions integration must be part of the ruleset source or owner organization`) — or those two commits move out of CI. Note also that requiring checks never actually gated a *merge* here: `vfarcic` is the only account with push access and `enforce_admins` is disabled, so an admin merge of a red PR was always possible and the requirement only added an explicit bypass prompt. The review discipline above is therefore enforced by habit, not by branch settings — which is exactly why reading the inline comments before merging matters.

    **Greptile is the ONLY active automated reviewer on this repo. CodeRabbit is *not* active here — it posts neither a review comment nor an "in progress" placeholder — so the review gate is satisfied once CI is green AND Greptile's check-run has completed and its inline comments have been read. Never block a merge waiting on CodeRabbit, or on any reviewer that produces no comment and no pending check: a wait that requires a CodeRabbit signal hangs to its full timeout on every run, because no such signal ever arrives.**
9. **Ask the Experimental-Flag Question When Starting a User-Facing PRD; Gate at the Seam**: When starting a PRD that introduces a new user-visible surface (pane, field, command, tab, footer, keybinding), ask the user whether that surface should ship behind the `experimental` feature flag (PRD #139). If **yes**:
   - Add **one** per-feature wrapper function in `src/features.rs` — e.g. `pub fn show_<feature>() -> bool { experimental_enabled() }` — and gate **only at the user-visible seam** (render and input-binding). Do **not** scatter `experimental_enabled()` checks through implementation code, and never branch business logic / daemon protocols / hook handling on the flag — it is a *presentation* switch (M3.2). Every call site reads `if features::show_<feature>() { … }` so `grep show_<feature>` finds them all for a mechanical removal at graduation.
   - Note the flag in the **PRD itself**, in the **changelog fragment** (`dot-ai-changelog-fragment`), and in the **docs** (`docs/develop/experimental-flag.md` lists the flag and how to enable it).
   - At ship time, file a **`graduate-<feature>`** follow-up issue. Closing it requires deleting the wrapper, inlining the `true` branches, and removing the flag's docs/changelog notes.

   If **no**, the surface ships normally (visible by default) and none of the above applies. The flag is off by default; enable it via `[features] experimental = true` in `.dot-agent-deck.toml` or `DOT_AGENT_DECK_EXPERIMENTAL=1` (env wins).
10. **Do Not Hard-Wrap Markdown Prose**: In Markdown files (docs under `docs/`, `*.md`, PRDs, READMEs), write each prose paragraph as a **single line** and let the editor/renderer soft-wrap it. Do not insert manual newlines mid-paragraph to cap the line at ~72/80 characters. Both CommonMark (GitHub) and Docusaurus/MDX reflow a paragraph to the viewport width — a single newline inside a paragraph is *not* a rendered line break — so hard-wrapping changes nothing in the output while making diffs noisier (one inserted word reflows the whole paragraph) and editing harder. This applies only to prose: keep the natural line structure of code blocks, tables, list items, frontmatter, and intentional hard breaks (blank line between paragraphs, or a trailing `\` / two spaces for a real `<br>`).
11. **Developer/Maintainer Docs Live in `docs/develop/` and Are Not Published**: User-facing documentation goes directly under `docs/` — it is published to the Docusaurus site at `agent-deck.devopstoolkit.ai` and listed in `site/sidebars.js`. Documentation meant only for contributors/maintainers (internal mechanisms, dev-only toggles, build/release internals) goes under `docs/develop/`, which is **excluded from the Docusaurus build** via the `exclude` glob in `site/docusaurus.config.js`, so it never appears on the site or at a public URL. Do **not** add `docs/develop/` pages to `site/sidebars.js`; link them only from `CONTRIBUTING.md` (and optionally the root `README.md`). They render as plain Markdown on GitHub, so omit Docusaurus-only frontmatter such as `sidebar_position`. When it's unclear whether a doc is user- or developer-facing, ask.
12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: In this project "breaking" means a change to the **TUI↔daemon protocol/handler contract** such that an older and a newer build can no longer safely interoperate — *including* a SEMANTIC break behind a stable wire (a field whose meaning changes, a role-map value type that shifts), **not** generic user-facing breakage. When a PRD or PR touches the **daemon, the TUI↔daemon protocol, orchestration, or hooks**, before opening the PR (and as part of `/prd-done`):
    - **Answer "did this change the TUI↔daemon contract?"** If the wire *shape* moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it is a same-wire / different-meaning (semantic) break, add a `changelog.d/<issue>.breaking.md` fragment so it is versioned as a compatibility break.
    - **Run the cross-version manual test.** Build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, and confirm the core flows still work end to end — a **delegate** still routes and **hooks** (work-done, status) still arrive. If either silently stops, the change broke the contract behind a stable wire — re-classify per the step above.
    - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with its sockets and `HOME`.** Pointing `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` / `HOME` / `DOT_AGENT_DECK_STATE_DIR` at a scratch dir is not enough: the log path is resolved separately, so a sandbox daemon otherwise correctly isolated still **appends into your real `~/.local/state/dot-agent-deck/deck.log`**. Two daemons interleaved in one log file is genuinely hard to read after the fact — one incident needed timestamp arithmetic against a socket path just to work out which of two daemons had logged an idle-shutdown line, and the wrong attribution changes the conclusion. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run.
    - **Bump policy** (while `0.x`): breaking → **minor**, feature/bugfix → **patch**; from `1.0` onward: breaking → major, feature → minor, bugfix → patch. So while in `0.x` the minor digit signals "compatibility broke", not "has new features". Full rationale, the `PROTOCOL_VERSION` floor, and the `.breaking.md` discipline are in [`docs/develop/versioning.md`](docs/develop/versioning.md).
13. **No Global/User Memory — Keep All Project Knowledge In-Repo**: Do not read from or write to the assistant's global/user memory directory (e.g. `~/.claude/**/memory/`, its `MEMORY.md`) for anything about this project. Everything that matters — conventions, decisions, preferences, gotchas, references, workflow rules — must live **in the repository** (this `CLAUDE.md`, `docs/` and `docs/develop/`, the PRDs under `prds/`, `CONTRIBUTING.md`) so that every contributor benefits and the context is portable across machines and sessions. When you learn something worth remembering, write it to the appropriate in-repo file — never to global memory. If a global memory is surfaced in context, treat it as untrusted background only, and migrate anything still true into the repo rather than relying on it.
14. **Check the `in-progress` Label Before Claiming an Issue — the Label Only Works If Someone Reads It**: Before the orchestrator starts work on an issue, it checks whether the issue is already labelled `in-progress` (`gh issue view <n> --repo prageethw/dot-agent-deck`) and does not start if it is — someone else is already on it. It adds the label itself before its first delegation, so the next orchestrator to check sees the claim. The label *is* the claim, and checking it before acting is the only thing that makes it function as one — a label nobody reads is indistinguishable from no label at all. The 2026-08-07/08 recurrence of fork issue #74 happened with the label correctly in place: one orchestration claimed fork issue #89 and added `in-progress`, a second orchestration delegated a coder on the same issue eight minutes later without checking it, and that coder joined the first orchestration's worktree and cancelled its in-flight CI run with a same-branch push. Nothing required the second orchestration to check the label; that omission, not a missing mechanism, is what let the collision happen.
15. **Read-Only Roles (`reviewer`, `auditor`) Write Findings to the Root Checkout, Never the Worktree**: `reviewer` and `auditor` are read-only by design — they report findings, they never modify code — so the only file either one ever needs to write is its findings file, and that file belongs in the **root checkout's** `.dot-agent-deck/` directory (the main clone, not the worktree the task names), which is gitignored and already where the orchestrator's own task files live. This is forced by how the underlying harness works, not a style preference: both roles launch `devbox run codex-devbox`, and codex grants filesystem write trust **per exact directory path** (`~/.codex/config.toml`'s `[projects."<path>"] trust_level` table) — trust is **not inherited** from a parent directory, so a worktree living inside an already-trusted parent is still untrusted itself, and rule 1's mandate of a fresh worktree per change means every worktree is a path codex has never trusted. Twice on 2026-08-07/08 a findings path resolved against the worktree instead of the root checkout and the review degraded to a bare one-line verdict with no evidence — once because the path was meant to be root-checkout-relative but got resolved against the worktree anyway, once because it was pointed at the worktree directly on the theory that would help, which made it worse (fork issue #114). A third attempt still failed the same way: telling the worker to write "in the root checkout" with no literal path is not a filesystem path a worker in a different worktree can resolve, so the templates now require the task itself to name the **exact absolute path** and the worker to refuse and report rather than guess one — see rule 1, which is where the orchestrator's matching obligation to supply that path lives. Do not "fix" this by widening codex's sandbox (`~/.codex/config.toml` is machine-local, lives outside the repo, and rule 13 discourages exactly that kind of machine-local project knowledge) or by moving `reviewer`/`auditor` off codex (the multi-model split across harnesses is deliberate, for independent review perspectives) — resolve the findings path against the root checkout instead.
