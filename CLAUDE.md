# CLAUDE.md — dot-agent-deck

## PERMANENT INSTRUCTIONS

1. **Every Fix Gets Its Own Worktree**: Any distinct piece of work — a PRD, a bugfix, a docs change, a review follow-up — gets its own dedicated git worktree, created up front. This is the default; do **not** ask whether the user wants a worktree or a plain branch, and do not reuse a worktree for a second, unrelated fix — one worktree per change. `/worktree-prd` remains the helper for PRD work. **Never work in the root checkout**: it is the long-lived checkout the running daemon and worker panes are attached to, and it routinely carries uncommitted state. The incident behind this rule (2026-08-07): the root checkout was sitting on `docs/prd-386-upstream-pr-record` with an uncommitted `.dot-agent-deck.toml` and an untracked `tests/snapshots/render_dashboard__pane_008_named_agent_badges.snap.new`, and a task told a worker to commit a documentation file "from the root checkout" — switching that checkout to `main` would have dragged the dirty `.dot-agent-deck.toml` along and risked committing the fork's local role-command config onto `main`. The worker refused and used a throwaway worktree instead; a dedicated worktree makes that class of mistake impossible rather than relying on each worker noticing. A worktree also keeps each branch's `target/` build state isolated, so switching work does not force a full rebuild. Remove the worktree once its branch is merged and dropped (`git worktree remove`) so they do not accumulate. This recurred on 2026-08-07/08 (fork issue #74) with a sharper root cause than the original filing assumed: two orchestrations worked the same issue concurrently because a second orchestration's task named no worktree path, so its worker found the first orchestration's existing branch and reasonably joined it — writing production code into a worktree it did not own, then pushing to it and cancelling the first orchestration's in-flight CI run. **The orchestrator creates the worktree and states its absolute path, exact expected commit SHA, and branch name in every task it delegates**, and that branch name carries a work-type prefix (`fix/`, `feat/`, `docs/`, `chore/` — see [`docs/develop/work-types.md`](docs/develop/work-types.md)); a task naming no path, SHA, or branch, or naming the root checkout, is itself the defect, not a judgement call the worker gets to make. **Unset the new branch's upstream immediately after creating it** (`git branch --unset-upstream` in that worktree, then push explicitly with `git push origin HEAD:refs/heads/<branch>`, substituting the task-named branch for `<branch>`) — `git worktree add -b <branch> <path> origin/main` sets the new branch to track `origin/main`, so a bare `git push` from that worktree lands on `main`; this happened for real on the #89 branch and was caught only because a worker noticed and pushed explicitly instead. **Before touching anything, a worker verifies the worktree is clean and `git rev-parse HEAD` equals the task-named SHA**; if either is wrong, report it through `work-done` and stop there — do not `git add -A`, do not stash, do not work around it to make progress anyway. **Never `git add -A` or `git add .` in a shared checkout — stage explicit paths.** This is the exact mechanism behind #74's original incident, where a live mutation-testing run was swept into a real commit and pushed to an open PR. **Mutation testing, and any other tool that rewrites source in place, runs against its own throwaway worktree or copy — never one an agent is actively editing.** **When delegating to a read-only role (`reviewer`, `auditor`), the task SHOULD state the exact absolute path of the findings file under the root checkout's `.dot-agent-deck/` directory** — but since 2026-08-14 omitting it is no longer a deadlock: rule 15 now has the worker **derive** the root checkout itself rather than refuse. Naming the path is still better where you know it, because it puts the destination in the task record; it is simply no longer load-bearing. This was a genuine deadlock four times in the #74/#114 lineage — a template requiring something of the worker that nothing required the orchestrator to supply — and rule 15 records how that class was closed rather than merely documented. See rule 16.
2. **Run `cargo fmt --check` and `cargo clippy --workspace --all-targets --features e2e,e2e-live -- -D warnings` Before Committing**: Always run both before creating any git commit. If fmt reports issues, run `cargo fmt` to fix them. If clippy reports warnings, fix the code. Stage any fixes before committing.

    **All four flags are load-bearing** — `--all-targets` and `--features e2e` per issue #407, `--workspace` per issue #436, `e2e-live` per issue #502 (the paragraph on it below). The old rule said `cargo clippy -- -D warnings`, which type-checks *no test file at all*: without `--all-targets` cargo builds only lib and bin targets, and every one of the 71 `tests/e2e_*.rs` files opens with a `feature = "e2e"` cfg (47 in lane 1 — 44 exactly `#![cfg(feature = "e2e")]` and three adding a `unix` term — and 24 in lane 2, 21 exactly `#![cfg(all(feature = "e2e", feature = "e2e-live"))]` and three adding `unix`, so six of the 71 carry that extra term), so without `--features e2e` they compile to empty crates. An e2e-only change therefore passed the gate instantly and meaninglessly — measured by injecting a deliberate `E0308` into `tests/e2e_handshake.rs`: `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` both exited 0, and only the feature-enabled command caught it. `cargo fmt --check` is *not* affected — rustfmt is cfg-blind and walks the cargo target list, so it has always covered these files.

    The one command is a strict superset of the old one, and here is the accurate version of why — the claim that used to sit here ("no `not(feature = "e2e")` or `not(feature = "e2e-live")` cfg exists anywhere, and `src/` never references either feature") was simply false, and had been since before `e2e-live` existed. `src/` **does** reference `e2e`, in five `#[cfg]` attributes (plus three prose mentions in doc comments at `src/main.rs:608/2701` and `src/state.rs:8681`): `src/platform/paths.rs:665/686/693` and `src/dispatch.rs:1105` are `#[cfg(feature = "e2e")]`, and `src/platform/paths.rs:673` is a genuine `#[cfg(not(feature = "e2e"))]` — the feature-off arm of `effective_current_exe`, which is exactly the point of gating that test seam on a feature instead of an env var (read the doc comment above it). So `--features e2e` does not merely *add* code to `src/`: it swaps that one function. What holds, and what the superset argument actually needs, is the narrower fact: **no `not(feature = "e2e-live")` cfg exists anywhere and nothing under `src/` references `e2e-live` at all** (`grep -rn 'feature = "e2e-live"' src/` is empty), so adding `e2e-live` to a command that already passed `e2e` can only widen what is compiled. The `e2e` half rests on something different, and it is not "nothing is swapped": `paths.rs:673`'s arm is a one-expression delegation to `std::env::current_exe()`, and it is still clippy-linted by `build-windows` and `build-macos`, which stay on bare `cargo clippy -- -D warnings` (paragraph below) and therefore lint precisely the feature-off configuration this command does not. So both arms are covered across the required jobs — just never by one command, which is worth knowing before writing a `not(feature = "e2e")` block with anything substantial in it. It is also **cheap**: cargo caches the feature-on and feature-off fingerprints side by side, so alternating this with `cargo test-fast` costs ~0.2s warm; a from-scratch re-check of every e2e target was ~14s when there were 62 of them (unremeasured at 71). **Re-measured 2026-08-31 and that "~0.2s warm" does not hold as an absolute cost, though the property behind it does.** Warm, back to back, 16 cores, all three runs `--workspace`: this command takes **9.3–10.4s** and the bare `cargo clippy -- -D warnings` takes **3.8–4.4s**, and neither ever reaches a no-op — both print `Compiling dot-agent-deck` every time, because `build.rs` watches `.git/index` for build-id freshness (PRD #103) and that file moves constantly. What survives is the part the claim was really about: running this straight after `cargo nextest list --workspace` costs 10.4s against its own 9.5s floor rather than a full re-check, so the two feature configurations genuinely do not evict each other. The ~5.5s over the bare command is re-linting the 71 `tests/e2e_*.rs` targets, which is the whole point of the flags. `bacon.toml`'s `[jobs.clippy]` carries the same command and the same measurement.

    This is a *type-check and lint*, not the e2e tier — it spawns no binaries and hits no LLM APIs, so naming the e2e features here does not put either e2e lane into this gate — in particular it does not run a single credentialed test, and never did (rule 5 has the lanes). Before this change, e2e code was clippy-linted by no gate anywhere and type-checked only by `cargo test-e2e`, which at the time ran nowhere but a contributor's own machine. The Linux CI `build` job runs the same command; `build-windows` / `build-macos` deliberately stay on bare `cargo clippy -- -D warnings` (see the comments there — the L2 tier is Unix-only and reports dozens of E0425s under the Windows target).

    **`cd` into the worktree before running any gate — never pass `--manifest-path` to `cargo xtask linkage-check`.** The `xtask` alias appends `--`, so `--manifest-path` is **not consumed as a `cargo run` flag**; resolution falls back to the current working directory, and the agent harness resets that between tool calls. The result is the worst possible shape: the check runs against **whichever checkout the shell happened to be in** — usually the root checkout, not your worktree — and still prints `ok`. It was found only because a tester noticed the catalog-id count looked wrong for the branch. Rule 1 puts *every* worker in a worktree, so for an unknown number of past runs "gates passed" may have meant "gates passed against the root checkout, which is 300+ commits from your branch". State the gate as `cd /absolute/path/to/worktree && cargo xtask linkage-check`, and treat a linkage-check result you cannot tie to a `cd` as no result at all. Fork **#234** — `linkage-check` silently mis-pairs a `#[spec]` on an async fn with an unrelated later function — is the same family: a gate that answers confidently about the wrong thing. See rule 8's closing paragraph for why that shape, not the check's colour, is what has to be read.

    **`--workspace` covers the `xtask/*` members** (issue #436). Cargo's default target selection is the root package alone, so `xtask/docs`, `xtask/linkage-check` and `xtask/spec` were linted by no gate anywhere. `xtask/spec` and `xtask-docs` are path dev-dependencies so they were at least *built*, but building is not linting, and `xtask/linkage-check` was not even built — which is how an `unnecessary_sort_by` sat in its `clean_tmp.rs` on `main` long enough to be discovered by an unrelated PR. That lint was fixed in the same commit that added this flag, so the widened gate landed green. The widening is **free warm**: measured back to back, `--workspace` and root-only both return in 0.20s once cargo has the fingerprints, since the three `xtask` members are small and dependency-light. Note `--workspace` does **not** change which features reach the root package, so this stays a strict superset of the pre-#436 command.

    **`e2e-live` is now the ONLY thing in CI that type-checks a third of the tier** (issue #502). The split moved the 24 real-agent files to `#![cfg(all(feature = "e2e", feature = "e2e-live"))]`, so under `--features e2e` alone those 24 compile to **empty crates** — the #407 hole reopened, just narrower, and the same hole class #436 and #489 each closed in their own corner. Measured exactly the way #407 was, by injecting a deliberate `E0308` into `tests/e2e_dispatcher_mode.rs` (a file that moved into the live set): `cargo clippy --workspace --all-targets --features e2e -- -D warnings` exited **0** and reported nothing, while the same command with `--features e2e,e2e-live` exited **101** and reported the `E0308`.

    **This flag was originally justified by the credentialed CI lane existing. That lane is gone, and the flag matters MORE, not less — the justification inverted rather than weakened.** While lane 2 ran in CI, a type error in those 24 files would eventually have been caught by the lane itself, and this command merely caught it sooner. Nothing in CI runs them now: no test that reaches a real agent runs on a runner (rule 5 has the decision and the two reasons). So this one command is the **entire** CI-side coverage of 24 test files — a third of the e2e tier — and its failure mode without the flag is silent: clippy exits 0 having compiled nothing, and the break surfaces whenever some developer next runs `cargo test-e2e-live`, which may be weeks. **Do not "simplify" `e2e-live` out of this command.** It costs nothing at run time (it is a type-check and a lint — it spawns no binary, hits no API, and needs no credential; naming an e2e feature here has never put an e2e lane into this gate) and it is the last line of defence for the files CI otherwise never sees.

    `cargo fmt --check` was separately proven unaffected for the reason given above — a formatting violation inside a live-gated file was caught by bare `cargo fmt --check` with no features at all, because rustfmt walks the cargo target list and is cfg-blind. The Linux CI `build` job runs the same two-feature command; `build-windows` / `build-macos` still stay on bare `cargo clippy -- -D warnings`, and that divergence is untouched by this — it is caused by `--all-targets --features e2e` against the Windows target, and adding a second feature to a command those jobs do not run changes nothing for them.
3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (e.g. `tests/event_forwarding.rs`), not for the milestone or PRD that introduced them (e.g. `tests/m2_17_event_forwarding.rs`, `src/prd76_*.rs`). Milestone tags belong in commit messages and the PRD doc — long-lived filenames must outlive the branch. Existing `m*_` test files are scheduled for cleanup; do not create new ones in that pattern.
4. **Add or Update TUI Tests for Functional UI Changes**: When a change adds or modifies user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, embedded panes, hook delivery), add or update tests in the TUI harness. Use L1 (in-process `TestBackend` + `insta`) for pure widget/layout changes; use L2 (PTY + vt100, files named `e2e_*.rs`, gated by `#![cfg(feature = "e2e")]`, plus a `feature = "e2e-live"` term when the test needs a real agent credential) when the change touches the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change do not require new tests. **For a major user-facing feature, include at least one PTY-attached L2 test** (the vt100 harness that drives the real binary, e.g. mirroring `scheduler/live/*`) that exercises the user-visible surface — not only headless daemon-serve (`RunNow`) tests. Only PTY-attached tests record a `.cast`, but a cast alone is **not** enough to be demo-reel-eligible: a clip must genuinely spin up a **real agent** (spawn → agent → work) **and** be explicitly opted in with a trailing ` [reel]` marker on its `tests/CATALOG.md` entry (PRD #180/#20 — see `.claude/skills/demo-reel-adapter`). A synthetic/stand-in PTY test (cat, scripted echo, recorder stubs, terminal-probe, synthesized hook events) is left unmarked and never becomes a clip even though it has a cast; a feature whose entire e2e coverage is headless (or unmarked) ships with no reel clip. (PRD #120's `issue_dispatch` is the cautionary case: `scheduler/dispatch/001-010` are all headless, so the showcase clip required adding the PTY-attached `scheduler/dispatch/011`.) **A major user-facing feature should also have at least one REAL-scenario e2e test** that drives the genuine spawn→agent→work path with a *real* agent on a **cheap model** (Haiku for Claude, a mini model for OpenCode) through a cheap, deterministic-enough operation — e.g. "list the files and report a known sentinel filename" — rather than relying solely on a stand-in like `cat`. We have historically over-relied on stand-ins; a stand-in proves the plumbing but never that an agent genuinely runs against the cloned/worktree/target state. Real-agent tests live in **lane 2** — the `e2e-live` half of the L2 suite (rule 5), which runs on a developer's machine and **nowhere in CI**, because no test that reaches a real agent runs on a runner. So writing one is only half the job: run it yourself with `cargo test-e2e-live <filter>`, and run it again whenever you touch the surface it covers, because nothing else will. They stay flaky-tolerant; make them robust with a directive prompt plus a uniquely-named fixture **sentinel file** so the assertion survives LLM phrasing/tool variance. **The bar is: at least one test per major feature must validate it AS A USER ACTUALLY USES AND SEES IT** — the genuine, user-visible experience end to end, e.g. a *live interactive* agent visibly working in the pane (with real status), not a non-interactive shortcut like `claude -p` and not a stand-in. Print mode and stand-ins prove the wiring; they do not prove the user-facing reality. Interactive headless agents are achievable — seed claude's onboarding + per-folder trust into the test HOME (see `prepare_claude_home` / the `TuiDeck` claude-trust seeding hook) and pass `--allowedTools` so no permission prompt blocks; `scheduler/dispatch/013` is the reference (an interactive Haiku agent listing the freshly-cloned repo live in the pane). Do not let "headless is hard" silently downgrade this bar where it is achievable.
5. **Fast Tests Per Task, Then the Tests Covering What You Touched; CI Runs Lane 1**: there are **three tiers of obligation**, and only the first two are yours.

    | tier | what | when |
    | --- | --- | --- |
    | always | `cargo test-fast` (alias for `cargo nextest run --workspace`) — protocol/state tests plus L1 widget/render tests | per task, unchanged |
    | **scoped to the change** | **the tests covering what you touched — any tier, credentialed included** | per task |
    | CI | lane 1 in full — the `e2e-deterministic` job running `cargo test-e2e` | per PR; **monitor and analyse that run, do not reproduce it locally** |

    **The obligation to run the full e2e tier locally before a PR is gone** (2026-08-31, issue #502, credential handling in #785) and nothing here brings it back. What replaces it is narrower and sharper: run the tests that cover the thing you changed, then read CI's lane-1 run rather than racing it.

    **How to find the covering tests, because "run the related tests" is useless without a way to locate them.** Three routes, in the order they are usually quickest: [`tests/CATALOG.md`](tests/CATALOG.md) maps catalog IDs to areas and records each test's layer, agent and lane, so grep it for the surface you touched (`orchestration/route`, `scheduler/dispatch`, `hooks/…`); the `#[spec(...)]` annotation on a test names its catalog ID, so the mapping runs both ways; and `cargo xtask list-tests` enumerates what exists when you do not yet know the vocabulary. **Name the tests you ran in your report** — "ran the related tests" is not a claim anyone can check, and the part of the tier CI does not run is on trust. (Lane 1 is not: `e2e-deterministic` runs it on every PR. Lane 2, and any credentialed test you scoped in, is.)

    **A change to shared harness code is the honest exception.** `tests/common/mod.rs` is linked by all 71 `tests/e2e_*.rs` files, so for a change there "the covering tests" genuinely *is* the whole tier: run one broad local pass and lean on CI for the rest. This is not hypothetical — the wrapped-credential matcher added under #502/#785 is shared by every redaction path in the harness, which is why lane 1 was run in full three times while it was being built.

    | Lane | Contents | Runs | Credentials |
    | --- | --- | --- | --- |
    | 1 — deterministic e2e | the 47 credential-free `tests/e2e_*.rs` files, `cargo test-e2e` | every PR, in CI (`e2e-deterministic` in `ci.yml`, `timeout-minutes: 60`) | none |
    | 2 — real-agent e2e | the 24 files that reach a real agent, `cargo test-e2e-live` (a **superset** run: lane 1 + lane 2, all 71 files) | **a developer's machine only — never CI** | the developer's own |
    | 3 — local debugging | the failing test, then its module | developer machine, while debugging | as the test needs |

    **NO E2E TEST REACHES A REAL AGENT IN CI, and this is a decision, not a gap.** No **test** credential is registered on this repository and none will be. Two reasons, both of which have to be re-argued before anyone adds one back. First, **running a credentialed job less often does not reduce the risk that a credential leaks from a public repository's CI** — it reduces the number of exposures, not the existence of the vulnerability. "Per-merge instead of per-PR", an environment with a required reviewer, a label gate: all of that is risk theatre once the key is on a runner at all. The fix actually available is to not put it there. Second, **the boundary is not "tests that read a key"** — it is "tests that reach a real agent by any route", because on a developer machine the agent CLIs are *pre-authenticated*, so a test that spawns `claude` and never touches `ANTHROPIC_API_KEY` still spends a credential. The `e2e-live` cargo feature draws exactly that line across 24 files, which is why the feature and the classification stay even though the CI job went. The working implementation of the deleted credentialed workflow is in git history — `edaa2b4` on `main`, `62ba861` on branch `agent/e2e-live-credential-sinks` — rather than parked in the tree as an unwired trap for whoever next registers a secret for an unrelated reason.

    **That claim is narrow on purpose, and the wider version of it — "no agent credential reaches CI at all" — is FALSE.** The Codex **issue-labeler** is a separately credentialed workflow that does send an agent credential onto a runner and does reach a real agent: `.github/workflows/issue-labeler.md` selects the `codex` engine and requires the repository secret `OPENAI_API_KEY`, the generated `issue-labeler.lock.yml` installs `@openai/codex` and runs `codex exec` with that secret as both `CODEX_API_KEY` and `OPENAI_API_KEY`, and `issue-labeler-batch.yml` exposes manually dispatchable preview and apply paths that forward it — all three workflows active. Its firewall excludes those variables from the agent container and proxies the call, which limits model visibility but not runner presence. That feature has its own threat model and its own docs ([`docs/develop/issue-labeling.md`](docs/develop/issue-labeling.md)) and is **out of scope for this rule**, which is about the e2e tier. Do not restate this rule absolutely; the false-absolute version is exactly the defect class the branch that narrowed it was fixing.

    **The unenforceable-verification gap is an accepted TRADE, and naming it honestly is part of the deal.** Nothing can force a contributor to run the credentialed tests locally. The only mechanism that could enforce it is CI, and CI has no credentials *by design* — so this rule is an instruction, not a gate. Instructions work reasonably well on agents, which read this file every session; on humans they are a hope. **The cost is real and stated plainly: real-agent regressions surface when someone happens to run them, not on any schedule.** A break in the spawn → agent → work path can sit on `main` for as long as nobody touches that area with `cargo test-e2e-live`. That is the price of not holding an API key in a public repository's CI, and it was judged the cheaper side of the trade. Whoever later proposes "let's just add the key to CI" is re-opening this trade and has to argue it again — against both reasons above, not merely against the inconvenience.

    **Lane 2 is what a developer runs, and running it is the point.** `check_claude_available` and `check_opencode_available` accept a non-empty `ANTHROPIC_API_KEY` as a **third** auth path, consulted after the credentials file and the macOS Keychain — so a developer with a real credential set authenticates exactly as before, and a key-only host works too. Three harness changes are **coupled** to the claude one and must never be split from it: `import_claude_credentials` writes no credentials file when the key authorises the run, `seed_claude_project_trust` pre-answers Claude Code's API-key approval prompt (it defaults to **No**, so an unattended agent stalls forever without it), and `INHERIT_PASS` lets the key cross the harness's `env_clear` into the spawned deck. The import and the seeding sit inside `launch_with_fixture`, which **panics rather than skips**, so widening the gate alone would have converted 22 silent skips into 22 hard panics. Set `DOT_AGENT_DECK_REQUIRE_REAL_E2E=1` when you want "cannot run" to read as UNVERIFIED rather than green: a preflight that cannot be satisfied prints `SKIP:` and **returns normally**, so nextest counts it as passed, and that flag turns every such skip into a failure.

    **The mechanism is a third cargo feature, not a nextest profile.** The 24 credentialed files open with `#![cfg(all(feature = "e2e", feature = "e2e-live"))]` (21 exactly that, three adding a `unix` term); the other 47 open with `#![cfg(feature = "e2e")]`, 44 of them bare and three adding `unix`. There is deliberately no live-*only* alias, because `e2e-live` without `e2e` compiles every e2e file to an empty crate — which is also why rule 2's clippy gate names **both** features, and why that gate is now the **only** thing in CI that type-checks those 24 files. A second nextest profile was rejected: issue #494 removed a `[profile.e2e]` that nothing selected, and the overrides in `.config/nextest.toml` are keyed by test-function name and are profile-independent, so they apply across all three aliases unchanged.

    **Why the old mandate went, and it is not merely that it was expensive.** It was self-defeating under the orchestration this repo runs on: every dispatched unit ran the whole tier, so N concurrent agents meant N copies of the whole thing on one box — #502 put that at N × 3738 tests. #415 measured **6–7 of 40 files failing in parallel against 40/40 at `-j 1`** — the same contention recorded in #351, #322 and #701. A gate that reddens because of how many copies of itself are running teaches people to re-run rather than to read, which is the failure mode #502 was opened about.

    **Lane 3 is what you actually run while debugging, and rule 6's procedure is unchanged by all of this.** Rerun the failing test alone to confirm the fix (`cargo test-e2e <one-test-name>`), then its module — rule 6 is still correct and was deliberately left as it stands. Read its closing parenthetical against this table, though: the tier to rerun before committing is `cargo test-fast` plus the scoped tests above, and for an e2e test its own module; the `plus cargo test-e2e pre-PR` half of that line is what #502 removed. Both `cargo test-e2e` and `cargo test-e2e-live` remain available locally and both take a filter; what disappeared is the obligation to run either **in full** before opening a PR — not the obligation to run what covers your change. `cargo test-e2e-live` needs a working agent credential of your own. **The `--exclude dot-agent-deck-desktop` that used to be needed here is gone** — issue #780 put Tauri's GTK/WebKit closure in `devbox.json`, and issue #815 verified it end to end: `cargo test-fast` in a devbox shell runs 3649 tests with no exclude, the desktop crate included. If it still dies on `libgdk-3.so.0`, your devbox environment is stale rather than short of packages; `scripts/devbox-check-gtk.sh` says so and gives the remedy, and [`docs/develop/desktop-gui.md`](docs/develop/desktop-gui.md) has the mechanism.

    **`--workspace` is load-bearing on all three aliases** (issue #489, duplicate #470 — written when there were two, and `test-e2e-live` inherited it) — the test-side sibling of rule 2's clippy flag, and it was missing for exactly as long. The workspace root is itself a package and there is no `default-members`, so cargo's default target selection is the **root package alone**: every test in `xtask/linkage-check` and `xtask/docs` executed in **no gate anywhere** — not `test-fast`, not `test-e2e`, not CI, which runs the same commands. Measured: `cargo nextest run` selects 1657 tests, `--workspace` selects 1705. (`xtask/spec` is a workspace member too but currently has no tests, so the 48 come from the other two.) **Those two figures are #489's, from when it was filed, and are kept as the evidence for the flag rather than as a current count.** Re-measured 2026-08-31: root-only selects **3231** and `--workspace` selects **3441**, so the gap the flag closes has grown from 48 tests to **210** — 199 in `xtask/linkage-check` and 11 in `xtask-docs`, `xtask/spec` still contributing none. Both current numbers are `--exclude dot-agent-deck-desktop`, because at the time of that measurement a `--workspace` run in the devbox died with `libgdk-3.so.0: cannot open shared object file` (issue #771); CI installs those deps with apt, so its counts include the desktop crate. **That exclude is no longer needed** — #780 added the closure and #815 measured 3649 tests with the desktop crate in, so the honest current figure is a whole-workspace one; the numbers above are kept as #489's evidence for the flag rather than as a current count.

        **Precondition, or the push produces nothing to read:** CI triggers on `pull_request` (opened/synchronize/reopened), on pushes to `main`, and on `workflow_dispatch` — a push to a feature branch with **no PR open fires no run at all**. "There was no CI to read" is never a reason to run the tests locally — it is a reason to open the PR.

        **A PR with merge conflicts also fires no CI, and this one is silent in a way the missing-PR case is not.** `pull_request` workflows check out `refs/pull/<n>/merge`; GitHub cannot compute that ref while the PR is `CONFLICTING`, so **the run is never created** — no error, nothing on the PR to say so. The class that hits this is the **sync PR**, which is also the class where CI matters most: it carries a whole upstream rebase and every conflict resolution in it. Ordinary PRs almost never hit it — this repo's docs commits are near-universally pure insertions, which git merges cleanly against neighbouring edits.

    **Only the orchestrator may authorise a carve-out run, and a worker may never self-authorise one** *(added 2026-08-06)*. An `@mention` in a comment notifies but does **not** put the PR in the reviewer's *Review requested* queue or their `gh pr status`, and is not what the approval rule counts; and do not *assign* the other maintainer, since an assignee is whoever drives the PR to done, normally the author. `.github/CODEOWNERS` carries one pathless rule (`* @vfarcic @prageethw`) and GitHub omits the author when auto-requesting from code owners, so the routing normally happens by itself — it is a **router, not a second gate** (`require_code_owner_review` stays `false`, so any maintainer's approval still satisfies the one required review). Three mechanics, every one of which fails *silently* rather than erroring — routing simply does not happen: `CODEOWNERS` is read from the **base** branch, so a PR that edits it does not benefit from its own change; a malformed entry disables routing altogether, so check `gh api repos/vfarcic/dot-agent-deck/codeowners/errors` after editing it; and a **draft** PR is not routed to code owners at all until it is marked ready, so do not open a PR with `--draft` unless you mean to, and run `gh pr ready <n>` the moment it is meant to be reviewed. **Request review LAST**, not first: `dismiss_stale_reviews_on_push: true` means any push after an approval voids it, so settle CI, read the inline comments, push the fixes and resolve the threads *before* asking, or you buy a guaranteed second round trip. **Merging is a separate act from approving, and there are now two legitimate routes.** Nothing in the ruleset constrains who presses the button (`require_last_push_approval` is `false`) and the approver is not obliged to, so the author normally merges after approval; reviewer-merges is a Prow convention where a *bot* does it. Since 2026-08-11 `allow_auto_merge` is `true`, so the alternative is to **arm auto-merge on the PR** and let GitHub land it once the ruleset's conditions are met — the one approval, the four required checks green, and every review thread resolved. **Arming it is not a bypass:** auto-merge waits for exactly the approval a manual merge needs, so nothing unapproved slips through it, which is why it is safe to arm *before* review lands. That holds **only while the ruleset is in force**, though — `allow_auto_merge` is a repository setting the ruleset does not own, so deleting the ruleset (the emergency override) makes every armed PR instantly mergeable with no approval. Disarm before lifting the gate; `docs/develop/governance.md`'s Emergency override gives the order. Note the interaction with `required_review_thread_resolution: true` — Greptile's findings arrive as review threads, so an armed PR will not merge while they are unresolved, and whoever resolves them is doing the reading this rule asks for. **Never merge your own unapproved PR:** for the owner the admin bypass makes that succeed silently rather than fail, which is exactly how the gate decays into ceremony. An automated flow whose last step is a merge (`/prd-done`, `/prd-full`) may now arm auto-merge and hand off, but must never merge directly. Full rationale in [`docs/develop/governance.md`](docs/develop/governance.md).

    CI consequently pushes to `main` under an admin identity instead: the `RELEASE_TOKEN` secret is an admin PAT, and both `release.yml` and `docs-publish.yml` check out with `token: ${{ secrets.RELEASE_TOKEN }}`. **Two things matter when you touch either workflow.** First, each job **verifies the secret is non-empty in its first step** and fails there with an actionable message. That guard replaced a `token: ${{ secrets.RELEASE_TOKEN || github.token }}` fallback which was correct when written — its comment said it kept the workflow unchanged "while the secret is unset, so this change is safe to merge before `main` is protected" — and became a trap once both halves of that condition flipped on 2026-08-08: all it could then do was silently degrade an **unset or empty** secret to `github-actions[bot]`, which cannot push to `main`, surfacing *late* at the push step with the release already half-done. Keep the failure at step 1; do not reintroduce a fallback. **Know what the guard does not cover:** it tests `-z`, so a token that is present but **expired, revoked or under-scoped passes it and still dies at `git push origin main`** in that same half-done state — the guard converts "nobody set the secret, or a caller did not forward it" from a late mystery into a named error, and claims nothing more. The old fallback did not cover the expired case either: a GitHub `||` yields the left operand whenever it is non-empty, so an expired PAT reached `actions/checkout` unchanged rather than being swapped out. Probing the token was rejected deliberately — an extra API call and a new failure mode on the release path, to cover a case that has never occurred. What actually validates a token is the `docs-publish.yml` canary (`gh workflow run docs-publish.yml`), so **re-run it after every PAT rotation**. Second — the one that actually bit — **a reusable workflow invoked via `uses:` receives no secrets unless the caller passes them.** `release.yml`'s `docs` job calls `docs-publish.yml` that way, so without `secrets: inherit` the callee's `secrets.RELEASE_TOKEN` is empty and its push dies on `GH013`; that is exactly how v0.35.9's `docs / publish` job failed at "Commit chart changes", leaving the docs image published to GHCR but `main`'s chart pointer stale, so the site never rolled forward (fixed in `428acef` by adding `secrets: inherit`). Same workflow, same push target, same job steps; **only the invocation differed**, and with it whether the secret was in scope.     **The same "read the surface, not the prose" discipline applies to a PR's closing keywords, and this one bites hardest when you are being careful** *(fork issue #278, hit on PR #270 on 2026-08-13)*. GitHub scans PR bodies **and commit messages** for `<keyword> #<n>` — `close`/`closes`/`closed`, `fix`/`fixes`/`fixed`, `resolve`/`resolves`/`resolved` — and **does not parse the surrounding sentence**. Negation is invisible to it. So writing *"this does **not** close #256"*, in order to be explicit that a partial-milestone PR must leave its issue open, is what **registers the PR as closing #256**.

    That is not hypothetical: PR #270 said so in its body *and* in a commit message, and `gh pr view 270 --json closingIssuesReferences` reported `closes: 256` regardless. Undoing it needed a body edit **and** a `git commit --amend` plus force-push, because the keyword was in both.

    It bites this repo specifically because our PR bodies are unusually explicit about scope boundaries — partial milestones, blocked follow-ups, "this carries the other half" — so *"this does not close #N"* is a phrase we reach for naturally, and every occurrence is live. The consequence is silent and **delayed**: the issue is auto-closed at **merge**, long after anyone would connect it to the wording, and an issue closed by accident is worse than one left open because nobody is looking for it any more.

    Write `issue #N stays open`, `#N is not addressed here`, or `#N is partially addressed; it stays open`. Then read the surface that carries the behaviour, not the prose you wrote:

    ```
    gh pr view <n> --repo prageethw/dot-agent-deck --json closingIssuesReferences \
      --jq '[.closingIssuesReferences[].number]'
    ```

    **Two refinements, both learned by getting them wrong while writing this paragraph.** First: **describing the trap in a PR body re-triggers it** — quoting the bad example *"this does not close &lt;issue&gt;"* with a real number in it links the issue you are using as the example. Write illustrative examples with a placeholder and **no numeral**. Second: **HTML-escaping the `#` does not help.** `&#35;256` renders as `#256`, and the parser works on the rendered text, so the link is created anyway — verified directly on PR #265, which kept reporting the reference until the numeral was removed altogether.

    **That command checks the PR body ONLY, and the trap has two halves — so it is necessary and not sufficient.** `closingIssuesReferences` reports issues linked through the pull request *description*; GitHub's own "Linking a pull request to an issue" documentation is explicit that a closing keyword in a **commit message** closes the issue on merge **without** the containing PR appearing as a linked pull request. So a worker can put `fixes #<n>` in a commit, run the command above, see nothing, and still close the issue at merge — the exact silent failure this paragraph exists to prevent, reintroduced by trusting one surface for a two-surface problem.

    Audit both:

    ```
    gh pr view <n> --repo prageethw/dot-agent-deck --json closingIssuesReferences \
      --jq '[.closingIssuesReferences[].number]'                      # body only
    gh pr view <n> --repo prageethw/dot-agent-deck --json commits \
      --jq '.commits[].messageHeadline, .commits[].messageBody' \
      | grep -inE '(clos|fix|resolv)[a-z]*[[:space:]]+#[0-9]+'        # commit messages
    ```

    A body edit does clear a body-side link, but only once the rendered text genuinely no longer matches — so re-run the first command after editing rather than assuming it worked. A commit-side keyword needs `git commit --amend` or a rebase, and a force-push; editing the body will not touch it.
9. **Ask the Experimental-Flag Question When Starting a User-Facing PRD; Gate at the Seam**: When starting a PRD that introduces a new user-visible surface (pane, field, command, tab, footer, keybinding), ask the user whether that surface should ship behind the `experimental` feature flag (PRD #139). If **yes**:
   - Add **one** per-feature wrapper function in `src/features.rs` — e.g. `pub fn show_<feature>() -> bool { experimental_enabled() }` — and gate **only at the user-visible seam** (render and input-binding). Do **not** scatter `experimental_enabled()` checks through implementation code, and never branch business logic / daemon protocols / hook handling on the flag — it is a *presentation* switch (M3.2). Every call site reads `if features::show_<feature>() { … }` so `grep show_<feature>` finds them all for a mechanical removal at graduation.
   - Note the flag in the **PRD itself**, in the **changelog fragment** (`dot-ai-changelog-fragment`), and in the **docs** (`docs/develop/experimental-flag.md` lists the flag and how to enable it).
   - At ship time, file a **`graduate-<feature>`** follow-up issue. Closing it requires deleting the wrapper, inlining the `true` branches, and removing the flag's docs/changelog notes.

   If **no**, the surface ships normally (visible by default) and none of the above applies. The flag is off by default *in the code*; enable it via `[features] experimental = true` in `.dot-agent-deck.toml` or `DOT_AGENT_DECK_EXPERIMENTAL=1` (env wins).

   **On this fork the flag is ON, in committed config** *(2026-08-14, commit `ad93333`)*. `.dot-agent-deck.toml` carries `[features] experimental = true`, so every experimental surface is live for anyone running this repo — it is one master switch, not a per-feature one. Two consequences worth stating rather than rediscovering. First, "off by default" describes `features.rs`, not what you will actually see: a surface gated behind `show_<feature>()` renders here, so gating a new PRD surface behind the flag does **not** hide it from this fork's own users, and "it's behind the flag" is not by itself an answer to "is this safe to ship". Second, a PRD asking the rule's question still gets a real answer — the gate remains the mechanical seam that makes graduation a `grep show_<feature>` away — but do not describe the result as hidden. If you need to see a surface in its off state, `DOT_AGENT_DECK_EXPERIMENTAL=0` wins over the file.

12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: In this project "breaking" means a change to the **TUI↔daemon protocol/handler contract** such that an older and a newer build can no longer safely interoperate — *including* a SEMANTIC break behind a stable wire (a field whose meaning changes, a role-map value type that shifts), **not** generic user-facing breakage. When a PRD or PR touches the **daemon, the TUI↔daemon protocol, orchestration, or hooks**, before opening the PR (and as part of `/prd-done`):
    - **Answer "did this change the TUI↔daemon contract?"** If the wire *shape* moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it is a same-wire / different-meaning (semantic) break, add a `changelog.d/<issue>.breaking.md` fragment so it is versioned as a compatibility break.
    - **Run the cross-version manual test.** Build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, and confirm the core flows still work end to end — a **delegate** still routes and **hooks** (work-done, status) still arrive. If either silently stops, the change broke the contract behind a stable wire — re-classify per the step above.
    - **"With an agent under it" is load-bearing, and skipping it produces a false green rather than an error.** Start the previous-release daemon with no agents, point the branch TUI at it, and the branch TUI **silently terminates that daemon and lazy-spawns its own in under a second** — PRD #103/#161's build-version handshake behaving exactly as designed: the build ids differ, nothing is running, so it restarts with no prompt. Nothing in the output says so. You then run a **same-version** test that looks like it passed, which is worse than not running one. Measured 2026-08-29 on the PRD #313 run, which lost a full attempt to it. The sequence that actually reaches the scenario is: previous-release daemon → **previous-release TUI** to bring the roles up under it → close that TUI (the daemon and its agents survive) → **branch TUI**, which now shows the mismatch prompt naming the live agents → **decline** it, and the new TUI attaches to the old daemon unchanged. Verify you got it before trusting the result: exactly **one** `Attach protocol listening` line for the whole run, and the same daemon pid and build id serving it end to end (that run: `0.38.0-g5a56361`, both sides reporting `server_version: 7`, so it exercised semantics behind a stable wire rather than a handshake rejection — which is what this rule is for). A corollary worth knowing when weighing how much a contract break would actually cost: because the handshake prompts whenever agents are live, **no ordinary user reaches a new TUI against an old daemon without consciously declining that prompt**. **The trap has a second mouth, and a correctly sequenced run falls into it too.** The daemon's idle window defaults to **30 seconds** (`DEFAULT_IDLE_SHUTDOWN_SECS`, `src/daemon.rs`), so letting more than that pass between `daemon serve` and the first attach logs `Daemon idle window elapsed (no clients, no agents, no pending schedules)`, the daemon exits, the TUI lazy-spawns a replacement, and the run is silently a same-version test again — measured on the PRD #745 run, which lost its first attempt to it exactly as #313 lost one to the no-agents cause. Export `DOT_AGENT_DECK_IDLE_SHUTDOWN_SECS=0` for every process in the run: it is a documented production knob (`0` = the "always on" / legacy remote behavior) and not a test hook, and `src/` reads it in exactly one place — `idle_shutdown_from_env`, whose only consumer is the idle-timer task — so it moves no protocol path. The `Attach protocol listening` count is therefore the tell for **both** causes: one line is the run you meant, two is a same-version test whichever cause swallowed it. And **do the status-hook check last** — sending `agent-event --type running` before the delegate check makes the daemon classify that pane's agent type as `Pi`, which routes prompt delivery differently and makes a delivered delegate briefly look undelivered.
    - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with its sockets and `HOME`.** Pointing `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` / `HOME` / `DOT_AGENT_DECK_STATE_DIR` at a scratch dir is not enough: the log path is resolved separately, so a sandbox daemon otherwise correctly isolated still **appends into your real `~/.local/state/dot-agent-deck/deck.log`**. Two daemons interleaved in one log file is genuinely hard to read after the fact — one incident needed timestamp arithmetic against a socket path just to work out which of two daemons had logged an idle-shutdown line, and the wrong attribution changes the conclusion. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run. **Export `DOT_AGENT_DECK_EXPERIMENTAL` too**, for the same class of reason: project-config discovery walks up from **cwd**, not from `$HOME`, so a sandbox rooted at a sibling path still reads the operator's real `~/.dot-agent-deck.toml` and both daemons come up with whatever feature flags that file sets — measured on the #702/#687 run, where both sides came up `experimental: ON`. It does not bias a comparison (both sides read the same file), but a cross-version sandbox whose feature flags come from the real home is not actually isolated, so pin the flag explicitly rather than inheriting it.
    - **Bump policy** (while `0.x`): breaking → **minor**, feature/bugfix → **patch**; from `1.0` onward: breaking → major, feature → minor, bugfix → patch. So while in `0.x` the minor digit signals "compatibility broke", not "has new features". Full rationale, the `PROTOCOL_VERSION` floor, and the `.breaking.md` discipline are in [`docs/develop/versioning.md`](docs/develop/versioning.md).

14. **Claim an Issue With `worker-agent-deck issue claim` Before Any Write to It — Not a Label You Check by Eye**: Before the orchestrator writes to an issue, it runs `worker-agent-deck issue claim <n> --repo <owner/name>` (PRD fork#235 M3, `src/issue_claim.rs`) rather than reading the `in-progress` label and reasoning about whether it means someone else is already on it. **"Write" means any write — a comment, a close, a label, an assignee — not only delegating implementation**, because scoping, analysis, and a doc-only fix folded into another PR are all writes, and all of them are how a claimed issue gets acted on by someone who never felt they were "starting work" on it. Rule 24 already says to name the executable the reader actually has installed; this rule naming the reserved upstream name was a violation of it, and the reason the whole claim discipline was reachable only through a compatibility symlink. The command posts an identifiable claim comment and sets the `in-progress` label — both hard writes, so a failure of either fails the claim — and then **attempts** the assignee, which is deliberately **best-effort**: it is skipped entirely when the login will not resolve, and a `gh` failure prints `warning: failed to write the assignee` without undoing a claim that already succeeded (`do_claim`, `src/issue_claim.rs`). That is the right behaviour — an assignee write must not be able to void a valid claim, and GitHub silently drops an assignee lacking repo access while `gh` still exits 0 — but it means **an issue can be validly claimed and show nobody assigned**, so never treat the assignee as the record of who holds it; the claim comment is. And — this is the part a manual label check could never do — it **refuses and exits non-zero** when a different identity already holds the issue, rather than printing something the orchestrator still has to read correctly. *(Corrected 2026-08-13, fork issue #290: this rule and rule 26 both said "sets the assignee … in one action". Not cosmetic — the phrasing was copied verbatim into a delegation task, and from there into the orchestrator's own seed prompt in `.dot-agent-deck.toml`, where a reviewer caught it as a P1 on PR #289. An inaccurate sentence in this file is inherited faithfully by every copy downstream of it.)* Starting work now IS the check; there is no separate "did I remember to look" step to skip. The 2026-08-07/08 recurrence of fork issue #74 is the incident that motivated moving off a label check at all: one orchestration claimed fork issue #89 and added `in-progress` correctly, a second orchestration delegated a coder on the same issue eight minutes later **without checking it**, and that coder joined the first orchestration's worktree and cancelled its in-flight CI run with a same-branch push. A refusing command removes that failure mode by construction — the orchestrator no longer has a checking step to forget, because the tool it already has to run to start work is the check. **Rule 26 extends this**: the claim comment `issue claim` posts records *who* holds an issue, not merely *that* it is held — and rule 26's own incident shows that even a label that IS read can still mislead a long-running orchestration reading its own past work, which the identifiable, machine-checked claim comment closes in a way a bare label never could.
15. **Read-Only Roles (`reviewer`, `auditor`) Write Findings to the Root Checkout, Never the Worktree**: `reviewer` and `auditor` are read-only by design — they report findings, they never modify code — so the only file either one ever needs to write is its findings file, and that file belongs in the **root checkout's** `.dot-agent-deck/` directory (the main clone, not the worktree the task names), which is gitignored and already where the orchestrator's own task files live. This was originally forced by how the underlying harness works, not as a style preference — **though the harness has since changed; see the 2026-08-14 note at the end of this rule before acting on the codex specifics below**. At the time the rule was written both roles launched `devbox run codex-devbox`, and codex grants filesystem write trust **per exact directory path** (`~/.codex/config.toml`'s `[projects."<path>"] trust_level` table) — trust is **not inherited** from a parent directory, so a worktree living inside an already-trusted parent is still untrusted itself, and rule 1's mandate of a fresh worktree per change means every worktree is a path codex has never trusted. Twice on 2026-08-07/08 a findings path resolved against the worktree instead of the root checkout and the review degraded to a bare one-line verdict with no evidence — once because the path was meant to be root-checkout-relative but got resolved against the worktree anyway, once because it was pointed at the worktree directly on the theory that would help, which made it worse (fork issue #114). A third attempt still failed the same way: telling the worker to write "in the root checkout" with no literal path is not a filesystem path a worker in a different worktree can resolve, so for a time the templates required the task itself to name the **exact absolute path**, and the worker to refuse and report rather than guess one.

    **That requirement is withdrawn as of 2026-08-14 — the worker DERIVES the root checkout instead.** From inside any linked worktree:

    ```bash
    dirname "$(git rev-parse --path-format=absolute --git-common-dir)"
    ```

    returns the root checkout exactly, because a linked worktree's admin dir always lives under the main repository's common dir. Verified from `dot-agent-deck-docsrules` → `/Users/prageeth.warnak/workspace/ai/dot-agent-deck`. Write findings to `<that>/.dot-agent-deck/<name>.md`. A task-named absolute path is still perfectly valid and takes precedence when given — this **removes a requirement, it does not forbid the old form**.

    The premise the old rule rested on — that a worker cannot resolve "the root checkout" from its worktree — was simply false, and cost four deadlocks (fork issues #114, #118) before anyone tested it. The product already had the same resolution in `resolve_common_dir` (`src/worktree_reclaim.rs`), used for worktree reclamation, which is where the technique came from. Rule 16 is satisfied *better* by this, not waived: the value still has a named supplier, and `git` is a more reliable one than a human retyping a path into a task file. Do not "fix" this by widening codex's sandbox (`~/.codex/config.toml` is machine-local, lives outside the repo, and rule 13 discourages exactly that kind of machine-local project knowledge) — resolve the findings path against the root checkout instead.

    **Both roles moved to `devbox run claude-opus-devbox` on 2026-08-14** (commit `ad93333`), replacing `devbox run codex-devbox`. This rule previously said not to do that, on the grounds that "the multi-model split across harnesses is deliberate, for independent review perspectives" — that instruction is **withdrawn**, because the split was traded away knowingly rather than eroded by accident. Three things follow, and they pull in different directions:

    - **The codex trust mechanism above no longer bites.** Claude has no per-directory `trust_level` table, so a findings path resolved against a worktree fails for ordinary reasons (a wrong path) rather than silently degrading a review to a bare verdict. Measured the same day: four reviewer/auditor passes across PRs #252, #260 and #297 each wrote full evidence-bearing findings files to root-checkout absolute paths with no trust prompt and no degradation.
    - **The requirement itself stands unchanged.** Keep naming the exact absolute path in the task. It is a rule 16 supply obligation — a worker cannot resolve "the root checkout" from a worktree whatever harness it runs — and the roles can move back to codex at any time, at which point the trust constraint returns without warning. A requirement that survives only while one config value holds is not a requirement.
    - **What was genuinely lost is independence.** `reviewer` and `auditor` now run the same model as `coder`, so a blind spot shared by the model is no longer caught by a second harness disagreeing. That is a real reduction in review value, accepted deliberately for output quality, and it is the reason to keep both passes *and* to weight a disagreement between them heavily when it happens — as on PR #260, where reviewer approved and auditor did not, and the auditor was right.
16. **Every Consumed Value Needs a Named Supplier**: When an instruction makes one party consume a value — a SHA, a path, a branch, a filename — the same change must make some other named party responsible for supplying it. An instruction whose input nothing guarantees isn't a rule; it's a trap that fires the first time someone follows it literally. The check runs both ways: adding a consumer obligates you to name a supplier; adding a supplier obligation obligates you to confirm nothing downstream now deadlocks waiting on it — a worker correctly refusing an unsupplied value is a stall, not a fix. This shipped four times in one evening across two PRs (fork issue #118), each caught only by a reviewer — no automated gate (`dot-agent-deck validate`, `cargo xtask linkage-check`, CI) reads prose for contract completeness:

| Consumed | Missing supplier |
|---|---|
| expected commit SHA | nothing required the orchestrator to name one |
| explicit `push origin HEAD:refs/heads/<branch>` form | unsetting upstream broke a bare `push`; no template supplied the explicit form |
| branch name in that push command | nothing required the task to name a branch |
| "the root checkout" as a findings path | a description, not a filesystem path a worker can resolve — **resolved 2026-08-14**: the supplier is now `git`, not the orchestrator (rule 15's derivation) |
17. **The Orchestrator Delegates; It Never Writes `src/` or `tests/`**: The orchestrator coordinates. It does **not** do implementation, review or audit work itself — it delegates. This duplicates what the `orchestrator` role's `prompt_template` in `.dot-agent-deck.toml` already says (*"You NEVER do implementation, review, or audit work yourself"*), and the duplication **is** the point: that prompt is delivered **once**, as a seed at spawn, while this file is re-injected every turn. In a long or compacted session the seed is no longer in context and this file still is — so a boundary stated only there silently stops existing exactly when the session is long enough for it to matter.

    **The test is mechanical, not a judgement.** The orchestrator may write `prds/`, `docs/`, `.dot-agent-deck/`, `changelog.d/` and this file, and may read anything — reading source, running `grep`, inspecting CI, and gathering evidence are all coordination, not implementation. It must **never** write `src/**` or `tests/**`, and never run tests. A commit authored by an orchestrator that touches `src/` or `tests/` is itself the defect, not a call it gets to make — the same shape as rule 1's "a task naming no path, SHA, or branch is itself the defect". If the work needs a code or test change, that is a delegation, however small the change looks.

    **The incident (2026-08-08, PRD #422).** The orchestrator wrote `tests/worktree_reclaim.rs` and its catalog entries outright instead of delegating the RED phase to `tester`. Nothing was ambiguous — the role prompt forbids it in as many words. What failed was durability: the instruction had aged out of context while every rule in this file was still in front of it, so the surviving guidance described *how* to work and nothing left said it was not the one working. There is also no visible line to cross — closing an issue, editing a PRD, writing a changelog and writing a test file are each a small step from the last, and the first three genuinely **are** orchestrator work. The path list above exists precisely because "notice when you have gone too far" is the thing that failed.

    **A blanket authorisation is scoped to the work class it was given for.** "Do everything yourself", said about closing out defects and bookkeeping, is not a standing licence to implement a PRD; it expires when the class of work changes and must be re-confirmed. This is the same failure mode as a carried-forward "focus upstream" reading that had quietly expired, which cost real effort earlier in the same session — a scope granted once and re-applied indefinitely is indistinguishable from one never bounded at all.

    **This rule is a workaround, not the cure.** It moves the boundary into the only channel that survives a long session. The underlying defect belongs to the product: `dot-agent-deck` defines roles with distinct remits, delivers each remit as a one-shot seed prompt, and never re-asserts it, so role adherence decays with session length — worst exactly when an orchestration is long and complex. Tracked upstream as [vfarcic/dot-agent-deck#423](https://github.com/vfarcic/dot-agent-deck/issues/423); do not let this rule's existence be mistaken for that being fixed.
18. **Never Put Build Artifacts or Worktrees on the Agent Scratchpad / a tmpfs**: A cargo `target/` built with `--features e2e` is several GB, and an agent session's scratchpad is often on a **tmpfs** (`/tmp` on the current dev box is a 14 GB RAM-backed mount). Two failure modes follow, both of which have already cost real debugging time. First, a build inside the scratchpad dies at link time with a misleading `error: linking with 'cc' failed` once the tmpfs fills — nothing points at the filesystem. Second, and less obviously, **whatever occupies a tmpfs occupies RAM**: a few GB of scratchpad shrinks what is left for `rustc` and lets the OOM killer reap a compile that would otherwise fit (a `signal: 9, SIGKILL` on a `rustc` invocation is the tell). Put every git worktree at a **disk-backed sibling** path — `../<repo>-<suffix>`, the scheme `/worktree-prd`'s `create.sh` and `/verify-pr`'s `setup.sh` already use — and never point `CARGO_TARGET_DIR` at the scratchpad. Use the scratchpad for what it is for: notes, diffs, logs, one-off scripts. `df -h /tmp` shows whether it is a tmpfs and how much room is left; `cargo xtask clean-e2e-tmp` (issue #322) reaps the e2e harness's per-process temp roots left behind by interrupted runs, and defaults to a dry run so you can see what it would remove first. It scans the **standard roots** — the harness's private `/var/tmp/dad-e2e-<uid>` parent, where current runs land, *and* the system temp dir, where every pre-#322 leftover still sits — vetting each one before reading it; a base you moved with `DAD_E2E_TMPDIR` is deliberately not scanned automatically and needs `--root`. Since issue #461 it decides by the owning PID embedded in each `dad-tests-<pid>-*` name rather than by age alone: a dead owner is reaped once the root is at least **30 minutes** old (`--older-than` does not hold it back — the floor is separate and much shorter), a live one is **never** reaped at any age and with no timestamp consulted at all, and the age threshold settles roots with no usable PID — `dad-unit-*` scratch dirs and the pre-fix lock dirs, which carry none; an untagged or malformed name; or a host with no `kill(2)`. The 30-minute floor is load-bearing, not caution: the PID names the *test* process, but the deck's lazily-spawned daemon `setsid`s out of that process group and can outlive it by up to `DOT_AGENT_DECK_TEST_MAX_LIFETIME_SECS` while still writing under the root, so reaping a dead owner instantly would hand `remove_dir_all` a live process's working directory. The old age-only rule was accidentally safe here because 6h is 72x that cap. **The floor is 2x the longest cap `tests/` pins, not 2x the 300s harness default** (issue #679): `orchestration_dispatch_002` pins **900**, and a `TuiDeck` builder's `with_env` is applied after the harness `env_clear` so that value reaches the child verbatim and `clamped()` — an *ambient*-value guarantee — never sees it. The floor sat at 600s reading as "2x 300" while that 900 was already on `main`, which left 300 seconds in which `--apply` could delete a root a still-entitled daemon was writing under. It is now derived in code (`DEAD_PID_MIN_AGE = MAX_PINNED_ORPHAN_CAP_SECS * 2`) and **linkage-check rule 11** fails the build on any pin under `tests/` above that constant, so raising a test's cap without raising the floor goes red instead of silently re-opening the window. Rule 11 deliberately has no per-line opt-out — unlike rules 8 and 10 it guards a pair of numbers that must move together, so the remedy is to raise the constant, not to exempt the line. In the other direction, a PID collision is only transient *within one boot*: across a reboot a leftover root's PID gets reissued to an early system unit, and the root is then pinned `live-pid` for the life of that boot — so pass `--ignore-liveness` to demote those roots to the age rule when you know the machine restarted. Survivors are listed individually with size and age, not just counted, so such a collision is visible. So if it reports nothing to reap, read the per-reason summary rather than assuming a threshold got in the way. There is deliberately **no** recycled-PID branch, which is a documented deviation from #461 as filed: proving recycling means ordering a process start against a directory timestamp, and that has to bridge the wall clock — `settimeofday` shifts the boot time behind `/proc/stat`'s `btime` while inode timestamps are never retroactively adjusted, so any forward clock step biases a *live* process toward looking recycled, which is the deletion-unsafe direction. Two implementations (the `/proc/<pid>` dentry mtime, then field 22 of `/proc/<pid>/stat`) both deleted live test roots. Losing the branch costs a deferral *within a boot*: a recycled PID pins its root until the colliding process exits, after which the next run reaps it as `dead-pid`. Across a reboot it costs more, which is what `--ignore-liveness` is for (above) — but that stays an operator assertion, never an inference. Do not reinstate it in any form, including a report-only annotation — the reasoning is in [`docs/develop/e2e-temp-dirs.md`](docs/develop/e2e-temp-dirs.md).
19. **Rebuild the Daemon After Every Commit While `tauri dev` Is Running**: The build version embeds `git describe`, so committing restamps the *desktop* binary on its next rebuild while the *daemon* binary on disk keeps the old hash. The deck then refuses the connection with "Desktop bridge error: build mismatch", and the GUI's **Replace daemon** button cannot recover it in dev — that path starts the bundled sidecar, which only exists in a packaged `.app`. Treat a commit in this repo as incomplete until you run `cargo build --locked --bin dot-agent-deck` (or `cd desktop && pnpm daemon:sync`), then `./target/debug/dot-agent-deck daemon stop` if one is running, then Reconnect in the app. The `pretauri` hook in `desktop/package.json` covers the *launch* case automatically but cannot cover mid-session commits. Note `cargo` may not be on PATH (rustup shims can be missing while the toolchain is present under `~/.rustup/toolchains/`); `pnpm daemon:sync` resolves it either way.
20. **Never Point a Workflow's cwd at the Worktree the GUI Is Running From**: `tauri dev`/vite watch the tree; agents editing those files trigger constant webview reloads (perceived app quit/reopen), destroy every terminal pane mid-run, and detach PTYs. Agent runs targeting this codebase must use a dedicated worktree at a disk-backed sibling path per rule 18's `../<repo>-<suffix>` convention (locally `~/dev/active/dot-agent-deck-agents`, branch `agents/workbench`; create with `git worktree add` if missing) — the GUI runs from `dot-agent-deck-gui`, agents work in `dot-agent-deck-agents`, and finished work merges back via the branch. This bit hard on 2026-08-08: the orchestrator implemented Tier-1 in the live tree and every file save reloaded the GUI observing it.
21. **Verify an Absolute Before You Write It, or Write the Narrower Claim**: When a sentence asserts something absolute about how the system *behaves* — what a function guarantees, what a job holds, what a gate covers, what a sweep found — enumerate the cases and check them, or write the narrower claim that is actually true. Constructions worth stopping at: `only`, `no` as a determiner, `never`, `nothing`, `none`, `all`, `every`, `any`, `cannot`, `can only`, `no longer`, `always`, `the sole` / `the last` / `the entire`, `complete`, `exhaustive`, `strictly`. This covers prose in this file, in `docs/`, in PRDs and in skills, and comments in code — a comment that overstates what a job holds is read as a safety property by whoever arrives next.

    **Absolutes about a DECISION are fine; absolutes about an IMPLEMENTATION are the dangerous ones.** Rule 13's "never write project knowledge to global memory" is a policy: it holds because someone decided it, and stays true until someone decides otherwise. "No agent credential reaches CI" is a claim about every file in `.github/workflows/`, and the Codex issue-labeler falsifies it — `issue-labeler.lock.yml` installs `@openai/codex` and passes the repository secret `OPENAI_API_KEY` into a `codex exec` step on a runner. Tell the two apart by asking whether a file you have not read could falsify the sentence.

    **The evidence is thirteen audit rounds on PR #805** (issues #502, #785). Every row below shipped and had to be narrowed:

    | claim as written | what was true |
    | --- | --- |
    | "no agent credential reaches CI" | the Codex issue-labeler holds `OPENAI_API_KEY` on a runner |
    | "NO SECRETS IN THIS JOB" (a `ci.yml` comment) | `actions/checkout` brings the automatic `GITHUB_TOKEN` and persists it into `.git/config` |
    | "NOTHING ELSE DOES EITHER" / "the ONLY place anyone will" | the `test-e2e-live` alias and `bacon test-e2e-live`, locally |
    | "the union can ONLY add redactions" | non-monotonic under a known matcher gap — enlarging the set can *reduce* protection |
    | "a recording can NO LONGER be stale" | two residual routes |
    | "NO credential worth protecting is shorter" than the 16-byte floor | `REDISCLI_AUTH` |
    | "`skip_unless!` is the first line of ALL of them" | a majority call it, and not always as the first statement |
    | "exercised by EVERY one of the `tests/e2e_*.rs` files" | the ones that launch a deck |

    Each row is the same shape — a narrower fact written one quantifier too wide — which is why this is a *grammatical* defect class and survives review aimed at subject matter.

    **So sweep for the construction, not the topic.** Sweeps aimed at subjects — the containment story's `env_clear` paths (`590a645`), then present-tense CI claims (`de8d5ca`) — each missed the next instance, and `65a873e` was confident enough to be titled "narrow the **last** false CI-credential absolute" before three later commits narrowed more of the same shape, one of them another CI-credential absolute in `ci.yml`. Enumerating the constructions instead and classifying every hit produced **26** edit sites across 14 files in a single commit: `git show -U0 --format='' 193f99c | grep -c '^@@'`.

    **If an absolute needs three qualifying clauses to become true, delete the sentence rather than repair it.** A narrowed claim earns its place when it still tells the reader something; caveats stacked on a dead over-claim only add maintenance. The goal is accurate prose, not hedged mush.

    **Grep with word boundaries, and blank inline code spans first** — the inverse trap cost a round of its own. A case-insensitive search for `actions` in `tests/common/mod.rs` matched 110 lines on PR #805's branch, and all 132 occurrences sat inside a `…redactions…` identifier; `\bActions\b` matched none of them. A sweep that drowns in substring noise gets abandoned, which buys exactly as much as not sweeping at all.
22. **Fix on the Fork, Merge It, Then Offer Upstream — Never Blocked by an Upstream Decision**: Before writing a change, ask **"would upstream want this?"** If **no — it is a preference** (badge removal, the worker-deck rename, role→model assignments, devbox wrapper commands, this fork's CLAUDE.md rules and PRDs, `cleanup.sh`'s fork evolution), it stays forked permanently and there is nothing to offer. If **yes — it is an improvement that merely happens to be written here** (a bugfix, a test-determinism fix, a real feature, a correction to an upstream doc), **fix it here, merge it here, ship it — and then open the upstream PR from the merged work.**

    **This fork is never blocked on an upstream decision, and never waits for one.** Not for a review, not for a maintainer's requested changes, not for a merge. The moment a fix merges here, this fork's users have it; whether upstream takes it, takes it in six weeks, or reimplements it differently changes nothing on this side. An open upstream PR is a **gift already given** — it is not a dependency, it is not "in flight" work, and it never appears as a blocking row in a progress report. If you catch yourself describing upstream work as *blocking* something here, that is the error; re-read this paragraph. *(Changed 2026-08-14 by maintainer decision. This rule previously read "Upstream-First Is the Default" and told you to branch from `upstream/main` and open the PR upstream first, letting the fix arrive here by sync. That delayed this fork's own users for no benefit they receive, and it is withdrawn. The **decision test** above is unchanged — only the **ordering** flipped.)*

    **The risk moves; it does not disappear. Under this ordering the offer is the step that does not happen, so it must be TRACKED, not remembered.** "Yes, but not yet" is a yes with an unscheduled second step. The mechanism is: **at merge time, file the upstream-offer issue** — not later, not when convenient. [#322](https://github.com/prageethw/dot-agent-deck/issues/322) is the pattern to copy (filed the moment PRD fork#314's PR merged, naming what to port, where upstream's matching issue is, and what makes the port non-trivial). A merge that should have produced an offer issue and did not is the same defect as a task naming no worktree — it is not a judgement call the next session gets to re-make, because the next session will not know the offer was ever owed.

    **Two costs make the offer worth filing rather than skipping.** First, the rebase tax: **193 commits** currently sit in the `fork-only` stack (`git rev-list --count upstream/main..origin/fork-only`, measured 2026-08-14), every one re-applied and re-conflict-resolved on **every** sync, forever. Most of that is legitimate preference divergence that stays forked by design — but landing upstream is the **only** way a commit ever leaves the stack, and the next rebase then drops it automatically. Second, duplicated work: `55021c3` (PRD #333) was dropped entirely in the 2026-08-09 sync because upstream merged its own version as PR #356, so the fork's diff had to be discarded. That work was done twice purely because it was offered late — which is an argument for offering *promptly after merge*, not for offering *before* merge.

    **Do not schedule a pass to "separate" upstream-worthy commits out of `fork-only`.** Once a commit lands upstream the next rebase drops it automatically (`--empty=drop`) — observed twice, on `ab71a28` and `55021c3`. A manual purification does by hand what the sync does for free, as one large rewrite of the branch `main` is reset to. The only real exceptions are commits that are *half* fork-only (`54066ca`, `b06b85b`); those need splitting when you reach them, not a phase up front.

    **Write access is permission to merge, not to skip review.** As of 2026-08-09 this fork's maintainer has **write** on `vfarcic/dot-agent-deck` (`vfarcic` remains `admin`). Upstream's Greptile genuinely works, unlike this fork, which has no automated code reviewer at all (rule 8) — and upstream review has been substantive rather than a rubber stamp. Open the PR and let the review run; merge it when it is approved.

    **But that review runs on upstream's clock, not ours, and an upstream PR left open costs this fork nothing.** Upstream PR [#506](https://github.com/vfarcic/dot-agent-deck/pull/506) is the worked example: the fork's own fix for the same defect merged here as PR #240 on 2026-08-11 and this fork's users have had it since, while the upstream PR sat green with a standing `CHANGES_REQUESTED` for days. Nothing on this side was waiting, because nothing on this side ever is. Do not chase it, do not re-ping the maintainer on a schedule, and do not treat "the upstream PR has not merged" as unfinished work in any status report. Full policy, the ordering, and the current backlog: [`docs/develop/upstream-contribution-policy.md`](docs/develop/upstream-contribution-policy.md).
23. **Search Both Trackers — Issues *and* Pull Requests — for the Subject Before Filing a PRD, an Issue, or an Upstream Offer**: Before filing a new issue, starting a PRD, or offering a change upstream, search **both** `prageethw/dot-agent-deck` **and** `vfarcic/dot-agent-deck` for existing work covering the same subject — and search by *what the code does*, not by the words you were about to use in your title. Both halves are required:

    ```bash
    gh issue list --repo <repo> --state open --search '<keywords>'
    gh pr list --repo <repo> --state all --search '<keywords>'
    ```

    over both repos, plus a `git grep` for the functions you expect to touch. If something overlapping is already open, join it rather than opening a parallel line of work.

    **The PR half is not optional, and searching issues alone will not find the work.** An issue records that something *should* be done; a PR records that it *has been*. They are different objects and `gh issue list` does not return PRs. Search `--state all`, not `--state open` — a closed-without-merging PR is exactly the case that needs an explicit re-offer-or-abandon decision (see [`docs/develop/upstream-contribution-policy.md`](docs/develop/upstream-contribution-policy.md)), and it is invisible to an open-only search.

    **This is a different failure from rule 14, and rule 14 does not catch it.** Rule 14 stops two orchestrations claiming *the same issue*. This stops two orchestrations opening *different issues about the same code* — and no label, assignee, or `in-progress` check can see that, because the two issues are different issues, often on different trackers.

    **The incident (2026-08-09).** Upstream issue #425 — *"Write the worktree ownership marker at creation time"* — was filed on 2026-08-08 and left open. The next morning a second orchestration filed fork issue #166 covering the same mechanism from the other end, wrote a PRD for it, and began a RED round. Meanwhile the first orchestration implemented #425 as fork PR #173 and merged it at 11:44, three hours after the same-day merge of fork #144 whose `mark_worktree_owned` it extended. The second orchestration discovered this only when its own PR went `CONFLICTING` and could not build CI at all — its base was no longer an ancestor of `main`. Nothing was lost, and PR #173's work turned out to be a usable foundation rather than a duplicate, but a day-old open issue would have been found by one search before the PRD was written.

    **The second incident (2026-08-10) — and why the PR half was added.** Asked whether PRD #421's triage/claim work should be offered upstream, an orchestration searched both trackers' *issues*, found upstream #421 open and unimplemented on `upstream/main` (`TRIAGE_LABELS` → 0 code-search hits; `src/issue_dispatch.rs` 23 KB upstream vs 42 KB here), concluded it was unoffered rule-19 debt, and wrote a full port plan — worktree, conflict resolution, reviewer/auditor passes, PR body. All of it was already done: **upstream PR #471**, opened from this fork the previous day, all 11 checks green, Greptile's P1 argued and resolved, sitting `MERGEABLE` and blocked only on the maintainer's approving review. It was caught at the last moment, by a `gh pr list` run for an unrelated reason. Following rule 20 exactly as it was then written did **not** prevent this: the rule said *issues*, the evidence was a *PR*, and the two `upstream/main` measurements above are entirely consistent with the work being un-offered — they only prove it has not **merged**. A search that cannot distinguish "never offered" from "offered and awaiting review" is not a duplicate check.

    **Note the shape, because worktrees do not help here.** Both orchestrations had their own worktrees and their own branches; the isolation worked exactly as designed. What collided was *subject matter* — both were editing `src/worktree_reclaim.rs` — and no filesystem boundary can prevent that. Do not let a worktree-per-change discipline create the impression that concurrent orchestrations cannot overlap; they overlap in the code, not on disk.

    **Also search when a PRD is already underway.** Upstream's tracker moves independently of this fork's, so an issue filed there after your PRD started is exactly as invisible as one filed before it. Re-checking at the point you open the implementation PR costs one command.
24. **Call the Fork's Product `worker-agent-deck` in Prose**: In anything you write — docs, PRDs, changelog fragments, release prose, issue and PR text, commit messages — refer to **this fork's** product and binary as **`worker-agent-deck`**. Reserve `dot-agent-deck` for [upstream](https://github.com/vfarcic/dot-agent-deck) and for the things genuinely still named that. The two are diverging (this fork shipped features upstream has not merged, and upstream PRs sit in review for long stretches), so prose that calls both "dot-agent-deck" makes it impossible to tell which one a sentence is about — and that ambiguity is worst exactly where it matters most, in release notes and in issues filed against one tracker about behaviour in the other.

    **Four names are in play today and only one of them is this convention.** Do not "correct" the others on sight:

    | Where | Name | Status |
    |---|---|---|
    | Prose — docs, PRDs, changelog, issues, PRs | **`worker-agent-deck`** | **This rule.** |
    | The crate, the cargo target, and release assets (`Cargo.toml`) | `dot-agent-deck` | Unchanged. Renaming it would move release-asset names and every documented command — a real change with real blast radius, deliberately not done. |
    | **The installed filename on `PATH`** | **`worker-agent-deck`** for a fork build; `dot-agent-deck` reserved for the upstream Homebrew install | **A second convention, and a real one — see below.** |
    | The TUI title (`src/ui.rs`) | `worker-deck` | Fork-only commit `b33cec2`, tagged **PERMANENT** in [`docs/develop/fork-sync-workflow.md`](docs/develop/fork-sync-workflow.md)'s stack table. Re-applied on every rebase; leave it alone. |

    **The installed-filename convention: a fork build is installed as `worker-agent-deck`; the name `dot-agent-deck` is reserved for the upstream Homebrew install.** This is not cosmetic. `vfarcic/tap` can never ship a fork build ([`docs/develop/upgrading-a-running-deck.md`](docs/develop/upgrading-a-running-deck.md) §"Fork releases never reach Homebrew"), so `/opt/homebrew/bin/dot-agent-deck` and a hand-installed fork build coexist on the same `PATH` indefinitely — and the filename is the **only** thing that tells them apart at a glance. A fork build installed as `dot-agent-deck` is therefore a defect, not a preference: it is indistinguishable from the upstream binary while behaving differently. Note that this makes `cargo install --path .` the **wrong** install command here — it writes the cargo target name, which is the reserved one. Build and copy explicitly instead; `upgrading-a-running-deck.md` carries the exact sequence, the per-binary version inventory, and the three separate ways a running deck resolves which binary to invoke.

    **The symlink exception below is retired as of 2026-08-15 — do not recreate it.** This paragraph previously read: *"One narrow, deliberate exception to the reservation: `~/.local/bin/dot-agent-deck` is also kept as a **symlink to `worker-agent-deck`**, because `delegate`/`work-done` are invoked by that name and are hardcoded that way — in `.dot-agent-deck.toml`'s role `prompt_template`s, and in `src/state.rs`/`src/ui.rs` — until that is fixed at the source. See `upgrading-a-running-deck.md`'s 'Row 2 collides with the naming convention' section for why removing it is more dangerous than it looks: `delegate`/`work-done` carry no protocol check, so falling through to the upstream brew binary fails *silently*, not loudly. That symlink is a deliberate redirect of the reserved name to the fork build on this one path — not a second violation of the reservation."* The hardcoding was real and the symlink was the correct interim answer for as long as it stood: `delegate`/`work-done` genuinely resolved the binary by bare name through `$PATH`, and a missing or dangling symlink genuinely fell through to the protocol-mismatched upstream brew binary in silence, because those two calls write to the unversioned hook socket and it exits 0 on a mismatch rather than refusing. It has since been fixed at the source: `binary_name()` (`src/platform/paths.rs`) resolves the running binary's own file name from `std::env::current_exe()`, with a `$PATH`-identity check and a malformed-input fallback, and `src/orchestrator_context.rs`/`src/state.rs` now interpolate that into every generated `delegate`/`work-done` example instead of a baked-in literal — landed on the fork as `9a7f2af8` (fork issue #253, fork PR #260, test-pinning commit `6e005881`), pinned by `orchestration/delegate/033` (and `orchestration/delegate/032`), and merged upstream as [vfarcic/dot-agent-deck#520](https://github.com/vfarcic/dot-agent-deck/pull/520) on 2026-08-14. **The exception is therefore retired, and `~/.local/bin/dot-agent-deck` should not be recreated as a symlink** — doing so reintroduces exactly what the reservation forbids, a fork build reachable under the name reserved for the upstream Homebrew install, for a reason that no longer holds. The four-name table above never described the symlink itself — that lived in `upgrading-a-running-deck.md`'s own per-path table, corrected alongside this paragraph — so the table needs no change here; the reservation it states is unaffected. **One caveat survives the fix and is worth knowing:** a deck installed from a build older than `9a7f2af8` still emits the hardcoded literal, because the fix lives in the source, not in an already-installed binary — observably true on this machine, where the running `worker-agent-deck` is v0.37.2 (tagged 2026-08-12, before the 2026-08-14 fix) and `.dot-agent-deck/orchestrator-context.md` still names `dot-agent-deck delegate --to` as a result. **The remedy for that is reinstalling the deck from current `main`, not recreating the symlink.**

    So the *prose* rule is a naming convention for what you write, and it is a separate thing from the crate name. When you need to name the executable in a command a reader will paste, name the one they actually have installed — `worker-agent-deck` on this fork, `dot-agent-deck` upstream — and let the prose around it say `worker-agent-deck`. A rule that made docs print a command nobody can run would be worse than the ambiguity it was meant to fix.

    **Upstream-bound text is the exception.** Anything destined for `vfarcic/dot-agent-deck` — an upstream PR body, an upstream issue, a doc correction offered upstream (rule 22) — uses upstream's own naming. The fork's product name has no meaning there and would read as a mistake.

    *(The orchestrator's own workflow text lives in `.dot-agent-deck.toml` and is regenerated into `.dot-agent-deck/orchestrator-context.md` on every orchestration start — editing that Markdown is silently reverted, see [`docs/develop/orchestrator-context-generation.md`](docs/develop/orchestrator-context-generation.md). This rule is stated here rather than there because this file is re-injected every turn while the role prompt is delivered once at spawn, which is rule 17's lesson. Adding it to the toml as well is reasonable; it was not done here because that file carries uncommitted machine-local role-command config, and committing it is the exact hazard rule 1 was written for.)*
25. **One Push Per Delegation: Batch Until the Change Is Complete, Then Push Once**: Rule 5 sends every test run to CI, which makes **each push a CI round trip** — roughly 4 minutes for the build jobs, 9–12 for e2e. So a push is not free and is not a save button. Within a single delegation, keep working until you reach the point where **one push answers every open question you have about your change**, and push there. Do not push per-iteration, do not push to "check something quickly", and do not push a commit whose only purpose is to see whether the next thing compiles — `cargo fmt --check`, `cargo clippy --all-targets --features e2e -- -D warnings` and `cargo xtask linkage-check` all run locally and answer most of those questions in seconds without touching CI at all.

    **This governs every change, not the big ones.** A bugfix, a feature, a docs-only edit, a test-only edit, a rebase, a one-line typo correction — all the same rule, because the CI cost is identical regardless of how small the diff is; a 2-line docs commit and a 500-line feature commit each buy one ~4-minute round trip. The case that bites hardest is the **review-findings fix round**: resolve *every* finding you agree with, run the local gates, then push **once**. Pushing after each finding is the single easiest way to turn one round trip into six, and it feels like diligence while it happens.

    **What this does NOT mean.** It does not collapse the TDD chain: `tester` pushing a RED and `coder` later pushing the GREEN are two *different delegations* and legitimately two pushes — the RED result is the whole point of the first one. It does not mean withholding a finished change to accumulate more work; complete means complete, not larger. And it does not override the draft-PR requirement in rule 5 — the branch still needs a PR open before the first push, or that push fires no CI run at all and there is nothing to read. The unit this rule governs is **one worker's turn**, not the branch.

    **The supply obligation is the orchestrator's** (rule 16): a worker cannot batch toward a target nobody named. Every task file must say what the single push is expected to answer — which tests should flip, which jobs must go green — so "am I done enough to push?" is a question with a stated answer rather than a judgement the worker makes alone under pressure to show progress. A task that says only "push when done" supplies nothing, and the worker will reasonably fall back to pushing per commit.

    **The incident (2026-08-10, PRD fork#192).** The branch landed **9 commits and triggered 9 distinct CI runs — exactly one per commit**, across two RED rounds, an M1.0 GREEN, an M1.1 pass, a review-findings fix round, a tester correction round, and a documentation-only closeout. Several of those runs answered a single question each, and at least one answered none that a local `clippy` could not have. Nothing was wrong with any individual push; the cost was entirely in the aggregate, which is why no reviewer flagged it and why it needs a rule rather than judgement. Rule 5 already said to "batch your work accordingly" — that phrasing described a habit without naming the unit of work, the person responsible, or a number, so it was read as advice and not followed.
26. **A Claim Must Say Who Is Claiming: Run `worker-agent-deck issue claim`, Don't Post the Comment by Hand**: Rule 14's `in-progress` label records **that** an issue is claimed. It does not record **who** claimed it, and that is the difference between a claim you can act on and one you can only guess at. PRD fork#235 mechanises what this rule used to ask you to do by hand: run `worker-agent-deck issue claim <n> --repo <owner/name>` (the orchestrator supplies both the issue number and the `--repo` slug — rule 16) and it posts an identifiable claim comment and sets the label, then attempts the assignee **best-effort** (rule 14 has the mechanics and why an unassigned issue can still be validly claimed) — you no longer write the comment yourself, and before starting on any labelled issue you no longer read the comment and reason about it either, because the command itself refuses and exits non-zero when someone else already holds it. **The claim comment, not the assignee, is the record of who holds an issue** — it is the value `decide_claim` compares against. Note the two distinctions are different: the comment and the label are *both* guaranteed by a successful claim (both `?`-propagated), so the comment is not the only write you can rely on — it is the only one that records **who**. The assignee is the one that may be missing.

    **The claim comment names the worktree path and branch** you created for the issue, per rule 1 — e.g. *"Claimed by the orchestration working `/Users/…/dot-agent-deck-fix160` on branch `fix/160-…` on host HOSTNAME at TIMESTAMP, for @LOGIN."* Those are the right identifiers because rule 1 **already obliges you to create and name them**, so this rule invents no new mechanism and consumes nothing rule 1 does not already supply (rule 16) — the command just writes them for you instead of you typing them. Order the three steps: create the worktree → run `issue claim` from inside it → make your first delegation. Unlike the old hand-typed version, there is no "claim before the worktree exists and edit the comment later" fallback: an agent-shaped caller (`DOT_AGENT_DECK_PANE_ID` set) that runs `issue claim` from anywhere that is not a linked worktree gets refused outright, on the reasoning that a `human:<login>` fallback there would collapse every agent on the deck onto the same identity and wave them all through the very check this rule exists to enforce.

    **Do not try to claim with the orchestration's own name — it cannot get one today.** Verified 2026-08-10: `DOT_AGENT_DECK_AGENT_ID` and `DOT_AGENT_DECK_PANE_ID` are the only identity in an orchestrator's environment, they are small daemon-scoped integers (both were `6`), and they recycle across a daemon restart. `worker-agent-deck worktree list --json` reports `owned` **and has carried an `owner` string since fork#166** — this sentence previously claimed otherwise; it appears absent only because `WorktreeReport.owner` is `#[serde(skip_serializing_if = "Option::is_none")]`, so a `None` owner (a `Foreign` worktree, or an `Ours` one whose marker predates fork#166's identity tracking) is omitted from the JSON document entirely rather than serialized as `null` (PRD fork#298 correction). Neither carries an orchestrator's own *name*, though, which is the actual gap this paragraph is about: fork#192 made *interactive* orchestration names unique at the form, but nothing plumbs that name back to the running orchestrator, so an orchestrator genuinely cannot answer "what am I called?" — which is why the anchor is the worktree, not the name. PRD fork#235 confirmed the pane-ID half of this the hard way, building `issue claim`'s own identity resolver: `next_pane_id` (`src/spawn.rs`) increments `PANE_COUNTER`, a process-global `AtomicU64` that starts back at zero on every daemon restart, so two claims years apart — one from before a restart, one after — can be handed the numerically identical pane id. That is a second, independent reason `DOT_AGENT_DECK_PANE_ID` was rejected as round 2's anchor (recycling *within* one daemon's lifetime was already reason enough on its own), and it is why `issue claim` reads no pane id into the identity it compares at all — only the worktree's own absolute path, branch, and hostname. If a future change gives an orchestrator its own name, prefer it and keep the worktree path as corroboration.

    **The test becomes factual instead of remembered — and enforced instead of merely checkable.** The question is no longer *"did I do this earlier?"* — which is exactly what a long-running orchestration cannot answer, since it has legitimately claimed several issues and its own past is no longer distinguishable in context from someone else's. It becomes *"does this comment name a worktree I created?"*, checkable against `git worktree list` and your own task files under `.dot-agent-deck/` — and, because `issue claim` runs that comparison itself before you can proceed, it is no longer a question you have to remember to ask before starting; the command asks it for you and stops you if the answer is no.

    **Two states that are not a claim, and what to do:**
    - **Label with no claim comment** — `issue claim` produces this as an explicit refusal (`RefuseNoIdentity`: "identity unknown") rather than something you have to notice yourself. It is still ambiguous, and ambiguity here is still expensive: do **not** silently adopt it. Escalate to the user in one line, as with any blocked decision — only a human can know whether another orchestration is live. Once a human confirms it is safe, `--takeover --confirm-stopped` clears it, the same override as the next state.
    - **A claim held by an identity whose worktree no longer exists** — you may take it over, but only via `worker-agent-deck issue claim <n> --repo <owner/name> --takeover --confirm-stopped` once you have confirmed the other agent has actually stopped; `--takeover` alone still refuses and tells you to re-run with `--confirm-stopped`, deliberately, so you cannot satisfy your own override in the same breath you discover the conflict. The takeover records who it displaced in the new comment, so the record stays legible to whoever reads it next.

    **The incident (2026-08-10, fork issues #160/#163/#166).** A long-running orchestration listed all three issues, saw `in-progress` on every one, read the labels as *its own* earlier work rather than as other orchestrations' claims, and delegated into two other orchestrations' branches — pushing two commits onto `fix/163-shutdown-recycled-pid` and coming within one delegation of fixing the same finding twice on `fix/160-ps-budget-degradation`. It was caught only because a coder refused a SHA mismatch under rule 1 and reported instead of reconciling. **Rule 14 as it then read worked exactly as written and did not prevent it**: the label was present, it was read, and reading it produced the wrong answer because the label cannot say whose it is. `issue claim`'s comparison is on the whole composed identity string (worktree path plus branch plus host), never a bare name, precisely so this cannot recur the same way: the second orchestration's own claim attempt would have compared its identity against the first's and refused, rather than letting a human-style "is this mine?" read reach the wrong answer. Note also what did *not* help — every orchestration had its own worktree, and the isolation was perfect; the collision was in the subject matter, which is rule 23's point restated at the claim layer.

    **This narrows a window; it does not close one.** `issue claim` reads the current label/comment state, decides, and writes — three separate `gh` calls, not one atomic operation — so two orchestrations that read-then-write at nearly the same moment can still both see "unclaimed" and both proceed; nothing here serialises them. The same shape as fork [#201](https://github.com/prageethw/dot-agent-deck/issues/201), where orchestration-name uniqueness is advisory because the form reads a snapshot taken once at open. A durable fix belongs in the product (a claim the daemon arbitrates), not in a CLI subprocess wrapping `gh`. Do not let this rule's existence be mistaken for that.

27. **On a Sync Conflict Over a Fork Feature, the Fork Wins — Never Let a Rebase Restore Upstream's Behaviour**: When `fork-only` is rebased onto `upstream/main` and a conflict touches a **deliberate fork divergence**, resolve it in the fork's favour. The fork's behaviour is authoritative; upstream's version does not get to win merely by being the incoming side of a rebase. This covers every **PERMANENT** row in [`fork-sync-workflow.md`](docs/develop/fork-sync-workflow.md)'s stack table — the `worker-deck` rename, role→model assignments, devbox wrapper commands, badge removal, this file's own rules, the fork's PRDs, the fork-only CI — and any fork feature upstream has not merged. If upstream later implements the same surface *differently*, that is still a fork feature: keep ours and note the divergence, rather than quietly adopting theirs because it arrived in a conflict hunk.

    **The fork wins by default. Upstream's side is adopted in exactly three cases, and in no others:**

    1. **A genuine bug fix.** Upstream corrects real broken behaviour.
    2. **A new feature.** Upstream adds something the fork does not have.
    3. **An enhancement.** Upstream's implementation of something that already exists is genuinely better.

    Anything outside those three — a rename, a reordering, a stylistic rewrite, a doc wording change, a config default, a re-added badge, or simply "upstream's file looked like this" — is **not** a reason to take upstream's side. If you cannot name which of the three applies, the fork wins. "It came in on the incoming side of the rebase" is not one of the three.

    **Upstream winning means "adopt upstream's improvement", never "lose a fork feature."** These are separate questions and a conflict marker collapses them into one. When upstream's bugfix, feature or enhancement lands in code that also carries a fork divergence, the resolution is to **take upstream's improvement and carry the fork's feature forward on top of it** — not to choose a side. Picking either hunk whole loses something real. If the two genuinely cannot coexist, **stop and escalate to the maintainer**; do not settle it inside the rebase (see the last paragraph).

    **Preference divergences are never eligible, whatever upstream did.** No upstream bugfix, feature or enhancement justifies reverting the `worker-deck` rename, the role→model assignments, the devbox wrapper commands, badge removal, this file's rules, the fork's PRDs, or the fork-only CI. Those are the fork's identity, they are marked **PERMANENT** in the stack table, and they are out of scope for case 1, 2 and 3 entirely.

    **One case that looks like the fork losing and is not: upstream landed our own offered work** (rule 22). That is *supersession*, not a clash — it is usually case 1 or 3 arriving in upstream's form, and it is the healthy end of an offer. Take upstream's version and let the fork commit drop. Precedent: `55021c3` (PRD #333) — upstream merged its own version as PR #356 after requesting behaviour changes, so upstream's had evolved past ours; taking upstream's whole reduced the commit to empty and `--empty=drop` removed it. `ab71a28` (PRD #336) went the same way, and `14bf83c` was skipped automatically with `warning: skipped previously applied commit`. **Do not "defend" a fork commit upstream has already absorbed** — that re-introduces a diff the fork no longer needs and pays rebase tax on it forever.

    **The failure mode is silent, which is why this needs a rule rather than judgement.** A conflict resolved toward upstream removes a fork feature with nothing going red: upstream has no test for a feature it never had, so the fork's own tests are the only net — and for a pure presentation divergence like the `worker-deck` TUI title (`b33cec2`), a snapshot may simply be regenerated to match the wrong side. `git rebase` also presents the fork commit as *incoming*, which makes "take upstream" feel like the conservative choice when it is the destructive one. **After any sync, verify the PERMANENT features are still present** before resetting `main` — the stack table's PERMANENT markers are that checklist, and [`fork-config-backups.md`](docs/develop/fork-config-backups.md) covers the config half (`devbox.json`, `.dot-agent-deck.toml`) with its own diff-and-restore procedure.

    **A resolution is not a place to redesign.** If honouring the fork's side looks wrong — the feature is obsolete, or upstream's approach is genuinely better — that is a decision to raise with the maintainer and handle as its own change, not something to settle inside a rebase where it is invisible to review. A sync PR should be readable as "upstream's changes, plus the fork's features intact"; anything else in it is a defect.
25. **Merge Without Asking Only When Every Condition Below Holds; Otherwise Stop and Ask**: The orchestration workflow used to end on an unconditional human confirmation — *"Never merge without that go-ahead."* That gate is replaced by a **checklist**, not removed. When every condition holds, the orchestrator merges and reports; when any one fails, it stops and asks exactly as before.

    **The conditions, all of which must hold:**

    - **Every expected PR check is present and passing**, and the **e2e result is read from the job log, never from the run conclusion**. `continue-on-error: true` means that field reports `success` for a run whose tests failed — rule 8 records the incident where a release was cut on that misreading while the log said `3 failed`. Quote the literal `Summary [...] N tests run: …` line; anything less is not evidence. **Check the expected check *names*, not just that nothing is red** — rule 8's "a check that never ran is not a pass" applies here, and "every check is passing" is otherwise vacuously true of an empty board. The set as of 2026-08-16 is 15 rows (`build`, `build-macos`, `build-windows`, `windows-cross-check`, `nix`, `devbox`, `e2e`, `security`, `semgrep`, `Semgrep OSS`, `sonarqube`, `SonarCloud Code Analysis`, `label`, and two `changes` — the duplicate is legitimate, one each from `ci.yml` and `e2e.yml`); a missing row fails this condition exactly as a red one does. **Treat that list as a floor, not a definition** — it is a hardcoded snapshot with no update obligation, so a 16th check added later would satisfy it while being verified by nobody, which is the very class this bullet exists to close. A row on the board but absent from the list must be accounted for too, and the list re-derived from the workflow files whenever they change. One legitimate exception: **Renovate PRs draw a reduced matrix** on purpose (`ci.yml`'s `changes` job gates on `PR_AUTHOR == renovate[bot]`), so a missing row there is expected rather than a defect.
    - **Both `reviewer` and `auditor` have returned.** Not "were delegated" — returned, with findings read. The automated review gate on this fork is **empty by construction** (Greptile never ran here and its machinery was deleted in `f5ffc3da`; CodeRabbit was never active), so these two passes are the only review that happens. A merge with either still in flight is a merge with no review at all.
    - **Every other condition on this list — those above it and those below — was established against the PR's FINAL head SHA.** This is the one the human pause was structurally covering, so it is the one most easily lost. It deliberately reaches *downward* as well: the closing-keyword audit is the bullet where staleness bites hardest, because a fix round's whole purpose is to add commits and rule 8's #278 trap fires on **commit messages**, so an audit run before that round is exactly the audit that misses one. The normal shape of a PRD is: review at SHA A → findings fixed at SHA B → pinning tests at SHA C. A defect introduced by the fix round at B or C is then reviewed by **nobody**, while every other condition on this list still reads green — the reviews are real, they are simply about an earlier commit. Nothing on this fork dismisses a stale review automatically: `dismiss_stale_reviews_on_push` is an upstream ruleset feature and this repo has no ruleset at all. So record the SHA each review verdict and each quoted CI summary line belongs to, compare all of them to `gh pr view <n> --json headRefOid`, and **if any predates the final head, re-run that gate rather than reasoning about whether the delta could have mattered**. Then make the check atomic instead of trusting the gap between it and the merge: **merge with `gh pr merge <n> --match-head-commit <sha>`**, which refuses if the head moved after you looked. Comparing and then merging are two operations, and rule 23 records what a read-then-write window costs when something else writes inside it.
    - **Every finding the orchestrator agreed with is resolved, and every *behavioural* fix is pinned by a test.** The pinning requirement is deliberately scoped: a behavioural fix that no test pins is one refactor away from silently reverting, which is the failure class most of this file exists to prevent. But many legitimate findings — a reworded doc, an added comment, a recorded advisory, a finding verified as needing no change — cannot be pinned by any test, and demanding it of them would make this condition unsatisfiable in practice. The worked example proves it: `c99bbe00` (PRD fork#340) resolved findings by all four of those routes. For anything unpinnable, **record the disposition and why no test applies** in the merge report; an unrecorded "I fixed it, no test needed" does not satisfy this condition. A finding the orchestrator **disagreed** with needs no fix and no test — but rule 8's *"fix it, or say why not"* is the other half, so the disagreement and its reason go in the merge report too. Otherwise this bullet is satisfiable by disagreeing quietly, which relocates the hole rather than closing it.
    - **No blocker-severity finding was accepted rather than fixed.** Accepting a blocker is a judgement the user is entitled to make, so it forces the ask.
    - **`mergeable=MERGEABLE`, and `mergeStateStatus=CLEAN` once the PR is out of draft.** A `CONFLICTING` PR produces **no `pull_request` CI run at all** while `pull_request_target` workflows keep firing, so the board looks alive and green while nothing has been checked (rule 5, fork #150). Read `mergeable` first and separately: `mergeStateStatus` reports `DRAFT` for the whole time a PR *is* a draft, which rule 5 requires it to be for most of its life, so treating `CLEAN` as a standing precondition would make this condition unsatisfiable until the moment `gh pr ready` runs. Check `CLEAN` at the merge itself; check `MERGEABLE` throughout.
    - **The closing-keyword audit is clean on *both* surfaces** — the PR body *and* every commit message — linking the PRD's own issue and nothing else (a deliberately multi-issue PR states so explicitly and lists each). Rule 8 covers both directions: a keyword in a commit closes an issue without the PR ever showing as linked, and a body phrased to *deny* a link creates one anyway.

    **Why this is a net increase in rigour rather than a shortcut.** Measured over the two PRDs run on 2026-08-15 (fork#339 and fork#340), the human merge gate caught **zero** defects. Every defect that mattered was caught by the `reviewer`/`auditor` passes — four blockers on fork#340 alone, including a gate that would have failed **every push to `main`, forever**. The pause added awareness, not defence. Converting it into a checklist keeps the awareness (the orchestrator still reports the full picture) while making the *actual* protections explicit and checkable instead of implicit in a human saying "go".

    **The conditions are the audit trail, and the audit trail is a comment on the PR.** *The merge report* is that comment, posted with `gh pr comment <n>` **before** merging — naming it is a rule 16 obligation, since every condition above consumes it and nothing else supplies it, and a report that exists only in an orchestrator's reply is gone the moment the session ends. State each condition and how it was verified — not "all green", but the quoted `Summary [...] N tests run: …` lines, the two review verdicts **and their findings-file paths** (rule 15: those files are the only durable record of a review; a verdict quoted without its path cannot be checked later), the head SHA each condition was established against, the disposition of every finding that no test pins, and the `closingIssuesReferences` output. A checklist asserted without evidence is the empty gate this repo keeps rediscovering — and one asserted only in conversation is an empty gate that also leaves no trace.

    **Three other surfaces still state the rule this one replaces, and this rule does not silently win over them.** `.dot-agent-deck.toml` step 7 — regenerated into `.dot-agent-deck/orchestrator-context.md` on **every** orchestration start, so it is what the orchestrator is actually seeded with — still says *"Never merge without that go-ahead"* and *"exactly TWO user gates"*; `docs/develop/governance.md` carries the *"must stop at 'green, reviewed, approved' and hand off"* clause; and rule 8 carries it too, of which this rule quotes only half. **Until [#375](https://github.com/prageethw/dot-agent-deck/issues/375) reconciles them, CLAUDE.md governs** — it is re-injected every turn while the seed prompt is delivered once, which is rule 17's lesson exactly, except that here the seed asserts the *opposite* rather than merely omitting it. Note the polarity before relying on this: an unwanted merge cannot be un-merged.

    **What the pause did that the checklist does not.** Being honest about the trade rather than only its upside: step 7 also asked the user for a **hands-on pass over the running deck** and for **watching the demo reel** (*"Watch before merging"* — the merge gate is the only point at which it is ever watched). Neither is a defect count, so neither appears in the measurement above, and neither is replaced by anything on this list. Circumstantially, fork [#351](https://github.com/prageethw/dot-agent-deck/issues/351) was filed from a direct user report **45 minutes after PR #342 merged**, against the very tab surface that PRD had touched. Auto-merging therefore trades a human look at the product for speed; that is a real trade, and the user is entitled to reverse it at any time.

    **This governs the fork only.** `prageethw/dot-agent-deck` carries no ruleset and no required checks, so nothing platform-side arbitrates a merge here — which is exactly why the discipline has to be written down. Upstream `vfarcic/dot-agent-deck` is different: its `main-protected` ruleset requires an approving review nobody can give themselves, and rule 8's *"never merge your own unapproved PR"* stands there unchanged. **Never auto-merge an upstream PR.**

    **Ask anyway, regardless of the checklist, when the change is not ordinary work** — a rule-12 protocol or `.breaking.md` change, a release or tag, or a diff that edits the machinery by which everything else is judged (this file's rules, `.github/workflows/**`, the release flow). A change to the rules that govern merging should not merge itself. **This exclusion is broad on purpose, and it bites often**: this file's rules are edited frequently here, so a substantial share of PRDs will land in the always-ask branch — the checklist will be exercised less often than its framing suggests. That is the intended direction of error. *(It applied first to the PR that introduced this rule, [#369](https://github.com/prageethw/dot-agent-deck/pull/369) for issue [#368](https://github.com/prageethw/dot-agent-deck/issues/368), whose entire diff is rule text: every other condition held and it was still merged on an explicit human go-ahead.)*

26. **Whoever Files an Issue Applies `size-*` and `priority-*` — `needs-triage` Is the Backstop, Not a Substitute for Filing Carefully**: When you file an issue on `prageethw/dot-agent-deck`, apply one `size-*` label (`size-high`/`size-medium`/`size-low`) and one `priority-*` label (`priority-high`/`priority-medium`/`priority-low`) at filing time, the same seven-label vocabulary `ensure_labels` (`src/issue_dispatch_run.rs`) defines and would maintain once an `issue_dispatch` task is scheduled. **If you are uncertain about priority, apply `needs-triage` and leave priority unset rather than guess.** A wrong priority is worse than an absent one — an absent priority is visibly unclassified, while a wrong one is indistinguishable from a considered judgement until someone checks. This is not a new judgement invented for this rule; it is the exact reasoning already encoded in `triage_instruction()` (`src/issue_dispatch.rs:1168`) for the agent-triage path, restated here for the human-filing path, which had no equivalent guidance anywhere.

    **The enforcement point is `.github/workflows/issue-triage.yml`.** It fires on `issues: [opened, reopened, labeled, unlabeled]` and, on **any** of those four events, stamps `needs-triage` onto an issue that is missing either a `priority-*` or a `size-*` label, self-healing only once **both** are present — a partially labelled issue (priority set, size not, or vice versa) stays flagged rather than reading as triaged, and a later label change that removes one of the two re-stamps it rather than leaving the issue silently under-labelled. The one carve-out is an issue carrying `wontfix`, `duplicate`, `invalid`, or `question`: those are left alone even while missing a label, on the reasoning that they are not going to be triaged. Because every event now re-checks and re-stamps, a human can no longer win by stripping `needs-triage` by hand while the issue is still under-labelled — it comes straight back on the next labelling event — so the escape hatch for "leave this alone" is applying one of the four exempt labels, and that label **suppresses future stamping rather than clearing a stamp already present**: stripping `needs-triage` first and applying the exempt label second does not work, because the strip alone re-triggers the stamp before the exempt label ever lands. Apply the exempt label *first*, then remove the stamp, and the removal sticks. A maintainer who re-applies `needs-triage` to an already fully-labelled issue (to say "re-triage this") is honoured only **on that one event** — the next labelling event of any kind, while the issue remains fully labelled, silently strips it again (including `in-progress` from `worker-agent-deck issue claim`), so treat the re-add as a one-shot flag rather than a durable override. Treat it as a backstop that keeps the backlog visibly triaged, not as a reason to skip labelling at filing time: it can tell you an issue is unclassified, it cannot tell you what its priority should be. The `.github/ISSUE_TEMPLATE/bug.yml` and `enhancement.yml` forms ask for size/priority as optional dropdowns, but a GitHub issue form cannot turn a dropdown answer into an applied label — so every answer, "Not sure" included, lands only in the issue body, and a human (the filer, if they have label-write access, or a maintainer) still has to apply the matching label by hand from what the form recorded. Only once both labels are actually applied does `needs-triage` clear.

    **Why the product's own `--triage` path does not already cover this.** `triage_instruction()` is real and already shipped (PRD #421 M2.0–M2.2), but it fires from `run_issue_dispatch` at **dispatch** time — when a scheduled `issue_dispatch` task pulls an issue to spawn an agent on it (`src/issue_dispatch_run.rs:402`, `:625`) — not at issue **creation**. A hand-filed issue that no scheduled dispatch ever picks up (or hasn't yet) never has that prompt appended to anything, because nothing appends it until an agent is dispatched onto that specific issue. And on this machine, `issue_dispatch` is not scheduled at all today: `docs/scheduled-tasks.md`'s "Opt-in triage" section says, in its own words, "the deck itself never classifies anything" absent a fire, and no `~/.config/dot-agent-deck/schedules.toml` entry exists to produce one — see [`docs/develop/fork-config-backups.md`](docs/develop/fork-config-backups.md) for the entry that *would* enable it, deliberately left unturned-on pending a separate decision. So until that changes, the workflow above and a human applying labels at filing time are the only two things that ever classify a freshly filed issue.

    **The incident.** #377 and #378 are the concretely reported cases of issues landing with no `size-*` and no `priority-*` label. Measured across all 180 issues on the repo at the time of #385's diagnosis: 58% carry a `priority-*` label, 30% carry a `size-*` label, 42% carry **neither**, and **0** carried `needs-triage` — because nothing had ever applied it. No `issues: [opened]` workflow existed at all; `.github/workflows/labeler.yml` is `pull_request_target` and path-based (PRs only), and `.github/workflows/issue-label-hygiene.yml` only strips `in-progress` on close. Nothing told a filer to apply the labels by hand, either — no template, no rule, no guidance anywhere. This rule, the workflow, and the issue-form templates are the fix for all three gaps at once.
