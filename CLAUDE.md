# CLAUDE.md — dot-agent-deck

This file was condensed on 2026-08-27 to keep operative rules only — full incident history, measured evidence, and superseded corrections for any rule are available via `git log -p -- CLAUDE.md`. Cross-references between rules (e.g. "rule 16") still hold; a rule's *why* is kept to one line, not the story behind it.

## PERMANENT INSTRUCTIONS

1. **Every Fix Gets Its Own Worktree**: Every distinct piece of work (PRD, bugfix, docs change, review follow-up) gets its own dedicated git worktree created up front — never ask, never share a worktree across unrelated changes. `/worktree-prd` helps with PRD work. **Never work in the root checkout** — it's the long-lived checkout the daemon/workers are attached to and routinely carries uncommitted state.
   - The orchestrator creates the worktree and states its absolute path, exact expected commit SHA, and branch name (with a work-type prefix — `fix/`, `feat/`, `docs/`, `chore/`, see [`docs/develop/work-types.md`](docs/develop/work-types.md)) in every delegated task. A task naming no path/SHA/branch, or naming the root checkout, is the defect, not a judgement call.
   - `git worktree add -b <branch> <path> origin/main` sets the new branch to track `origin/main`, so a bare `git push` lands on `main`. **Immediately run `git branch --unset-upstream`**, then push explicitly: `git push origin HEAD:refs/heads/<branch>`.
   - Before touching anything, a worker verifies the worktree is clean and `git rev-parse HEAD` equals the task-named SHA. If either is wrong, report via `work-done` and stop — do not `git add -A`, stash, or work around it.
   - **Never `git add -A` or `git add .` in a shared checkout — stage explicit paths.**
   - Mutation testing (or any tool that rewrites source in place) runs against its own throwaway worktree/copy — never one an agent is actively editing.
   - Read-only roles (`reviewer`, `auditor`) write findings to the root checkout's `.dot-agent-deck/` directory (see rule 15 for how a worker derives that path).
   - Remove the worktree once its branch is merged and dropped (`git worktree remove`).

2. **Run `cargo fmt --check` and `cargo clippy --workspace --all-targets --features e2e -- -D warnings` Before Committing**: Fix `fmt` issues with `cargo fmt`; fix clippy warnings in code. Stage fixes before committing.
   - **All three flags are load-bearing.** Without `--all-targets --features e2e`, every `tests/e2e_*.rs` file (gated by `#![cfg(feature = "e2e")]`) type-checks as an empty crate — an e2e-only bug can pass this gate meaninglessly. `--workspace` covers the `xtask/*` members (`xtask/docs`, `xtask/linkage-check`, `xtask/spec`), which default target selection otherwise skips entirely. `cargo fmt --check` is unaffected either way — rustfmt is cfg-blind.
   - This is a lint/type-check, not the e2e test tier — it spawns no binaries, hits no LLM APIs, so it doesn't conflict with rule 5. Cheap: ~0.2s warm.
   - CI's `build` job runs the same command; `build-windows`/`build-macos` deliberately stay on bare `cargo clippy -- -D warnings` (the L2 tier is Unix-only).
   - **`cd` into the worktree before running any gate — never pass `--manifest-path` to `cargo xtask linkage-check`.** The `xtask` alias silently falls back to the current working directory when `--manifest-path` is used, so the check can run against the wrong checkout (usually root) and still print `ok`. State the gate as `cd /absolute/path/to/worktree && cargo xtask linkage-check`; a linkage-check result you can't tie to a `cd` is no result at all.

3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (`tests/event_forwarding.rs`), not the milestone/PRD that introduced them (`tests/m2_17_event_forwarding.rs`). Milestone tags belong in commit messages and the PRD doc. Existing `m*_` test files are scheduled for cleanup; don't create new ones in that pattern.

4. **Add or Update TUI Tests for Functional UI Changes**: Changes to user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, hook delivery) need tests in the TUI harness — L1 (`TestBackend` + `insta`) for pure widget/layout, L2 (PTY + vt100, `tests/e2e_*.rs`, `#[cfg(feature = "e2e")]`) when touching the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change need no new test.
   - **A major user-facing feature needs at least one PTY-attached L2 test** exercising the visible surface, not just headless daemon-serve tests. A cast alone isn't demo-reel-eligible — it also needs a genuine real-agent spawn (not a stand-in like `cat`/scripted echo) **and** an explicit trailing ` [reel]` marker on its `tests/CATALOG.md` entry (see `.claude/skills/demo-reel-adapter`).
   - **A major user-facing feature also needs at least one REAL-scenario e2e test** driving a genuine spawn→agent→work path with a real agent on a cheap model (Haiku / a mini model), not solely a stand-in — live in the **pre-PR e2e tier** (not CI, which has no credentials — rule 5). Use a directive prompt plus a uniquely-named sentinel file so assertions survive LLM phrasing variance.
   - **The bar: at least one test per major feature validates it as a user actually sees it** — a live interactive agent visibly working in the pane, not `claude -p` or a stand-in. Interactive headless agents are achievable (seed claude's onboarding + per-folder trust into the test HOME via `prepare_claude_home`, pass `--allowedTools`); `scheduler/dispatch/013` is the reference.

5. **Fast Tests Per Task, E2E Before PR**: `cargo test-fast` (= `cargo nextest run --workspace`) is the per-task gate — protocol/state tests plus L1 widget/render tests. `cargo test-e2e` (= `cargo nextest run --workspace --features e2e`) additionally runs the L2 PTY/real-agent suite and is required before the release flow, not per task (it spawns binaries and hits LLM APIs).
   - **`--workspace` is load-bearing on both aliases** — without it, tests in `xtask/linkage-check` and `xtask/docs` run in no gate anywhere, including CI. Free warm (adds well under a second to a ~26s tier). One family of `xtask/linkage-check` tests genuinely shells out to real `git` (against sandboxed throwaway repos with ambient git config disabled) because the code they cover shells out to git — that's an earned exception, not a precedent for casually shelling out in a fast-tier test.
   - All three CI jobs (`build`, `build-windows`, `build-macos`) carry `--workspace`.

   **Fork-only addendum — ALL test runs happen in CI, not locally. Lint/build checks stay local.**
   - **ALL tests → CI, no exceptions, including progression testing.** A filtered single test, a whole binary, or a full tier — always pushed and read from CI, never run locally. A tester writes a RED test, commits, pushes, and reads RED from CI; the coder implements, pushes, and reads GREEN from CI.
   - **Precondition: CI only fires on an open PR** (`pull_request`, or pushes to `main`, or `workflow_dispatch`) — a push to a branch with no PR fires nothing. Open the PR as a **draft** as soon as the branch has a first commit; `/prd-done` marks it ready later. `gh workflow run ci.yml --ref <branch>` is the fallback.
   - **A `CONFLICTING` PR (merge conflicts) also fires no `pull_request` CI run — silently.** `pull_request_target` workflows (e.g. `PR Labeler`) keep firing, so the PR doesn't look inert. Check `gh pr view <n> --json mergeable` before assuming CI is just slow, and rebase rather than waiting.
   - **Drafts get no bot review either way** — no bot reviews this fork's PRs at all (rule 8) — so the draft→ready transition costs nothing on the review axis. The actual review gate is the delegated `reviewer`/`auditor` pass, which runs *before* the PR is even marked ready.
   - Consequence: RED/GREEN confirmation costs a CI round trip (~1–2 min fast tier, ~9–12 min e2e). Batch work so one push answers several questions (see rule 22) rather than pushing per-iteration.
   - **Lint/build checks stay LOCAL**: `cargo fmt --check`, `cargo clippy --all-targets --features e2e -- -D warnings` (rule 2), `cargo xtask linkage-check`. These aren't tests — fast, no binaries/daemons, don't contend for the machine.
   - Why: running the L2 tier locally repeatedly starved the dev machine (load average 20+) during concurrent work — twice.
   - CI runs the L2 tier via the fork-only `e2e:` job as **informational, non-blocking** (`continue-on-error: true`) — a red e2e run is a signal to triage, not a merge blocker. A branch cut directly from `upstream/main` carries no `e2e:` job unless it also carries the fork-only CI commit.
   - **Two carve-outs only**: (a) real-agent spawn/attach paths — CI has no credentials, so the ~19 real-agent e2e files (`grep -rln 'skip_unless' tests/e2e_*.rs`) never run there; a local `cargo test-e2e` is the only way to exercise them. (b) demo-reel `.cast` recording (`DOT_AGENT_DECK_RECORD=1`) needs to run locally.
   - **Only the orchestrator may authorise a carve-out run; a worker may never self-authorise one.** The delegation must name the carve-out, why it applies, and the specific tests to run. A worker who believes a carve-out applies reports it via `work-done` and stops — it does not decide and run. An authorised run is filtered to the specific tests, never a bare tier.

6. **Iterate on a Failing Test by Rerunning Only That Test**: After fixing code for a single failing test, rerun just that test first (`cargo test-fast lifecycle_001`) to verify in isolation before the full tier. Decision 17's `<sub-area>_<NNN>_…` function-name prefix makes the filter pick exactly one test.
   - **Fork-only addendum**: this now happens in CI, not locally (rule 5) — commit, push, and read the filtered result from CI. `cargo fmt --check`/clippy/`cargo xtask linkage-check` still run locally before every commit.

7. **Every `#[spec]` Test Has a Scenario Comment**: A `#[spec(...)]`-annotated test needs a `/// Scenario:` doc comment (1–3 sentences, plain English) describing what it does. `cargo xtask docs --tests` regenerates a local `.md` under `.dot-agent-deck/recordings/<test>/test.md` (gitignored). CI's linkage-check fails the build if the Scenario comment is missing or the generator fails.

8. **No Automated Code Reviewer Runs Here — Gate on CI Plus a Delegated Review**: No bot posts automated code review on this fork's PRs — Greptile produced zero reviews here despite being configured and was removed; CodeRabbit was never active. **Never block a merge waiting on a reviewer signal that may never arrive.**
   - **The permanent gate — decided 2026-08-27, [#354](https://github.com/prageethw/dot-agent-deck/issues/354) — is a delegated `reviewer` pass plus an `auditor` pass before merging.** This was originally framed as interim pending a replacement automated reviewer; the maintainer decided to keep the delegated pass as the standing gate rather than adopt a new tool. Respond to every finding you agree with — fix it or say why not. `semgrep` (blocking via `--error`), SonarCloud/SonarQube, and the `security` job still run and can turn the board red, but none of them gates a merge mechanically on this fork — no rulesets, no required checks, no required approval on `prageethw/dot-agent-deck`. What remains unfilled is diff-reading review that posts automatically with no human needing to invoke it.
   - **Upstream (`vfarcic/dot-agent-deck`) is different and this section mostly describes it, not this fork — this fork's own merge conditions are rule 25's checklist**: it has an active `main-protected` ruleset requiring 1 approval + `build`/`build-macos`/`build-windows`/`security` status checks, stale-review dismissal, and required thread resolution. `RELEASE_TOKEN` (an admin PAT) is what lets `release.yml`/`docs-publish.yml` push the changelog/docs-bump commits directly to `main` around that ruleset — each job fails fast in step 1 if the secret is empty, but an expired/revoked token still dies later at `git push`. A reusable workflow invoked via `uses:` needs `secrets: inherit` or the callee gets no secrets at all. Two bypass actors exist: Admin role (`bypass_mode: always`) and the Renovate app (`bypass_mode: pull_request` — Renovate can merge with zero human approval and all required checks `SKIPPED`, covered by `ci.yml`'s post-merge `push:` re-verification). Request review via the PR's reviewer field (not an `@mention`, not an assignee) and request it **last** — `dismiss_stale_reviews_on_push: true` means any push after approval voids it. `allow_auto_merge` is on; arming it is safe because it still waits for the same approval a manual merge needs, but only while the ruleset exists. Never merge your own unapproved PR upstream. `scripts/apply-branch-protection.sh` reconstructs the whole ruleset with a full `PUT` — anything it doesn't emit gets deleted; run `status` after `apply`.
   - **This fork's own `main` (`prageethw/dot-agent-deck`) has none of the above, deliberately** ([#356](https://github.com/prageethw/dot-agent-deck/issues/356)): no ruleset, no required checks, no required approval, no force-push/deletion protection. This is intentional — `non_fast_forward` protection would block `fork-only`'s own routine rebase-and-force-push during upstream-sync re-curation, which this fork isn't willing to give up. The compensating control is that `fork-sync-workflow.md` tells anyone holding a stale branch to hard-reset after a sync, not a platform rule. Consequence: every merge discipline here (this file) is enforced by habit and by CI's advisory checks, never by the platform.
   - **A passed/green check and an empty one look identical on the board — read the surface that carries the result, not the check's colour.** The `e2e:` job's `continue-on-error: true` makes the run-level `conclusion` field report `success` even when tests failed — **never read an e2e result from `gh run … --json conclusion`; always grep the log for the literal `Summary [...] N tests run: N passed, N failed` line** (`gh run view <id> --log | sed 's/\x1b\[[0-9;]*m//g' | grep -E 'tests run:|TRY 3 FAIL'`). SonarQube goes green having analysed nothing on a fork PR (`SONAR_TOKEN` absent). A `CONFLICTING` PR gets no `pull_request` run created at all — no row, not a red row.
   - **A PR's closing keywords are matched on literal text, not sentence meaning, across THREE surfaces: the PR body, every commit message, and (on a squash-merge) the PR title.** Writing "this does **not** close #256" still registers as closing #256 — negation is invisible to the parser, and HTML-escaping `#` doesn't help either. Write "issue #N stays open" instead, with no keyword+number pattern, and don't put a real issue number next to an illustrative example of the trap. Audit all three before merging:
     ```
     gh pr view <n> --repo prageethw/dot-agent-deck --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'   # body
     gh pr view <n> --repo prageethw/dot-agent-deck --json commits --jq '.commits[].messageHeadline, .commits[].messageBody' | grep -inE '(clos|fix|resolv)[a-z]*[[:space:]]+#[0-9]+'   # commits
     gh pr view <n> --repo prageethw/dot-agent-deck --json title --jq '.title' | grep -inE '(clos|fix|resolv)[a-z]*[[:space:]]+#[0-9]+'   # title, only matters for --squash
     ```
     A body edit needs re-verifying (only counts once the rendered text no longer matches); a commit-side keyword needs an amend/rebase + force-push; a title match needs `gh pr edit <n> --title`.

9. **Ask the Experimental-Flag Question When Starting a User-Facing PRD; Gate at the Seam**: For a PRD introducing a new user-visible surface, ask whether it should ship behind the `experimental` feature flag (PRD #139). If yes:
   - Add **one** per-feature wrapper in `src/features.rs` (`pub fn show_<feature>() -> bool { experimental_enabled() }`), gate **only** at the user-visible seam (render + input-binding) — never scatter checks through implementation code or branch business logic/protocols/hooks on it.
   - Note the flag in the PRD, the changelog fragment, and `docs/develop/experimental-flag.md`.
   - At ship time, file a `graduate-<feature>` follow-up issue to delete the wrapper and inline the flag at graduation.
   - If no, ship normally; none of the above applies.
   - **On this fork the flag is ON in committed config** (`.dot-agent-deck.toml`: `[features] experimental = true`) — one master switch, not per-feature. A surface gated behind `show_<feature>()` renders here regardless, so "it's behind the flag" is not itself an answer to "is this safe to ship." `DOT_AGENT_DECK_EXPERIMENTAL=0` (env) overrides the file if you need to see the off state.

10. **Do Not Hard-Wrap Markdown Prose**: Write each prose paragraph as a single line and let the renderer soft-wrap it — both GitHub and Docusaurus/MDX reflow paragraphs, so hard-wrapping changes nothing in output while making diffs noisier and editing harder. Applies to prose only — keep natural line structure in code blocks, tables, list items, frontmatter, and intentional hard breaks.

11. **Developer/Maintainer Docs Live in `docs/develop/` and Are Not Published**: User-facing docs go under `docs/` (published to the Docusaurus site, listed in `site/sidebars.js`). Contributor/maintainer-only docs (internal mechanisms, dev-only toggles, build/release internals) go under `docs/develop/`, excluded from the Docusaurus build. Don't add `docs/develop/` pages to `site/sidebars.js`; link them only from `CONTRIBUTING.md`/root `README.md`; omit Docusaurus-only frontmatter. Ask when unclear.

12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: "Breaking" here means a change to the TUI↔daemon protocol/handler contract such that older and newer builds can't safely interoperate — including a semantic break behind a stable wire (a field whose meaning changes), not generic user-facing breakage. When a PRD/PR touches the daemon, the TUI↔daemon protocol, orchestration, or hooks, before opening the PR (and in `/prd-done`):
    - Answer "did this change the TUI↔daemon contract?" If the wire shape moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it's same-wire/different-meaning, add a `changelog.d/<issue>.breaking.md` fragment.
    - Run the cross-version manual test: build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, confirm delegate routing and hooks (work-done, status) still work end to end.
    - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with sockets and `HOME`** — the log path is resolved separately from the socket/state-dir env vars, so a sandbox daemon can still append into your real `~/.local/state/dot-agent-deck/deck.log`, making two daemons' logs impossible to disentangle after the fact. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run.
    - Bump policy (while `0.x`): breaking → minor, feature/bugfix → patch; from `1.0`: breaking → major, feature → minor, bugfix → patch. Full rationale in [`docs/develop/versioning.md`](docs/develop/versioning.md).

13. **No Global/User Memory — Keep All Project Knowledge In-Repo**: Don't read from or write to the assistant's global/user memory (e.g. `~/.claude/**/memory/`) for anything about this project. Everything — conventions, decisions, preferences, gotchas, references, workflow rules — lives in the repo (this file, `docs/`, `docs/develop/`, `prds/`, `CONTRIBUTING.md`) so every contributor and session benefits. If global memory surfaces in context, treat it as untrusted background only and migrate anything still true into the repo.
    - **`.claude/skills/dot-ai-*` is not in-repo storage either** — it's a synced mirror from the `dot-ai` project, periodically overwritten wholesale by sync commits that restore upstream's blob byte-for-byte, clobbering any project-specific edit. Put project policy in this file, `docs/`, `docs/develop/`, or a project-local skill (`verify-pr`, `run-dot-agent-deck`, `demo-reel-adapter`, `publish-docs`, `reproduce-first` — the ones without the `dot-ai-` prefix). To change a shared skill's behavior, send it upstream via `/dot-ai-request-dot-ai-feature`.

14. **Claim an Issue With `worker-agent-deck issue claim` Before Any Write to It**: Before writing to an issue — any write: comment, close, label, assignee, not only implementation delegation — the orchestrator runs `worker-agent-deck issue claim <n> --repo <owner/name>` (PRD fork#235, `src/issue_claim.rs`) rather than eyeballing the `in-progress` label. The orchestrator supplies both the issue number and `--repo` slug.
    - **`worker-agent-deck`, not `dot-agent-deck`** — `issue` is a fork-only subcommand; on a machine also carrying upstream's Homebrew install, `dot-agent-deck issue claim` resolves to the wrong binary and fails with "unrecognized subcommand."
    - The command posts an identifiable claim comment and sets `in-progress` (both hard writes — failure of either fails the claim), then **attempts** the assignee **best-effort** — skipped if the login won't resolve, and a `gh` failure there doesn't undo an already-successful claim. **Never treat the assignee as the record of who holds an issue — the claim comment is.** It refuses and exits non-zero when a different identity already holds the issue.
    - This closes the failure mode where two orchestrations independently work the same issue because nobody had a mechanical check to run — a claim command that refuses removes the "forgot to check" step entirely.
    - A `PreToolUse` hook (`.claude/hooks/check-issue-claim.sh`, `worker-agent-deck issue claim-check`) also gates `gh issue`/`gh pr merge` writes mechanically — see [`docs/develop/issue-claim-check-hook.md`](docs/develop/issue-claim-check-hook.md). It's an accident-preventer alongside this rule's discipline, not a replacement.

15. **Read-Only Roles (`reviewer`, `auditor`) Write Findings to the Root Checkout, Never the Worktree**: `reviewer`/`auditor` only ever need to write their findings file, and it belongs in the **root checkout's** `.dot-agent-deck/` directory (gitignored), never the worktree named in the task. From inside any linked worktree, derive the root checkout with:
    ```bash
    dirname "$(git rev-parse --path-format=absolute --git-common-dir)"
    ```
    (A linked worktree's admin dir always lives under the main repo's common dir.) Write findings to `<that>/.dot-agent-deck/<name>.md`. A task-named absolute path still takes precedence when given — this removes a requirement to always name one, it doesn't forbid it.
    - Both roles run `devbox run claude-opus-devbox` (not the old `codex-devbox` split) — this trades independent-harness review diversity for output quality, deliberately. Keep naming the exact absolute path in tasks anyway (rule 16) — a worker can't resolve "the root checkout" from a worktree regardless of harness, and the roles could move back to a per-directory-trust harness like codex at any time, where an unresolved path silently degrades a review to a bare one-line verdict instead of erroring.

16. **Every Consumed Value Needs a Named Supplier**: When an instruction makes one party consume a value (a SHA, a path, a branch, a filename), the same change must make some other named party responsible for supplying it. An instruction whose input nothing guarantees isn't a rule, it's a trap. Check runs both ways: adding a consumer obligates naming a supplier; adding a supplier obligation obligates confirming nothing downstream now deadlocks waiting on it — a worker correctly refusing an unsupplied value is a stall, not a fix. No automated gate reads prose for contract completeness, so this has to be checked by hand every time a rule or task template is written.

17. **The Orchestrator Delegates; It Never Writes `src/` or `tests/`**: The orchestrator coordinates — it never does implementation, review, or audit work itself. The orchestrator may write `prds/`, `docs/`, `.dot-agent-deck/`, `changelog.d/`, and this file, and may read anything (reading source, grepping, inspecting CI is coordination). It must **never** write `src/**` or `tests/**`, and never run tests. A commit authored by the orchestrator touching `src/` or `tests/` is itself the defect. If work needs a code or test change, that's a delegation, however small it looks.
    - A blanket authorisation ("do everything yourself") is scoped to the work class it was given for — it expires when the class of work changes and must be re-confirmed; it is never a standing licence to implement.
    - This rule exists because role prompts (`.dot-agent-deck.toml`) are delivered once at spawn while this file is re-injected every turn — a boundary stated only in the seed silently stops existing once a session is long enough for the seed to have aged out of context. This is a workaround for an upstream product gap (roles decay with session length — tracked as [vfarcic/dot-agent-deck#423](https://github.com/vfarcic/dot-agent-deck/issues/423)), not a fix for it.

18. **Never Put Build Artifacts or Worktrees on the Agent Scratchpad / a tmpfs**: A cargo `target/` built with `--features e2e` is several GB; a scratchpad is often tmpfs-backed (RAM). Filling it kills a build with a misleading `linking with 'cc' failed`, or lets the OOM killer reap `rustc` because the tmpfs ate the available RAM. Put every git worktree at a disk-backed sibling path (`../<repo>-<suffix>`) and never point `CARGO_TARGET_DIR` at the scratchpad. Use the scratchpad only for notes, diffs, logs, one-off scripts.
    - `cargo xtask clean-e2e-tmp` reaps the e2e harness's leftover per-process temp roots (dry-run by default). It decides by the owning PID embedded in each root's name: a dead owner is reaped once the root is ≥10 minutes old (the daemon can outlive its parent test process by design, hence the floor, not caution); a live owner is never reaped at any age; a root with no usable PID falls back to the age threshold. There's deliberately no recycled-PID detection — every attempt at one risked deleting a live process's directory, so a stale root from before a reboot instead stays pinned until you pass `--ignore-liveness` to demote it to the age rule. Full reasoning in [`docs/develop/e2e-temp-dirs.md`](docs/develop/e2e-temp-dirs.md) — don't reinstate recycled-PID detection in any form.

19. **Fix on the Fork, Then Offer Upstream — Except an Upstream-Code Defect, Which Is Filed Upstream — Never Blocked by an Upstream Decision**: Before writing a change, ask "would upstream want this?"
    - **No — it's a preference** (badge removal, the worker-deck rename, role→model assignments, devbox wrapper commands, this fork's rules/PRDs, `cleanup.sh`'s fork evolution): stays forked permanently, nothing to offer.
    - **Yes — it's a genuine improvement, but does upstream still carry the defect in code the fork hasn't already diverged on?** If it does: **file it upstream at the point it's found** (see below), don't fix-here-then-offer. If the fork has already diverged (a feature, an enhancement, or a fix to code the fork has already changed): fix it here, merge it here, ship it — **then** open the upstream PR from the merged work.
    - **This fork is never blocked on an upstream decision.** Not for review, not for requested changes, not for merge timing. The moment a fix merges here, this fork's users have it. An open upstream PR is a gift already given, never a blocking row in a status report.
    - **Filing an upstream-code defect: gather evidence at the defect, not the file.** `git fetch upstream` first, then `git grep -nF '<the defective literal>' upstream/main -- <path>` **and** the same against `HEAD` — `-F` (literal) is load-bearing, since `git grep`'s default basic-regex silently mismatches on literals containing `[`/`]` etc. and a false no-hit reads as "fork has diverged" when it hasn't. File-level divergence (`git diff --numstat`) does **not** disqualify — the defective expression can be byte-identical inside a heavily-diverged file. What genuinely disqualifies is divergence that changes the defective *behavior itself* and leaves something here worth fixing (the fork already guards it differently) — then fall back to fix-here-then-offer. Anything that doesn't land cleanly is a judgement to raise with the maintainer, not settle silently either way.
    - Search both trackers (rule 20) before filing; link an existing upstream issue instead of duplicating.
    - **One carve-out: a defect crossing a privilege/trust boundary is escalated to the maintainer before filing** — filing is public and immediate. (Narrow: this product's trust boundary is same-uid and there's no private disclosure channel today, so this hasn't been needed yet — it exists for a future case that reaches outside that boundary, destroys data, or leaks credentials.)
    - **Closing the corresponding fork issue needs the maintainer's decision, not the finder's** — always apply `affects-upstream` and comment the upstream number/why; only the maintainer decides whether to close (their call, since it depends on fork roadmap intent the finder doesn't have visibility into). Leave open if undecided.
    - **On the fix-here-then-offer path, file the upstream-offer issue at merge time, not later** — "yes, but not yet" is a yes with an unscheduled second step, and the next session won't know one was owed. Pattern: [#322](https://github.com/prageethw/dot-agent-deck/issues/322).
    - **Don't schedule a pass to "separate" upstream-worthy commits out of `fork-only`** — once a commit lands upstream, the next rebase drops it automatically (`--empty=drop`). The only real exception is a commit that's *half* fork-only, which needs manual splitting when you reach it.
    - **Write access is permission to merge, not to skip review** — this fork's maintainer has write on upstream; open the PR, let upstream's (real, substantive) Greptile review run, merge once approved. But upstream review runs on upstream's clock — don't chase it, don't treat an unmerged upstream PR as unfinished work on this side.
    - Full policy: [`docs/develop/upstream-contribution-policy.md`](docs/develop/upstream-contribution-policy.md).

20. **Search Both Trackers — Issues *and* Pull Requests — for the Subject Before Filing a PRD, an Issue, or an Upstream Offer**: Search both `prageethw/dot-agent-deck` and `vfarcic/dot-agent-deck`, by what the code does rather than your intended title:
    ```bash
    gh issue list --repo <repo> --state open --search '<keywords>'
    gh pr list --repo <repo> --state all --search '<keywords>'
    ```
    plus a `git grep` for the functions you expect to touch. If something overlapping is open, join it.
    - **The PR half is not optional and issues alone won't find it** — an issue records intent, a PR records that work has happened; `gh issue list` doesn't return PRs. Use `--state all` — a closed-without-merging PR needs an explicit re-offer-or-abandon decision and is invisible to an open-only search.
    - This is a different failure from rule 14: rule 14 stops two orchestrations claiming the *same issue*; this stops two orchestrations opening *different issues about the same code* — no label or claim check can see that, because the issues are different objects, often on different trackers. This has happened twice for real, once nearly duplicating a fully-implemented, CI-green, awaiting-approval upstream PR that an issues-only search couldn't see.
    - Worktree isolation doesn't help here — the collision is in subject matter, not on disk. Re-search when opening the implementation PR too, since the tracker moves independently of your PRD's timeline.

21. **Call the Fork's Product `worker-agent-deck` in Prose**: In docs, PRDs, changelog fragments, release prose, issue/PR text, commit messages, refer to this fork's product/binary as **`worker-agent-deck`**. Reserve `dot-agent-deck` for upstream and the things still genuinely named that:

    | Where | Name |
    |---|---|
    | Prose (docs, PRDs, changelog, issues, PRs) | `worker-agent-deck` (this rule) |
    | The crate, cargo target, release assets | `dot-agent-deck` (unchanged — renaming would move release-asset names) |
    | Installed filename on `PATH` | `worker-agent-deck` for a fork build; `dot-agent-deck` reserved for the upstream Homebrew install |
    | TUI title (`src/ui.rs`) | `worker-deck` (fork-only, permanent) |

    - **The installed-filename convention is load-bearing, not cosmetic**: upstream Homebrew can never ship a fork build, so both binaries coexist on `PATH` indefinitely and the filename is the only thing distinguishing them at a glance. `cargo install --path .` writes the reserved cargo-target name — build and copy explicitly instead; see [`docs/develop/upgrading-a-running-deck.md`](docs/develop/upgrading-a-running-deck.md).
    - **Do not create a `~/.local/bin/dot-agent-deck` symlink to the fork build.** This used to be a deliberate exception (because `delegate`/`work-done` hardcoded the bare name), but the hardcoding is fixed at the source (`binary_name()` in `src/platform/paths.rs` resolves the running binary's own name) — a build predating that fix (before commit `9a7f2af8`) can still emit the old literal; the remedy is reinstalling from current `main`, not recreating the symlink.
    - When naming an executable a reader will paste into a command, name the one they actually have installed.
    - **Upstream-bound text uses upstream's own naming** — an upstream PR/issue body has no meaning for the fork's product name.

22. **One Push Per Delegation: Batch Until the Change Is Complete, Then Push Once**: Since rule 5 sends every test run to CI, each push is a CI round trip (~4 min build jobs, ~9–12 min e2e) — not a save button. Within one delegation, keep working until one push answers every open question about your change, then push once. Don't push per-iteration or to "check something quickly" — `cargo fmt --check`, clippy, and `cargo xtask linkage-check` run locally and answer most of those questions in seconds.
    - Governs every change size equally — a 2-line docs fix costs the same CI round trip as a 500-line feature. The case that bites hardest is a **review-findings fix round**: resolve every finding you agree with, run local gates, push **once** — not once per finding.
    - Doesn't collapse the TDD chain (RED and GREEN are legitimately separate delegations/pushes), doesn't mean withholding a finished change to accumulate more, and doesn't override the draft-PR requirement (rule 5) — the branch still needs an open PR before the first push or there's no CI run to read.
    - **The supply obligation is the orchestrator's** (rule 16): every task must state what the single push is expected to answer (which tests should flip, which jobs must go green) — a task that says only "push when done" supplies nothing and the worker falls back to pushing per commit.

23. **A Claim Must Say Who Is Claiming: Run `worker-agent-deck issue claim`, Don't Post the Comment by Hand**: Rule 14's `in-progress` label records *that* an issue is claimed, not *who* claimed it. `worker-agent-deck issue claim <n> --repo <owner/name>` posts an identifiable claim comment naming the worktree path/branch/host, sets the label, then attempts the assignee best-effort. It refuses and exits non-zero when someone else already holds the issue — so the test becomes factual ("does this comment name a worktree I created?", checkable against `git worktree list`) instead of "did I do this earlier?", which a long-running orchestration genuinely cannot answer about its own past claims.
    - Create the worktree first, then run `issue claim` from inside it, then delegate — an agent-shaped caller running it from outside a linked worktree is refused outright (a fallback identity there would let every agent on the deck wave through the very check this exists to enforce).
    - **A label with no claim comment** is an explicit refusal (`RefuseNoIdentity`) — don't silently adopt it; escalate to the user, since only a human can know whether another orchestration is genuinely live. Once confirmed dead, `--takeover --confirm-stopped` clears it (both flags required together, deliberately, so you can't satisfy your own override in the same breath you discover the conflict).
    - This narrows a claim/read race, it doesn't close it — `issue claim` is three separate `gh` calls, not atomic, so two near-simultaneous claims can still both read "unclaimed." A durable fix belongs in the product (daemon-arbitrated claims), not a CLI wrapping `gh`.

24. **On a Sync Conflict Over a Fork Feature, the Fork Wins — Never Let a Rebase Restore Upstream's Behaviour**: When rebasing `fork-only` onto `upstream/main` and a conflict touches a deliberate fork divergence (any **PERMANENT** row in [`fork-sync-workflow.md`](docs/develop/fork-sync-workflow.md)'s stack table — the `worker-deck` rename, role→model assignments, devbox commands, badge removal, this file's rules, the fork's PRDs, fork-only CI — or any fork feature upstream hasn't merged), resolve in the fork's favour by default.
    - Upstream's side is adopted **only** in three cases: (1) a genuine bug fix, (2) a new feature the fork lacks, (3) an enhancement to something existing that's genuinely better. If you can't name which of the three applies, the fork wins — "it was the incoming side of the rebase" is never a reason.
    - **Preference divergences are never eligible**, whatever upstream did — no bugfix/feature/enhancement justifies reverting a PERMANENT row.
    - When upstream's genuine improvement lands in code that also carries a fork divergence, **take upstream's improvement and carry the fork's feature forward on top of it** — don't pick one hunk whole. If they genuinely can't coexist, stop and escalate to the maintainer.
    - **Exception: upstream landing our own offered work is supersession, not a clash** — take upstream's version and let the fork's now-redundant commit drop (`--empty=drop` removes it automatically on the next rebase). Don't "defend" a fork commit upstream has already absorbed.
    - The failure mode is silent — upstream has no test for a fork-only feature, so nothing goes red when a rebase quietly drops it, and a snapshot test can even be regenerated to match the wrong side. After any sync, verify the PERMANENT features are still present before resetting `main` (the stack table is the checklist; [`fork-config-backups.md`](docs/develop/fork-config-backups.md) covers config).
    - A resolution is not a place to redesign — if honouring the fork's side looks wrong, raise it with the maintainer as its own change rather than settling it invisibly inside a rebase.

25. **Merge Without Asking Only When Every Condition Below Holds; Otherwise Stop and Ask**: The old unconditional human-confirmation gate is replaced by a checklist. When every condition holds, the orchestrator merges and reports; when any fails, it stops and asks.
    - **Every expected PR check is present and passing**, and **the e2e result is read from the job log, never the run conclusion** (`continue-on-error: true` makes `conclusion` report `success` even on failing tests — quote the literal `Summary [...] N tests run: …` line). Check the expected check *names* are present, not just that nothing's red — a missing row is the same failure as a red one (rule 8). Renovate PRs and docs-only PRs legitimately draw a reduced matrix; the check-set is a floor to re-derive from the workflow files, not a fixed list to trust blindly.
    - **Both `reviewer` and `auditor` have returned** — delegated, not just started — since the automated review gate is empty by construction here (rule 8).
    - **Every other condition on this list was established against the PR's FINAL head SHA** — a fix round adds commits after review, and nothing on this fork dismisses stale reviews automatically. Record the SHA each review verdict and CI summary belongs to; re-run any gate that predates the final head. Merge with `gh pr merge <n> --squash --match-head-commit <sha>` so the check-then-merge gap can't be raced.
    - **Every finding the orchestrator agreed with is resolved, and every behavioral fix is pinned by a test.** Unpinnable fixes (doc reword, recorded advisory, verified-no-change-needed) are fine but their disposition and reasoning must be recorded in the merge report. A disagreed-with finding needs a recorded reason, not silence.
    - **No blocker-severity finding was accepted rather than fixed** — accepting a blocker is the user's call, so it forces the ask.
    - **`mergeable=MERGEABLE`**, and **`mergeStateStatus=CLEAN`** once out of draft (checked separately, since `mergeStateStatus` legitimately reads `DRAFT` for most of a PR's life).
    - **The closing-keyword audit is clean on all three surfaces** (rule 8: body, commits, and title on a squash-merge).
    - **Post a merge report as a PR/issue comment before merging**, naming how each condition was verified (quoted CI lines, review verdicts + findings-file paths, the head SHA each was established against, unpinned-finding dispositions, `closingIssuesReferences` output) — a checklist asserted only in conversation is the empty gate this repo keeps rediscovering.
    - **This governs the fork only.** `prageethw/dot-agent-deck` has no ruleset arbitrating merges, which is exactly why this discipline has to be written down. **Never auto-merge an upstream PR** — upstream's ruleset requires an approval nobody can give themselves.
    - **Ask anyway, regardless of the checklist, when the change is not ordinary work**: a rule-12 protocol/`.breaking.md` change, a release/tag, or a diff editing the machinery that judges everything else (this file's rules, `.dot-agent-deck.toml`'s orchestrator workflow text, `.github/workflows/**`, the release flow). This exclusion is broad on purpose and will be hit often, since this file's rules are edited frequently.

26. **Whoever Files an Issue Applies `size-*` and `priority-*` — `needs-triage` Is the Backstop, Not a Substitute**: When filing an issue on `prageethw/dot-agent-deck`, apply one `size-*` and one `priority-*` label at filing time. **If uncertain about priority, apply `needs-triage` and leave priority unset rather than guess** — a wrong priority is worse than an absent one, since it's indistinguishable from a considered judgement until someone checks.
    - `.github/workflows/issue-triage.yml` stamps `needs-triage` onto any issue missing either label, on every `opened`/`reopened`/`labeled`/`unlabeled` event, and only clears once both are present — so stripping the stamp by hand while under-labelled doesn't work, it just comes back. Exempt: issues carrying `wontfix`/`duplicate`/`invalid`/`question`.
    - This is a backstop, not a substitute for labelling at filing time — it can tell you an issue is unclassified, not what its priority should be. The product's own `--triage` path (`issue_dispatch`) only fires at dispatch time for a scheduled task, and no schedule is configured on this machine today, so a hand-filed issue that nothing dispatches onto is never classified by anything but this workflow and a human.

27. **The Orchestrator Writes a Task List Before the First Edit or Delegation, and Reconciles It Against What Was Actually Asked**: Any assignment with more than one step (more than one file, or any delegation at all) gets an explicit, ordered task list before work starts — genuinely single-step work (a typo, a one-line edit) is exempt, narrowly (if you're weighing whether it applies, it doesn't). Each item states who executes it and where it runs (local vs. CI is load-bearing here — rule 5/rule 2). Keep it current as items complete.
    - This list gates nothing — it's additional to, never a substitute for, the orchestrator workflow's own test-plan-approval step, which is the workflow's standing user gate.
    - **This is the orchestrator's obligation alone** — it's the only party that sees the whole assignment and can notice an item quietly reshaping. A worker's own multi-item brief is a real but separately-open problem.
    - The point is visibility, not progress tracking: a silently reshaped or dropped scope item is the same failure as rule 16's unsupplied value, one level up. **When the user numbered their own items, map to that numbering and name explicitly every item that changes shape or isn't done, with the reason** — put the reconciliation in the PR body or issue (durable), not only in a chat reply (gone when the session ends).

28. **Wait on Any External Result With One Sustained Foreground Command, Never Discrete Gapped Polls**: When a pane's only remaining job is waiting on an external/async outcome (dispatched CI, a PR's aggregate checks, an external build/deploy, an approval), do the waiting as one sustained foreground blocking command, never a sequence of separate short calls with gaps. The deck's shell-activity signal only shows a pane as `Working` while it has a live foreground descendant process — a gapped `gh run list` / `gh run list` sequence has none between calls, so the pane reads `Idle` the whole time real work is outstanding.
    - Use a purpose-built blocking primitive: `gh run watch <run-id> --repo <owner/name> [--exit-status]` for one workflow run; `gh pr checks [<n>] --repo <owner/name> --watch` for all of a PR's checks (fails immediately rather than blocking if no check runs exist yet — e.g. right after push, or a `CONFLICTING` PR — use `gh run watch` against an explicit run id instead). Pass `--interval 30` (and `--compact` for `gh run watch`) — the default refresh rate is chatty enough to flood the calling agent's own context on a long wait.
    - Waiting on more than one thing at once is still one foreground call: `gh run watch A --repo … & gh run watch B --repo … & wait` inside a single Bash invocation, not separate sequential tool calls (which reopen the gap).
    - When no purpose-built primitive exists, wrap the check in one **bounded** foreground loop (`timeout 3600 bash -c 'until <condition>; do sleep <N>; done'`) with a distinguishable timed-out exit — an unbounded wait turns a temporary false-`Idle` into a permanent false-`Working`, which is harder to notice.
    - This only fixes visibility of the wait, not the reliability of the result — still read the e2e job's log for the real outcome (rule 8's caveat), regardless of which blocking primitive got you there.
    - A genuinely long **local background** process (`run_in_background`) is not this rule's target — it's already a live descendant of the pane, so it reads `Working` throughout regardless of polling cadence. This rule targets waits with no local process behind them at all.
    - Nothing here is enforced or detected mechanically — no lint or CI check turns red on gapped polling, and the Claude-pane classification it depends on (an argv cross-check keyed to one Claude Code version) is known to degrade silently on prompt/shell changes. If a wait mysteriously reads `Idle` despite following this rule, suspect that classification before suspecting compliance. Treat this as convention, not a guaranteed-caught violation.
