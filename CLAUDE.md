# CLAUDE.md — dot-agent-deck

## PERMANENT INSTRUCTIONS

1. **Every Fix Gets Its Own Worktree**: Any distinct piece of work — a PRD, a bugfix, a docs change, a review follow-up — gets its own dedicated git worktree, created up front. This is the default; do **not** ask whether the user wants a worktree or a plain branch, and do not reuse a worktree for a second, unrelated fix — one worktree per change. `/worktree-prd` remains the helper for PRD work. **Never work in the root checkout**: it is the long-lived checkout the running daemon and worker panes are attached to, and it routinely carries uncommitted state. The incident behind this rule (2026-08-07): the root checkout was sitting on `docs/prd-386-upstream-pr-record` with an uncommitted `.dot-agent-deck.toml` and an untracked `tests/snapshots/render_dashboard__pane_008_named_agent_badges.snap.new`, and a task told a worker to commit a documentation file "from the root checkout" — switching that checkout to `main` would have dragged the dirty `.dot-agent-deck.toml` along and risked committing the fork's local role-command config onto `main`. The worker refused and used a throwaway worktree instead; a dedicated worktree makes that class of mistake impossible rather than relying on each worker noticing. A worktree also keeps each branch's `target/` build state isolated, so switching work does not force a full rebuild. Remove the worktree once its branch is merged and dropped (`git worktree remove`) so they do not accumulate. This recurred on 2026-08-07/08 (fork issue #74) with a sharper root cause than the original filing assumed: two orchestrations worked the same issue concurrently because a second orchestration's task named no worktree path, so its worker found the first orchestration's existing branch and reasonably joined it — writing production code into a worktree it did not own, then pushing to it and cancelling the first orchestration's in-flight CI run. **The orchestrator creates the worktree and states its absolute path, exact expected commit SHA, and branch name in every task it delegates**; a task naming no path, SHA, or branch, or naming the root checkout, is itself the defect, not a judgement call the worker gets to make. **Unset the new branch's upstream immediately after creating it** (`git branch --unset-upstream` in that worktree, then push explicitly with `git push origin HEAD:refs/heads/<branch>`, substituting the task-named branch for `<branch>`) — `git worktree add -b <branch> <path> origin/main` sets the new branch to track `origin/main`, so a bare `git push` from that worktree lands on `main`; this happened for real on the #89 branch and was caught only because a worker noticed and pushed explicitly instead. **Before touching anything, a worker verifies the worktree is clean and `git rev-parse HEAD` equals the task-named SHA**; if either is wrong, report it through `work-done` and stop there — do not `git add -A`, do not stash, do not work around it to make progress anyway. **Never `git add -A` or `git add .` in a shared checkout — stage explicit paths.** This is the exact mechanism behind #74's original incident, where a live mutation-testing run was swept into a real commit and pushed to an open PR. **Mutation testing, and any other tool that rewrites source in place, runs against its own throwaway worktree or copy — never one an agent is actively editing.** **When delegating to a read-only role (`reviewer`, `auditor`), the task must also state the exact absolute path of the findings file under the root checkout's `.dot-agent-deck/` directory** — rule 15 requires the worker to refuse a relative or unnamed findings path rather than guess it from its worktree, so a task that omits the path produces the same deadlock a missing worktree path, SHA, or branch would. This exact defect happened three times in the #74 lineage before it happened a fourth time here (fork issue #114): a template requires something of the worker that nothing requires the orchestrator to supply. See rule 16.
2. **Run `cargo fmt --check` and `cargo clippy --workspace --all-targets --features e2e -- -D warnings` Before Committing**: Always run both before creating any git commit. If fmt reports issues, run `cargo fmt` to fix them. If clippy reports warnings, fix the code. Stage any fixes before committing.

    **All three flags are load-bearing** — `--all-targets` and `--features e2e` per issue #407, `--workspace` per issue #436. The old rule said `cargo clippy -- -D warnings`, which type-checks *no test file at all*: without `--all-targets` cargo builds only lib and bin targets, and every one of the 62 `tests/e2e_*.rs` files opens with `#![cfg(feature = "e2e")]` (two with `#![cfg(all(feature = "e2e", unix))]`), so without `--features e2e` they compile to empty crates. An e2e-only change therefore passed the gate instantly and meaninglessly — measured by injecting a deliberate `E0308` into `tests/e2e_handshake.rs`: `cargo clippy -- -D warnings` and `cargo clippy --all-targets -- -D warnings` both exited 0, and only the feature-enabled command caught it. `cargo fmt --check` is *not* affected — rustfmt is cfg-blind and walks the cargo target list, so it has always covered these files.

    The one command is a strict superset of the old one: no `not(feature = "e2e")` cfg exists anywhere, and `src/` never references the feature. It is also **cheap**: cargo caches the feature-on and feature-off fingerprints side by side, so alternating this with `cargo test-fast` costs ~0.2s warm; a from-scratch re-check of all 62 e2e targets is ~14s.

    This is a *type-check and lint*, not the e2e tier — it spawns no binaries and hits no LLM APIs, so it does not conflict with rule 5's "do not run `cargo test-e2e` per task". Before this change, e2e code was clippy-linted by no gate anywhere and type-checked only by `cargo test-e2e`, the most expensive gate in the repo. The Linux CI `build` job runs the same command; `build-windows` / `build-macos` deliberately stay on bare `cargo clippy -- -D warnings` (see the comments there — the L2 tier is Unix-only and reports dozens of E0425s under the Windows target).

    **`--workspace` covers the `xtask/*` members** (issue #436). Cargo's default target selection is the root package alone, so `xtask/docs`, `xtask/linkage-check` and `xtask/spec` were linted by no gate anywhere. `xtask/spec` and `xtask-docs` are path dev-dependencies so they were at least *built*, but building is not linting, and `xtask/linkage-check` was not even built — which is how an `unnecessary_sort_by` sat in its `clean_tmp.rs` on `main` long enough to be discovered by an unrelated PR. That lint was fixed in the same commit that added this flag, so the widened gate landed green. The widening is **free warm**: measured back to back, `--workspace` and root-only both return in 0.20s once cargo has the fingerprints, since the three `xtask` members are small and dependency-light. Note `--workspace` does **not** change which features reach the root package, so this stays a strict superset of the pre-#436 command.
3. **No Milestone or PRD Prefixes in Source / Test Filenames**: Name files for what they contain (e.g. `tests/event_forwarding.rs`), not for the milestone or PRD that introduced them (e.g. `tests/m2_17_event_forwarding.rs`, `src/prd76_*.rs`). Milestone tags belong in commit messages and the PRD doc — long-lived filenames must outlive the branch. Existing `m*_` test files are scheduled for cleanup; do not create new ones in that pattern.
4. **Add or Update TUI Tests for Functional UI Changes**: When a change adds or modifies user-visible TUI behavior (panes, statuses, prompts, focus, layout, modes, embedded panes, hook delivery), add or update tests in the TUI harness. Use L1 (in-process `TestBackend` + `insta`) for pure widget/layout changes; use L2 (PTY + vt100, files named `e2e_*.rs`, gated by `#[cfg(feature = "e2e")]`) when the change touches the spawned binary, daemon, hooks, attach protocol, or real agent integration. Pure refactors with no observable behavior change do not require new tests. **For a major user-facing feature, include at least one PTY-attached L2 test** (the vt100 harness that drives the real binary, e.g. mirroring `scheduler/live/*`) that exercises the user-visible surface — not only headless daemon-serve (`RunNow`) tests. Only PTY-attached tests record a `.cast`, but a cast alone is **not** enough to be demo-reel-eligible: a clip must genuinely spin up a **real agent** (spawn → agent → work) **and** be explicitly opted in with a trailing ` [reel]` marker on its `tests/CATALOG.md` entry (PRD #180/#20 — see `.claude/skills/demo-reel-adapter`). A synthetic/stand-in PTY test (cat, scripted echo, recorder stubs, terminal-probe, synthesized hook events) is left unmarked and never becomes a clip even though it has a cast; a feature whose entire e2e coverage is headless (or unmarked) ships with no reel clip. (PRD #120's `issue_dispatch` is the cautionary case: `scheduler/dispatch/001-010` are all headless, so the showcase clip required adding the PTY-attached `scheduler/dispatch/011`.) **A major user-facing feature should also have at least one REAL-scenario e2e test** that drives the genuine spawn→agent→work path with a *real* agent on a **cheap model** (Haiku for Claude, a mini model for OpenCode) through a cheap, deterministic-enough operation — e.g. "list the files and report a known sentinel filename" — rather than relying solely on a stand-in like `cat`. We have historically over-relied on stand-ins; a stand-in proves the plumbing but never that an agent genuinely runs against the cloned/worktree/target state. Real-agent tests live in the **pre-PR e2e tier** (flaky-tolerant, and not exercised by CI, which has no credentials configured — see rule 5); make them robust with a directive prompt plus a uniquely-named fixture **sentinel file** so the assertion survives LLM phrasing/tool variance. **The bar is: at least one test per major feature must validate it AS A USER ACTUALLY USES AND SEES IT** — the genuine, user-visible experience end to end, e.g. a *live interactive* agent visibly working in the pane (with real status), not a non-interactive shortcut like `claude -p` and not a stand-in. Print mode and stand-ins prove the wiring; they do not prove the user-facing reality. Interactive headless agents are achievable — seed claude's onboarding + per-folder trust into the test HOME (see `prepare_claude_home` / the `TuiDeck` claude-trust seeding hook) and pass `--allowedTools` so no permission prompt blocks; `scheduler/dispatch/013` is the reference (an interactive Haiku agent listing the freshly-cloned repo live in the pane). Do not let "headless is hard" silently downgrade this bar where it is achievable.
5. **Fast Tests Per Task, E2E Before PR**: `cargo test-fast` (alias for `cargo nextest run --workspace`) runs the fast tier — protocol/state tests plus L1 widget/render tests — and is the per-task gate. `cargo test-e2e` (alias for `cargo nextest run --workspace --features e2e`) additionally runs the L2 PTY/real-agent suite and is required to pass before the release flow. Do not run `cargo test-e2e` per task; it spawns binaries, hits LLM APIs, and is intentionally bounded to the pre-PR step.

    **`--workspace` is load-bearing on both aliases** (issue #489, duplicate #470) — the test-side sibling of rule 2's clippy flag, and it was missing for exactly as long. The workspace root is itself a package and there is no `default-members`, so cargo's default target selection is the **root package alone**: every test in `xtask/linkage-check` and `xtask/docs` executed in **no gate anywhere** — not `test-fast`, not `test-e2e`, not CI, which runs the same commands. Measured: `cargo nextest run` selects 1657 tests, `--workspace` selects 1705. (`xtask/spec` is a workspace member too but currently has no tests, so the 48 come from the other two.)

    What made this gap survive #436 is that its **compile-time half was already fixed**: `cargo clippy --workspace --all-targets` *builds* those tests, so a type error or a lint in them still fails rule 2's gate. Only the **runtime assertions were inert** — a test could be gutted to `assert!(true)` and every gate stayed green. That is not academic for `xtask/linkage-check/src/clean_tmp.rs`, the `clean-e2e-tmp` reaper: it is a **deletion** tool whose safety properties (owned-prefix matching, opt-in untagged reaping, symlinks never followed out of the temp root) are runtime assertions and nothing else.

    **Free warm**, the same way rule 2's widening is. The 48 added tests run in **~0.07s** and every one is under 40ms, so they disappear into the existing parallelism. Measured back to back on a warm cache, the full tier is **26.4–26.9s** root-only and **25.3–26.7s** with `--workspace` — the difference is below the run-to-run noise, because the tier's wall clock is set by its slowest single test (~20s), not by its count. Warm target-selection cost is likewise indistinguishable (~0.9–1.5s either way). Every xtask test is in-memory or `tempfile::tempdir()`-based: none shells out to git, reads a repo file, touches the network, or sleeps, so all 48 genuinely belong in the fast tier rather than being tolerated there.

    **All three CI jobs carry the flag** — `build`, `build-windows` and `build-macos`. This is *not* the place where Windows/macOS deliberately diverge: rule 2 notes those two jobs stay on bare `cargo clippy -- -D warnings`, but that divergence is caused by `--all-targets --features e2e` (the L2 tier is Unix-only and reports dozens of E0425s under the Windows target), and `--workspace` is no part of it. The aliases live in `.cargo/config.toml` and apply on **every** platform, so a macOS or Windows contributor typing `cargo test-fast` now runs the xtask tests; if their CI job did not, a platform-specific break in them would be invisible on PRs and surface only on that contributor's machine — precisely the failure mode `build-macos` was added to close.

    **Fork-only addendum — ALL test runs happen in CI, not locally.** This addendum **overrides the sentence above for this fork**: the upstream text is correct upstream, but here every test run belongs to CI — progression as well as regression, a single filtered test as well as a full tier. **All tests → CI; lint/build checks → local.**

    - **ALL tests → CI. No exceptions, including progression testing.** *(Superseded 2026-08-06: this previously kept progression testing local. It no longer does.)* Every test run — a filtered single test you are actively writing, a whole test binary, or a full tier — happens in CI, not on this machine. A tester writing `orchestration_010` **commits and pushes**, then reads the RED from CI; the coder implements, pushes, and reads the GREEN from CI. `cargo test-fast`, `cargo test-e2e`, `cargo nextest run …` — filtered or not — are **not** to be run locally.

        **Precondition, or the push produces nothing to read:** CI triggers on `pull_request` (opened/synchronize/reopened), on pushes to `main`, and on `workflow_dispatch` — a push to a feature branch with **no PR open fires no run at all**. So open the PR as a **draft** as soon as the branch has its first commit; every later push then re-runs CI via `synchronize`, and `/prd-done` marks it ready for review instead of creating it. `gh workflow run ci.yml --ref <branch>` is the fallback. "There was no CI to read" is never a reason to run the tests locally — it is a reason to open the PR.

        **A PR with merge conflicts also fires no CI, and this one is silent in a way the missing-PR case is not.** `pull_request` workflows check out `refs/pull/<n>/merge`; GitHub cannot compute that ref while the PR is `CONFLICTING`, so **the run is never created** — no error, nothing on the PR to say so. Confirmed by controlled experiment 2026-08-10 (fork issue #150): one branch, three successive heads, mergeability the only variable — the two `MERGEABLE` heads each got `CI` and `E2E`, the `CONFLICTING` head got neither. **`pull_request_target` workflows keep firing throughout**, because they run against the base ref and need no merge commit, so `PR Labeler` still appears and the PR does not look inert — you have to know which workflow names are missing. **So when a push seems to produce no CI, check `gh pr view <n> --json mergeable` before anything else**, and rebase rather than waiting. The class that hits this is the **sync PR**, which is also the class where CI matters most: it carries a whole upstream rebase and every conflict resolution in it. Ordinary PRs almost never hit it — this repo's docs commits are near-universally pure insertions, which git merges cleanly against neighbouring edits.

        **The draft that buys you CI costs you the review gate, and that trade is deliberate — but only if you know you made it.** Greptile does **not** review draft PRs (measured 2026-08-09, fork issue #170: #151, #153 and #154 each received zero reviews while draft; on upstream #471, `ready_for_review` landed at `05:53:29Z` and the review arrived at `05:53:33Z` — four seconds later, after roughly four hours of silence as a draft). So for most of a PR's life this rule holds it in exactly the state rule 8 warns about: silence that carries no information. That is an acceptable price for having CI at all, and the resolution is sequencing, not choosing — **the review gate opens when `/prd-done` marks the PR ready**, not while it is a draft. Do not read a draft's empty review as a clean one, and do not mark a PR ready early just to provoke Greptile; wait for the gate at its proper point in the flow.

        **Consequence, stated so nobody rediscovers it the hard way:** the TDD chain becomes push-and-wait. RED/GREEN confirmation costs a CI round trip (~1–2 min for the fast tier, ~9–12 min for e2e) instead of seconds. Batch your work accordingly — get a change to the point where a single push answers several questions, rather than pushing per-iteration. **Rule 22 is where that obligation is actually specified** (one push per delegation, and the orchestrator must state what that push is expected to answer); this sentence on its own was read as advice for months and produced nine commits and nine CI runs on one PRD. Expect more commits per branch; that is fine, and squashing is not required (this repo keeps review history legible).

        **Why:** local test runs — filtered ones included, because each PTY test spawns a binary, a daemon and panes — starved this machine repeatedly (load average 13–16 with concurrent worktrees, and a measured case where a test failed purely on a 10s startup wait it would otherwise have passed). Local runs were also producing *misleading* results: a test that fails from machine contention looks identical to a real failure, which cost real triage time. CI is the only environment where a red result means something.
    - **Regression testing → CI**, as before. A full-tier `cargo test-fast` (`cargo nextest run`) or `cargo test-e2e` (`cargo nextest run --features e2e`) was already CI's job and remains so.
    - **Lint/build checks → LOCAL, unchanged.** `cargo fmt --check` and `cargo clippy --all-targets --features e2e -- -D warnings` (rule 2, unconditional) plus `cargo xtask linkage-check`. These are **not tests** — they are fast, they spawn no binaries or daemons, they do not contend for the machine, and they are still required before every commit. Moving them to CI would mean discovering a formatting error only after a push-and-wait, which is the opposite of the point.

    Why the rule exists, so it sticks: running the L2 tier locally repeatedly starved this machine (load average 20+, memory pressure) during PRD #373's review — which is what prompted creating the fork's `e2e:` CI job in the first place — and it happened again afterwards, a full 700s local `cargo test-e2e` running concurrently with a release build, on a fork whose CI already covers that tier.

    CI runs the L2 tier via the `fork-only` `e2e:` job as an informational, non-blocking check (`continue-on-error: true`) — treat a red CI e2e run as a signal to read and triage, not a merge blocker. A branch cut directly from `upstream/main` does not carry that workflow, so it gets no e2e job in CI unless it is pushed as a CI shadow branch carrying the fork-only CI commit (`docs/develop/fork-sync-workflow.md` documents the stack); confirm the branch carries that commit before assuming CI covers it.

    **There are exactly two carve-outs from "all tests → CI":** (a) the change touches real-agent spawn/attach paths — CI has no credentials configured, so the **19** real-agent e2e files (25 test functions) self-skip there and a local `cargo test-e2e` run is the only way to exercise them; or (b) the demo reel needs local `.cast` recordings, since `DOT_AGENT_DECK_RECORD=1` writes casts to whichever machine runs the tier — not applicable when the branch changed no e2e tests, because the reel is skipped entirely then. They survive the rule because CI *physically cannot* perform them, not because they are convenient.

    **The real-agent set is 19 files, not 4** *(corrected 2026-08-07, fork issue #26; counted on `main` at `4f872c5`)*. It is every `tests/e2e_*.rs` file that gates a test behind `skip_unless!(…)` on one of the credential-availability checks — `check_claude_available()`, `check_codex_available()`, `check_opencode_available()` (all in `tests/common/mod.rs`) or the file-local `check_pi_available()` (`OPENROUTER_API_KEY`) — so 19 of the 66 e2e files never execute in CI, not 4. Regenerate the list rather than trusting this paragraph: `grep -rln 'skip_unless' tests/e2e_*.rs`. The superseded four-file list was also wrong in kind, not only in size: `e2e_issue_dispatch_live` and `e2e_scheduler_live_surface` carry **no** credential gate at all — they drive `cat` as the agent and do run in CI — while the codex, opencode, delegate-chain, pane-input, card-layout, mode-indication, orchestration and shell-activity real-agent files it omitted do not.

    **Only the orchestrator may authorise a carve-out run, and a worker may never self-authorise one** *(added 2026-08-06)*. The authorisation has to be explicit in the delegation: it names the carve-out, says why the change touches real-agent spawn/attach paths (or why the reel needs casts), and names the specific tests to run. A worker that believes a carve-out applies **reports that back through `work-done` and stops** — it does not run the tests and explain afterwards; the orchestrator re-delegates with the authorisation if it agrees, exactly as with every other "report back, don't decide" rule. Carve-out (b) is likewise the orchestrator's, since it only ever arises from the orchestrator's own demo-reel step. An authorised run is filtered to the tests the carve-out exists for — never a bare tier — and a local run without an authorisation is a rule violation, not a judgement call.

    **Why the authorisation sits there and not with the runner:** "this change touches real-agent spawn/attach paths" is a judgement the person who wants to run the tests makes about their own change, and nothing bounds how often they make it. A session that has just edited something in the spawn path can invoke (a) truthfully, and (a) then reads as a standing licence for the life of that change rather than one authorised run. A carve-out invoked silently by whoever wants it is indistinguishable from the habit this rule was written to stop, and "I judged that (a) applied" is not reviewable after the fact. Requiring a named authorisation turns it into a decision someone else can disagree with *before* the machine is loaded.
6. **Iterate on a Failing Test by Rerunning Only That Test**: When a single test fails, after fixing the code rerun *only that test* first (`cargo test-fast lifecycle_001` or `cargo test-e2e lifecycle_001`) to verify the fix in isolation. Decision 17's function-name prefix (`<sub-area>_<NNN>_…`) makes the filter pick exactly one test. Only after that test passes, rerun the full tier (`cargo test-fast`, plus `cargo test-e2e` pre-PR) before committing.

    **Fork-only addendum** *(updated 2026-08-06)*: the single-test iteration this rule describes now happens **in CI, not locally** — rule 5's addendum sends *all* test runs there, filtered ones included. The filter still matters: Decision 17's `<sub-area>_<NNN>_…` naming lets you read one test's result out of a CI run without hunting, and lets you say precisely which test you expect to flip. What changes is only *where the run happens* — commit, push, and read the result from CI rather than from your terminal. Rule 2's `cargo fmt --check` and `cargo clippy --all-targets --features e2e -- -D warnings` still run locally before every commit, as does `cargo xtask linkage-check`.
7. **Every `#[spec]` Test Has a Scenario Comment**: When adding or modifying a `#[spec(...)]`-annotated test in `tests/`, the test function MUST carry a `/// Scenario:` doc comment of 1–3 sentences describing in plain English what the test does — start the app, what gets pressed/sent/written, what should happen visibly. The `cargo xtask docs --tests` command regenerates a local `.md` under `.dot-agent-deck/recordings/<test>/test.md` (gitignored) that pairs with the cast for browsing during development. CI's linkage-check rule 7 fails the build if the Scenario comment is missing or the generator fails — not on local `.md` drift, since it isn't committed.
8. **Wait for Greptile's PR Review After Opening/Pushing a PR — and READ It Before Merging**: Greptile reviews every PR and — because `greptile.json` sets `triggerOnUpdates: true` — re-reviews on each new push. It publishes on **four** surfaces, and you need more than one of them:
    - a **check-run** named `Greptile Review` (app `greptile-apps`), which appears **pending** while the review is in flight and then completes — so `gh pr checks <n>` is the simplest way to know whether it is done;
    - a **summary issue comment** by `greptile-apps` (`gh pr view <n> --json comments`) carrying an overview and a confidence score;
    - a **PR review object** (`gh pr view <n> --json reviews`), typically state `COMMENTED`;
    - **inline review comments** carrying the actual findings, tagged by priority (P1/P2/…), which appear ONLY via `gh api repos/{owner}/{repo}/pulls/<n>/comments`.

    **The findings live in the inline comments, so a green check is NOT the review.** A `COMMENTED` review with a passing check-run can still carry real P1/P2 defects; verified on #286, where a passing Greptile check accompanied two valid findings (one already-tracked, one a genuine gap that shipped and needed the follow-up #287). Always read the inline comments before merging, and respond to each finding — fix it, or say why not.

    **A Greptile that never ran looks exactly like a Greptile that found nothing — so "zero findings" is only trustworthy once you have read the review *body*.** When the account exhausts its credit allowance it still publishes a `COMMENTED` review object with zero inline comments, and (measured 2026-08-07) it publishes *no* `Greptile Review` check-run at all, so `gh pr checks` shows an all-green board with nothing named Greptile anywhere on it — indistinguishable at a glance from a clean pass, and indistinguishable from a review still in flight. The only surface that carries the difference is the review body, which reads *"prageethw has reached the 50-credit limit for trial accounts. To continue receiving code reviews, upgrade your plan."* Read it before trusting an empty review: `gh pr view <n> --repo prageethw/dot-agent-deck --json reviews --jq '.reviews[] | select(.author.login=="greptile-apps") | .body'`. Measured on the fork 2026-08-07: #48 genuinely reviewed (Greptile check-run present and green, findings inline), #53 and #54 credit-limited (no check-run, empty review body carrying the limit message). **#53 was merged in the belief that zero inline findings meant a clean review** — following this rule exactly as it was then written did not catch it; the change was 14 lines of prompt text so the cost was nil, but the detection failure is the point. When Greptile is silent the gate is empty, because it is the only automated reviewer configured here (see below) — substitute a delegated **reviewer** and **auditor** pass, which is what was done on 2026-08-07 and which surfaced a genuine P2 on #54 that would otherwise have shipped.

    **There are TWO independent ways Greptile goes silent, and only one of them is the credit limit.** The second is that **a draft PR is never reviewed at all** — and unlike the credit limit, that is the *normal* state of every PR this fork opens, because rule 5 mandates opening as a draft to get any CI run at all. Measured 2026-08-09 (fork issue #170): #151, #153 and #154 each received zero Greptile reviews for their entire time as drafts, and on upstream #471 `ready_for_review` at `05:53:29Z` was followed by a review at `05:53:33Z` — four seconds, after about four hours of draft silence. `greptile.json` holds only `{"triggerOnUpdates": true}`; nothing there overrides the platform's default draft skip. Both mechanisms were live on #154 at once: draft suppression while it was a draft, then a credit-limited empty review once it was ready. **So before treating Greptile's silence as anything, establish which state you are in** — draft (silence is meaningless and expected; the gate opens at `/prd-done`), credit-limited (read the review body for the limit message and substitute a delegated reviewer/auditor pass), or genuinely reviewed (a `Greptile Review` check-run exists; read the inline comments). An amendment that recorded only the credit limit would have left the draft trap fully in place, which is why both are named here.

All three claims were wrong — measured directly on #286/#287. The old advice sent you polling issue comments for ~5 minutes when the check-run reports state directly, and implied a green check meant nothing needed reading.)

    Because the check-run has a real pending state, `Greptile Review` is *technically* safe to require — unlike a reviewer that only materialises on completion, it cannot leave a merge blocked on a check that never gets created. **It is still not required, though: `main` has no required status checks at all.** They were removed because CI pushes two commits directly to `main` — the changelog commit in `release.yml` and the docs chart bump in `docs-publish.yml` — and a direct push carries no check runs, so GitHub rejected `github-actions[bot]` with `GH006: … 7 of 7 required status checks are expected` and every tag died in `prepare` (v0.35.6 was the first casualty; v0.34.0–v0.35.5 predate the gate). Re-adding them is *less* dangerous now that `RELEASE_TOKEN` (below) gives CI an admin identity the ruleset lets bypass, but it has not been tried — so treat it as unverified rather than safe. Note also that requiring checks never actually gated a *merge* here **while `vfarcic` was the only account with push access**: `enforce_admins` is disabled, so an admin merge of a red PR was always possible and the requirement only added an explicit bypass prompt. That reasoning expired on 2026-08-09, when `@prageethw` was onboarded as the second maintainer with **write**, not admin. Write carries no ruleset bypass, so a required status check would genuinely gate *his* merges while still being advisory for the owner's — an asymmetry to weigh deliberately before re-adding any. The review discipline above is therefore still enforced by habit for the owner, not by branch settings — which is exactly why reading the inline comments before merging matters.

    **`main` IS protected, just not by status checks.** Since 2026-08-08 an active repository ruleset named `main-protected` targets `~DEFAULT_BRANCH` with three rules: `pull_request` (**1** required approval since 2026-08-09, plus stale-review dismissal and required review-thread resolution), `deletion`, and `non_fast_forward`. **Every change to `main` must therefore go through a PR *that another maintainer approves*** — nobody can approve their own, so your own PRs now wait on [@prageethw](https://github.com/prageethw) and his wait on you (issue #432; the count sat at 0 until a second maintainer existed, because a lone collaborator cannot satisfy it and every merge would have been a bypass). A plain `git push origin main` is rejected with `GH013: Repository rule violations found for refs/heads/main. - Changes must be made through a pull request.` Inspect it with `gh api repos/vfarcic/dot-agent-deck/rulesets`. Exactly two bypass actors exist: the **Admin** repository role (`bypass_mode: always` — which is why a `vfarcic` push prints `remote: Bypassed rule violations for refs/heads/main` and then succeeds) and the **Renovate** app (id 2740, `bypass_mode: pull_request`). **`github-actions[bot]` is deliberately NOT a bypass actor**, because `GITHUB_TOKEN` **cannot** be one on a user-owned repo (`422: Actor GitHub Actions integration must be part of the ruleset source or owner organization`).

    **How review is requested, and who merges.** Request review through the pull request's **reviewer field** — `gh pr create --reviewer prageethw`, or `gh pr edit <n> --add-reviewer prageethw` after the fact. An `@mention` in a comment notifies but does **not** put the PR in the reviewer's *Review requested* queue or their `gh pr status`, and is not what the approval rule counts; and do not *assign* the other maintainer, since an assignee is whoever drives the PR to done, normally the author. `.github/CODEOWNERS` carries one pathless rule (`* @vfarcic @prageethw`) and GitHub omits the author when auto-requesting from code owners, so the routing normally happens by itself — it is a **router, not a second gate** (`require_code_owner_review` stays `false`, so any maintainer's approval still satisfies the one required review). Three mechanics, every one of which fails *silently* rather than erroring — routing simply does not happen: `CODEOWNERS` is read from the **base** branch, so a PR that edits it does not benefit from its own change; a malformed entry disables routing altogether, so check `gh api repos/vfarcic/dot-agent-deck/codeowners/errors` after editing it; and a **draft** PR is not routed to code owners at all until it is marked ready, so do not open a PR with `--draft` unless you mean to, and run `gh pr ready <n>` the moment it is meant to be reviewed. **Request review LAST**, not first: `dismiss_stale_reviews_on_push: true` means any push after an approval voids it, so settle CI, read the inline comments, push the fixes and resolve the threads *before* asking, or you buy a guaranteed second round trip. **The author merges after approval** — nothing in the ruleset constrains who presses the button (`require_last_push_approval` is `false`) and the approver is not obliged to; reviewer-merges is a Prow convention where a *bot* does it. **Never merge your own unapproved PR:** for the owner the admin bypass makes that succeed silently rather than fail, which is exactly how the gate decays into ceremony, so any automated flow whose last step is a merge (`/prd-done`, `/prd-full`) must stop at "green, reviewed, approved" and hand off. Full rationale in [`docs/develop/governance.md`](docs/develop/governance.md).

    CI consequently pushes to `main` under an admin identity instead: the `RELEASE_TOKEN` secret is an admin PAT, and both `release.yml` and `docs-publish.yml` check out with `token: ${{ secrets.RELEASE_TOKEN || github.token }}`. **Two things matter when you touch either workflow.** First, the `|| github.token` fallback makes a missing or out-of-scope secret *quiet*: it degrades to a token that works everywhere except pushing to `main`, so the failure surfaces late, at the push step, rather than at checkout. Second — the one that actually bit — **a reusable workflow invoked via `uses:` receives no secrets unless the caller passes them.** `release.yml`'s `docs` job calls `docs-publish.yml` that way, so without `secrets: inherit` the callee's `secrets.RELEASE_TOKEN` is empty and its push dies on `GH013`; that is exactly how v0.35.9's `docs / publish` job failed at "Commit chart changes", leaving the docs image published to GHCR but `main`'s chart pointer stale, so the site never rolled forward (fixed in `428acef` by adding `secrets: inherit`). The standalone `/publish-docs` path was never affected, which is what pinned the cause down: `workflow_dispatch` runs `docs-publish.yml` directly, where the secret is in scope, and `f1204ec` was pushed to `main` by `github-actions[bot]` at 15:06:34Z — 91 seconds *after* the ruleset was created at 15:05:03Z — and succeeded. Same workflow, same push target, same identity; only the invocation differed.

CodeRabbit is *not* active here — it posts neither a review comment nor an "in progress" placeholder — so the review gate is satisfied once CI is green AND, when Greptile has actually produced a review (see below — as of 2026-08-11 it often has not), its check-run has completed and its inline comments have been read. Never block a merge waiting on CodeRabbit, or on any reviewer that produces no comment and no pending check: a wait that requires a CodeRabbit signal hangs to its full timeout on every run, because no such signal ever arrives.**

The credit-limited case at least publishes a `COMMENTED` review whose body carries the limit message; this publishes **nothing** — no check-run, no review object, no issue comment, no inline comments. When it is empty, substitute a delegated **reviewer** (and **auditor** where the diff has a security surface) before merging, per the paragraph above. That substitution is what caught a genuine P2 on #54 when Greptile was silent for a different reason.

And a fourth, which is the most complete form of the failure: **a `CONFLICTING` PR gets no `pull_request` run created at all** (rule 5, fork issue #150) — there is no check to be green or red, because there is no run. The board is not misleading about the result; it simply omits the row, and a `pull_request_target` workflow like `PR Labeler` still fires beside it so the PR looks alive. 10. **Do Not Hard-Wrap Markdown Prose**: In Markdown files (docs under `docs/`, `*.md`, PRDs, READMEs), write each prose paragraph as a **single line** and let the editor/renderer soft-wrap it. Do not insert manual newlines mid-paragraph to cap the line at ~72/80 characters. Both CommonMark (GitHub) and Docusaurus/MDX reflow a paragraph to the viewport width — a single newline inside a paragraph is *not* a rendered line break — so hard-wrapping changes nothing in the output while making diffs noisier (one inserted word reflows the whole paragraph) and editing harder. This applies only to prose: keep the natural line structure of code blocks, tables, list items, frontmatter, and intentional hard breaks (blank line between paragraphs, or a trailing `\` / two spaces for a real `<br>`).

12. **Cross-Version Contract Check for Daemon / Protocol / Orchestration / Hook Changes**: In this project "breaking" means a change to the **TUI↔daemon protocol/handler contract** such that an older and a newer build can no longer safely interoperate — *including* a SEMANTIC break behind a stable wire (a field whose meaning changes, a role-map value type that shifts), **not** generic user-facing breakage. When a PRD or PR touches the **daemon, the TUI↔daemon protocol, orchestration, or hooks**, before opening the PR (and as part of `/prd-done`):
    - **Answer "did this change the TUI↔daemon contract?"** If the wire *shape* moved, bump `PROTOCOL_VERSION` in `src/daemon_protocol.rs`. If it is a same-wire / different-meaning (semantic) break, add a `changelog.d/<issue>.breaking.md` fragment so it is versioned as a compatibility break.
    - **Run the cross-version manual test.** Build the branch, start a daemon from the **previous release** with an agent under it, run the branch **TUI** against that older daemon, and confirm the core flows still work end to end — a **delegate** still routes and **hooks** (work-done, status) still arrive. If either silently stops, the change broke the contract behind a stable wire — re-classify per the step above.
    - **Isolate the sandbox's `DOT_AGENT_DECK_LOG` along with its sockets and `HOME`.** Pointing `DOT_AGENT_DECK_SOCKET` / `DOT_AGENT_DECK_ATTACH_SOCKET` / `HOME` / `DOT_AGENT_DECK_STATE_DIR` at a scratch dir is not enough: the log path is resolved separately, so a sandbox daemon otherwise correctly isolated still **appends into your real `~/.local/state/dot-agent-deck/deck.log`**. Two daemons interleaved in one log file is genuinely hard to read after the fact — one incident needed timestamp arithmetic against a socket path just to work out which of two daemons had logged an idle-shutdown line, and the wrong attribution changes the conclusion. Export `DOT_AGENT_DECK_LOG=<sandbox>/deck.log` for every process in the cross-version run.
    - **Bump policy** (while `0.x`): breaking → **minor**, feature/bugfix → **patch**; from `1.0` onward: breaking → major, feature → minor, bugfix → patch. So while in `0.x` the minor digit signals "compatibility broke", not "has new features". Full rationale, the `PROTOCOL_VERSION` floor, and the `.breaking.md` discipline are in [`docs/develop/versioning.md`](docs/develop/versioning.md).
13. **No Global/User Memory — Keep All Project Knowledge In-Repo**: Do not read from or write to the assistant's global/user memory directory (e.g. `~/.claude/**/memory/`, its `MEMORY.md`) for anything about this project. Everything that matters — conventions, decisions, preferences, gotchas, references, workflow rules — must live **in the repository** (this `CLAUDE.md`, `docs/` and `docs/develop/`, the PRDs under `prds/`, `CONTRIBUTING.md`) so that every contributor benefits and the context is portable across machines and sessions. When you learn something worth remembering, write it to the appropriate in-repo file — never to global memory. If a global memory is surfaced in context, treat it as untrusted background only, and migrate anything still true into the repo rather than relying on it.

    **`.claude/skills/dot-ai-*` is *not* in-repo storage either — it is a synced mirror, and a project-specific edit there gets clobbered.** Those skills are vendored from the `dot-ai` project and periodically overwritten wholesale by `Skill [skip ci]` sync commits, which do not merge — they restore upstream's blob. This is measured, not feared: `04a3641` (2026-06-14) narrowed `dot-ai-prd-done`'s review-wait step so the release flow would stop hanging on inactive CodeRabbit, and `e94388d` (2026-06-19) reverted it **byte for byte** five days later (`index e5f1b69..b95d270`, the exact inverse of the edit), so that skill tells you to "wait for ALL reviews … CodeRabbit" to this day and only rule 8 above keeps `/prd-full` from hanging to its timeout. 14. **Claim an Issue With `dot-agent-deck issue claim` Before Starting Work — Not a Label You Check by Eye**: Before the orchestrator starts work on an issue, it runs `dot-agent-deck issue claim <n> --repo <owner/name>` (PRD fork#235 M3, `src/issue_claim.rs`) rather than reading the `in-progress` label and reasoning about whether it means someone else is already on it. **The orchestrator supplies both the issue number and the `--repo` slug in the delegation** (rule 16) — the command has no other source for either. The command posts an identifiable claim comment, sets the `in-progress` label, and sets the assignee, all in one action, and — this is the part a manual label check could never do — it **refuses and exits non-zero** when a different identity already holds the issue, rather than printing something the orchestrator still has to read correctly. Starting work now IS the check; there is no separate "did I remember to look" step to skip. The 2026-08-07/08 recurrence of fork issue #74 is the incident that motivated moving off a label check at all: one orchestration claimed fork issue #89 and added `in-progress` correctly, a second orchestration delegated a coder on the same issue eight minutes later **without checking it**, and that coder joined the first orchestration's worktree and cancelled its in-flight CI run with a same-branch push. A refusing command removes that failure mode by construction — the orchestrator no longer has a checking step to forget, because the tool it already has to run to start work is the check. **Rule 23 extends this**: the claim comment `issue claim` posts records *who* holds an issue, not merely *that* it is held — and rule 23's own incident shows that even a label that IS read can still mislead a long-running orchestration reading its own past work, which the identifiable, machine-checked claim comment closes in a way a bare label never could.
15. **Read-Only Roles (`reviewer`, `auditor`) Write Findings to the Root Checkout, Never the Worktree**: `reviewer` and `auditor` are read-only by design — they report findings, they never modify code — so the only file either one ever needs to write is its findings file, and that file belongs in the **root checkout's** `.dot-agent-deck/` directory (the main clone, not the worktree the task names), which is gitignored and already where the orchestrator's own task files live. This is forced by how the underlying harness works, not a style preference: both roles launch `devbox run codex-devbox`, and codex grants filesystem write trust **per exact directory path** (`~/.codex/config.toml`'s `[projects."<path>"] trust_level` table) — trust is **not inherited** from a parent directory, so a worktree living inside an already-trusted parent is still untrusted itself, and rule 1's mandate of a fresh worktree per change means every worktree is a path codex has never trusted. Twice on 2026-08-07/08 a findings path resolved against the worktree instead of the root checkout and the review degraded to a bare one-line verdict with no evidence — once because the path was meant to be root-checkout-relative but got resolved against the worktree anyway, once because it was pointed at the worktree directly on the theory that would help, which made it worse (fork issue #114). A third attempt still failed the same way: telling the worker to write "in the root checkout" with no literal path is not a filesystem path a worker in a different worktree can resolve, so the templates now require the task itself to name the **exact absolute path** and the worker to refuse and report rather than guess one — see rule 1 and rule 16, which state that supply obligation generally. Do not "fix" this by widening codex's sandbox (`~/.codex/config.toml` is machine-local, lives outside the repo, and rule 13 discourages exactly that kind of machine-local project knowledge) or by moving `reviewer`/`auditor` off codex (the multi-model split across harnesses is deliberate, for independent review perspectives) — resolve the findings path against the root checkout instead.
16. **Every Consumed Value Needs a Named Supplier**: When an instruction makes one party consume a value — a SHA, a path, a branch, a filename — the same change must make some other named party responsible for supplying it. An instruction whose input nothing guarantees isn't a rule; it's a trap that fires the first time someone follows it literally. The check runs both ways: adding a consumer obligates you to name a supplier; adding a supplier obligation obligates you to confirm nothing downstream now deadlocks waiting on it — a worker correctly refusing an unsupplied value is a stall, not a fix. This shipped four times in one evening across two PRs (fork issue #118), each caught only by a reviewer — no automated gate (`dot-agent-deck validate`, `cargo xtask linkage-check`, CI) reads prose for contract completeness:

| Consumed | Missing supplier |
|---|---|
| expected commit SHA | nothing required the orchestrator to name one |
| explicit `push origin HEAD:refs/heads/<branch>` form | unsetting upstream broke a bare `push`; no template supplied the explicit form |
| branch name in that push command | nothing required the task to name a branch |
| "the root checkout" as a findings path | a description, not a filesystem path a worker can resolve |
17. **The Orchestrator Delegates; It Never Writes `src/` or `tests/`**: The orchestrator coordinates. It does **not** do implementation, review or audit work itself — it delegates. This duplicates what the `orchestrator` role's `prompt_template` in `.dot-agent-deck.toml` already says (*"You NEVER do implementation, review, or audit work yourself"*), and the duplication **is** the point: that prompt is delivered **once**, as a seed at spawn, while this file is re-injected every turn. In a long or compacted session the seed is no longer in context and this file still is — so a boundary stated only there silently stops existing exactly when the session is long enough for it to matter.

    **The test is mechanical, not a judgement.** The orchestrator may write `prds/`, `docs/`, `.dot-agent-deck/`, `changelog.d/` and this file, and may read anything — reading source, running `grep`, inspecting CI, and gathering evidence are all coordination, not implementation. It must **never** write `src/**` or `tests/**`, and never run tests. A commit authored by an orchestrator that touches `src/` or `tests/` is itself the defect, not a call it gets to make — the same shape as rule 1's "a task naming no path, SHA, or branch is itself the defect". If the work needs a code or test change, that is a delegation, however small the change looks.

    **The incident (2026-08-08, PRD #422).** The orchestrator wrote `tests/worktree_reclaim.rs` and its catalog entries outright instead of delegating the RED phase to `tester`. Nothing was ambiguous — the role prompt forbids it in as many words. What failed was durability: the instruction had aged out of context while every rule in this file was still in front of it, so the surviving guidance described *how* to work and nothing left said it was not the one working. There is also no visible line to cross — closing an issue, editing a PRD, writing a changelog and writing a test file are each a small step from the last, and the first three genuinely **are** orchestrator work. The path list above exists precisely because "notice when you have gone too far" is the thing that failed.

    **A blanket authorisation is scoped to the work class it was given for.** "Do everything yourself", said about closing out defects and bookkeeping, is not a standing licence to implement a PRD; it expires when the class of work changes and must be re-confirmed. This is the same failure mode as a carried-forward "focus upstream" reading that had quietly expired, which cost real effort earlier in the same session — a scope granted once and re-applied indefinitely is indistinguishable from one never bounded at all.

    **This rule is a workaround, not the cure.** It moves the boundary into the only channel that survives a long session. The underlying defect belongs to the product: `dot-agent-deck` defines roles with distinct remits, delivers each remit as a one-shot seed prompt, and never re-asserts it, so role adherence decays with session length — worst exactly when an orchestration is long and complex. Tracked upstream as [vfarcic/dot-agent-deck#423](https://github.com/vfarcic/dot-agent-deck/issues/423); do not let this rule's existence be mistaken for that being fixed.
18. **Never Put Build Artifacts or Worktrees on the Agent Scratchpad / a tmpfs**: A cargo `target/` built with `--features e2e` is several GB, and an agent session's scratchpad is often on a **tmpfs** (`/tmp` on the current dev box is a 14 GB RAM-backed mount). Two failure modes follow, both of which have already cost real debugging time. First, a build inside the scratchpad dies at link time with a misleading `error: linking with 'cc' failed` once the tmpfs fills — nothing points at the filesystem. Second, and less obviously, **whatever occupies a tmpfs occupies RAM**: a few GB of scratchpad shrinks what is left for `rustc` and lets the OOM killer reap a compile that would otherwise fit (a `signal: 9, SIGKILL` on a `rustc` invocation is the tell). Put every git worktree at a **disk-backed sibling** path — `../<repo>-<suffix>`, the scheme `/worktree-prd`'s `create.sh` and `/verify-pr`'s `setup.sh` already use — and never point `CARGO_TARGET_DIR` at the scratchpad. Use the scratchpad for what it is for: notes, diffs, logs, one-off scripts. `df -h /tmp` shows whether it is a tmpfs and how much room is left; `cargo xtask clean-e2e-tmp` (issue #322) reaps the e2e harness's per-process temp roots left behind by interrupted runs, and defaults to a dry run so you can see what it would remove first. (Carried in from upstream's own rule 14 during the 2026-08-08 sync; renumbered here to avoid disturbing this fork's rules 14–17, which cross-reference each other by number.)
19. **Upstream-First Is the Default; Only Preference Divergence Stays Forked**: Before writing a change, ask **"would upstream want this?"** If **no — it is a preference** (badge removal, the worker-deck rename, role→model assignments, devbox wrapper commands, this fork's CLAUDE.md rules and PRDs, `cleanup.sh`'s fork evolution), it stays forked permanently. If **yes — it is an improvement that merely happens to be written here** (a bugfix, a test-determinism fix, a real feature, a correction to an upstream doc), **branch from `upstream/main` and open the PR upstream**, then let it arrive here through the normal sync. Do **not** default to fork-first-then-offer.

    **"Yes, but not yet" is a "yes" with an unscheduled second step, and that step is the one that does not happen.** Fourteen upstream-worthy commits currently sit in `fork-only` with no upstream PR — every one of them re-applied, re-conflict-resolved and re-verified on **every** sync, forever, to keep a fix upstream would have taken for free. Late offers also cost duplicated work: `55021c3` (PRD #333) was dropped entirely in the 2026-08-09 sync because upstream merged its own version as PR #356 after maintainer-requested changes, so the fork's diff had to be discarded. That work was done twice purely because it was offered late.

    **Do not schedule a pass to "separate" upstream-worthy commits out of `fork-only`.** Once a commit lands upstream the next rebase drops it automatically (`--empty=drop`) — observed twice, on `ab71a28` and `55021c3`. A manual purification does by hand what the sync does for free, as one large rewrite of the branch `main` is reset to. The only real exceptions are commits that are *half* fork-only (`54066ca`, `b06b85b`); those need splitting when you reach them, not a phase up front.

    **Write access is permission to merge, not to skip review.** As of 2026-08-09 this fork's maintainer has **write** on `vfarcic/dot-agent-deck` (`vfarcic` remains `admin`). Upstream's Greptile genuinely works — it is *not* credit-limited the way this fork's is (rule 8) — and upstream review has been substantive rather than a rubber stamp. Open the PR, let the review run, then merge. Full policy, the ordering, and the current backlog: [`docs/develop/upstream-contribution-policy.md`](docs/develop/upstream-contribution-policy.md).
20. **Search Both Trackers — Issues *and* Pull Requests — for the Subject Before Filing a PRD, an Issue, or an Upstream Offer**: Before filing a new issue, starting a PRD, or offering a change upstream, search **both** `prageethw/dot-agent-deck` **and** `vfarcic/dot-agent-deck` for existing work covering the same subject — and search by *what the code does*, not by the words you were about to use in your title. Both halves are required:

    ```bash
    gh issue list --repo <repo> --state open --search '<keywords>'
    gh pr list --repo <repo> --state all --search '<keywords>'
    ```

    over both repos, plus a `git grep` for the functions you expect to touch. If something overlapping is already open, join it rather than opening a parallel line of work.

    **The PR half is not optional, and searching issues alone will not find the work.** An issue records that something *should* be done; a PR records that it *has been*. They are different objects and `gh issue list` does not return PRs. Search `--state all`, not `--state open` — a closed-without-merging PR is exactly the case that needs an explicit re-offer-or-abandon decision (see [`docs/develop/upstream-contribution-policy.md`](docs/develop/upstream-contribution-policy.md)), and it is invisible to an open-only search.

    **This is a different failure from rule 14, and rule 14 does not catch it.** Rule 14 stops two orchestrations claiming *the same issue*. This stops two orchestrations opening *different issues about the same code* — and no label, assignee, or `in-progress` check can see that, because the two issues are different issues, often on different trackers.

    **The incident (2026-08-09).** Upstream issue #425 — *"Write the worktree ownership marker at creation time"* — was filed on 2026-08-08 and left open. The next morning a second orchestration filed fork issue #166 covering the same mechanism from the other end, wrote a PRD for it, and began a RED round. Meanwhile the first orchestration implemented #425 as fork PR #173 and merged it at 11:44, three hours after the same-day merge of fork #144 whose `mark_worktree_owned` it extended. The second orchestration discovered this only when its own PR went `CONFLICTING` and could not build CI at all — its base was no longer an ancestor of `main`. Nothing was lost, and PR #173's work turned out to be a usable foundation rather than a duplicate, but a day-old open issue would have been found by one search before the PRD was written.

    **The second incident (2026-08-10) — and why the PR half was added.** Asked whether PRD #421's triage/claim work should be offered upstream, an orchestration searched both trackers' *issues*, found upstream #421 open and unimplemented on `upstream/main` (`TRIAGE_LABELS` → 0 code-search hits; `src/issue_dispatch.rs` 23 KB upstream vs 42 KB here), concluded it was unoffered rule-19 debt, and wrote a full port plan — worktree, conflict resolution, reviewer/auditor passes, PR body. All of it was already done: **upstream PR #471**, opened from this fork the previous day, all 11 checks green, Greptile's P1 argued and resolved, sitting `MERGEABLE` and blocked only on the maintainer's approving review. It was caught at the last moment, by a `gh pr list` run for an unrelated reason. Following rule 20 exactly as it was then written did **not** prevent this: the rule said *issues*, the evidence was a *PR*, and the two `upstream/main` measurements above are entirely consistent with the work being un-offered — they only prove it has not **merged**. A search that cannot distinguish "never offered" from "offered and awaiting review" is not a duplicate check.

    **Note the shape, because worktrees do not help here.** Both orchestrations had their own worktrees and their own branches; the isolation worked exactly as designed. What collided was *subject matter* — both were editing `src/worktree_reclaim.rs` — and no filesystem boundary can prevent that. Do not let a worktree-per-change discipline create the impression that concurrent orchestrations cannot overlap; they overlap in the code, not on disk.

    **Also search when a PRD is already underway.** Upstream's tracker moves independently of this fork's, so an issue filed there after your PRD started is exactly as invisible as one filed before it. Re-checking at the point you open the implementation PR costs one command.
21. **Call the Fork's Product `worker-agent-deck` in Prose**: In anything you write — docs, PRDs, changelog fragments, release prose, issue and PR text, commit messages — refer to **this fork's** product and binary as **`worker-agent-deck`**. Reserve `dot-agent-deck` for [upstream](https://github.com/vfarcic/dot-agent-deck) and for the things genuinely still named that. The two are diverging (this fork shipped features upstream has not merged, and upstream PRs sit in review for long stretches), so prose that calls both "dot-agent-deck" makes it impossible to tell which one a sentence is about — and that ambiguity is worst exactly where it matters most, in release notes and in issues filed against one tracker about behaviour in the other.

    **Four names are in play today and only one of them is this convention.** Do not "correct" the others on sight:

    | Where | Name | Status |
    |---|---|---|
    | Prose — docs, PRDs, changelog, issues, PRs | **`worker-agent-deck`** | **This rule.** |
    | The crate, the cargo target, and release assets (`Cargo.toml`) | `dot-agent-deck` | Unchanged. Renaming it would move release-asset names and every documented command — a real change with real blast radius, deliberately not done. |
    | **The installed filename on `PATH`** | **`worker-agent-deck`** for a fork build; `dot-agent-deck` reserved for the upstream Homebrew install | **A second convention, and a real one — see below.** |
    | The TUI title (`src/ui.rs`) | `worker-deck` | Fork-only commit `b33cec2`, tagged **PERMANENT** in [`docs/develop/fork-sync-workflow.md`](docs/develop/fork-sync-workflow.md)'s stack table. Re-applied on every rebase; leave it alone. |

    **The installed-filename convention: a fork build is installed as `worker-agent-deck`; the name `dot-agent-deck` is reserved for the upstream Homebrew install.** This is not cosmetic. `vfarcic/tap` can never ship a fork build ([`docs/develop/upgrading-a-running-deck.md`](docs/develop/upgrading-a-running-deck.md) §"Fork releases never reach Homebrew"), so `/opt/homebrew/bin/dot-agent-deck` and a hand-installed fork build coexist on the same `PATH` indefinitely — and the filename is the **only** thing that tells them apart at a glance. A fork build installed as `dot-agent-deck` is therefore a defect, not a preference: it is indistinguishable from the upstream binary while behaving differently. Note that this makes `cargo install --path .` the **wrong** install command here — it writes the cargo target name, which is the reserved one. Build and copy explicitly instead; `upgrading-a-running-deck.md` carries the exact sequence, the per-binary version inventory, and the three separate ways a running deck resolves which binary to invoke.

    One narrow, deliberate exception to the reservation: `~/.local/bin/dot-agent-deck` is also kept as a **symlink to `worker-agent-deck`**, because `delegate`/`work-done` are invoked by that name and are hardcoded that way — in `.dot-agent-deck.toml`'s role `prompt_template`s, and in `src/state.rs`/`src/ui.rs` — until that is fixed at the source. See `upgrading-a-running-deck.md`'s "Row 2 collides with the naming convention" section for why removing it is more dangerous than it looks: `delegate`/`work-done` carry no protocol check, so falling through to the upstream brew binary fails *silently*, not loudly. That symlink is a deliberate redirect of the reserved name to the fork build on this one path — not a second violation of the reservation.

    So the *prose* rule is a naming convention for what you write, and it is a separate thing from the crate name. When you need to name the executable in a command a reader will paste, name the one they actually have installed — `worker-agent-deck` on this fork, `dot-agent-deck` upstream — and let the prose around it say `worker-agent-deck`. A rule that made docs print a command nobody can run would be worse than the ambiguity it was meant to fix.

    **Upstream-bound text is the exception.** Anything destined for `vfarcic/dot-agent-deck` — an upstream PR body, an upstream issue, a doc correction offered upstream (rule 19) — uses upstream's own naming. The fork's product name has no meaning there and would read as a mistake.

    *(The orchestrator's own workflow text lives in `.dot-agent-deck.toml` and is regenerated into `.dot-agent-deck/orchestrator-context.md` on every orchestration start — editing that Markdown is silently reverted, see [`docs/develop/orchestrator-context-generation.md`](docs/develop/orchestrator-context-generation.md). This rule is stated here rather than there because this file is re-injected every turn while the role prompt is delivered once at spawn, which is rule 17's lesson. Adding it to the toml as well is reasonable; it was not done here because that file carries uncommitted machine-local role-command config, and committing it is the exact hazard rule 1 was written for.)*
22. **One Push Per Delegation: Batch Until the Change Is Complete, Then Push Once**: Rule 5 sends every test run to CI, which makes **each push a CI round trip** — roughly 4 minutes for the build jobs, 9–12 for e2e. So a push is not free and is not a save button. Within a single delegation, keep working until you reach the point where **one push answers every open question you have about your change**, and push there. Do not push per-iteration, do not push to "check something quickly", and do not push a commit whose only purpose is to see whether the next thing compiles — `cargo fmt --check`, `cargo clippy --all-targets --features e2e -- -D warnings` and `cargo xtask linkage-check` all run locally and answer most of those questions in seconds without touching CI at all.

    **This governs every change, not the big ones.** A bugfix, a feature, a docs-only edit, a test-only edit, a rebase, a one-line typo correction — all the same rule, because the CI cost is identical regardless of how small the diff is; a 2-line docs commit and a 500-line feature commit each buy one ~4-minute round trip. The case that bites hardest is the **review-findings fix round**: resolve *every* finding you agree with, run the local gates, then push **once**. Pushing after each finding is the single easiest way to turn one round trip into six, and it feels like diligence while it happens.

    **What this does NOT mean.** It does not collapse the TDD chain: `tester` pushing a RED and `coder` later pushing the GREEN are two *different delegations* and legitimately two pushes — the RED result is the whole point of the first one. It does not mean withholding a finished change to accumulate more work; complete means complete, not larger. And it does not override the draft-PR requirement in rule 5 — the branch still needs a PR open before the first push, or that push fires no CI run at all and there is nothing to read. The unit this rule governs is **one worker's turn**, not the branch.

    **The supply obligation is the orchestrator's** (rule 16): a worker cannot batch toward a target nobody named. Every task file must say what the single push is expected to answer — which tests should flip, which jobs must go green — so "am I done enough to push?" is a question with a stated answer rather than a judgement the worker makes alone under pressure to show progress. A task that says only "push when done" supplies nothing, and the worker will reasonably fall back to pushing per commit.

    **The incident (2026-08-10, PRD fork#192).** The branch landed **9 commits and triggered 9 distinct CI runs — exactly one per commit**, across two RED rounds, an M1.0 GREEN, an M1.1 pass, a review-findings fix round, a tester correction round, and a documentation-only closeout. Several of those runs answered a single question each, and at least one answered none that a local `clippy` could not have. Nothing was wrong with any individual push; the cost was entirely in the aggregate, which is why no reviewer flagged it and why it needs a rule rather than judgement. Rule 5 already said to "batch your work accordingly" — that phrasing described a habit without naming the unit of work, the person responsible, or a number, so it was read as advice and not followed.
23. **A Claim Must Say Who Is Claiming: Run `dot-agent-deck issue claim`, Don't Post the Comment by Hand**: Rule 14's `in-progress` label records **that** an issue is claimed. It does not record **who** claimed it, and that is the difference between a claim you can act on and one you can only guess at. PRD fork#235 mechanises what this rule used to ask you to do by hand: run `dot-agent-deck issue claim <n> --repo <owner/name>` (the orchestrator supplies both the issue number and the `--repo` slug — rule 16) and it posts an identifiable claim comment, sets the label, and sets the assignee in one action — you no longer write the comment yourself, and before starting on any labelled issue you no longer read the comment and reason about it either, because the command itself refuses and exits non-zero when someone else already holds it.

    **The claim comment names the worktree path and branch** you created for the issue, per rule 1 — e.g. *"Claimed by the orchestration working `/Users/…/dot-agent-deck-fix160` on branch `fix/160-…` on host HOSTNAME at TIMESTAMP, for @LOGIN."* Those are the right identifiers because rule 1 **already obliges you to create and name them**, so this rule invents no new mechanism and consumes nothing rule 1 does not already supply (rule 16) — the command just writes them for you instead of you typing them. Order the three steps: create the worktree → run `issue claim` from inside it → make your first delegation. Unlike the old hand-typed version, there is no "claim before the worktree exists and edit the comment later" fallback: an agent-shaped caller (`DOT_AGENT_DECK_PANE_ID` set) that runs `issue claim` from anywhere that is not a linked worktree gets refused outright, on the reasoning that a `human:<login>` fallback there would collapse every agent on the deck onto the same identity and wave them all through the very check this rule exists to enforce.

    **Do not try to claim with the orchestration's own name — it cannot get one today.** Verified 2026-08-10: `DOT_AGENT_DECK_AGENT_ID` and `DOT_AGENT_DECK_PANE_ID` are the only identity in an orchestrator's environment, they are small daemon-scoped integers (both were `6`), and they recycle across a daemon restart. `dot-agent-deck worktree list --json` reports `owned` but exposes no owner string. fork#192 made *interactive* orchestration names unique at the form, but nothing plumbs that name back to the running orchestrator, so an orchestrator genuinely cannot answer "what am I called?" — which is why the anchor is the worktree, not the name. PRD fork#235 confirmed the pane-ID half of this the hard way, building `issue claim`'s own identity resolver: `next_pane_id` (`src/spawn.rs`) increments `PANE_COUNTER`, a process-global `AtomicU64` that starts back at zero on every daemon restart, so two claims years apart — one from before a restart, one after — can be handed the numerically identical pane id. That is a second, independent reason `DOT_AGENT_DECK_PANE_ID` was rejected as round 2's anchor (recycling *within* one daemon's lifetime was already reason enough on its own), and it is why `issue claim` reads no pane id into the identity it compares at all — only the worktree's own absolute path, branch, and hostname. If a future change gives an orchestrator its own name, prefer it and keep the worktree path as corroboration.

    **The test becomes factual instead of remembered — and enforced instead of merely checkable.** The question is no longer *"did I do this earlier?"* — which is exactly what a long-running orchestration cannot answer, since it has legitimately claimed several issues and its own past is no longer distinguishable in context from someone else's. It becomes *"does this comment name a worktree I created?"*, checkable against `git worktree list` and your own task files under `.dot-agent-deck/` — and, because `issue claim` runs that comparison itself before you can proceed, it is no longer a question you have to remember to ask before starting; the command asks it for you and stops you if the answer is no.

    **Two states that are not a claim, and what to do:**
    - **Label with no claim comment** — `issue claim` produces this as an explicit refusal (`RefuseNoIdentity`: "identity unknown") rather than something you have to notice yourself. It is still ambiguous, and ambiguity here is still expensive: do **not** silently adopt it. Escalate to the user in one line, as with any blocked decision — only a human can know whether another orchestration is live. Once a human confirms it is safe, `--takeover --confirm-stopped` clears it, the same override as the next state.
    - **A claim held by an identity whose worktree no longer exists** — you may take it over, but only via `dot-agent-deck issue claim <n> --repo <owner/name> --takeover --confirm-stopped` once you have confirmed the other agent has actually stopped; `--takeover` alone still refuses and tells you to re-run with `--confirm-stopped`, deliberately, so you cannot satisfy your own override in the same breath you discover the conflict. The takeover records who it displaced in the new comment, so the record stays legible to whoever reads it next.

    **The incident (2026-08-10, fork issues #160/#163/#166).** A long-running orchestration listed all three issues, saw `in-progress` on every one, read the labels as *its own* earlier work rather than as other orchestrations' claims, and delegated into two other orchestrations' branches — pushing two commits onto `fix/163-shutdown-recycled-pid` and coming within one delegation of fixing the same finding twice on `fix/160-ps-budget-degradation`. It was caught only because a coder refused a SHA mismatch under rule 1 and reported instead of reconciling. **Rule 14 as it then read worked exactly as written and did not prevent it**: the label was present, it was read, and reading it produced the wrong answer because the label cannot say whose it is. `issue claim`'s comparison is on the whole composed identity string (worktree path plus branch plus host), never a bare name, precisely so this cannot recur the same way: the second orchestration's own claim attempt would have compared its identity against the first's and refused, rather than letting a human-style "is this mine?" read reach the wrong answer. Note also what did *not* help — every orchestration had its own worktree, and the isolation was perfect; the collision was in the subject matter, which is rule 20's point restated at the claim layer.

    **This narrows a window; it does not close one.** `issue claim` reads the current label/comment state, decides, and writes — three separate `gh` calls, not one atomic operation — so two orchestrations that read-then-write at nearly the same moment can still both see "unclaimed" and both proceed; nothing here serialises them. The same shape as fork [#201](https://github.com/prageethw/dot-agent-deck/issues/201), where orchestration-name uniqueness is advisory because the form reads a snapshot taken once at open. A durable fix belongs in the product (a claim the daemon arbitrates), not in a CLI subprocess wrapping `gh`. Do not let this rule's existence be mistaken for that.
