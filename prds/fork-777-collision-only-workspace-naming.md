## Problem Statement

PRD #544's Design §1 specified workspace directory naming as `<root-checkout-basename>-<sanitize_clone_segment(name)>` — picking repo `im` with Name `features` gave the folder `im-features`. No subpath, no prefix, for either a toplevel or a nested (subdirectory) pick.

Issue #607 found a real bug in that scheme: two different picks could sanitize to the same segment and silently share one physical clone, mixing branch/checkout state across sessions. Concretely:

1. **Name uniqueness is live-only, not durable.** `orchestration_name_claims` (`src/agent_pty.rs`) is an in-memory map; `release_orchestration_name` fires on `StopAgent`. Close an orchestration named `features`, later open a new one also named `features` against a *different* subdirectory of the same repo — no uniqueness violation, but the same segment, a different actual target.
2. **Name uniqueness checks the raw typed string, not the sanitized segment.** `claim_orchestration_name`'s own doc comment gives the example: `"fix/544"` and `"fix-544"` are different raw Names, both independently pass live uniqueness, and both sanitize to the identical segment `fix-544` — while simultaneously live.

Issue #607's fix, `disambiguate_workspace_segment` (`src/ui.rs:10341`, commit `8fef97a0`, PR #751), closes this correctly but unconditionally: for **any** nested pick, it always prepends `{segment.len()}-` and appends the sanitized subpath, whether or not a collision would ever actually occur. A repo `im`, Name `features`, subdirectory `baseline/intent` now always produces `im-8-features-baseline-intent` instead of #544's plain `im-features` — even though, in the overwhelming majority of picks, no other orchestration is or ever will be contending for that same segment.

PRD #760 attempted to address the resulting naming-ergonomics complaints (a restored, optional "Worktree slug" field, PR #761) but was reverted 2026-09-13/14 (PR #771) per the maintainer's own direct call, and never actually touched this regression — the length-prefix/subpath join applies unconditionally regardless of which field feeds the segment, so #760's whole back-and-forth left the actual defect untouched. Issue #763 even found the prefix still applied to a *typed* slug, defeating the point of that field, which was part of what led to the revert.

No existing open issue or PRD proposes the actual fix: making disambiguation conditional on a genuine collision, detected at the point machinery already exists to detect it, instead of unconditional for every nested pick.

## Decisions

| Question | Direction | Why |
|---|---|---|
| Does the default naming scheme change? | **Yes — reverts to PRD #544's plain `<root-checkout-basename>-<sanitize_clone_segment(name)>`**, for both toplevel and nested picks. `disambiguate_workspace_segment`'s unconditional length-prefix/subpath join is no longer applied up front. | Matches #544's original, reviewed design. The subpath/prefix machinery was never a deliberate ergonomics tradeoff — commit `8fef97a0`'s own message and issue #607's discussion never consider or reject a collision-only alternative; it just wasn't discussed. |
| Where does collision detection move? | **Into the provisioning transaction** (`provision_isolated_clone_sync_resolved`, `src/issue_dispatch_run.rs`), inside the same attach-race lock already used for the resume path — not as a separate pre-provisioning pure function. **Shipped differently — see Design §2's correction note below.** | Naming and provisioning happening as two independent steps (pure-name-then-provision) is exactly what created the TOCTOU concern that made #607's fix go unconditional in the first place. Doing the check inside the lock that already exists for resume-safety closes that concern without inventing new locking. |
| How is "genuine collision" distinguished from "safe to resume"? | Reuse `isolated_clone_ancestry_matches_source` and the provenance marker's `creator=`/`name=` fields — exactly what `resume_existing_isolated_clone` already uses to decide `Resumed` vs. `NameCollision`/`AncestryMismatch`. If the plain-named folder that already exists is *this* pick's own prior clone (same repo, same subpath) → resume as today, unaffected. If it belongs to a genuinely different pick → **that's** the collision, and only then does the disambiguated form get computed and (re-)attempted under the same lock. | This is the exact machinery #544 M3/M4 built for resume-safety and #607 partially reused for `resume_existing_isolated_clone` — extending it to also gate the *initial* naming choice, rather than adding a second, different collision-detection mechanism. |
| Does the length-prefix/subpath join itself change? | No — `disambiguate_workspace_segment`'s actual join format is untouched and still used, just moved from "always" to "only on confirmed collision, as a retry." | The join format itself was never the problem; when it fires is. No reason to redesign a working format. |
| Any retry-loop / infinite-fallback risk? | No new one. On a confirmed collision, exactly one retry with the disambiguated name is attempted under the same held lock; a further real collision on the disambiguated name itself (already effectively impossible today, since #751 made the join length-prefixed/injective) surfaces as an ordinary `Rejected`, same as any other unresolvable provisioning failure today. | The disambiguated name was already designed to be collision-resistant (#751); this PRD doesn't need to make it more so, only decide when it's computed. |
| Does this touch Name uniqueness (`ClaimOrchestrationName`) itself? | No. Both gaps in Name uniqueness identified in the Problem Statement (live-only scope, raw-string-not-sanitized-segment check) are accepted as-is — they're what *causes* a possible collision, not what this PRD is fixing. This PRD only changes how a collision, once it occurs, is handled. | Tightening Name uniqueness (e.g. scoping it to the sanitized segment, or making it durable across closes) is a separate, larger design question with its own tradeoffs (does a closed orchestration's Name become permanently unavailable forever?) and isn't needed to fix the naming regression this PRD targets. |

## Design

1. **Naming.** `resolve_orchestration_workspace` (`src/ui.rs`, the current equivalent of the call site originally named `resolve_workspace_path`) stops calling `disambiguate_workspace_segment` unconditionally. The segment passed into provisioning becomes plain `sanitize_workspace_segment(name)` for both toplevel and nested picks. Shipped as designed.
2. **Provisioning-time collision check.** `provision_isolated_clone_sync_resolved` (`src/issue_dispatch_run.rs`), when it finds the plain-named target directory already exists, runs the same ancestry + provenance-marker identity check `resume_existing_isolated_clone` already performs. Same identity → proceed to resume, unchanged. Different identity → the caller computes `disambiguate_workspace_segment`'s form for this pick's actual `(segment, subpath)` and retries.
   **Correction — deviation from the design as originally written, confirmed by two independent review/audit rounds on PR #779:** the retry does NOT happen "inside the same lock acquisition" as this section originally specified. It shipped instead as **two separate, sequentially locked calls** to `provision_isolated_clone_sync_resolved` from `provision_isolated_clone_or_status` (`src/ui.rs`) — the first call returns `Rejected(NameCollision)` and its lock is released before the second call (under the disambiguated name) acquires its own. Reviewers judged this does not reopen a race: a retry always targets a path `disambiguate_workspace_segment` cannot produce for a *toplevel* pick (see the guard below, which removes that case from the retry entirely), and two colliding *nested* picks always resolve to disjoint disambiguated paths by construction (the length-prefix join is injective, per `disambiguate_workspace_segment`'s own doc comment) — so there is no window where two racers could compute and win the *same* disambiguated path. Accepted as a genuine but harmless deviation rather than sent back for a rewrite. If this code is touched again, preserve the two-call structure's safety argument (disjoint retry targets) rather than assuming the single-lock design this paragraph originally called for.
   **Addition not in the original design:** retrying is skipped entirely for a **toplevel** pick (`relative_subpath.is_none()`) on `NameCollision`, since `disambiguate_workspace_segment(_, None)` is a documented no-op — retrying would re-attempt the identical path just refused, degrading an accurate `NameCollision` refusal into a misleading `Contested` one. A toplevel collision is now a direct, terminal refusal, never retried.
3. **Existing collision-safety machinery.** `disambiguate_workspace_segment` (#607/#751), the symlink-toplevel guard (#595), and the resolved-workspace-path-qualified `creator` identity all stay exactly as they are — this PRD changes only *when* the first of these is invoked, not its own logic. The `creator` identity itself gained a new, additional input this PRD didn't originally anticipate — see item 5 below.
4. **Migration for existing on-disk workspaces.** A workspace already sitting at a disambiguated path (e.g. `im-8-features-baseline-intent`, created before this change) is not renamed automatically — renaming a live git worktree out from under any in-flight session is its own hazard, out of scope here.
   **Correction — the sentence originally here overstated the guarantee.** The old disambiguated-path workspace is not actively re-discoverable by any production UI path either. The next time that same pick is opened, the deck computes the new plain location and provisions a brand-new, empty clone there — it does not look for, resume, or migrate the old decorated directory. The old workspace, including any uncommitted work in it, is left completely untouched on disk, findable only by the user manually locating it by its old directory-name shape (a sibling directory whose name starts with a decimal number followed by a dash, e.g. `12-myrepo-features-team-b-proj`). There is currently no in-app action to find or retire it automatically. See `changelog.d/777.breaking.md` for the exact user-facing wording this corrected text is aligned with. `forget_isolated_workspace` (PRD fork#544 §M5) still applies once a user has located such a workspace by hand.
5. **Creator-seed digest (not in the original design — added during the PR #779 fix round to close a review/audit BLOCKER).** Restoring collision-only naming reopened a truncation hazard fork issue #763 had already fixed, which fork#760 Part A's revert (commit `8d1c3332`) deleted along with the rest of that PRD's typed-slug work: `sanitize_marker_creator` truncates any `creator` provenance string past 200 characters, and two DIFFERENT nested picks whose folded `<worktree_path>/<relative_subpath>` seeds happen to agree on their first ~186 characters — easy to reach in a deep monorepo layout — previously produced byte-identical truncated `creator` markers after truncation, silently causing the second pick to `Resume` onto the first pick's live clone instead of being refused. `spawn_pane_creator_identity_seed` (`src/ui.rs`) restores the mitigation: for any pick with a non-empty relative subpath, it digests the STRUCTURED inputs — `(resolved_root_dir, relative_subpath, segment)`, NUL-separated — with `fnv1a64` (the same fixed-constant hash the attach-lock path already uses) and places the 16 hex digits at the FRONT of the seed, immediately after `orchestration_creator_string`'s own `"orchestration:"` prefix, so truncation, if it ever fires, can only ever drop the now-redundant folded-path tail, never the digest bytes that keep two colliding picks distinguishable. A no-op for a toplevel pick (no relative subpath) — its own `worktree_path` already uniquely identifies its clone, and naming refuses to retry a toplevel collision at all (item 2 above), so two toplevel picks can never collide on one physical clone in the first place.
6. **`LegacyNestedIdentityUnverifiable` refusal (not in the original design — the maintainer's explicit direction during the PR #779 fix round: never silently fork or abandon a workspace that might hold uncommitted work).** `resume_existing_isolated_clone`'s ancestry/provenance check (item 2 above) gained a distinct third outcome alongside the ordinary `Resumed`/`NameCollision` split: when the plain-named directory's on-disk provenance marker is a pre-subpath-aware LEGACY-format record (predating fork issue #766's marker upgrade) whose stored identity happens to match the CALLER'S OWN segment, the two cases — "this is my own earlier workspace, written before today's subpath-aware format" and "this is a genuinely different nested pick that merely shares the same top-level Name" — are indistinguishable on disk, because the legacy format never carried subpath information at all. Rather than guess, and risk either silently forking a new, empty clone that abandons the user's real workspace, or silently adopting a stranger's, the deck refuses the open outright with a distinct, actionable error (`ResumeRejection::LegacyNestedIdentityUnverifiable`) and does NOT retry under the disambiguated name — deliberately different from the ordinary `NameCollision` → disambiguate-and-retry path in item 2, which is safe to auto-resolve precisely because it's never ambiguous in this way. The user is told to pick a different Name or inspect the existing directory by hand. Known, accepted over-refusal: a legacy marker records no nested/toplevel distinction, so this refusal can also fire for a plain-named directory left by a legacy **toplevel** pick whose Name happens to match a nested caller's segment — an unambiguously different pick, refused rather than disambiguated. Fail-closed is the accepted tradeoff.
7. **`OrchestrationSnapshot.claim_cwd` (not in the original design — added during the PR #779 fix round to close a review/audit MAJOR: a daemon-restart-only reopening of fork issue #607's original shared-clone hazard).** `OrchestrationSnapshot` (`src/config.rs`, the TUI's own local session-restore-on-disk format, `session.toml`) gains a new `claim_cwd: Option<String>` field. It is persisted at live-spawn time with the pre-provisioning LOGICAL claim cwd — the same `cwd` string the live orchestration's own `ClaimOrchestrationName` request sent (toplevel + segment + relative subpath, collision-UNAWARE) — not the physical directory provisioning may have actually landed on after a collision retry. On restore, the daemon-empty restore path reuses this persisted value verbatim for its own `ClaimOrchestrationName` request, rather than recomputing a claim cwd from the physical saved directory (`saved_pane.dir`) the way it did before this fix — because for a collision-disambiguated orchestration those two derivations genuinely diverge, and recomputing from the physical dir would let a fresh pick after a restart claim a DIFFERENT logical cwd than the live orchestration it's actually colliding with, silently defeating the collision detection this PRD exists to add. `#[serde(default)]`: a pre-fork#777 snapshot loads with `claim_cwd == None` and falls back to the old physical-dir derivation — the historically correct value for that population, since every nested pick was unconditionally disambiguated before this PRD shipped, so the physical and logical paths always agreed for it.
8. **Rule 12 check (updated — confirmed during implementation, as this section originally asked; a `.breaking.md` fragment WAS added, though not for a protocol-version reason).** `OrchestrationSnapshot`/`SavedPane` never cross the daemon socket — `src/daemon_protocol.rs` has no reference to either type; they are the TUI's local `session.toml` format only, and the `claim_cwd` field above never changes what is sent over the wire, only which caller-side value populates the pre-existing `AttachRequest::ClaimOrchestrationName { cwd }` field. **No `PROTOCOL_VERSION` bump was needed** — confirmed independently by both round-2 review and audit passes. `changelog.d/777.breaking.md` was added regardless, not for a protocol-version reason, but because this PRD's naming-scheme change is itself a genuine user-facing behavior break (existing nested-pick workspaces silently stop being reused, per item 4 above) that rule 12's `.breaking.md` convention exists to warn users about.

- Tightening `ClaimOrchestrationName` uniqueness itself (durable-across-close scope, or checking the sanitized segment instead of the raw string) — see Decisions table; a separate, larger design question.

- Any change to Name's role as instance identity (PRD fork#192) or to the resume eligibility rules themselves (PRD fork#544 §"Decisions").

## Risks and Mitigations

- **Reintroducing #607's original bug via a subtle lock-ordering mistake.** **Mitigation, as originally written:** the collision check must run strictly inside the same held lock the create-vs-resume decision already uses — M3's review explicitly checks this ordering, not just that the feature works on the happy path. **Outcome:** the shipped implementation does NOT hold one lock across the retry (see Design item 2's correction note) — M3's review explicitly checked this deviation for exactly the race this risk names, and found it does not reopen it, because a retry's disambiguated target is always disjoint from the plain path and from any other colliding pick's own disambiguated target. Recorded here because the original mitigation text no longer describes what actually shipped.
- **A legacy disambiguated-path workspace becoming unresumable.** **Mitigation, as originally written:** M1(e)/design §4 explicitly keep the old path resumable; nothing renames or migrates it. **Outcome, narrower than originally intended:** nothing renames, migrates, or deletes the old path, so a user who navigates to it directly (e.g. via a saved shell alias or manual `cd`) can still resume it exactly as before — but no production UI path automatically finds or resumes it for a fresh pick of the same (repo, Name, subpath) anymore; see Design item 4's correction note.
