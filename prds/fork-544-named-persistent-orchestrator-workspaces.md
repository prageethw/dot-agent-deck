## Problem Statement

Opening a 2nd+ concurrent orchestration against a root checkout already correctly isolates it into its own git clone (PRD fork#325 M3), and that clone is already never auto-deleted (M4a/M4b). But the clone's identity and lifecycle don't match how this repository's own workflow (CLAUDE.md rule 1: every fix gets its own worktree, sometimes reused deliberately) actually wants to use them. Verified against `main` @ `c3d69bd1`:

1. **The workspace directory's name is not the orchestration's name.** The directory comes from a separate "Worktree slug" form field, auto-generated as `<dir-basename>-orchestrator-N` when left blank (`auto_generate_worktree_slug`, `src/ui.rs:9862-9875`) — the exact `repo-orchestrator-1`, `repo-orchestrator-2` sprawl this issue describes. The typed, required-unique orchestration **Name** (fork#192) only feeds the ownership marker's `creator` string (`src/ui.rs:10898-10899`) — it never touches the path. The two fields look related by naming convention only; they are computed independently.
2. **There is no reuse.** `provision_isolated_clone_sync` (`src/issue_dispatch_run.rs:1375-1404`) always returns `AlreadyClaimed` the moment the target directory exists — regardless of whether the prior owner is still live. Contrast Model C (`provision_repo`, `src/issue_dispatch_run.rs:1144-1181`), which already does clone-if-absent-else-fetch-and-fast-forward, keyed on a stable task name — but that fetch/ff behavior is itself unsafe to copy wholesale here, since our workspaces must carry forward uncommitted changes and local-only commits across sessions.
3. **Persistence today is an absence, not a decision — on the tab-close path only.** `RemovalPolicy::IsolatedClone` (`src/issue_dispatch_run.rs:155-172`, `:329-342`) always reports `Kept` — no removal is ever attempted on that path — and `src/ui.rs` has no tab-close cleanup path for isolated clones at all. Model A never even calls `record_worktree`, so these clones are invisible to the daemon's own `WorktreeRegistry` and only discoverable via fork#325 M4a's separate sibling-directory scan. **Correction (2026-08-22):** this is true only for `decide()`'s tab-close path. A *separate* code path, `src/worktree_reclaim.rs`'s `worktree reclaim --yes` CLI command, already does remove isolated clones today — see the Predecessors line above and issue [#546](https://github.com/prageethw/dot-agent-deck/issues/546).
4. **The existing anti-forgery evidence is content-free.** The M4b provenance artifact (`isolated_clone_provenance_path`/`write_isolated_clone_provenance`, `src/issue_dispatch_run.rs:2530-2593`) is literally the bytes `b"deck\n"`, keyed only by `fnv1a64(canonical_path)` — it proves "the deck created *something* here," never *what*, or *from which source repository*. The only place a Name/creator string is recorded today is the **in-repo** `OWNER_MARKER_FILENAME` (`created-by: ...`, `src/worktree_reclaim.rs`) — the exact mechanism two prior M4b review rounds proved forgeable by a same-uid actor. This matters directly for resume-safety design below.

Fork#325's own PRD names this residual directly, as M4c: *"whether an isolated clone can ever become automatically reclaimable, and under what stricter safety condition"* — flagged there as needing the same explicit maintainer sign-off M1 needed, and explicitly not bundled into an implementation PR. **This PRD was intended to answer it, but M4c was actually already answered and shipped** (the heuristic condition fork#325's own notes were tentatively weighing — PR-merged AND HEAD-equals-merge-SHA — is exactly what `a8f37894`/PR #526 implemented) **before this PRD existed.** What this PRD ships instead, unaffected by that discovery: deliberate, name-keyed reuse — the orchestration's Name becomes the sole, stable identity for its workspace directory; an existing named workspace is resumed — never silently suffixed, never silently refreshed — when it isn't held by another live orchestration and passes a verified-safe eligibility check; and M5 adds an explicit, confirmation-gated retire action as *the* deliberate way to clear a named workspace. Reconciling that action with the already-shipped heuristic reclaim is issue [#546](https://github.com/prageethw/dot-agent-deck/issues/546), not this PRD.

## Decisions

| Question | Direction | Why |
|---|---|---|
| What becomes the workspace directory's identity? | **The orchestration Name** (already required and unique-among-live since fork#192), sanitized via the existing `sanitize_clone_segment` (`src/issue_dispatch_run.rs:445`). The separate "Worktree slug" field is **retired outright**, not kept as a manual override. | Two identity fields for one workspace is the exact mismatch causing the reported sprawl. Model B (`dispatch <name>`) never had a separate slug to begin with — it already sanitizes its `name` argument directly into the path — proving a single-field identity is sufficient. Keeping a rarely-used override field would reintroduce the "two things that look related but aren't linked" confusion this PRD removes, for no offsetting benefit. |
| Does resuming an existing named workspace ever fetch/pull/merge automatically? | **Fetch, yes (read-only). Integrate, never automatically.** A read-only `git fetch` (updates only the `origin/main` remote-tracking ref; touches no local branch, no working tree) runs on resume so ahead/behind info stays accurate. Any fast-forward, rebase, or merge of the actual branch stays fully manual and user-initiated. | The PRD's own constraint — preserve uncommitted changes and existing work — rules out Model C's fetch+ff pattern for the checked-out branch; that pattern is right for Model C's fresh-per-dispatch clones and wrong for a workspace meant to carry forward local state across sessions. A read-only fetch mutates nothing the user owns, so it's safe to do automatically; integrating the branch is not. |
| What makes a name "safe to resume" vs. a conflict to reject? | A **three-part check**: (1) not held by any currently-live orchestration (fork#192's existing query); (2) the directory carries this deck's own M4b ownership evidence for the canonical path; (3) **new** — the directory's `origin` remote and shared history (a merge-base probe) match the root checkout being opened. All three must hold, and the directory must be healthy (not corrupt / mid-delete). | M4b's evidence alone only proves "the deck created *something* here" — not *what* or *from which repo* (Problem Statement #4). Without an ancestry check, reusing a Name against an unrelated same-basename repository would silently attach a session to foreign history. This reuses M4b's already-hardened anti-forgery property rather than inventing new trust. |
| Auto-suffix on conflict? | **Never**, for the directory any more than for the Name. | The PRD's explicit constraint. fork#192 already refuses (not suffixes) on a live Name collision; this extends the same non-negotiable to the workspace path. |
| What happens on a refusal (stranger directory / wrong ancestry / unhealthy)? | **Never auto-delete.** Refuse with a message naming which of the three it is; point at the new explicit "forget this workspace" action as the only deliberate way to clear one. | None of the three refusal states is proof the contents are safe to discard — a stranger directory might be an unrelated user folder, a wrong-ancestry directory is still real prior work (just unrelated), and "corrupt" can be transient/recoverable (a stale git lock, an interrupted operation) rather than actually destroyed. Modeled on this codebase's existing `issue claim --takeover --confirm-stopped` pattern: refuse by default, require an explicit confirming action. |
| Should a fresh clone start from up-to-date `main`? | **Yes** — needs verification as an implementation task (not assumed) whether today's creation path already fetches from origin at clone time or inherits the root checkout's own staleness; fix if the latter. | A new workspace starting from a stale base undermines the whole point of a durable, resumable workspace. |
| What happens to other live workspaces, and to this one, when a merge lands? | **Other live workspaces**, on an unrelated merge: proactive read-only fetch only, branch untouched. **This workspace**, once its own branch is confirmed merged (tied to the existing merge phase / `release`'s `/prd-done`): auto-switch to updated `main` (checkout + fast-forward) — **conditionally**, only if the tree carries nothing beyond what was just merged. | The just-merged case is safer than the general one: the merge is positive confirmation the branch's content now lives on `origin/main` too, so nothing is lost by moving on. Any additional uncommitted change is genuinely unprotected work the merge didn't capture, so in that case leave the workspace untouched and surface a note instead. This is what makes the workspace immediately ready for the next piece of related work under the same name — the actual point of a durable, reusable workspace. |

## Design

1. **Naming.** Replace the slug-based path derivation with `<root-checkout-basename>-<sanitize_clone_segment(name)>`, reusing the existing sanitizer. Retire the New Pane form's "Worktree slug" field entirely; retire `auto_generate_worktree_slug`'s numbering for this purpose.
2. **Resume arm.** Give the isolated-clone provisioning function a third outcome alongside today's create/`AlreadyClaimed`: `Resumed`. On the derived path: absent → create, exactly as today (and verify/fix creation-time freshness against origin, per the Decisions table). Present → run the three-part eligibility check plus a health probe; a full pass → `Resumed`, reattach with a read-only fetch and zero other git mutation. Any failure → `Rejected(reason)`, naming which of stranger / wrong-ancestry / unhealthy / name-in-use it is.
3. **Race.** Reuse the existing attach-race lock (`worktree_attach_lock_path`, PR #331/#282 — already keyed on canonical target path, anchored under the root checkout's common `.git` dir; no new locking primitive needed). Acquire it *before* the liveness check, hold it through registering the (new-or-resumed) orchestration as live, then release — so a second near-simultaneous opener blocks on the flock and, on acquiring it, correctly sees the first opener's registration and refuses. This closes a race that resume introduces and today's refuse-always behavior did not have: today, two racers both hit `AlreadyClaimed` harmlessly; with resume, existence becomes the success case, so both racers passing the eligibility check would otherwise attach live sessions to the same tree concurrently without this lock.
4. **Ownership tracking.** Extend the ownership marker/M4b artifact to record the orchestration Name and canonical workspace path as explicit structured data (currently only implicit via file location and a bare, forgeable `creator` string) — and add a schema tag plus a hash of the root checkout's canonical path at write time, so evidence written under a future naming-scheme change doesn't silently vouch for content created under today's rule. Read path must tolerate markers written by builds that predate these fields (older format → absent, not an error) — same discipline fork#192's M1.2 applied to `display_title`.
5. **Explicit retire ("forget this workspace") action.** M4b's own documented limitation — evidence is never removed on deletion, so it "vouches" for anything later recreated at the same canonical path — turns from cosmetic into a live hazard once evidence drives an action (resume). Add an explicit action that atomically removes both the directory and its provenance entry, modeled on this codebase's `--takeover --confirm-stopped` pattern: refuses by default, requires an explicit confirming flag. This is the only way a stale or unwanted named workspace is ever cleared — never automatic, never a side effect of merely trying to open a new one.
6. **Registration and cleanup guarantee.** Call `record_worktree` for Model A's isolated clones (today only Models B/C do), so they're uniformly visible in `WorktreeRegistry`/`worktree list`. Pin with a test that tab-close never deletes a named workspace — turning "never removed via the tab-close path because nothing tries" into "never removed via that path because that's the decision." **Correction (2026-08-22):** this is scoped to the tab-close path only, not a general reclaim guarantee — `worktree reclaim --yes`'s separate heuristic path can already remove one today (issue [#546](https://github.com/prageethw/dot-agent-deck/issues/546)); it no longer "answers M4c" since M4c already shipped elsewhere before this PRD existed.
7. **Post-merge sync.** Tied into the existing merge phase (orchestrator workflow step 7 / `release`'s `/prd-done`): for other live workspaces, a proactive read-only fetch; for the just-merged workspace, a conditional auto-switch to updated `main` (checkout + fast-forward) gated on the tree carrying nothing beyond what was merged — otherwise leave untouched and surface a note.
8. **Rule 12 check.** If the wire carries a `worktree_slug`-shaped field that changes shape or meaning, or the marker's on-disk format changes, this needs a `changelog.d/544.breaking.md` fragment, an explicit `PROTOCOL_VERSION` decision, and the cross-version manual test (previous-release daemon + this branch's TUI) — mirroring fork#192 M1.2 exactly.

## Risks and Mitigations

- **Test churn from the naming change.** Same shape as fork#192's own risk. **Mitigation:** the M2 RED round reports the real affected-test count before implementation.
- **A resumed workspace with unexpected foreign contents.** **Mitigation:** the three-part eligibility check plus health probe, reusing M4b's already-hardened evidence rather than inventing new trust; the ancestry check specifically closes the gap the Plan-agent review found (content-free evidence can't alone prove source repo).
- **The race resume introduces.** Existence becomes the success case, so two near-simultaneous opens could otherwise both pass eligibility and attach concurrently. **Mitigation:** reuse of the existing attach-race lock, acquired before the liveness check and held through registration.
- **Silent data loss on resume or post-merge sync.** The single biggest hazard this PRD must not introduce. **Mitigation:** resume issues zero mutating git commands beyond a read-only fetch; the post-merge auto-switch is conditional on the tree carrying nothing beyond what was merged, and any refusal path never auto-deletes — only an explicit, separately-confirmed "forget this workspace" action ever discards anything.
- **Stale evidence vouching for a later, unrelated directory at the same path.** A known M4b limitation, now higher-stakes since evidence drives an action. **Mitigation:** the ancestry check, plus the schema/root-path-hash hardening in M4, plus the explicit retire action being the only path that clears evidence at all — closing the loop the earlier limitation left open.
- **A wire/marker-format change invisible to CI.** Same class fork#192 M1.2 flagged. **Mitigation:** the M8 cross-version manual test is a milestone, not a checklist line.
