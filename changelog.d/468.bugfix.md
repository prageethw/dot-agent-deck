## A Codex hook-trust failure found while draining pre-write events now reaches the retry veto too

Issue #459 taught the dispatch/scheduler delivery path to veto retry arming for a Codex pane whose native hook install/trust is known to have failed — but only when that failure was learned from the readiness wait that runs before the pre-write event drain. If that wait timed out before the wrapper's fork-time `SessionStart` event landed, the drain could see the failure directly and had no way to report it back: a later, metadata-free Codex event drained in the same pass would still arm the delivery, silently defeating the veto for the whole delivery.

The drain now carries that signal back to the caller and it is folded into the same veto at every point capability is decided — before the first write, during the gap drain inside the post-write confirmation loop, and into the confirmation task's own standing flag — the same accumulate-only pattern the rest of the #459 fix already uses. A hook-trust failure observed at any point during a delivery now vetoes arming for that delivery, regardless of which check happens to see it first.
