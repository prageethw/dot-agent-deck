## `display_name` metadata is now sanitized and length-clamped on ingest

`AppState::apply_event` already sanitized and length-clamped `event.model` on ingest (PRD fork#378), but `display_name` metadata (`DISPLAY_NAME_METADATA_KEY`) arriving on the same hook-socket wire was stored with only an `is_empty()` filter — a hostile or unbounded `display_name` (Unicode bidi/format-character overrides, an arbitrarily long value) reached `SessionState.display_name` unsanitized — issue #410. `display_name` is now routed through `terminal_sanitize::sanitize_for_terminal_display` and then clamped via `clamp_display_name_bytes` to `DISPLAY_NAME_MAX_LEN` (bound to `agent_pty::DISPLAY_NAME_MAX_LEN`, the same 128-byte cap the rename path's `is_valid_display_name` already enforces) before the emptiness check and storage. Ingest and rename share that one *constant*, not one *rule*: rename validates and rejects the raw value at that length, while ingest truncates the already-escaped value — a name containing backslashes can therefore be accepted by one path and truncated by the other.

**Scope note**: this closes the gap on `SessionState.display_name`, which the dashboard card falls back to. It does **not** cover `ui.display_names` (the primary source the card prefers when present, hydrated from `AgentRecord.display_name` on `StartAgent`/`RenameAgent`) — that path is not scrubbed by `sanitize_record_tab_membership` and is not caught by `is_valid_display_name`'s validation, so a hostile display name set via those paths still reaches the card render unsanitized today. Tracked as a follow-up rather than fixed here, since it's a different code path with its own hydration/validation seam.
