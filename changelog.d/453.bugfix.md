## A bugfix + breaking changelog fragment pair on a fix/ branch is now a valid breaking bug fix

`cargo xtask work-type-check`'s `derive_work_type` correctly resolves a *lone* `.breaking.md` changelog fragment on a `fix/` branch to `Bug` — a carve-out fork#451 shipped for exactly that case, since a breaking bug fix is still a bug fix. But the most natural way to write a breaking bugfix's changelog is arguably two separate fragments: a `.bugfix.md` summarizing the fix, and a `.breaking.md` detailing the compatibility break. That shape never reached the carve-out at all — the tier-1 loop that compares fragment-derived work types pairwise errored with `ConflictingFragments` the moment it saw a `.bugfix.md` (`Bug`) and a `.breaking.md` (`Prd`'s fallback mapping) disagree, before the branch-aware carve-out that already knows how to resolve this was ever consulted.

The tier-1 loop now recognizes this specific pairing — an established `Bug` fragment alongside a `.breaking.md` fragment, with no genuine `.feature.md` anywhere in the set — and lets it through to the existing carve-out instead of erroring immediately, resolving the pair to `Bug` on a `fix/` branch exactly as a single `.breaking.md` already does. Any other fragment-type disagreement (a `.bugfix.md` alongside a `.feature.md`, for instance) still hard-conflicts unchanged.

No-Test: pinned entirely by plain `#[test]` functions in `xtask/linkage-check/src/work_type.rs`'s `mod tests` (`bugfix_plus_breaking_fragments_on_fix_branch_resolve_to_bug` for the fix itself, `bugfix_plus_feature_fragments_still_conflict_regression_guard` proving the carve-out doesn't overcorrect) rather than a `#[spec]`-annotated one — `xtask/**` is a build-time linting tool, not TUI-observable behavior, so a unit test pins this more directly than any `#[spec]` scenario could, matching `468.bugfix.md`'s precedent for the same class of change.
