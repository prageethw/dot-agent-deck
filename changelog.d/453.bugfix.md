## A bugfix + breaking changelog fragment pair on a fix/ branch is now a valid breaking bug fix

`cargo xtask work-type-check`'s `derive_work_type` correctly resolves a *lone* `.breaking.md` changelog fragment on a `fix/` branch to `Bug` — a carve-out fork#451 shipped for exactly that case, since a breaking bug fix is still a bug fix. But the most natural way to write a breaking bugfix's changelog is arguably two separate fragments: a `.bugfix.md` summarizing the fix, and a `.breaking.md` detailing the compatibility break. That shape never reached the carve-out at all — the tier-1 loop that compares fragment-derived work types pairwise errored with `ConflictingFragments` the moment it saw a `.bugfix.md` (`Bug`) and a `.breaking.md` (`Prd`'s fallback mapping) disagree, before the branch-aware carve-out that already knows how to resolve this was ever consulted.

The tier-1 loop now recognizes this specific pairing — an established `Bug` fragment alongside a `.breaking.md` fragment, with no genuine `.feature.md` anywhere in the set — and lets the `.bugfix.md`'s `Bug` reading stand instead of erroring immediately. On a `fix/` branch that reading agrees with the branch, so the pair resolves to `Bug` there. On a branch with **no recognized prefix at all**, nothing else supplies a competing type either, so the pair now also resolves to `Bug` — this is a genuine (and pre-existing-elsewhere) loosening: a lone `.bugfix.md` already resolved to `Bug` with no branch signal, and this pairing now does too, rather than hard-conflicting as it did before this fix. On `feat/` and `docs/`, where the branch *does* supply a competing type, the pair still disagrees with it exactly as before and still errors, naming the `.bugfix.md`. This is deliberately narrower than the existing lone-`.breaking.md` carve-out (fork#451): that one lets the *branch* win because nothing else supplies a type; here the `.bugfix.md` directly supplies `Bug`, so the branch merely has to agree (or be silent) rather than override. Any other fragment-type disagreement (a `.bugfix.md` alongside a `.feature.md`, for instance) still hard-conflicts unchanged, on every branch.

No-Test: pinned entirely by plain `#[test]` functions in `xtask/linkage-check/src/work_type.rs`'s `mod tests` (`bugfix_plus_breaking_fragments_on_fix_branch_resolve_to_bug` and `breaking_then_bugfix_fragments_on_fix_branch_resolve_to_bug_production_order` for the fix itself in both fragment orderings, `bugfix_plus_feature_fragments_still_conflict_regression_guard` and `feature_then_bugfix_fragments_still_conflict_guard_regression` proving the carve-out doesn't overcorrect in either order, `bugfix_breaking_feature_three_fragment_permutations_all_conflict` for the 3-fragment case) rather than a `#[spec]`-annotated one — `xtask/**` is a build-time linting tool, not TUI-observable behavior, so a unit test pins this more directly than any `#[spec]` scenario could, matching `468.bugfix.md`'s precedent for the same class of change.
