## Automated background writes no longer land in a stranger's pane after a respawn

Four background code paths resolved their delivery target purely by pane id, with no check that the pane's live occupant was still who the write was originally intended for: a scheduled task's deliver-on-idle reuse delivery, `handle_work_done`'s orchestrator feedback, the daemon's dispatch-result delivery, and the native-seed PTY-injection fallback. If a pane changed hands — via a `clear = true` delegate or a manual respawn — between the moment a delivery was decided and the moment it actually wrote, the write could land in the new occupant's PTY instead of the one it was meant for.

All four now refuse to write when the pane's current occupant took over via a respawn since whatever decision queued the delivery, rather than risk delivering into a stranger's session. A related gap in the native-seed bookkeeping (`set_pending_seed` / `take_pending_seed_fallback`) let a seed silently bind to a stale, exited-but-not-yet-reaped registry entry with no live occupant at all; both now skip exited entries, matching the liveness filter already used elsewhere in the registry.

Issue #492 stays open — see the issue for anything not addressed here.
