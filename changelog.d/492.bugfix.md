## Automated background writes no longer land in a stranger's pane after it changes hands

Four background code paths resolved their delivery target purely by pane id, with no check that the pane's live occupant was still who the write was originally intended for: a scheduled task's deliver-on-idle reuse delivery, `handle_work_done`'s orchestrator feedback, the daemon's dispatch-result delivery, and the native-seed PTY-injection fallback. If a pane's `pane_id_env` was freed and reused by an unrelated agent — the previous occupant closed or crashed and something else spawned onto the same id — between the moment a delivery was decided and the moment it actually wrote, the write could land in the new, unrelated occupant's PTY instead of the one it was meant for.

All four now bind their write to the pane's currently-authorized occupant and verify that identity atomically, immediately before writing (`AgentPtyRegistry::write_and_submit_guarded`), the same identity-guarded primitive already used elsewhere in the registry. That authorized identity is tracked per pane rather than per agent: a pane's first-ever occupant establishes it, and a deliberate respawn (a `clear = true` delegate) updates it to the new successor — so a pane that is legitimately respawned any number of times keeps delivering — while a pane whose id is silently handed to an unrelated agent via a fresh spawn is refused, since nothing updates the record for that case. A related gap in the native-seed bookkeeping (`take_pending_seed_native` / `seed_delivered_native`) let a native `get-seed` pull resolve a stale, exited-but-not-yet-reaped registry entry instead of the live one a seed was actually stashed on; both now skip exited entries, matching the liveness filter `set_pending_seed` / `take_pending_seed_fallback` already used.

Issue #492 stays open — see the issue for anything not addressed here.

No-Test: pinned by five plain `#[tokio::test]` unit/integration tests against the registry and the daemon hook loop, not `#[spec]`-tagged PTY-cast scenarios, so this diff carries no `#[spec]` test delta for `work-type-check` to detect.
