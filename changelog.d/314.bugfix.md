## A renamed orchestration no longer silently rebuilds its tab from stale role data

Rename (or remove) an orchestration in `.dot-agent-deck.toml` while one of its tabs is live, then reattach the TUI to the running daemon. The tab was rebuilt from the role metadata the daemon still held rather than from the project config, and nothing on screen said so — the role cards simply stopped matching the file that had just been edited, and the only trace was a log line at `info`.

The symptom that reaches the user is "the roles in my deck don't match the roles in my toml", with no way to connect it back to the rename. Reattaching is exactly when the config was last read, so it is also the moment the discrepancy is least likely to be attributed to the config.

Reconnect now says so. When the project config loads successfully but carries no orchestration under that tab's name, the deck names the orchestration and states that the cards were rebuilt from the live daemon rather than from the project config — on the status line while the deck is running, so it arrives while the mismatched cards are actually on screen, with the directory appended too (a narrow terminal may truncate it there), and again in full on exit alongside the other session warnings.

Which config wins is unchanged. The synthesised fallback is still used, because it is the correct answer for the case it was built for: a laptop TUI attached to a remote daemon whose working directory does not exist locally. That case is a legitimate reconnect rather than a drift, so it stays silent and is not warned about.
