## `root_checkout_has_live_sibling` now fails closed on an orchestration record with no resolvable cwd

`root_checkout_has_live_sibling`'s per-record loop treated a live orchestration record whose `orchestration_cwd` was `None` exactly like a record that isn't an orchestration member at all — a single `let-else` match silently `continue`d past both shapes, even though the first is a genuine live orchestration this gate simply couldn't resolve a cwd for. An older client's record (`orchestration_cwd` is `#[serde(default)]` on the wire, so a pre-#325 client's record deserializes with it as `None`) could therefore slip past the Nth-concurrent-orchestration clone gate undetected, reintroducing the shared-checkout race the gate exists to refuse.

The loop now distinguishes the two shapes: a record whose `tab_membership` genuinely isn't `Orchestration` still `continue`s as before, but a record that IS an `Orchestration` member with `orchestration_cwd: None` now fails the whole function closed (`Err`) instead of falling through — matching this function's fail-closed contract for every other ambiguous or unresolvable case it already handles.

**User-visible consequence and trade-off:** in a mixed-version deck where an older client's live orchestration is the only one on record, `dispatch` now refuses outright (with a message naming the cause and a remedy) instead of silently isolating into a clone and succeeding. This is a deliberate fail-closed choice, and it is stricter than the pre-fix behavior — but the alternative is exactly the shared-checkout race this gate exists to refuse, so refusing when the gate genuinely cannot resolve a live orchestration's cwd is the correct direction even though it trades away some availability. The refusal is scoped to the `dispatch` CLI path only: PRD fork#544 M2b retired both interactive (`Ctrl+N`) call sites to this gate, so opening an orchestration tab in the TUI cannot reach this `Err` at all.

A second, still-open route to the same cwd-less shape — `sanitize_record_tab_membership` (`src/daemon_client.rs`) clamping the whole `tab_membership` to `None` when an invalid `orchestration_cwd` is rejected — is deliberately out of scope here; it needs `sanitize_record_tab_membership` to preserve more information than a bare `None`, a separate design question left for a fresh follow-up issue.

No-Test: pinned by plain `#[test]`s in `src/ui.rs`'s own `mod tests` (`root_checkout_has_live_sibling_fails_closed_on_orchestration_record_with_no_cwd`, plus the negative-side counterweight `root_checkout_has_live_sibling_ignores_non_orchestration_record`), matching its sibling `root_checkout_has_live_sibling_fails_closed_on_*` tests in the same module — in-crate unit tests, not an e2e `#[spec]`-tagged catalog scenario, so this diff carries no `#[spec]` test delta for `work-type-check` to detect.
