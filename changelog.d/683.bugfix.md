Fixes `xtask/linkage-check/src/work_type.rs`'s `resolve_base` — the read-path sibling issue #669 didn't touch — trusting whatever repository an ambient `GIT_DIR`/`GIT_WORK_TREE` (left behind by, e.g., a `pre-commit` hook or a `git rebase --exec` parent) pointed at instead of the `repo_dir` it was explicitly given, because its `git merge-base HEAD <base>` invocation only set `current_dir` and cleared no environment at all; per issue #683 the original symptom fails loud (a false-FAILED gate run), not silently. It now clears the same `SCRATCH_REPO_GIT_ENV_VARS_TO_CLEAR` list issue #669's `run_git` already carries (with `GIT_CEILING_DIRECTORIES` bound to `repo_dir`'s parent rather than cleared, since `repo_dir` isn't guaranteed to be a repository itself), so `resolve_base` always resolves the base commit against the repository it was actually asked about. This fix is scoped to `resolve_base` only — the diff-reading siblings that consume that base (`current_head_sha`, `current_branch`, `collect_added_fragments`, `changed_files`, `added_files`, `added_diff_text`) are unchanged and still resolve ambiently, so under an ambient `GIT_DIR` the gate now fails loudly on a `bad object` rather than reporting against the wrong repository; the remaining sites are tracked separately, not closed by this fix.

No-Test: this fix is pinned by `resolve_base_leaks_ambient_git_dir` in `xtask/linkage-check/src/work_type.rs` — a real test (RED before this fix, GREEN after), not a documentation gap.
