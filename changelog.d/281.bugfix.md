## `cargo xtask linkage-check` now catches a catalog id two branches independently claimed

`cargo xtask linkage-check` validated `tests/CATALOG.md` catalog-id uniqueness only within the one tree it was run against. Two concurrent PRs each adding a test under the same catalog id (e.g. `orchestration/seed/017`) both passed linkage-check cleanly in isolation, because neither branch's tree contained the other's entry — the collision existed only once both merged, and nothing caught it there either: not linkage-check (one tree at a time), not git (the two entries landed in different files/locations, so the merge itself was clean). This has recurred for real three times (fork issue #281).

A new check compares this branch's newly-added catalog ids — the ones not already present at the merge-base with `origin/main`, i.e. genuinely new rather than inherited — against `origin/main`'s CURRENT tip (not just the merge-base, since `origin/main` may have moved since this branch forked, which is exactly the concurrent-collision case). A colliding id fails the check, naming the id and both locations.

This is best-effort defense-in-depth: it skips gracefully, without failing, whenever `origin/main` cannot be resolved at all — local dev without the remote, or a shallow/PR-only clone — matching how `work_type::resolve_base`'s other callers already treat that case, rather than making linkage-check newly fail in an environment that previously worked.

No-Test: pinned by four `mod real_git` fixture tests in `xtask/linkage-check/src/main.rs` that build real git repositories (`colliding_id_added_independently_on_origin_main_is_reported`, `id_not_present_on_origin_main_passes`, `id_inherited_from_merge_base_is_not_flagged`, `unresolvable_origin_main_skips_gracefully`) — in-crate unit tests, not e2e `#[spec]`-tagged catalog scenarios, so there is no `#[spec]` delta for this gate to see.
