## `cargo xtask linkage-check` now catches a catalog id two branches independently claimed

`cargo xtask linkage-check` validated `tests/CATALOG.md` catalog-id uniqueness only within the one tree it was run against. Two concurrent PRs each adding a test under the same catalog id (e.g. `orchestration/seed/017`) both passed linkage-check cleanly in isolation, because neither branch's tree contained the other's entry — the collision existed only once both merged, and nothing caught it there either: not linkage-check (one tree at a time), not git (the two entries landed in different files/locations, so the merge itself was clean). This has recurred for real three times (fork issue #281).

A new check compares this branch's newly-added catalog ids — the ones not already present at the merge-base with `origin/main`, i.e. genuinely new rather than inherited — against `origin/main`'s CURRENT tip (not just the merge-base, since `origin/main` may have moved since this branch forked, which is exactly the concurrent-collision case), by CONTENT rather than by id alone: an id whose entry text is byte-identical on both sides is treated as inherited (a rebase, cherry-pick, or squash-merge carried it across, not a new claim), and only a genuine content difference under the same id fails the check. A colliding id's failure names the id and `origin/main`'s current tip SHA.

On a GitHub `pull_request` checkout, `HEAD` is a merge commit whose first parent already IS `origin/main`'s tip — a naive merge-base comparison against `HEAD` is therefore always empty there by construction, which shipped a fix-round-1 version of this check that could never actually fail on the one CI path it runs on. The check now detects that exact commit-graph shape and compares the PR branch's own second-parent tip instead, so it can genuinely fire where it is enforced. Two concurrent, still-open PRs still cannot catch each other (each sees only its own tree) — but once the first merges, the second PR's next CI run now correctly detects the collision, which the fix-round-1 version would not have done either.

This is best-effort defense-in-depth: it skips gracefully, without failing, whenever `origin/main` cannot be resolved at all — local dev without the remote, or a shallow/PR-only clone — matching how `work_type::resolve_base`'s other callers already treat that case, rather than making linkage-check newly fail in an environment that previously worked. The success summary now reports whether check 11 ran (naming the `origin/main` SHA compared against and how many newly-added ids it checked) or skipped (naming why), so a clean run is auditable after the fact instead of looking identical to a silently dead check.

No-Test: pinned by `mod real_git` fixture tests in `xtask/linkage-check/src/main.rs` that build real git repositories — including a fixture that reproduces GitHub's `refs/pull/<n>/merge` two-parent shape via `commit-tree` plumbing, and a pair that reproduce a rewritten `origin/main` (this fork's own sync workflow) to prove identical content is treated as inherited while genuinely different content under the same id still fails — in-crate unit tests, not e2e `#[spec]`-tagged catalog scenarios, so there is no `#[spec]` delta for this gate to see.
