## A role prompt could reach an agent twice, or not at all — the delivery path now tells the two apart

When worker-agent-deck starts an agent, it writes that agent's role prompt into the pane and presses return for it. Getting this wrong is not cosmetic: the prompt is the entire instruction the agent starts from, so a prompt that silently never arrives leaves an agent with no remit, and a prompt that arrives twice can mean the work is done twice.

Both were possible. An orchestrator session could open with its role prompt delivered **twice**, concatenated into a single message with no separator between the copies. The cause was a retry that could not tell "the write never landed" from "the write landed but has not been submitted yet". If the return keystroke arrived while the agent was still starting up, the agent treated it as a newline rather than a submit, so the text sat visibly in the composer without dispatching. A couple of seconds later the retry wrote the *same text again* into that same composer, and its return submitted both copies at once. The retry budget is why there were exactly two copies and not more — and because the confirmation check accepted a match on the beginning of the observed text, the doubled prompt still reported as a successful delivery, so nothing flagged it.

The retry now sends only a submit rather than re-sending the prompt text, so a prompt that already reached the pane can no longer be duplicated by the attempt to confirm it. Separately, the mode-seed prompt path — a different path to the same job — was still treating "the bytes were written" as "the prompt was delivered", and was bypassing the startup wait that exists precisely because a return pressed too early does not submit. It now uses the same delivery-and-confirmation handling as the orchestrator path, so a prompt lost on that path is retried instead of silently dropped.

Underneath both, the delivery path now distinguishes its states — written, landed, confirmed, abandoned — in the code itself rather than in comments explaining which sense a particular expression meant. Three near-identical defects had already been fixed in this area, each one an expression that was correct when written and became wrong once the delivery path gained another state; the duplicate prompt above was the fourth. Some smaller consequences of the same confusion are fixed with it: a delivery that *succeeded* no longer ends by logging that it timed out and was abandoned, and a role prompt longer than the deck's internal 200-byte limit can now be confirmed by matching its text, where previously any longer prompt could only ever be confirmed by waiting out the full timeout.

One known gap is deliberately left open, because closing it would break a working setup. Confirming that a prompt was genuinely submitted relies on observing the agent report the text it received. Agents driven through a wrapper — Codex among them — never report that text, so for those agents the deck falls back to watching the agent's status change instead. That fallback is not a real submission signal: the status can change simply because the agent finished starting up, which means it can confirm a delivery that never happened, and it cannot fail. Removing it was tried and made things worse — every Codex delivery then waited out the full 60-second timeout and fired a stray return keystroke into the pane — so the fallback stays until wrapper-driven agents have a signal that can actually report failure. That work is tracked separately.
