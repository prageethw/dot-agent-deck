## Concurrent orchestrations against the same checkout now get an isolated clone, not a shared worktree

Opening a 2nd (or 3rd, or Nth) orchestration against a root checkout that already has a live orchestration running from it used to always provision a `git worktree add` sibling off that same shared `.git` object store — the exact shape of issue #325's original incident, where concurrent git operations from multiple orchestrations against one shared repo corrupted it.

`Action::SpawnPane` now checks, at the point it would otherwise create that worktree, whether the target root checkout already shares its git object store with any live orchestration (compared by `git rev-parse --git-common-dir`, not just by directory path — two orchestrations can each have their own worktree sibling and still share one underlying object store). The 1st orchestration against any given checkout is unaffected: it shares the checkout exactly as before. The 2nd and later concurrent orchestration against that same checkout is now provisioned into its own isolated local clone instead — a fully independent object store, so the orchestrations can no longer race each other's git operations against shared refs and packs.

This check requires a reachable daemon to answer authoritatively. If the daemon can't be reached, the spawn is refused rather than silently falling back to the old shared-worktree behavior as if no other orchestration were live — a down or wedged daemon must not be able to quietly reintroduce the collision this feature exists to prevent.

Model B (the `dispatch` CLI) does not yet have the equivalent live-orchestration check; that is tracked as a follow-up.

An isolated clone is its own independent repository, not a linked worktree of the root checkout — until a future milestone teaches `worktree list`/`worktree reclaim` to discover it too, it will not appear in either, and `reclaim` will not clean it up automatically; remove it by hand once the orchestration using it is done.

The isolated clone's `origin` is now the SOURCE checkout's own origin URL, not the local filesystem path a plain `git clone` would otherwise default it to (which made `git push origin` succeed silently into the root checkout instead of reaching GitHub). If your root checkout has no `origin` configured at all — an ordinary local project with no remote added — the isolated clone gets no `origin` either, matching the source: `gh` and `git push origin` will not work inside it until you add one, same as they would not have worked in the source checkout.
