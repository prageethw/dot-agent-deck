A wrapped agent's boot-provenance `SessionStart` events — the card-surfacing/readiness signals `dot-agent-deck wrap` sends about its own child (fork-time, interface-ready, and output-settled), seconds before that child has done any real work — could prematurely mark a pane's `session.agent_type` as known, before the wrapped agent had identified itself. That defeated the dashboard's "Starting…" readiness gate (`is_untyped_agent` / `is_pending` in `render_session_card`), so a Codex-backed pane whose native hooks hadn't fired yet could fall through to a stale leftover status (e.g. "Thinking") shown indefinitely instead — one of the mechanisms named in issue #730's reported symptom. An earlier round of this fix excluded only the fork-time signal; review found the interface-ready/settled signals re-stamped `agent_type` within a couple of seconds regardless, undoing the fix almost as soon as it took effect — `src/wrap.rs`'s own doc on the output-settled signal calls it "a GUESS" that can fire while a shellenv-heavy launcher (`devbox run codex-big`, issue #730's own production shape) is still canonical, not the exec'd agent. `AppState::apply_event` now excludes all three wrapper boot-provenance origins from resolving `agent_type`, both when updating an existing session and when a wrapper-origin event creates the session in the first place (the daemon-side shape, since placeholder sessions are a TUI-only concept). The daemon's own hook-ingest path (`AgentPtyRegistry::set_agent_type`, the registry's display badge) gets the identical guard, closing a second door the same premature value could re-enter through on a `dot-agent-deck connect` reconnect.

Known, deliberately unaddressed gap: `AppState::seed_hydrated_session`'s reconnect fallback to a caller-DECLARED `agent_type` (a role config's declared identity, PRD #76 M2.13) is unchanged — a documented, pre-existing tradeoff, not a defect this fix closes. For a declared-identity wrapped pane (issue #730's own shape), that value is seeded at spawn time and the new registry guard is upgrade-only, so it does not clean this input the way it does for a genuinely-unresolved-at-spawn pane. This fallback stays safe for a different, independent reason: `seed_hydrated_session` always seeds `expects_agent_report = false`, so the "Starting…" render gate (`is_pending = is_untyped_agent && session.expects_agent_report`) is neutralized for reconnect hydration regardless of what `agent_type` resolves to. That does not clean the value itself — prompt-delivery `agent_ready` checks and `ConfirmationCapability` still see a typed pane after reconnect for an agent that has not genuinely identified itself yet, which is an accepted, pre-existing gap for reconnected panes specifically, not addressed by this fix (and not a change in behavior — reusing `session_start_means_ready` at those call sites to close it is a larger, separate change left out of this round).

This is a unit-level fix at the `apply_event`/registry layer; issue #730 stays open pending a live re-verification against a real reviewer/auditor pane, per the maintainer's own standing instruction on that issue.
