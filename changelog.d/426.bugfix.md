## `hooks_manage::shell_quote_if_needed`'s Windows arm no longer permits command injection through an embedded quote

`shell_quote_if_needed`'s Windows arm (`src/hooks_manage.rs`) wrapped a `binary_path` needing quoting in `"..."` and escaped an embedded `"` to `\"` — but `\` is not a `cmd.exe` quote-escape, so the escaped `"` still counted toward the total quote character count `cmd.exe /C` tallies on the whole line (`cmd /?`: unless the line has exactly two quote characters naming an existing executable, `cmd.exe` strips the leading quote and the *last* quote character anywhere on the line, then re-parses what remains with its normal quote-toggling grammar). A `binary_path` carrying two adjacent embedded `"` characters immediately ahead of injected shell syntax survived that strip as a self-closing empty quoted region, leaving whatever followed — e.g. `& type nul > injected.marker &` — unquoted and reaching `cmd.exe` as a live, separately-executed command. This was flagged twice in PR #423's review and never fixed there: #423 patched the analogous leading-program-token position in `mode_manager::watch_invocation` and `codex_hooks_manage::build_command`, not this one.

The Windows arm now delegates to `crate::platform::shell::escape_cmd_exe_program`, the same function those two call sites already use. It closes this vulnerability class by construction rather than by patching the specific two-quote shape: it never emits a leading quote at all, caret-escaping whitespace and `cmd.exe` metacharacters (including `"` itself) in place instead, so no unescaped quote ever reaches `cmd.exe`'s own quote-parity scan. The Unix arm (`#[cfg(unix)]`, POSIX single-quoting) is untouched — it was already analyzed as safe and is a different code path.

`unquote_if_needed`, used only to recover an already-installed rule's binary path for dedup/coexistence/staleness identification (never for anything that reaches a real shell), gained a matching caret-unescape arm alongside its existing single-/double-quote stripping, so a Windows-written rule still round-trips to its original path for that identification purpose under the new escaping scheme.
