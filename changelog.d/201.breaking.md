## Attach-protocol bump: daemon-side orchestration-name claim (`PROTOCOL_VERSION` 9 → 10)

**New request variants, not additive fields.** `AttachRequest` gains two new operations, `ClaimOrchestrationName { name, pane_id }` and `ReleaseOrchestrationName { pane_id }`, closing fork issue #201: the New-Pane form's uniqueness check (`name_collision()` in `src/ui.rs`) used to refuse a submit only against `live_orchestration_names`, a list captured once at form-open via a single `ListAgents` round-trip. Two New-Pane forms opened close together both read the same stale snapshot, so neither submit was refused even though both would claim the same name — two orchestrator panes could end up with byte-identical titles.

The daemon now holds an atomic, in-memory claim (`AgentPtyRegistry::orchestration_name_claims`, name → owning pane id) checked at the moment a claim is actually taken, not against a snapshot. `ClaimOrchestrationName` is sent from the `Action::SpawnPane` handler right after `TabManager::open_orchestration_tab` returns the real, daemon-minted pane id for the START role — the earliest point that id exists, since `StartAgent` (PRD #365 M2) is what mints it — and becomes the *authoritative* refusal; a lost race rolls back every role pane the spawn just created, the same way a mid-spawn failure already does. `name_collision()`'s existing snapshot-based check stays as an immediate, non-authoritative UI hint. `ReleaseOrchestrationName` frees a claim explicitly (used by the same rollback path); `StopAgent`'s handler also releases a claim automatically when its owning pane closes, so a claim never outlives its orchestrator pane.

Because `AttachRequest` is externally tagged with no `#[serde(other)]` catch-all, an older daemon receiving either new op fails to deserialize the request entirely and returns a "malformed request" error rather than silently ignoring it — the module's documented "new `AttachRequest` variant" bump category, not the additive-optional-field exception. `PROTOCOL_VERSION` bumped from 9 to 10 so a mixed TUI/daemon pairing refuses the handshake outright rather than letting a stale daemon silently skip the new exclusivity check.

Compatibility impact: a TUI and daemon must be on the same `PROTOCOL_VERSION` to interoperate; after upgrading in place, an older still-running daemon and the new TUI fail the handshake until the daemon is restarted, matching this codebase's existing cross-version recovery policy (fork #17 / upstream #405).

Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.
