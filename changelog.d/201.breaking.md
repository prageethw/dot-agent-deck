## Attach-protocol bump: daemon-side orchestration-name claim (`PROTOCOL_VERSION` 9 → 10)

**New request variants, not additive fields — and a claim-before-provisioning redesign.** `AttachRequest` gains three new operations, `ClaimOrchestrationName { name, token }`, `ConfirmOrchestrationClaim { token, pane_id }`, and `ReleaseOrchestrationName { token }`, closing fork issue #201: the New-Pane form's uniqueness check (`name_collision()` in `src/ui.rs`) used to refuse a submit only against `live_orchestration_names`, a list captured once at form-open via a single `ListAgents` round-trip. Two New-Pane forms opened close together both read the same stale snapshot, so neither submit was refused even though both would claim the same name — two orchestrator panes could end up with byte-identical titles.

The daemon now holds an atomic, in-memory claim (`AgentPtyRegistry::orchestration_name_claims`, name → owning holder string) checked at the moment a claim is actually taken, not against a snapshot. Reviewer/auditor feedback on the first round of this bump (claiming with the real, daemon-minted START-role pane id) pushed the claim earlier still: `ClaimOrchestrationName` is now sent by `Action::SpawnPane` at the very top of a New-Pane spawn, before any worktree/clone provisioning and before `open_orchestration_tab`, keyed by a caller-minted opaque `token` rather than a pane id — no real pane id exists that early. A refusal now means nothing is created at all, not a rollback of already-provisioned worktree/pane work. Once provisioning genuinely succeeds and the real START-role pane id is known, `ConfirmOrchestrationClaim` rebinds the token's claim onto that pane id so `StopAgent`'s existing by-pane-id `ReleaseOrchestrationName` still frees it on close; the daemon validates the confirmed `pane_id` against its own live `agent_records()` before accepting the rebind, so a claim can never be rebound onto a pane id nothing minted and left to squat the name for the daemon's lifetime. `name_collision()`'s existing snapshot-based check stays as an immediate, non-authoritative UI hint. `ReleaseOrchestrationName` frees a claim explicitly, addressed by either a pre-confirm token (the `Action::SpawnPane` rollback-after-provisioning-failure path) or a confirmed pane id (`StopAgent`'s automatic release) — the daemon treats `token` as a plain opaque holder key either way.

Because `AttachRequest` is externally tagged with no `#[serde(other)]` catch-all, an older daemon receiving any of these ops — or the renamed `token` field on the two carried over from the first round — fails to deserialize the request entirely and returns a "malformed request" error rather than silently ignoring it or misreading the field: the module's documented "new `AttachRequest` variant" bump category, not the additive-optional-field exception, and a field rename on a struct-variant with no `#[serde(default)]` is bump-worthy the same way. `PROTOCOL_VERSION` bumped from 9 to 10 so a mixed TUI/daemon pairing refuses the handshake outright rather than letting a stale daemon silently skip the new exclusivity check.

Compatibility impact: a TUI and daemon must be on the same `PROTOCOL_VERSION` to interoperate; after upgrading in place, an older still-running daemon and the new TUI fail the handshake until the daemon is restarted, matching this codebase's existing cross-version recovery policy (fork #17 / upstream #405).

Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.
