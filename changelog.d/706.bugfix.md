Fixes both "worker pane whose registry record is gone" recreate legs — `dispatch_one_owned`'s `clear = true` respawn path (issue #606 heritage) and `handle_restart_role_with_state`'s `pane restart` recreate branch (PRD #699) — injecting no `DOT_AGENT_DECK_REGISTRATION_GENERATION`/`DOT_AGENT_DECK_DAEMON_BOOT_ID` into a genuinely recreated worker's environment. Both sites called `register_orchestration_role`, which reserves a fresh generation itself, entirely AFTER the child process was already spawned with only `DOT_AGENT_DECK_PANE_ID` in its env — so a recreated worker's own `work-done` always carried neither variable, and `handle_work_done`'s compound staleness gate (fork issue #358) refused every report a recreated pane ever sent.

Both sites now follow `handle_spawn_role_with_state`'s existing fix-round B1 pattern: `AppState::reserve_registration_generation` reserves the generation and `AppState::daemon_boot_id` reads the boot id under one write-guard acquisition BEFORE the respawn/recreate call, both values are injected into the child's env alongside `DOT_AGENT_DECK_PANE_ID`, and the SAME reserved value is handed to the new `AppState::confirm_orchestration_role` afterward instead of `register_orchestration_role` — closing the desync between what the child's env carries and what `pane_registration_generation` ends up holding. `handle_restart_role_with_state`'s existing detached-`tokio::spawn` shape for its post-respawn registration (needed because the write lock is taken only after this function's own read guard has already been released) is preserved: only the final `confirm_orchestration_role` call moves into the detached task, while the reservation and env injection happen synchronously, before the spawn.

Pinned by `delegate_respawn_recovery::delegate_044_recreate_leg_injects_matching_registration_generation` (`tests/delegate_respawn_recovery.rs`) and `pane_restart::pane_restart_007_recreate_leg_injects_matching_registration_generation` (`tests/pane_restart.rs`) — real tests (RED before this fix, GREEN after), not a documentation gap.
