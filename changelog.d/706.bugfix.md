Fixes both "worker pane whose registry record is gone" recreate legs — `dispatch_one_owned`'s `clear = true` respawn path (issue #606 heritage) and `handle_restart_role_with_state`'s `pane restart` recreate branch (PRD #699) — injecting no `DOT_AGENT_DECK_REGISTRATION_GENERATION`/`DOT_AGENT_DECK_DAEMON_BOOT_ID` into a genuinely recreated worker's environment. Both sites called `register_orchestration_role`, which reserves a fresh generation itself, entirely AFTER the child process was already spawned with only `DOT_AGENT_DECK_PANE_ID` in its env — so a recreated worker's own `work-done` always carried neither variable, and `handle_work_done`'s compound staleness gate (fork issue #358) refused every report a recreated pane ever sent.

Both sites now follow `handle_spawn_role_with_state`'s existing fix-round B1 pattern: `AppState::reserve_registration_generation` reserves the generation and `AppState::daemon_boot_id` reads the boot id under one write-guard acquisition BEFORE the respawn/recreate call, both values are injected into the child's env alongside `DOT_AGENT_DECK_PANE_ID`, and the SAME reserved value is handed to `AppState::confirm_orchestration_role` on the recreate outcome instead of `register_orchestration_role` — closing the desync between what the child's env carries and what `pane_registration_generation` ends up holding for that leg.

**Fix round 2** (reviewer B1/B2, auditor A1/A2/A3): the first round reserved the generation UNCONDITIONALLY, before every respawn/restart attempt, but only reconciled the map on the rare `recreated == true` branch. On the far more common ORDINARY respawn — which replays the previous child's env verbatim and never consumes the reservation — and on the `Err(_)` respawn-failure branch, nothing rolled the eager reservation back, so the map was left one generation ahead of the unchanged child's env on precisely the mainline path this issue exists to keep correct. Both sites now capture the pane's prior `pane_registration_generation` value alongside the reservation and restore it, via the new `AppState::restore_registration_generation`, on both the non-recreate and the error outcomes — all under the same `pane_dispatch_lock` guard the reserve→spawn→branch sequence already holds. `handle_restart_role_with_state`'s `confirm_orchestration_role` call for the recreate outcome also moved from a detached `tokio::spawn` to run synchronously inside that same guard's scope: the read guard that originally motivated detaching it is already dropped well before the guard is even acquired, so the write lock is safe to take inline, and doing so closes the window where a later dispatch/restart on the same pane could confirm a NEWER generation before the detached task ran and then have that task overwrite the map back to the OLDER value.

Pinned by `delegate_respawn_recovery::delegate_044_recreate_leg_injects_matching_registration_generation` / `delegate_045_ordinary_respawn_leg_keeps_registration_generation_in_sync` (`tests/delegate_respawn_recovery.rs`) and `pane_restart::pane_restart_007_recreate_leg_injects_matching_registration_generation` / `pane_restart_008_ordinary_respawn_leg_keeps_registration_generation_in_sync` (`tests/pane_restart.rs`) — real tests (RED before the respective fix, GREEN after), not a documentation gap.

**Fix round 2 confirmation pass, accepted-as-is (not fixed, recorded per rule 25):** `restore_registration_generation`'s `None`-branch (removes the map entry rather than inserting a placeholder) is correct by inspection but has no direct unit test — production callers can't reach it with a `None` prior generation via these two call sites, so both reviewer and auditor judged it low-risk to leave unpinned. The `Err(_)` restore legs at both sites are likewise correct and symmetric with the `recreated == false` arm but have no test forcing that error path (constructing a deterministic respawn failure from an in-process fixture is genuinely awkward); accepted unpinned. Finally, the eager-reservation design leaves a new, transient window (bounded to the respawn's terminate-with-grace timeout, ~9s max) on the ordinary respawn leg where a `work-done` from the still-live outgoing child could be refused where `main` would have accepted it; both roles judged this the safe direction (fail-closed rather than fail-open) and strictly better than round 1's permanent desync, so it is accepted rather than fixed.
