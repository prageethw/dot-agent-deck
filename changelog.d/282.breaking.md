- **Restart both sides together after upgrading past this change** — the shared worktree-attach lock's filename derivation changed from `DefaultHasher` (not specified by std, effectively stable in practice but not guaranteed) to the explicitly stable `fnv1a64`. A daemon or TUI still running a build from before this change and one running a build from after it compute *different* lock filenames for the same worktree and therefore do not contend on the same lock at all — silently reopening the exact worktree-admin-entry corruption fork issue #331 closed, for the duration of any mixed-version window. This is a same-wire, different-meaning break (CLAUDE.md rule 12): nothing in the TUI↔daemon protocol version changed, but the on-disk lock-file naming contract between an old and a new build did. Upgrade by restarting the daemon and any attached TUI onto the matching build rather than rolling one side forward independently.

  Also worth knowing, not itself a compatibility break: the interactive TUI's own worktree-attach (`create_worktree_sync`, on the render/event loop) can now block that loop for up to the same 30s bound the scheduler's async path already used, on a scheduled dispatch contending for the same lock. Bounded and intended, not a regression, but a new source of a brief TUI stall worth knowing about if one is observed.
