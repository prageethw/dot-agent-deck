- **Audited the 2026-08-15 upstream sync for silent commit drops beyond the already-tracked DeliveryPhase loss, and found one more**

  A naive PR-mergeCommit-vs-content-commit SHA-ancestor check is not a meaningful signal on this fork — 0 of 20 sampled PR merge commits, and 156 of 203 of `fork-sync-workflow.md`'s own cited stack-table SHAs, are not ancestors of current `main`, purely because `fork-only` gets fully rebased on every sync. `docs/develop/audit-range-diff.sh` adds a reusable method that matches by patch content via `git range-diff` instead, which survives that churn.

  Running it confirmed the already-documented `619d0f60`/DeliveryPhase loss is correctly tracked and out of scope for this issue, and ruled out two suspected false positives — fork#253's `binary_name()` and the `DelegateResponse` visibility work — via direct symbol search on current `main`. It also found one **new**, previously-undocumented silent loss with the same shape as the DeliveryPhase one, caused by the same sync: PR #268 (fork issue #257, the retry-backoff-override capability) merged cleanly, but its actual content commits — the `send_retry_base()`/`SEND_RETRY_BASE_MS` override and both of its pinning tests — never made it into `main`.

  Issue #257 has been reopened to track restoring that capability; restoring it is a separate follow-up, out of scope for #443 itself, which is audit-only.
