`AttachRequest::ClaimOrchestrationName`'s wire shape is unchanged — no `PROTOCOL_VERSION` bump — but what its `cwd` field *means* for a given orchestration Name changed. It used to be derived as `<repo-basename>-<sanitized Name>`; it is now derived from the (Name-independent) Worktree slug — a typed slug, or an auto-generated `orchestrator-N` when left blank.

If a TUI build from before this change and a TUI build from after it both attach to the *same* daemon and both claim the identical Name in the identical directory, they compute two different `cwd` values for that claim. The daemon's uniqueness check is scoped by `cwd`, so the two claims no longer collide the way they would have under a single-version deployment — two orchestrations that would previously have been refused as a duplicate Name can now coexist silently when the TUI and the daemon (or two TUI instances) are on different sides of this change.

Restart the daemon after upgrading the TUI (or upgrade both together) rather than running a pre-change and a post-change build against the same live daemon.
