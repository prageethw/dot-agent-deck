## Heuristic reclaim of an isolated clone no longer leaves a stale provenance artifact behind

`remove_isolated_clone_dir` (`worktree reclaim --yes`'s removal path for an isolated clone) deleted the clone directory via `remove_dir_all` and stopped, but the M4b provenance artifact that vouches for that path lives entirely outside the directory, under `state_dir()`. A later, unrelated directory created at the same path was then silently vouched for by that stale evidence — fork issue #546's Hazard 1, reachable via the heuristic-reclaim path that PRD fork#544 never touched.

`remove_isolated_clone_dir` now also removes the provenance artifact once the directory removal succeeds, best-effort: a failure to clear the marker is logged rather than propagated, since by that point the clone is already gone from disk and reporting the row as a failed removal (`run_reclaim`'s batch loop classifies a row as "removed" on `Ok` and "kept" on `Err`) would misrepresent an isolated clone that is genuinely gone as one that still needs attention.

This fixes Hazard 1 of #546 only; #546 stays open for Hazard 2.
