## A worktree whose ownership marker failed to write is no longer silently reclaimable

When worker-agent-deck creates a worktree it writes an ownership marker into that worktree's private git directory, which is how `worktree reclaim` later knows the worktree is its own and can remove it without asking. If writing that marker failed — a full disk, a read-only or unwritable git admin directory, an unresolvable git-dir — the failure was discarded: creation reported success, nothing was shown to the user, and the only trace was a line in the daemon log. The worktree then looked foreign to the deck, so `reclaim` would ask about it, and there was no way to tell that apart from a genuinely foreign worktree.

Both creation paths now surface the failure at the moment it happens, which is the one moment the tool has that information. The interactive path adds a non-fatal warning to the status it already shows after creating the worktree, and scheduled issue dispatch reports it as its own event while still going on to spawn the agent — a failed marker is a degradation, not a reason to strand a worktree that was created successfully. The warning names the worktree and says plainly that reclaiming it later will need `--yes`. The `worktree reclaim` help text has been corrected to match: a worktree skips the confirmation only when the deck created it **and** successfully marked it, which is the claim that can silently fail.

The marker write itself is now atomic — written to a temporary file alongside the marker and renamed into place. Previously a write that failed partway through could leave a partially written marker file behind, and because ownership was decided by the marker's presence rather than its contents, that half-written file still counted as proof of ownership. A worktree could therefore be told it needed `--yes` while actually being removable without it. A failed write now leaves the marker either absent or exactly as it was, so the two agree.
