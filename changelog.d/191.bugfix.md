Fixes `resolve_pr_state` (used by worktree reclaim's PR-state check) reporting `NoPr` for a branch that genuinely has an open pull request — it queried only the `origin` remote's `gh --repo` slug, so this fork's documented upstream-first contribution workflow (CLAUDE.md rule 19), where the real PR is opened against `upstream` and `origin` never carries one for that branch at all, was invisible to it.

`resolve_pr_state` now derives a slug for `upstream` the same way it already does for `origin` (`derive_repo_slug_for_remote`, generalized from `derive_repo_slug`) and, only when `origin` resolves to `NoPr`, queries `upstream` as a fallback — matched against `upstream`'s own head-repository owner, never cross-checked against `origin`'s. Any other `origin`-side outcome (a clean match, or an `Unresolvable` ambiguous/hard-failure case) is returned as-is without even consulting `upstream`: `upstream` is consulted only for genuinely new information when `origin` found nothing, never used to override or tiebreak a real `origin`-side answer. A checkout with no `upstream` remote (or one whose URL doesn't parse) behaves exactly as before.

Pinned by `worktree/reclaim/083` (`src/worktree_reclaim.rs`), a real test using a `gh` stub that answers differently per `--repo` slug to prove both remotes are actually queried.
