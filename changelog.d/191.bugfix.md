Fixes `resolve_pr_state` (used by worktree reclaim's PR-state check) reporting `NoPr` for a branch that genuinely has an open or merged pull request — it queried only the `origin` remote's `gh --repo` slug, so this fork's documented upstream-first contribution workflow (CLAUDE.md rule 19), where the real PR is opened against `upstream` and `origin` never carries one for that branch at all, was invisible to it.

`resolve_pr_state` now derives a slug for `upstream` the same way it already does for `origin` (`derive_repo_slug_for_remote`, generalized from `derive_repo_slug`) and, only when `origin` resolves to `NoPr`, queries `upstream` as a fallback. Any other `origin`-side outcome (a clean match, or an `Unresolvable` ambiguous/hard-failure case) is returned as-is without even consulting `upstream`: `upstream` is consulted only for genuinely new information when `origin` found nothing, never used to override or tiebreak a real `origin`-side answer. A checkout with no `upstream` remote (or one whose URL doesn't parse) behaves exactly as before.

The `upstream` query's owner check accepts a PR whose `headRepositoryOwner` matches EITHER `origin`'s own owner or `upstream`'s (`query_pr_state` now takes a set of acceptable owners rather than one) — a PR opened from this fork against `upstream` carries `headRepositoryOwner.login` equal to `origin`'s owner, not `upstream`'s, since the head repository is the fork, not the base; that cross-fork shape is the majority real-world case (6 of 10 sampled upstream PRs), and the original single-owner check reported it as `Unresolvable` rather than `Merged`/`Open`. Still a bounded, two-entry allowlist of owners this checkout is genuinely attached to via its own remotes, never a wildcard — issue #144's original protection is unchanged in kind.

Two security-hardening pieces travel with the correctness fix, since a same-uid actor able to write a worktree's or clone's `.git/config` could otherwise steer the new `upstream` fallback at a repository they control:

- On the linked-worktree path, a `Merged`/`Open` verdict sourced from `upstream` (a third party's repository, unlike the same-uid-trusted `origin`) is only ever trusted when the worktree's own local branch-tip SHA matches the reply's `headRefOid` — closing a same-named-branch collision (this fork's branch names, e.g. `fix/<n>-<slug>`, are shared and predictable) that could otherwise get an unrelated, still-in-use worktree removed. New function `resolve_pr_state_for_linked_worktree`.
- On the isolated-clone paths (`isolated_clone_report`, `remove_isolated_clone_dir`), the `upstream` fallback is never attempted at all — those paths' existing slug-equality guard (fork#533) only ever validated the candidate's `origin`, and validated nothing about a second `upstream` remote the same untrusted candidate could plant, which would otherwise let a forged `upstream`-sourced `Merged` verdict launder into an automatic deletion. New function `resolve_pr_state_for_isolated_clone`, which queries `origin` only and never derives an `upstream` slug in the first place.
