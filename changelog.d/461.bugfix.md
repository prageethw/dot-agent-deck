## `work-done`'s Registration-Context Reader Gains Fast-Tier Test Coverage

The `work-done` CLI handler's registration-generation/daemon-boot-id reader — the fail-closed guard fork issue #358 added so a report is refused at delivery rather than silently accepted when it doesn't match the pane's current registration — is now a small, pure `read_registration_context` function instead of inline logic, with unit tests pinning its parse-and-fallback behavior (present, missing, and unparseable-generation cases) in the fast tier. Previously the only e2e coverage of this logic, in the non-blocking `e2e` tier, was `orchestration/work-done/004`'s happy path (both env vars present and valid) — the missing and unparseable fallbacks — the `(0, "")` values that make such a report **refused** at delivery rather than accepted — were asserted by nothing, so a regression in those constants (an `unwrap_or(1)`, say) could have silently turned the guard fail-open with every check staying green. This is a pure extraction — no behavior change for real callers.

No-Test: pinned by three plain `#[test]`s in `src/main.rs`'s own `mod tests` (`read_registration_context_reads_both_vars_when_present` and its missing/unparseable siblings) — in-crate unit tests, not e2e `#[spec]`-tagged catalog scenarios, so there is no `#[spec]` delta for this gate to see.
