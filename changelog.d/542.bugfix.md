Fixes the badge/"expects a report" gap for a `devbox`-wrapped agent launch (this fork's own `devbox run claude-sonnet-devbox`-shaped orchestration role commands): `AgentType::from_command_including_devbox` compared its first token against the literal string `"devbox"` instead of resolving its basename the way `detect_from_tokens` does, so an absolute-path or `env`/`sudo`-prefixed devbox invocation went unrecognized. It also had no shell-launcher recursion at all, so a `sh -c 'devbox run claude-sonnet-devbox'`-shaped invocation fell through to "No agent" too; it now recurses into the script argument the same way `detect_from_tokens` already does for ordinary (non-devbox) commands, decrementing the same shell-launcher recursion budget so a deeply nested shell hop still terminates safely. Separately, three restore-path call sites in `src/ui.rs` (the plain single-pane restore, and both mode-restore fallback arms) still seeded a placeholder session via the plain `insert_placeholder_session` constructor instead of `insert_placeholder_session_awaiting_report`, so a restored pane whose saved command was a devbox-wrapped recognized agent showed "No agent" instead of "Starting…" until its first hook event arrived.

No-Test: this fix is pinned by `from_command_including_devbox_recognizes_devbox_run` in `src/event.rs` (including its `sh -c 'devbox run …'` shell-launcher-hop assertion) and `restore_021_devbox_wrapped_restore_shows_starting_not_no_agent` in `tests/e2e_session_restore.rs` (the latter already carries `#[spec("session/restore/021")]`) — real tests (RED before this fix, GREEN after), not a documentation gap.
