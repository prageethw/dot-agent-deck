## A bare-CR retry no longer races a genuine late confirmation on a reporting-capable pane

Issue #422 item 2: when an automatic orchestrator prompt was written into a reporting-capable pane (Codex, and any other producer that can report a submitted prompt back), the deck retried with a bare carriage return on an escalating 0.5/1/2/4/8/15s schedule while it waited for the agent to confirm the prompt was actually submitted. The issue's own measurements found a genuine Codex TEXT confirmation can legitimately take as long as 8.45s to arrive after the write — well past the old schedule's first three retries at 0.5s, 1s and 2s. Those retries fired before the confirmation had a realistic chance to land, resubmitting into a pane whose genuine confirmation was already on its way: a false-positive bare-CR retry racing (and, in the worst case, duplicating) a delivery that did not need one.

`unconfirmed_retry_delay`'s first retry is now 10s — comfortably past the measured 8.45s worst case — capped at 15s for every retry after that, replacing the old escalating schedule. Nothing resubmits into the pane until a genuine confirmation has had a realistic chance to arrive; the whole automatic-prompt deadline is still covered in single-digit attempts (5 submissions now cover it, versus 8 before). This lowers the number of automatic writes made into a pane while a delivery is still in flight, which is the safer direction for every guard downstream of a write (the user-draft guards, the delivery ledger's fingerprint check). The one accepted trade is latency for the case the retry exists to recover: a producer that arms very late, or a wrapper that swallows the submit CR and leaves the prompt sitting unsubmitted in the pane, now waits up to 10s for the first recovery attempt instead of 0.5s.

This affects only the deck's own retry timing, both in the TUI's orchestrator-prompt delivery (`src/ui.rs`) and the daemon's detached confirmation loop (`confirm_prompt_delivery`, `src/spawn.rs`), which share the same constant. It answers CLAUDE.md rule 12's cross-version question explicitly: no wire-shape moved and no field changed meaning, so there is no `PROTOCOL_VERSION` bump and no accompanying `.breaking.md` fragment. An older daemon paired with a newer TUI (or vice versa) simply retries on a different clock — nothing about what is sent over the wire or how it is interpreted changes.
