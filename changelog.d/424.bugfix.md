Fixed an orchestration role occasionally showing as working when the agent never actually received its starting prompt. The daemon sometimes couldn't tell whether the bytes it wrote for a spawn-time role prompt had truly reached the agent's input — a CR that landed as a plain newline in the agent's own input box, for instance, looks identical to a real submit from the daemon's side. Previously "the write went through" was treated as good enough, so the pane sat there showing as working while the agent itself never saw a prompt at all.

The daemon now waits for independent confirmation that the prompt was actually submitted before calling a role delivered, and retries once if that confirmation doesn't show up in time. Confirmation is checked against the exact agent session the prompt was written to — never a different session that happens to be sharing the same pane, such as after an agent crash and reload — and a stale or unrelated busy state that predates our write no longer counts on its own; the daemon also recognizes the agent's own submitted text matching what was sent, so activity that merely looks similar (an ordinary tool call, for instance) can't be mistaken for a real submission. If the daemon still can't get independent confirmation before giving up, the retry itself is what fixes the original bug this PRD closed: earlier builds silently wrote the retried prompt to a cache and never resent it, so the retry never really happened. It now reaches the agent for real. And if a prompt genuinely landed but confirmation never arrived in the time allotted, the daemon now reports it as delivered-but-unconfirmed with a warning, rather than incorrectly claiming it was never delivered at all — unless the failure itself is evidence the target session was replaced, in which case it's reported as not delivered instead.
