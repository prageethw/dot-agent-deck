## Fixed a macOS-only test-harness failure blocking real-Codex e2e coverage

`import_codex_credentials` (the e2e test harness's helper for setting up a real Codex agent's trust) wrote Codex's project-trust entry keyed by the harness's own temp-root path as constructed, uncanonicalized. On macOS, `/var` is a symlink to `/private/var`, so Codex's own subprocess resolved its working directory through that symlink at runtime and looked up trust for `/private/var/tmp/...` while the harness had written the entry under `/var/tmp/...` — an exact-string miss that made Codex fall back to its interactive "Do you trust this directory?" prompt, which a synthetic PTY test can never answer, hanging the test to its boot-readiness deadline.

The trust-writing half of `import_codex_credentials` is now `write_codex_project_trust`, a small extracted helper that canonicalizes the project path before writing it into `config.toml`'s `[projects."..."]` key, so the key matches whatever path Codex's subprocess actually resolves to.

This is test-harness-only — no product code changed, and no user-facing behavior changed.

No-Test: this *is* the test fix, pinned by `codex_project_trust_canonicalizes_symlinked_project_path` (`tests/codex_trust_fixture.rs`), a plain `#[test]` rather than a `#[spec]`-annotated one since it's a harness meta-test (no production code path renders this behavior) — same category as the existing `harness_isolation.rs::harness_clears_inherited_deck_endpoints` test.
