**New: `dot-agent-deck worktree list` shows an OWNER column, and `worktree list --mine` lists only the worktrees the calling orchestration created.** The human table now names which orchestration created each worktree (a dash for one predating this feature, or one worker-agent-deck did not create); `--json` already carried the field. Every pane of an orchestration that **created a worktree** now carries a `DOT_AGENT_DECK_WORKTREE_OWNER` environment variable — the exact identity stamped into its own worktrees' `created-by:` markers — mirroring the existing `DOT_AGENT_DECK_PANE_ID` (which, unlike this variable, really is set in every orchestration pane), so `worktree list --mine` can match "mine" by comparing two plain strings, with no daemon round-trip and no dependency on in-memory state (it still works immediately after a daemon restart). The identity is persisted in the saved session, so a tab that is closed and reopened restores with the SAME identity, and `--mine` still matches its earlier worktrees. Two cases restore with no identity instead: a tab whose session snapshot predates this fix — saved before the identity was captured, or before this field existed at all — and a tab reattached to a still-running ("warm") daemon, whose metadata is rebuilt without the saved identity, so a session saved in that state also restores with none. In both cases `--mine` then fails loudly for that tab alone rather than silently listing everything or nothing. Run outside an orchestration pane, in a pane whose orchestration created no worktree, or with the identity set to the `orchestration:unknown` sentinel a nameless orchestration falls back to, `--mine` fails loudly (non-zero exit, names what is missing) rather than silently listing everything or nothing — a wrong answer here would hand one orchestration another's worktrees, the fork #74 collision this feature exists to prevent. One deployment note: an orchestration with no typed Name that also creates a worktree stamps the `orchestration:unknown` sentinel, which `--mine` always refuses, superseding the `orchestration:<config_name>` fallback fork#192's M2.1 shipped in v0.37.0 — a worktree marked by that earlier fallback keeps showing its old string in the OWNER column while the same (now-nameless) orchestration identifies as the sentinel, so `--mine` refuses it. Loud and safe, but worth knowing about before it surprises anyone.
