Windows watch-pane invocations (`dot-agent-deck watch --interval N <command>`, spawned into a `watch = true` mode pane or reactive rule) now quote the executable and command positions with position-aware, `cmd.exe`-safe escaping instead of reproducing `main`'s pre-#157 `{:?}`-Debug-escaped format. `{:?}` is Rust `Debug` escaping, not a `cmd.exe` grammar: `cmd.exe` does not treat a backslash before an embedded `"` as an escape, so a watch command containing `" & <anything> & rem "` closed the quoted word early and ran the injected tail as its own, unquoted command (finding A1 on fork PR #277) — and the executable token, emitted bare, was never locatable at a path containing a space either (issue #157's original executable-quoting regression, still present on Windows only).

Any control character inside `command` — not only `\r`/`\n` — is now replaced with a space before either quoting pass runs, rather than left raw (`\t` is exempt, since both quoting functions already caret-escape it deliberately). No caret encoding can neutralize a raw control character the way it neutralizes every other `cmd.exe` metacharacter — on the persistent-watch-pane path the Windows console's cooked-mode line editor consumes several as *editing commands* before `cmd.exe`'s own grammar is ever consulted (a newline submits the current input; `ESC` clears the entire typed buffer, up to and including the program token; `BS`/`DEL` delete backwards; `ETX` cancels the line), and on the `/C <string>` path `cmd.exe` treats an embedded newline as a statement separator the same way a batch file would — so a `[[modes.panes]]` `command` value containing a real newline, or an `ESC`/`BS`/`ETX` byte (all legal TOML), previously either ran everything after it as its own, separate `cmd.exe` command, or — for `ESC` on the typed-PTY path — let `cmd.exe` run an attacker-chosen program name outright. This was a regression against `main`, whose old `{:?}`-Debug-quoted format at least kept the mangled content on one line and never emitted a raw control byte (PR #423 review findings B1 and C1).

`escape_cmd_exe_program`'s escape set also now includes `;` and `=`, `cmd.exe`'s other two command-line delimiters besides `,` (already escaped) that are legal in NTFS path components — a deck installed under a path containing either previously split the program token the same way an unescaped space did in #157. Both functions' doc comments now state plainly that `%` and `!` are only incidentally, not actually, neutralized (delayed expansion still reaches `!VAR!`; an undefined `%VAR%` still mangles under batch-file rules), per this issue's explicit request not to leave that implied.
