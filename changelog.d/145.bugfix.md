- **The hook CLI no longer reads an unbounded stdin payload**

  `read_stdin` read the incoming hook event to completion with no size cap, unlike the reply path a few hundred lines below it in the same file, which has been carefully bounded since fork issues #99/#101/#125. A wedged or misbehaving agent harness writing an enormous hook payload would have the short-lived hook process allocate it in full before rejecting it at the JSON-parse stage. The read is now capped (reusing `daemon_protocol::MAX_FRAME_LEN`, 16 MiB — sized for a tool's whole argument, e.g. a `Write`/`Edit` call's full file content, rather than the reply path's much smaller seed-sized cap) and a payload over the cap is rejected outright rather than truncated and handed on to the parser, which could otherwise turn a corrupted payload into one that happens to still parse.

No-Test: covered by new plain `#[test]`s (`read_bounded_accepts_payload_at_cap`, `read_bounded_rejects_payload_over_cap`, `read_bounded_rejects_payload_far_over_cap`, `read_bounded_empty_input_is_empty_string`) in `src/hook.rs`'s `mod tests`, not `#[spec]`-annotated since this is an internal parsing guard with no user-visible scenario to narrate.
