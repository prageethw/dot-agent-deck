- **The hook CLI no longer reads an unbounded stdin payload**

  `read_stdin` read the incoming hook event to completion with no size cap, unlike the reply path a few hundred lines below it in the same file, which has been carefully bounded since fork issues #99/#101/#125. A wedged or misbehaving agent harness writing an enormous hook payload would have the short-lived hook process allocate it in full before rejecting it at the JSON-parse stage. The hook **CLI's** read is now capped (reusing `daemon_protocol::MAX_FRAME_LEN`'s literal, 16 MiB — sized for a tool's whole argument, e.g. a `Write`/`Edit` call's full file content, rather than the reply path's much smaller seed-sized cap; the reuse is of the number only, not of that constant's framed-transport rationale, since the hook path is newline-delimited, not framed) and a payload over the cap is rejected outright rather than truncated and handed on to the parser, which could otherwise turn a corrupted payload into one that happens to still parse.

  This closes the unbounded read in the short-lived, single-event hook CLI process only. The **daemon's** hook-socket reader (`src/daemon.rs`'s `BufReader::lines()`) is a separate, still-unbounded read in a long-lived, multiplexed process and is not touched by this change — tracked as its own follow-up in #393.

  #145's suggested fix also asked to "fail with a clear error rather than truncating silently" on an over-cap payload. That third clause is declined here, deliberately: `src/hook.rs` calls no `tracing`/`eprintln!` anywhere, and every other failure on this path (malformed JSON, an unmapped event type, a failed socket send) already returns silently, so adding a diagnostic only for the over-cap case would be a new pattern in an otherwise-silent file rather than an extension of its existing one. An over-cap hook payload is dropped with no trace on either side as a result.

No-Test: covered by new plain `#[test]`s (`read_bounded_accepts_payload_at_cap`, `read_bounded_rejects_payload_over_cap`, `read_bounded_rejects_payload_far_over_cap`, `read_bounded_empty_input_is_empty_string`) in `src/hook.rs`'s `mod tests`, not `#[spec]`-annotated since this is an internal parsing guard with no user-visible scenario to narrate.
