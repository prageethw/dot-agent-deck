`dot-agent-deck get-seed` no longer lets a misbehaving daemon grow its reply buffer without limit. The previous release bounded how *long* the call would wait for a reply line — a total-operation deadline, so a peer that dribbles a byte at a time can no longer keep the read alive forever — but it did not bound how *large* that reply could get. A peer that flooded rather than dribbled could still drive the buffer up freely until the 5 second deadline expired.

A single reply line is now capped at 1 MiB, and busting the cap folds into the same "no seed" outcome as any other non-answer, so the pane falls back to the PTY-injection safety net exactly as it already did for a timeout. The number is chosen with real headroom: the only thing this reply carries is a seed prompt, and the daemon already clamps stored prompts to 64 KiB, so a legitimate seed is never anywhere near the cap and cannot be silently truncated by it.

Like the timeout before it, this is defence-in-depth against a local same-user denial of service rather than a fix for anything observed in use — the hook socket's trust boundary means a wedged or buggy daemon is enough to trigger it, not a remote attacker. The matching bound on the daemon's own hook ingestion is tracked separately.
