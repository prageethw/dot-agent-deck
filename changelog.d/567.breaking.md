## `Commands::Delegate` now carries a registration-generation/boot-id compound key, and a mismatch refuses the delegate

**Behavioural change, no wire-shape change.** Fork issue #358 gave `work-done` a fail-closed guard: a completion report is refused at delivery when its `(generation, daemon_boot_id)` compound key no longer matches the sending pane's CURRENT registration — the pane was re-registered (worktree teardown + reuse) or the daemon restarted since the signal was produced. `Commands::Delegate`'s own signal type (`DelegateSignal`) carried no such fields at all, so the same class of stale-signal problem #358 closed for `work-done` was entirely unprotected on the `delegate` path (fork issue #567).

`DelegateSignal` gains two new fields, `generation: u64` and `daemon_boot_id: String`, both `#[serde(default)]` — additive, so no `PROTOCOL_VERSION` bump. `handle_delegate_with_state` now refuses a `Delegate` signal whose compound key doesn't match the SENDING (orchestrator) pane's current registration, mirroring `handle_work_done`'s guard and its `(0, "")`-can't-match reasoning exactly: an old CLI build that doesn't send these fields defaults to `generation: 0` / `daemon_boot_id: ""`, which never matches a real registration (those start at generation `1`, and no real `daemon_boot_id` is ever minted as the empty string), so an old CLI talking to a post-#567 daemon has its delegate refused rather than silently misrouted into whatever now occupies that pane_id.

No `PROTOCOL_VERSION` bump is included: the wire shape itself is additive (both new fields are optional on the same message). This is a semantic break behind a stable wire, per CLAUDE.md rule 12 — a `delegate` from a pane the daemon has since moved on from (or from an old CLI/daemon on either side of an upgrade that doesn't populate these fields) now means "refuse" where it previously meant "route it anyway, whatever currently holds that pane_id".

**What this guard covers:** a stale `Delegate` signal from a pane whose registration has since moved on — daemon restart, or worktree teardown + pane_id reuse by a different orchestration. **What it does not cover:** it does not replace `refuse_unless_orchestrator_caller` (the existing pane-identity/orchestration-membership check, which still runs first and independently), and it says nothing about the routing of the delegate's TARGET roles — only about whether the SENDER's own registration is still current.

**Recovery:** any client that relied on a `delegate` succeeding from a pane whose registration has moved on (or that sends no generation/boot-id fields at all) must upgrade to a build that populates `DelegateSignal::generation`/`daemon_boot_id` from its own `DOT_AGENT_DECK_REGISTRATION_GENERATION`/`DOT_AGENT_DECK_DAEMON_BOOT_ID` environment (the same values `work-done` already reads, injected at spawn time), or its delegates to that pane will be refused.
