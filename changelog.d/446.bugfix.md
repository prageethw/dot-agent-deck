- **The dashboard grid no longer hides cards to fit — it divides evenly and shows every one**
  An orchestration tab with 7 roles painted only 5 cards, the other two reachable only by scrolling — not a cosmetic issue but an observability defect, since the tab's aggregated status can report "working" while the card naming *which* role is working sits scrolled out of view. The root cause: `fit_grid` searched column count and card density jointly, but density bottomed out at a fixed 6-row `Compact` card height, so any column narrow enough to force a single column (common on a split dashboard/panes layout) capped visible rows regardless of how many roles existed.
  The grid now falls back to even division whenever the existing density search can't fit every card: columns are maximised (`max_cols_for_width`), then the available height divides across all rows as evenly as possible (`even_row_heights` — first-remainder rows get one extra row so the heights sum to exactly the available space), down to a floor of 1 row per card. Card rendering is tiered by the height it actually gets: 3+ rows renders as today; 2 rows drops to a top-border-only card; 1 row drops the border entirely, showing just the role name and status on one line. Role name and status are the two things that survive every degradation — everything else (prompts, tool lines, `Dir:`) gives way first. This only engages when cards would otherwise be truncated; a layout that already fits is untouched.
  One existing test guard is deliberately inverted: `layout_001_seven_decks_fit_single_column`'s assertion that "scrolling must still engage" for a large deck count now asserts the opposite — decks keep dividing evenly and all render, since hiding cards silently is exactly the defect this PRD fixes. Issue #446 stays open; the hydration-drift defect (wrong role names, not a short count) and the reviewer-pane blank-status issue are explicitly out of scope and tracked separately.
