## A failed multi-role dispatch no longer force-removes a worktree a live sibling role is still rooted in

When one role of a multi-role orchestration failed to spawn, the dispatch rollback path force-removed the worktree it had just created — even when an earlier role in the same orchestration was already a live PTY child rooted in that same worktree, holding possibly-uncommitted work. The worktree, its branch, and the registry entry were all destroyed out from under the still-running sibling.

The rollback path now checks whether any live agent is still rooted in the worktree before removing anything (issue #469). If one is, the worktree, its branch, and the registry entry are all left in place, and the failure message names the reason and states the remedy: close the remaining role panes to release it automatically via the existing tab-close cleanup. Nothing changes for a single-role dispatch, or for a multi-role dispatch where no sibling is left live — those are still cleaned up immediately.

`issue_dispatch_run::remove_worktree`'s own logging (the tab-close / scheduled cleanup path) also now records who performed each removal, kept, or failed removal — not only successful ones as before — and the wording of its success log message no longer wrongly claims every removal happened "on tab close" when the spawn-rollback path uses the same function for a different reason.
