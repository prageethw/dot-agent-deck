## A paned write-and-submit with no caller-supplied agent identity is now refused, not delivered pane-only

**Behavioural change, no wire-shape change.** A `Live` paned target previously accepted a write-and-submit that carried no `expected_agent_id` at all by degrading to pane-only authorization — deliver by pane id alone, with no confirmation of which agent actually holds that pane. That degrade path was a deliberate cross-version fail-safe for legacy / non-guarded clients (see the comment at `src/daemon_protocol.rs` around the `WriteAndSubmitExtras` decode). It is now closed: a `Live` target with `expected_agent_id: None` returns `SendResult::NoLiveTarget` and writes nothing, the same refusal already used for a non-live target.

No `PROTOCOL_VERSION` bump is included: the wire shape itself did not change (`expected_agent_id` was already an optional field on the same payload). This is a semantic break behind a stable wire, per CLAUDE.md rule 12 — an absent identity now means "refuse" where it previously meant "degrade and proceed".

**Recovery:** any client that relied on the old no-identity write path must now supply `expected_agent_id` on `WriteAndSubmit` requests to a paned target, or its writes to that target will be refused with `NoLiveTarget`.

## A paned write-and-submit with no caller-supplied session generation is now refused on an attached pane that already has a conversation

**Behavioural change, no wire-shape change.** A `Live` paned target's delivery-time re-validation previously performed its session-generation check only when the caller supplied `expected_session_id`; a caller that supplied `expected_session_id: None` skipped that check entirely and could deliver keyed by agent identity alone, with no confirmation of which conversation generation actually received it. That degrade path is now closed for the case that matters: on an attached (live-interactive) pane that already has a recorded hook session or has closed at least one prior generation, a `None` `expected_session_id` is now refused (`SendResult::Stale`), the same "refused too" treatment already applied when the caller names a session that no longer matches.

**This is the more significant of the two axes fixed by this PR: unlike the agent-id axis above, this one does not self-heal.** `SendResult::Stale` is non-terminal and does not advance `delivery.attempts`, so a caller that keeps retrying with the same unnamed session would otherwise be refused identically forever.

**A pane with no recorded hook session and no closed generation at all is deliberately unaffected — this is what makes the fallback below still work.** The deck's own spawn-time role-prompt delivery (`src/ui.rs`) legitimately writes with `expected_session_id: None` as a 10-second fallback for agent types (e.g. opencode-style wrappers) that never emit a `SessionStart` hook at all. A pane that has never had a conversation has nothing to fail to name, so it is let through exactly as before — only a pane that already has a conversation it failed to correctly name is now refused.

No `PROTOCOL_VERSION` bump is included: the wire shape itself did not change (`expected_session_id` was already an optional field on the same payload). This is a semantic break behind a stable wire, per CLAUDE.md rule 12.

**Recovery:** any client that relied on delivering to an attached, already-conversing pane with no `expected_session_id` must now supply the pane's current hook session id, or its writes will be refused with `Stale`. A client whose target pane has no hook history yet is unaffected.
