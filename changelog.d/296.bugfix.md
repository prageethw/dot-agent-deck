## The drift-check workflow could never report drift when there was any

The `drift-check` workflow measures how far `main` has drifted from the fork's curated branch and reports the oldest un-curated commit's age. It found that age by piping `git log --reverse` into `head -1` to grab the first line of the reversed log. `head` exits as soon as it has its one line, closing the pipe while `git log` still has commits left to write — `git log` receives SIGPIPE and dies with exit code 141. The step runs under `set -uo pipefail` and GitHub's default `shell: /usr/bin/bash -e {0}`, so that 141 aborted the whole step with `Process completed with exit code 141`, and nothing after the crash — including the summary drift-check exists to produce — ever ran.

This was deterministic, not a flake: the crashing line only runs when the commit count is greater than zero, which is exactly the case the workflow exists to report. It could only ever succeed when drift was precisely zero.

The pipeline now reads `git log | tail -1` instead — dropping `--reverse` and taking the *last* line of the log yields the same oldest commit, but `tail` reads to EOF, so `git log` is never SIGPIPEd and no output is suppressed.
