## Isolated-clone ownership attribution is no longer inheritable, forgeable, or blind from inside another clone

`worktree list`/`worktree reclaim`'s isolated-clone ownership check (`owned`/`owner`/`owner_kind`, added in the previous fragment on this issue) relied on a persistent attach-lock artifact the deck writes and never removes. Two ways a same-uid actor could exploit that persistence to get a directory attributed to someone else's identity are now closed: a forged directory occupying a path whose lock artifact was left behind by a since-removed, unrelated linked worktree, and a directory pre-planted at a dispatch's deterministic target path before the dispatch itself acquires the lock and then fails as already-claimed. Neither can inherit ownership attribution anymore.

`worktree list --mine` also now correctly finds sibling isolated clones owned by the same identity when run from inside another isolated clone, not just from the root checkout — the case that matters most, since a concurrent orchestration issuing this command is, by definition, running from inside one.

The mechanism behind all of this moved twice in the course of closing it out. It first moved into a dedicated provenance artifact written directly inside each clone's own `.git` directory — which closed the two inheritance paths above, but reopened a cheaper variant of the original attribution forgery: a same-uid attacker able to plant a sibling directory at all could plant that artifact too, with nothing beyond a `touch`. The artifact now lives outside every clone entirely, in the deck's own per-user state directory, keyed to the clone's canonical path — a location no candidate directory, genuine or forged, ever controls. This is the same trust boundary the deck's linked-worktree ownership check has always relied on, extended to isolated clones for the first time without the shortcut that briefly undid it.
