- **The scheduled `issue_dispatch` worktree attach no longer races itself**
  Fork #331 closed the interactive TUI's own worktree-attach race by taking an exclusive lock around the whole probe→add attempt, but explicitly left the unattended `issue_dispatch` scheduler's separate, asynchronous `create_worktree` untouched — that path had no lock at all. Two scheduled dispatches attaching the same existing branch (or a scheduled dispatch racing an interactive attach) could both report success while git registered two administrative entries for one on-disk worktree, or leave one racer's `git worktree add` silently overwritten by the other's cleanup.
  `create_worktree` now takes the same lock, keyed the same way (`worktree_attach_lock_path`, anchored on the shared clone's real `--git-common-dir` rather than the branch name), so a scheduled dispatch and an interactive attach contend on the identical key instead of each locking a key the other never touches. Acquisition is bounded against the same 30s `WORKTREE_GIT_TIMEOUT` the surrounding `git` calls already use, via a new bounded-async primitive (`platform::lock::acquire_spawn_lock_bounded`) rather than an external `tokio::time::timeout` around the unbounded one — the bound lives inside the primitive so a timeout genuinely terminates the wait instead of merely abandoning it, refusing with an error rather than blocking a scheduler tick indefinitely if the lock cannot be granted in time.
  Issue #282 is now closed for both paths.
