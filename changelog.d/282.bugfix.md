## Concurrent orchestrations no longer corrupt each other's git state

Running several orchestrations at once shares one git repository between them — one worktree registry, one object store — and nothing scoped either. A worktree isolates your working tree; it does not isolate the two things underneath it, and both were writable by everything on the machine. Two failures came out of that, and neither announced itself.

**Two orchestrations creating a worktree on the same existing branch could both succeed.** Git serialises the creation of a *new* branch on its own ref lock, so that case was always safe. Attaching an *existing* branch was not: both processes exited 0, and git registered two separate administrative entries pointing at one directory. Nothing downstream had any reason to look, because both callers were told they had created it.

The same race had a second shape that only appeared once the first was measured properly. A caller whose own attempt timed out would clean up after itself — but with nothing serialising the two, that cleanup could remove the *other* caller's just-completed registration instead, leaving a worktree that had been reported as created with nothing registered for it. Both shapes are closed the same way: an attach now takes a lock covering the whole attempt, including any cleanup it triggers, so two attempts on one directory can no longer interleave at all. The loser is told the worktree is already claimed, which is what every caller already believed was happening.

**A shallow fetch anywhere made the whole repository shallow, for every worktree at once.** The marker git writes for that lives beside the object store rather than in the worktree that caused it, so one truncated fetch silently truncated history for every orchestration on the machine. Nothing reported an error. Logs read normally, status was clean, and branches still resolved to the commits you expected. The only symptom was that merges and rebases against the upstream remote began failing as though the histories were unrelated — which reads like a misconfigured remote, not a truncated one, and sends you looking in the wrong place. `worktree list` now says so plainly when it sees a shallow clone, explains that every worktree sharing it is affected rather than just whoever ran the fetch, and gives the command that repairs it.

Neither failure was reachable by a single orchestration working alone, which is why both survived: each needs two, and their symptoms surface far away in time from their cause.
