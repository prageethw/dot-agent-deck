## Concurrent orchestrations no longer corrupt each other's git state

Running several orchestrations at once shares one git repository between them — one worktree registry, one object store — and nothing scoped either. A worktree isolates your working tree; it does not isolate the two things underneath it, and both were writable by everything on the machine. Three failures came out of that, and none of them announced itself.

**Two orchestrations creating a worktree on the same existing branch could both succeed.** Git serialises `worktree add -b` on its own ref lock, so creating a *new* branch was always safe. Attaching an *existing* one was not: both processes exited 0, and git registered two separate administrative entries pointing at one directory. Nothing downstream had any reason to look. That path now takes a lock, so one caller creates the worktree and the other is told the worktree is already claimed — which is what it always believed was happening.

**A shallow fetch anywhere made the whole repository shallow, for every worktree at once.** The marker git writes for that lives beside the object store rather than in the worktree that caused it, so one truncated fetch silently truncated history for every orchestration on the machine. Nothing reported an error. Logs read normally, status was clean, and branches still resolved to the commits you expected. The only symptom was that merges and rebases against the upstream remote began failing as though the histories were unrelated — which reads like a misconfigured remote, not a truncated one, and sends you looking in the wrong place. The deck now detects this and says what happened and how to repair it, rather than leaving you to infer it from a merge error.

**A worktree could be removed while another orchestration was working in it.** Removal went through git directly, which has no notion of who created a worktree, so nothing consulted the ownership marker the deck already writes — and a worktree could vanish under an agent mid-task. Removal now has a deck command that reads that marker and refuses to remove a worktree belonging to someone else, naming the owner. The reclaim command's own rules are unchanged; this covers the removals people do by hand.

None of these were reachable by a single orchestration working alone, which is why they survived: every one needs two, and their symptoms surface far away in time from their cause.
