- **The scheduled `issue_dispatch` worktree attach no longer races itself**
  Fork #331 closed the interactive TUI's own worktree-attach race by taking an exclusive lock around the whole probe→add attempt, but explicitly left the unattended `issue_dispatch` scheduler's separate, asynchronous `create_worktree` untouched — that path had no lock at all. Two scheduled dispatches attaching the same existing branch (or a scheduled dispatch racing an interactive attach) could both report success while git registered two administrative entries for one on-disk worktree, or leave one racer's `git worktree add` silently overwritten by the other's cleanup.
  `create_worktree` now takes the same lock, keyed the same way (`worktree_attach_lock_path`, anchored on the shared clone's real `--git-common-dir` rather than the branch name), so a scheduled dispatch and an interactive attach contend on the identical key instead of each locking a key the other never touches. The async primitive (`platform::lock::acquire_spawn_lock`) has no timeout of its own, unlike the sync path's bounded `acquire_worktree_lock_sync`, so acquisition here is bounded with `tokio::time::timeout` against the same 30s `WORKTREE_GIT_TIMEOUT` the surrounding `git` calls already use, refusing with an error rather than blocking a scheduler tick indefinitely if the lock cannot be granted in time.
  Issue #282 is now closed for both paths.

No-Test: pinned by `worktree/create/003` (`create_003_concurrent_async_attach_never_double_creates`, `src/issue_dispatch_run.rs`'s `mod tests`), a plain `#[test]` racing 60 concurrent pairs of the async `create_worktree` against the same branch/target path and asserting exactly one `Created`, one `.git/worktrees` admin entry, and one `git worktree list` row per trial — not `#[spec]`-annotated, since this is internal scheduler-path locking with no independent TUI-visible scenario to narrate, matching how fork #331's own sync-path fix was covered.
