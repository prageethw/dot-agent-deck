## Issue dispatch now claims its issues, and can hand each one off already triaged

Issue-dispatch tasks used to know only two things about an issue: whether its worktree already existed, or whether an open PR already targeted its branch. Both are inferred side-effects — nothing ever said, in the open, "this issue is spoken for." A schedule you paused mid-cycle, a worktree cleaned up by hand, or simply two decks pointed at the same repo could all end up dispatching the same issue twice, and there was no way for a human glancing at the issue to tell it was already claimed.

A successful dispatch now writes the `in-progress` label onto the issue and posts a comment naming the claimant — which scheduled task claimed it, on which host, and when. That label is a third idempotency signal, and it is honoured no matter who applied it: this deck's own prior dispatch, a human working the issue by hand, or an external tool. The other two signals are inferred from state a dispatch happens to leave behind; the label is dispatch saying so directly. A **failed** dispatch leaves the issue completely unmarked — labelling before the outcome is known would risk a false claim that nothing ever clears, permanently keeping the issue un-dispatchable.

Every skip is now reported with a specific, distinguishable reason instead of a generic "skipped": the worktree already exists, an open PR already targets the branch, the issue is labelled `in-progress` (naming the claimant when one can be found, or saying plainly that none was recorded), or a concurrent dispatch won the worktree-creation race. Silent exclusion was the real risk here — a stray label left by a human looks identical to nothing happening unless the skip says why.

Issue dispatch can also opt into **triage**. Set `triage = true` under a task's `[scheduled_tasks.issue_dispatch]` sub-table, or pass the new `--triage` flag to `schedule add`, and every issue the fire actually dispatches gets a triage instruction appended to its prompt. The deck ensures a seven-label vocabulary exists on the repo (`priority-high/medium/low`, `size-high/medium/low`, `needs-triage`) but never classifies anything itself — the spawned agent applies its own labels using its own `gh` calls, the same way it would apply any other label while working the issue. Under uncertainty it applies `needs-triage` and leaves priority unset rather than guess, because a wrong priority is worse than an absent one: absent reads as unclassified, wrong reads as considered until someone checks.

Triage is opt-in and off by default, and it only ever touches issues a fire actually dispatches — nothing sweeps the rest of your backlog. Recording a priority does not currently change dispatch order either; `max_per_run` still takes issues in the order `gh` returns them, and nothing sorts by priority yet.
