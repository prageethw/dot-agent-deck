Fixed a keystroke-misrouting defect in PRD #393's lock-governed auto-focus. While the command-entry lock is engaged, the deck steers focus to the lowest-role-order pane that is `WaitingForInput`. That steer was applied unconditionally, once per frame, before the event loop drained input that was already queued — so if you were mid-answer to one waiting pane and a lower-order pane also went `WaitingForInput`, focus moved first and your buffered keystrokes were then forwarded to the pane you had not been typing at. Because the new pane is itself `WaitingForInput`, the lock's own carve-out for waiting panes let those keys straight through, where they could answer a permission or command prompt you never saw.

The sibling all-clear focus move already guarded itself with a zero-duration `crossterm::event::poll` pending-input peek for exactly this reason; the waiting branch did not. Both branches now share a single per-frame guard: when input is pending, the focus decision is deferred rather than dropped — the all-clear edge stays latched, and the waiting target is recomputed from scratch on the next frame — so steering still happens, just after the queued input reaches the pane it was aimed at.
