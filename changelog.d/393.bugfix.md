Fixes the daemon's hook-socket line reader (`run_hook_loop` in `src/daemon.rs`) reading each line via `BufReader::lines().next_line()` with no size cap and no deadline — the daemon-side half of the unbounded-read family #145 already fixed on the hook CLI's stdin path (released, and noted at the time as leaving this side open — see #145's own release note). A peer that connected to the hook socket and dribbled bytes forever without ever sending a terminating newline would hold that connection's read loop, and its accumulating buffer, open indefinitely, since neither growth nor elapsed time was ever checked. The reader is now bounded the same way the reply-path read in `src/hook.rs` already is: a distinct `MAX_HOOK_LINE_LEN` constant (16 MiB, intentionally equal to `daemon_protocol::MAX_FRAME_LEN` but not aliased from it, so a future wire-motivated change to that constant cannot silently retune this input bound too) is checked before each chunk extends the line buffer, and a 5s total-operation deadline — wrapping the whole per-line read in `tokio::time::timeout`, so it holds regardless of how the peer paces its bytes — closes the connection if a line never completes in time. Unlike the hook CLI, which logs nothing anywhere on this path, the daemon does log elsewhere, so a rejected line now gets one `tracing::warn!` naming which bound was hit; it never echoes the accumulated payload into the log, since that would just move the unbounded-untrusted-input hazard from memory into the log file instead of closing it.

Three behavior changes fall out of replacing `next_line()` with this bounded reader, worth calling out explicitly rather than only as an attacker-facing bound. First, a connection that closes after writing a complete line but with no trailing newline used to be delivered as a final partial line; it is now dropped with no log line, matching the reply-path read's existing "a partial line was never valid JSON either way" stance. Second, an open connection that never sends a complete line — including one that has sent nothing at all yet — is now closed after 5s of wall-clock idleness; previously such a connection could sit open indefinitely with no cap. Third, because the 5s deadline bounds the *whole* read operation rather than re-arming per byte received, a legitimate hook event that is simply slow to arrive — for example under a saturated runtime with many agents and heavy delegate handling — can now be dropped rather than eventually delivered. Hook delivery is fire-and-forget with no ack and no retry, so the sender has no way to learn the event was lost; the only record is the daemon's `warn!` for the deadline-exceeded case. This is a deliberate tradeoff (the alternative, an idle-reset deadline, would reopen the slow-drip vector this fix closes), not an oversight, but it means a dropped orchestration-critical event (`SessionStart`, `work-done`, status) is a real possibility under load, not just a theoretical one.
