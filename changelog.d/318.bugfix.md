## A config the deck cannot read no longer looks identical to one it read fine

Four different situations used to reach the same silent outcome when the deck rebuilt an orchestration tab: the project's `.dot-agent-deck.toml` was genuinely absent, it existed but couldn't be read, it existed but no longer parsed, or it parsed but no longer listed that orchestration. Only the first is ordinary — it is what a laptop TUI attached to a remote daemon sees, and it is why the deck fell back to the roles the daemon still remembered.

The other three are the user's own edit (or their filesystem) coming back at them, and they were the ones with no way to be recognised. A mistyped config, a config a permission change made unreadable, and a renamed orchestration all produced role cards that quietly stopped matching the file, which is the same symptom a rename produces and the last thing anyone suspects immediately after saving — as far as the deck let on, it had read the file.

All three are now named. An unparseable config says so and names where in the file parsing failed, so the fix is the one thing the message points at. A config that exists but couldn't be read says so and names why. A config that no longer lists the orchestration reports the drift as before. A genuinely absent config stays silent, because nothing is wrong with it.

The live-orchestration path has the same treatment. Tabs the daemon opens mid-session — an issue dispatch, a scheduled run — went through a separate code path that collapsed all four cases and, unlike reconnect, recorded nothing at all, not even a log line. It now resolves the config through the same states and reports through the same surfaces, so an orchestration that appears while you are working can no longer be built from stale roles without saying so.

Which config wins is unchanged in every case. The deck still falls back to the roles the daemon holds; it just no longer does it silently.
