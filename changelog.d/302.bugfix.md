Command-entry lock: pastes are now gated, the unlock hint names all three keypresses, and a persistent LOCKED / UNLOCKED chip shows the state.

Three defects in the orchestration command-entry lock. A bracketed paste into a locked worker pane was delivered instead of being dropped, so the lock held against typing but not against pasting. The bottom-bar hint read `Pane locked — Ctrl+d then Ctrl+e to unlock`, which omits the third keypress actually required — `Ctrl+E` leaves you in command mode — and now reads `Pane locked — Ctrl+d, Ctrl+e, Ctrl+d to type here`. And no persistent indicator existed in either state, so a working lock and an inert one were indistinguishable on screen; a ` LOCKED ` / ` UNLOCKED ` chip is now drawn in the bottom bar while you are typing into a pane, with `Ctrl+E` added to the help overlay.

The lengthened hint also collided with the right-aligned `[Command Mode Ctrl+D]` button below 87 columns, truncating the new `type here` clause at the very common 80-column width. The button is now elided when both cannot fit, on the reasoning that a transient message explaining what just happened outranks a chord that keeps working without an on-screen affordance.
