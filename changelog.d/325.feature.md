## `worktree reclaim` can now auto-remove a deck-provisioned isolated clone, not just a linked worktree

Fork issue #325 M4c: `worktree list`/`worktree reclaim` already discovered deck-provisioned isolated clones (a genuine `git clone` sibling of a repo, not a `git worktree list`-registered linked worktree) and reported them, but every such clone was permanently kept — never auto-removed by `worktree reclaim`, with or without `--yes`, regardless of PR state or cleanliness. An isolated clone can now report the new `"isolated_clone_reclaimable"` verdict and actually be removed by `worktree reclaim --yes`, under a maintainer-decided, five-condition safety rule: the clone must be **owned** (a genuine deck-written attach-lock provenance artifact — a forged sibling directory cannot satisfy this), **clean** (no uncommitted or untracked content), have **exactly one local branch** (the one it resolved/checked out, no others), an **empty `git stash list`**, and its own current HEAD commit SHA must equal the merged PR's own `headRefOid` exactly (the PR branch's own tip commit, compared via `gh pr list --json headRefOid` — not the merge commit GitHub creates on the base branch, which live measurement against this repo showed essentially never matches a genuine clone under any merge strategy). Any one of the five failing to resolve, or resolving negatively, keeps the clone exactly as conservatively as before.

Immediately before removal, the deck re-verifies every one of those signals fresh from disk — cleanliness, the local branch list, the stash list, and HEAD SHA against a freshly re-resolved `headRefOid` — and refuses rather than deletes if anything has changed since the clone was first examined, closing the window a large reclaim batch can otherwise leave open between examining a clone and actually removing it.

**This is user-visible and irreversible behavior for `worktree reclaim --yes`:** an isolated clone that previously always survived a reclaim can now genuinely be deleted from disk. As before, a bare `worktree reclaim` (no `--yes`) never removes anything on its own — an eligible clone is reported under the pending list instead, naming the exact path and the `--yes` command that would remove it.

One known, deliberately documented limit: the five conditions above prove the deck created the clone and that nothing local-only would be lost, but not that the clone isn't currently in active use — `worktree reclaim` is a plain CLI subprocess with no connection to the daemon's own in-process liveness tracking, so that signal isn't reachable from this command today. This is accepted as an explicit residual rather than papered over with a guess.

The `worktree list --json`/`worktree reclaim` document's `schema_version` moves from `3` to `4` for the new `"isolated_clone_reclaimable"` verdict value — a `--json` consumer that filters on the old five-value verdict set (`remove`/`ask`/`keep`/`isolated_clone`) would otherwise silently stop seeing rows in this new state.
