Opening an orchestration against a directory nested inside a git repository (not the repo's own root) now provisions its isolated-clone workspace at the plain `<repo>-<name>` sibling directory by default — the same naming a toplevel pick has always used. Since fork issue #607 shipped, every nested pick unconditionally got a longer, decorated name instead (`<length>-<repo>-<name>-<sanitized-subpath>`), even when nothing else was ever contending for that name. That unconditional disambiguation is gone; it now only ever happens when provisioning actually finds the plain name already occupied by a genuinely different pick, in which case only the second, colliding pick gets the decorated name — the first keeps the plain one.

**If you already have a nested-pick workspace from before this change** (any nested pick opened since fork#607 shipped), it is not automatically found, migrated, or renamed. The next time that same pick is opened or resumed, the deck computes the new, plain workspace location instead of reusing the old, decorated one — provisioning a brand-new, empty clone there. The old workspace (including anything uncommitted in it) is left completely untouched on disk; it is not deleted, and there is currently no in-app action to find or retire it automatically. If you have uncommitted work in an existing nested-pick workspace, locate it manually before reopening that pick — it is the sibling directory next to your repo checkout whose name starts with a decimal number followed by a dash (e.g. `12-myrepo-features-team-b-proj`) — and either keep working in it directly or migrate what you need out of it first.

One case is refused rather than silently migrated or forked: if the plain-named directory the deck would otherwise reuse turns out to belong to a nested pick whose on-disk ownership record is in the older, pre-subpath-aware format, and that record's identity happens to match the Name you just typed, the deck cannot tell whether this is that exact workspace from before the upgrade or a different, coincidentally-same-named one — either answer risks real data loss (silently working in someone else's clone, or silently abandoning your own). Rather than guess, it refuses the open and asks you to pick a different Name or to inspect the existing directory by hand.

This does not change the TUI↔daemon wire protocol — no `PROTOCOL_VERSION` bump. A newer TUI attached to an older daemon (or vice versa) sees no interoperability issue from this change on its own.
