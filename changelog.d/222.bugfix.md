Fixes two independent owner-identity collision edges (fork issue #222), then closes three follow-on gaps found in review. First, `validate_task` (`src/config.rs`) never bounded a `ScheduledTask.name`'s length: an overlong name — long enough that its `issue-dispatch:{name}#{issue}` marker-creator string exceeds `sanitize_marker_creator`'s 200-character truncation cap (`MARKER_CREATOR_MAX_CHARS`, `src/worktree_reclaim.rs`) — let two distinct scheduled tasks collide onto the same truncated creator string, so a worktree marker written by one could be misattributed to the other. `validate_task` now rejects, at load time, any `task.name` longer than `DISPLAY_NAME_MAX_LEN` (the same cap the daemon already enforces on a live orchestration's display name), reported as a `ScheduleLoadError` like the existing missing-`command` check rather than letting the entry load and collide later. The length bound alone still left a normalization gap open: `sanitize_marker_creator` also drops control characters and maps `\n`/`\r` to a space before truncating, so two short, distinct names (e.g. `"deploy prod"` and `"deploy\nprod"`) could still collapse to the identical creator string. `validate_task` (and `schedule add`, which writes `schedules.toml` directly and previously bypassed this bound entirely) now also reject any name that normalization would change at all, via a new `worktree_reclaim::marker_creator_normalizes` helper. Second, the New Pane form's `NewPaneFormState::name_collision` (`src/ui.rs`) only checked a typed name against live orchestrations' names, so typing the literal `unknown` was accepted even though `orchestration_creator_string` resolves it to `orchestration:unknown` — byte-identical to `ORCHESTRATION_UNKNOWN_SENTINEL`, the reserved value every nameless spawn's marker-creator string already collapses to. `name_collision` now also returns `true` when the typed name resolves to that sentinel (compared against the raw typed field, not the empty-Name fallback value, so an orchestration whose config name or directory basename happens to be `"unknown"` isn't wrongly blocked), blocking submission and rendering a new, accurate warning that this specific name is reserved rather than reusing the "already in use by a live orchestration" copy, which was false in this case.
