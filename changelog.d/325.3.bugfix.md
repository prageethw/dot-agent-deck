## `worker-agent-deck dispatch` now also gets the isolated-clone gate

`Action::SpawnPane` (the TUI's New Pane form) already checks, at the point it would create a worktree, whether the target root checkout already shares its git object store with a live orchestration, and provisions an isolated clone instead of a shared-checkout sibling when it does — closing issue #325's original incident shape for that path.

`worker-agent-deck dispatch` (the CLI path `handle_dispatch` in `src/dispatch.rs`) now performs the same check. A `dispatch` from a plain, non-orchestration pane whose checkout has no live sibling is unaffected — it shares the checkout exactly as before. But `dispatch`'s dominant caller is different from the TUI's: a role pane inside a live orchestration has its own cwd already equal to that orchestration's `orchestration_cwd`, so any `dispatch` issued from inside a live orchestration self-matches the gate's fast path and is **always** isolated — including what would otherwise be "the first" dispatch against that specific target. In other words, for the orchestrator-issues-`dispatch` pattern this feature targets, isolation is the normal case, not the edge case: each dispatched sub-task is provisioned into its own fresh clone, so its git operations can no longer race the dispatching orchestration's (or any other concurrent dispatch's) against shared refs and packs.

Same fail-closed behavior as the TUI path: if the daemon can't be reached, or answers in a shape that cannot be trusted to mean "no live sibling" (an error response, or the older-daemon shape that omits per-agent tab membership), `dispatch` refuses to provision rather than silently falling back to the old shared-worktree behavior as if nothing else were live.

Like Model A's isolated clones, an isolated clone provisioned by `dispatch` is never automatically removed — it is its own independent repository, not a linked worktree of the root checkout, so tab close does not touch it and `worktree list`/`worktree reclaim` cannot see it. Its dispatched name stays unusable for later dispatches until you remove it by hand (`rm -rf`) once its work is captured.

No-Test: primarily pinned by plain `#[tokio::test]` functions in `src/dispatch.rs`'s `mod tests` (`dispatch_shares_the_checkout_when_no_live_sibling_exists`, `dispatch_isolates_into_a_fresh_clone_when_a_live_sibling_shares_the_checkout` — which also asserts the isolated-clone arm registers `RemovalPolicy::IsolatedClone`, `dispatch_fails_closed_on_daemon_error_response`, `dispatch_fails_closed_on_legacy_agents_only_response`, plus the two pre-existing issue #469 rollback tests restored to exercise their real code path again now that this gate precedes them, `spawn_rollback_skips_cleanup_when_a_live_sibling_still_roots_the_worktree` and `spawn_rollback_force_removes_when_nothing_else_roots_the_worktree`; and, added across this fix round for the rollback/cleanup and message-surfacing logic, `spawn_rollback_force_removes_the_isolated_clone_when_nothing_else_roots_it` (which also pins that the isolated-clone rollback path never runs `branch -D` against the root checkout — the original round-1 BLOCKER), `spawn_rollback_skips_cleanup_when_a_live_sibling_still_roots_the_isolated_clone` (which also pins the origin-warning fold into the skip-cleanup message), `isolated_clone_is_always_kept_on_tab_close_even_when_clean`, `dispatch_surfaces_the_origin_warning_in_the_success_message`, and `dispatch_sanitizes_git_stderr_in_the_isolated_clone_failed_message`) rather than a `#[spec]`-annotated one — `handle_dispatch` is the CLI's internal worktree-provisioning logic, not TUI-observable behavior, so a unit test pins this more directly than any `#[spec]` scenario could, matching how Model A's own `root_checkout_has_live_sibling_*` gate-decision tests in `src/ui.rs` are pinned. Model A additionally carries `#[spec]`-annotated e2e coverage (`orchestration/worktree/014`/`015`) for the isolated-clone provisioning itself, which this CLI path does not yet have — a gap sharpened by the point above (isolation is `dispatch`'s normal case, not its edge case) and tracked as follow-up work rather than closed here. Deliberately NOT pinned by any test: the exact wording of the less-critical status/error branches these tests don't drive into — `IsolatedCloneOutcome::AlreadyClaimed`/`TimedOut`, `WorktreeCreation::BranchExists`/`TimedOut`, and the `spawn_blocking`-panic (`Err(join_err)`) arms on both the provisioning and the isolated-clone-cleanup paths — which remain covered only by manual inspection, not by an assertion that would fail if their message text regressed.
