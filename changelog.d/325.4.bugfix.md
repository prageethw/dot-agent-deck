## `worker-agent-deck worktree list`/`reclaim` now discover isolated clones

An isolated clone (provisioned when a 2nd or later concurrent orchestration shares a root checkout with a live one — see the earlier fragment on this issue) is a fully independent repository, not a linked worktree of the root checkout, and is never automatically removed on tab close. Until now `worktree list`/`worktree reclaim` had no way to see one at all: both walk `git worktree list` from the root checkout, which structurally cannot enumerate a separate repository.

Both commands now also discover deck-owned isolated clones sitting as sibling directories of the root checkout, reporting them distinctly from ordinary linked worktrees via a new `kind` field (`"linked"` or `"isolated_clone"`) and a fourth `verdict` value (`"isolated_clone"`, alongside the existing `remove`/`ask`/`keep`) — the `--json` document's `schema_version` accordingly moves from 2 to 3. An isolated clone is never assigned an automatic-removal verdict — deleting one destroys its own `.git`, so a clean working tree does not prove its local-only branch commits are safe to lose, unlike a linked worktree whose commits remain in the root checkout's shared object store even after removal. Whether an isolated clone can ever become automatically reclaimable, and under what stricter safety condition, is left to a documented follow-up.
