Fixed several follow-up issues in `.claude/skills/dot-ai-tag-release/cleanup.sh` (the release skill's worktree/branch cleanup detection, Step 6) found in a post-merge review of the previous fix. A second, linked worktree on the default branch could be offered for deletion — `git worktree remove` succeeds on it, unlike the root checkout, so this was worse than the original bug. A remote whose URL couldn't be resolved to a GitHub slug could leak its credentials into the script's own output. The main working tree's own path could silently resolve to the wrong location instead of degrading. A full page of merged PRs made the degraded marker permanent once this repo crosses 200 merged PRs, so that case now gets its own informational `MERGED_LIST_TRUNCATED=true` marker instead.

A follow-up review found the main working tree's path could still silently resolve to the wrong location in a second scenario, and closed it the same way — degrade rather than trust an unverified path. An scp-style remote pointing at a non-GitHub host could leak an internal hostname and username into the script's output; it's now rejected before that can happen. An unset `origin/HEAD` no longer makes the script silently guess `main` as the default branch — it degrades instead, since the wrong guess could leave the wrong branch protected from deletion. A worktree whose path contains an embedded newline is no longer offered with a truncated path. The merged-PR check is now a single query instead of two, which also removes a rare case where a merged-PR count query's own failure could block cleanup entirely.
