## Orchestration launch no longer fails when the project directory is a repo subdirectory

Launching any orchestration from a project directory that is not itself a git repository root, but a subdirectory of one (e.g. `.dot-agent-deck.toml` living at `<repo>/baseline/intent`, with the real `.git` two levels up at `<repo>/`), failed instantly and silently. Since PRD fork#544 M2b, every orchestration launch unconditionally provisions an isolated clone before spawning any role panes, via `git clone -- <picked-dir> <clone-dir>` — but unlike ordinary git subcommands, `git clone`/`git fetch` treat their source argument as a literal transport target and do not walk up parent directories to find `.git`, so the clone failed with `fatal: repository '<picked-dir>' does not exist`.

`provision_isolated_clone_sync` now resolves the real git toplevel the picked directory sits under (`git rev-parse --show-toplevel --show-prefix`) and clones/fetches from that toplevel throughout — the fresh-create path's `git clone` and the resume path's ancestry-probe fallback `git fetch` both shared the same defect. The role panes' working directory inside the fresh/resumed clone reproduces the picked directory's position relative to the toplevel (e.g. `<clone>/baseline/intent`), rather than landing at the clone root. A picked directory that already IS the repo root, or that isn't inside a git repository at all, is unaffected.

No-Test: pinned by plain `#[test]`s in `src/issue_dispatch_run.rs`'s own `mod tests` (`resolve_git_toplevel_distinguishes_root_from_nested_subdirectory`, `provision_isolated_clone_sync_succeeds_when_source_dir_is_a_repo_subdirectory`, `provision_isolated_clone_sync_resumes_when_source_dir_is_a_repo_subdirectory`) — in-crate unit tests against a pure Rust function, not e2e `#[spec]`-tagged TUI catalog scenarios, so there is no `#[spec]` delta for this gate to see.
