## Orchestration launch no longer fails, or corrupts the source repo, when the project directory is a repo subdirectory

Launching any orchestration from a project directory that is not itself a git repository root, but a subdirectory of one (e.g. `.dot-agent-deck.toml` living at `<repo>/baseline/intent`, with the real `.git` two levels up at `<repo>/`), failed instantly and silently. Since PRD fork#544 M2b, every orchestration launch unconditionally provisions an isolated clone before spawning any role panes, via `git clone -- <picked-dir> <clone-dir>` — but unlike ordinary git subcommands, `git clone`/`git fetch` treat their source argument as a literal transport target and do not walk up parent directories to find `.git`, so the clone failed with `fatal: repository '<picked-dir>' does not exist`.

`resolve_git_toplevel` resolves the real git toplevel the picked directory sits under (a single `git rev-parse --show-toplevel`, with the relative subpath computed in Rust rather than parsed from a second output line, closing a newline-injection edge case in the old two-line parse) and every isolated-clone entry point clones/fetches from that toplevel — the fresh-create path's `git clone`, the resume path's ancestry-probe fallback `git fetch`, and the ad hoc `dispatch <name>` CLI path in `dispatch.rs`, which reaches this same nested-directory shape whenever it is invoked from a pane already running inside a resolved isolated clone at a nested prefix. The toplevel is resolved once per launch and threaded through, rather than re-resolved independently in each of `ui.rs`/`issue_dispatch_run.rs`/`dispatch.rs`.

The isolated-clone **destination** is now also derived from that same toplevel, not from the picked (possibly nested) directory. Deriving it from the picked directory placed the clone as a sibling of the picked directory rather than of the repository — for a nested pick this materialized a full second clone of the whole repository *inside* the repository's own working tree (`<repo>/baseline/intent-<name>`), leaving `git status` permanently dirty and making `git clean -xdff` in the source repo destroy the entire orchestration workspace, including any uncommitted agent work in it. The destination is now a genuine sibling of the toplevel, matching this codebase's existing sibling-worktree convention (`../<repo>-<suffix>`) everywhere else. The role panes' (and, via `dispatch.rs`, the delegated agent's) working directory inside the fresh/resumed clone reproduces the picked directory's position relative to the toplevel (e.g. `<clone>/baseline/intent`), and is now verified to actually exist in the clone before being handed to a spawning pane — a picked subdirectory that is untracked or excluded by `.gitignore` is absent from a fresh clone, and previously produced a pane silently handed a nonexistent cwd. The resolved toplevel is surfaced in the launch's success status message whenever it differs from the picked directory, so a launch that resolves to an ancestor repository (e.g. `$HOME` itself being a git repository) is visible rather than silent. A picked directory that already IS the repo root, or that isn't inside a git repository at all, is unaffected.

A follow-up hardening pass closed a narrower reopening of the same defect: a picked directory that is itself a symlink planted *inside* the repository and pointing back at the repository's own root also resolves to an empty relative prefix, which the "root case stays unchanged" carve-out (added to avoid a spelling-only regression on symlinked temp-dir mounts, e.g. macOS `/tmp` → `/private/tmp`) read as "already at the toplevel" — deriving the clone destination from that raw, still-nested path reopened the original defect in a symlink-gated form. The carve-out now checks containment of the derived destination against the canonicalized toplevel directly, rather than inferring safety from an empty prefix. The pane-cwd existence check (both `ui.rs` and `dispatch.rs`) has the same hardening: it used to check only `is_dir()`, which follows symlinks, so a repository whose HEAD tracks a symlink at the picked subpath (with the source's own working tree having locally, uncommittedly, replaced it with a real directory) could pass the check while the clone's own checkout of that subpath resolved outside the clone entirely; it now also requires the resolved path to stay contained within the canonicalized workspace. The three new user-visible strings this fix introduces (the ancestor-repository disclosure and the two untracked-subpath refusal messages) are now terminal-escape-sanitized like every other path this codebase surfaces to the user. `dispatch <name>`'s own toplevel resolution now runs off the synchronous daemon request thread (`spawn_blocking`, matching every other blocking git/socket call on that path) and no longer re-resolves an already-resolved toplevel a second time before cloning.
