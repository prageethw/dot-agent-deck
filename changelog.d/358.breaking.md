## A worker's completion report can no longer land in the wrong orchestration's worktree — and an old `work-done` CLI now has every report refused, not just stale ones

**Behavioural change.** `handle_work_done` used to resolve a report's destination purely from the sender's bare `pane_id`, via `pane_cwd_map`/`pane_role_map` — the same maps `register_orchestration_role` overwrites whenever a pane_id is reused (a torn-down worktree's role pane recycled by a later, unrelated orchestration). A report produced under one registration but delivered after that pane_id was reassigned would silently land in the new tenant's worktree, under the new tenant's role label, and surface in the new tenant's orchestrator feedback — with the original sender's report simply gone.

Every pane registration now carries a generation counter, reserved and injected into the worker's own environment (`DOT_AGENT_DECK_REGISTRATION_GENERATION`, sibling to `DOT_AGENT_DECK_PANE_ID`) **at spawn time** — not re-read from the daemon when the worker later reports. That distinction matters: an earlier cut of this fix asked the daemon what the pane's generation was immediately before sending, which by construction is always the pane's *current* generation and could never disagree with itself microseconds later at delivery, so the actual issue #358 scenario (a worker that outlives its own orchestration's teardown) went straight through unchanged. Capturing the value at spawn means a worker's report genuinely carries the registration it was produced under; `handle_work_done` now refuses delivery (logs and drops, does not write) when that no longer matches the pane's current registration — the pane was re-registered, most likely for a different orchestration entirely, since this worker began.

The misdelivery reported in issue #358 is fixed by this. A related, narrower leak on the same signal — a stale report still disarms the *new* tenant's silence/idle watch before the refusal, even though it writes nothing and notifies nobody — is out of scope here and tracked separately in issue #444.

**Compatibility impact, no wire-shape change.** This rides the existing hook socket; no `PROTOCOL_VERSION` bump. A `work-done` CLI built before this change has no code path that reads or sends a registration generation at all, so its report is missing the field entirely; `#[serde(default)]` decodes that as `0`, which never matches a live pane's real registration (those start at `1`). Every report from an old CLI is therefore refused as stale, not only genuinely stale ones — the fix's fail-closed design cannot distinguish an old binary from a delayed report from a torn-down orchestration; both look identical on the wire.

If you run the daemon and any worker's `work-done` CLI from different installed versions, upgrade the worker's binary alongside the daemon — a mixed old-CLI/new-daemon pairing will silently drop every worker completion report until both sides match. On this fork the binary you'd actually run is `worker-agent-deck` (`worker-agent-deck work-done --task-file …`), not `dot-agent-deck`.
