## An old `work-done` CLI talking to a new daemon now has every report refused, not just stale ones

**Behavioural change, no wire-shape change.** Fixing issue #358's cross-orchestration misdelivery required the daemon to verify a `work-done` report's registration generation before delivering it (see the accompanying bugfix entry). The daemon now asks the running `work-done` CLI to report its current registration generation over the existing hook socket (`GetRegistrationGeneration`, additive, same unversioned channel as `GetSeed` — no `PROTOCOL_VERSION` bump).

**Compatibility impact**: a `work-done` CLI built before this change has no code path to answer that request, so its report always carries the placeholder generation `0` — which never matches a live pane's real registration (registrations start at `1`). Every report from an old CLI is therefore refused as stale, not only genuinely stale ones. This is the one case the fix's own fail-closed design cannot distinguish from real staleness: an old binary looks identical, on the wire, to a delayed report from a torn-down orchestration.

If you run the TUI/daemon and any worker CLI from different installed versions, upgrade the `work-done` CLI (or the whole binary, since this fork ships one binary) alongside the daemon — a mixed old-CLI/new-daemon pairing will silently drop every worker completion report until both sides match.

Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.
