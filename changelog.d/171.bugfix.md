The scheduled issue-dispatch feature could write to a remote GitHub repository unattended, on a cron, with no way to limit which repos it was allowed to touch and no way to try a new schedule safely before letting it write anything. A misconfigured or overly broad schedule could post claim comments, apply labels, and (with triage enabled) create new repo labels on a repo the operator never intended to target.

Two new, optional settings fix this. A repo allowlist can now be set on an issue-dispatch schedule so it refuses to do anything at all — no GitHub activity of any kind, not even reading the issue list — against a repo that isn't on the list. A dry-run mode can also be turned on so a schedule still runs its normal idempotency checks and reports which issues it would dispatch, but does none of the actual dispatch work: no per-issue worktree or branch is created, no agent is spawned, and none of the GitHub writes happen (no claim comment, no label changes, no assignee changes) — until you're satisfied it's doing the right thing. Because a dry run never creates a worktree, it's also safe to run repeatedly and then flip straight to a real run against the same issues: nothing it does can be mistaken by a later real run for "already claimed."

Both settings are off by default, so existing schedules keep working exactly as they did before.
