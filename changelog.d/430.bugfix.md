## Scheduled-task pane ids no longer collide across a daemon restart

`next_pane_id`'s only source of entropy was a bare in-memory `AtomicU64` counter that resets to 0 on every daemon restart, so a scheduled task fired once before a restart and again after could mint the identical `DOT_AGENT_DECK_PANE_ID` — issue #430. The two ids now differ across a restart too: `next_pane_id` mints its numeric component from the same restart-resistant nonce+sequence recipe `mint_pane_id` already used for TUI-attached spawns, extracted into a shared `agent_pty::mint_nonce_seq` helper. The nonce is hashed from the process id and a nanosecond timestamp and cached for the life of the process, so it differs across a restart even if the pid is reused.

No-Test: pinned entirely by plain `#[test]` functions rather than a `#[spec]`-annotated one — `mint_nonce_seq_nonce_differs_across_two_simulated_restarts` in `src/agent_pty.rs`'s `mod tests`, which pins the restart-safety property directly (two independent nonce cells, standing in for two daemon processes, mint distinct nonces even though both sequences start at zero), and the extended `next_pane_id_is_valid_and_unique` in `src/spawn.rs`'s `mod tests`, which now also covers the long-task-name/length-cap case against `PANE_ID_ENV_MAX_LEN`. `next_pane_id` and `mint_nonce_seq` are internal pane-id-minting bookkeeping with no TUI-observable rendering of their own, so unit tests pin the fix more directly than any `#[spec]` scenario could, matching `453.bugfix.md`/`468.bugfix.md`'s precedent for the same class of change.
