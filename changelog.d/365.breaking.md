## Attach-protocol bump: daemon-authoritative `pane_id` (`PROTOCOL_VERSION` 8 → 9)

**Wire-shape and semantic change.** `AttachRequest::StartAgent` used to trust whatever `DOT_AGENT_DECK_PANE_ID` the attaching client proposed inside its `env`, extracted server-side into `pane_id_env`. Two independently-attached clients never coordinate that value with each other or with the daemon beyond a one-shot hydration bump, so the same id could be minted twice — most dangerously across a daemon restart, or by two panes with no live overlap at all — and every consumer keyed on it (routing maps, report-path digests, `AgentPtyRegistry`) would silently collide or misroute. See PRD fork#365 for the full evidence trail.

The daemon is now authoritative: it mints its own collision-resistant `pane_id` (a per-process nonce hashed from PID + nanosecond epoch time, combined with a monotonic per-process sequence — the same recipe `mint_orchestration_id` already used, prefixed `pane-` for legibility) at `StartAgent` time, overriding whatever the client sent, and returns it on the new `AttachResponse.pane_id` field. That field is additive on the wire, but this is a same-wire/different-*meaning* semantic break, not a forward-compatible add: an old client that doesn't read the returned `pane_id` keeps minting a client-side id the new daemon never asked for and no longer treats as authoritative — exactly the ambiguity this change exists to close. `PROTOCOL_VERSION` bumped from 8 to 9 so the attach handshake refuses the mismatched pairing rather than letting a stale client limp along in that broken mode, matching the codebase's only existing cross-version policy (fork #17 / upstream #405): the local-attach handshake recovers by restarting the daemon to match the attaching binary; the remote/SSH path points the user at `remote upgrade`.

Compatibility impact: a TUI and daemon must be on the same `PROTOCOL_VERSION` to interoperate. After upgrading in place, an older still-running daemon and the new TUI will fail the handshake until the daemon is restarted (the standard recovery the build-version handshake already prompts for).

`spawn_agent`'s existing duplicate-`pane_id_env` rejection (`agent_pty.rs`) stays in place unchanged as a backstop — it now defends against a daemon-minting bug rather than a client-minting race, a strictly smaller threat surface. Every downstream consumer of `DOT_AGENT_DECK_PANE_ID` (hooks, `issue claim`'s identity resolver, report-path digests, the pane-keyed routing maps) treats the value as an opaque string and needs no change.

Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.
