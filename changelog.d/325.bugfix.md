`cargo xtask linkage-check` now runs a repository-state preflight (checks 10-12) before every other check: it fails loudly, naming the exact remedy, when the repository is unexpectedly shallow (`git fetch --unshallow <remote>`), when the `git worktree list` registry carries an entry whose path no longer exists on disk (`git worktree prune`), or when the current worktree's own directory is gone. `worktree_reclaim.rs`'s ownership gate only ever sees a mutation that goes through the deck's own reclaim path — a raw `git fetch --depth=1` or `git worktree remove` run from any agent's shell in a shared multi-worktree checkout bypasses it entirely and previously misdiagnosed as an unrelated failure elsewhere (a shallow `upstream/main` presents as `fatal: refusing to merge unrelated histories`). The preflight is gated structurally rather than with an `if CI` escape hatch: it only fires when the repository has more than one worktree, or the current checkout is itself a linked worktree, so a CI runner's fresh single-worktree clone (every job here defaults to depth 1 except `sonarqube`) is exempt by construction.

No-Test: covered by new plain `#[test]`s — unit tests in `xtask/linkage-check/src/repo_state.rs`'s `mod tests` for the pure gating/parsing logic, and integration tests in `xtask/linkage-check/tests/repo_state_preflight.rs` driving the real compiled binary against real, throwaway git repositories (shallow clones, added/removed worktrees). None are `#[spec]`-annotated: this is a dev-tool build-time check with no user-visible TUI scenario tracked in `tests/CATALOG.md`.
