## A worker that exits without calling work-done is now reported to the orchestrator promptly, instead of after a 120-minute/30-second timeout — or not at all

When a delegated worker's process ended on its own — finished its task and its session simply exited — without ever calling `work-done` and without an explicit `StopAgent` close, its armed idle-worker delegation (PRD #126) and delegate-silence watch (PRD #249) had no way to learn the process was gone. Both mechanisms were cancelled only by `work-done` or by an explicit close; neither one asked the daemon's own reader thread, which already knows the moment a pane's PTY reaches EOF that its process has died. The records sat armed until their full timeout window elapsed — 120 minutes and 30 seconds by default — indistinguishable in the meantime from a worker that was merely slow.

`pump_reader`'s EOF branch (`src/agent_pty.rs`) now retires any armed `OutstandingDelegation`/`SilenceWatchRecord` for that pane the moment PTY EOF is observed, via a new `AgentPtyRegistry::sweep_delegations_on_exit` that reuses the same drain logic an explicit `StopAgent` close already applies — without that close path's `closing_panes`/`close_waiters` side effects, which have no natural "finish" moment for a process that died on its own. Retirement is idempotent, so a late, legitimate `work-done` racing the same EOF is safe either way: a worker that reports completion just before its process ends produces no spurious second notice.

Retirement alone was silent, though — it stopped a stale record from lingering, but told the orchestrator nothing. A new, fixed daemon-authored notice (`AppState::compose_worker_exited_notice`) is now delivered through the same identity-guarded, non-submitting path PRD #249's silence notice already uses, naming the exited worker's pane so the orchestrator knows which one to check. Matching that notice's own injection-safety precedent, the text carries no role name and no delegated task content — a repository-controlled role name is exactly what PRD #249's review flagged as unsafe to interpolate into a notice delivered this way, so role and elapsed-armed detail stay in the daemon log instead. Because the reader thread that observes PTY EOF runs on a bare OS thread with no `tokio` context of its own, delivery is handed off via a `tokio::runtime::Handle` captured (with `try_current()`, never the panicking `current()`) at the moment the agent was spawned.
