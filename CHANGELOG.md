# Changelog

## [0.37.1] - 2026-08-22

### Fixed

- **A failed dispatch no longer deletes a worktree that agents are still working in**
  Dispatching an orchestration whose roles do not all start — one role's command misspelled, or a tool that is not on the daemon's `PATH` — reported the failure and then deleted the dispatched worktree, even though the roles that *had* started were live agents whose working directory that was. Their shell prompts still pointed at a path that no longer existed, and any file they went on to write landed nowhere recoverable.
  The rollback assumed no agent could be running yet, which holds for a single-agent dispatch and never held for an orchestration: roles start one after another, so a failure at the third leaves the first two already running. The rollback now asks the same question the tab-close path has always asked — is any live agent still rooted in this tree? — before removing anything. When the answer is yes it leaves the worktree, its branch and its cleanup record alone, and the failure message says how many agents are still running in it and that closing them releases it. This is distinct from never force-removing a *dirty* tree on tab close: the risk here is not uncommitted content but a live process losing its working directory.
  Partial orchestration spawns are now rolled back before the rollback is reached (see the entry for the orphaned agents), so in practice the dispatch reclaims its worktree exactly as it did for a spawn that never started anything. The check remains because deleting a working directory out from under a running agent is not a mistake worth risking on an assumption.
- **A `clear = true` delegate no longer discards the task when its replacement worker never comes up**
  Delegating to a `clear = true` worker role kills the current worker and spawns a fresh one before writing the task pointer. When that replacement failed to come up — it died during boot, or something else took the pane — the daemon waited out the full 30-second readiness window, wrote into a pane with no agent on it, had the write refused, and then dropped the task with a single line in the daemon log. The `delegate` command had already exited 0, so the orchestrator was told nothing was wrong and waited indefinitely for a completion that could never arrive. Dispatched orchestrations hit this most often, because the delegate's respawn is the only place their worker roles are ever relaunched.
  The readiness wait now ends the moment the replacement's terminal reaches end-of-file, instead of always running to its deadline, so a dead replacement is noticed in the second it happens rather than half a minute later. A replacement that is not the pane's live agent is then reported into the orchestrator's own pane — "delegated worker never came up … the task pointer was NOT delivered and no work-done can arrive for it" — and its outstanding-completion record is released, so a later unsolicited report from that pane is still labelled as one. The role, command and underlying error stay in the daemon log, which the notice points at.
- **A deck too short for all its cards now widens the grid to fit them, and says so when it still cannot**
  A seven-role orchestration in a window under 100 columns wide showed five role cards. The other two — `researcher` and `documenter` — were simply never drawn, with nothing on screen to say so: the title counted all seven, the config listed all seven, and `dot-agent-deck daemon status` reported seven live panes. On screen a card that was scrolled out of view looked exactly like a role that had failed to start, which is what made this expensive rather than merely untidy — the same symptom sent two separate investigations after a hydration defect that was not there.
  The deck decided its two layout axes independently, so neither could compensate for the other. The column count came from window width alone (under 100 columns meant one column, always), and the card size came from height alone. When the tallest usable grid still overflowed, the card size shrank as far as it could and the deck then quietly painted whatever fitted. Seven single-column cards needed 35 rows and had 25; two columns would have needed 20 and fitted comfortably, but width alone had already ruled a second column out and nothing reconsidered.
  Columns and card size are now chosen together: the deck searches for the first combination that shows **every** card and widens the grid — to a second or third column — when that is what it takes. Width still sets a ceiling, but a real one, from an explicit minimum card width rather than the old thresholds' implicit and much more generous assumption. A deck that already fits is untouched: widening is only ever spent on completeness, so the grid never narrows its cards to look busier.
  When a window is genuinely too small for its cards at any layout, the deck no longer hides them in silence. The title now carries the same scroll marker the Scheduled Tasks list has always used — `— 7 session(s)  (↓2)` for two cards below the window, `(↑2)` for two above — so the count in the title and the cards on screen can no longer disagree without saying so. Move the selection with `j` / `k` to bring the rest into view. See [Troubleshooting › The deck is missing cards](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for the full explanation.
- **A failed orchestration dispatch no longer leaves agents running with no way to close them**
  When one role of a multi-role orchestration failed to start, the roles that had already started stayed alive — as real child processes, holding their panes — while the dispatch reported that it had failed. No tab or card was ever surfaced for them and no handle was returned to whatever asked for the dispatch, so there was nothing anywhere in the deck to close them with. They kept running until the daemon stopped, and a later reconnect could still find their records.
  Starting an orchestration is now all-or-nothing: if any role fails, the roles that already started are shut down before the failure is reported, and the routing state registered for them is dropped with them. A dispatch or scheduled fire that reports failure now leaves nothing behind.
  The alternative — surfacing the roles that did start, so you could decide what to do with them — was rejected because a half-started orchestration cannot do its job: the orchestrator has been handed a briefing that names co-workers who do not exist, and every task it tries to hand them has nowhere to go. Shutting the partial set down and reporting the real error is the outcome that leaves you somewhere you can act from.
- **Delegating to a role just after closing its pane no longer breaks that role for the session**
  Closing a worker's pane and delegating to that role a moment later left the role permanently unreachable. Closing a pane removes its entry from the daemon's registry before spending its termination grace, so for up to three seconds the pane exists but has no record to relaunch — and a `clear = true` delegate arriving in that window failed outright, put "respawn failed for role …" in the orchestrator's pane, and every later delegate to that role was then rejected with "reached no worker".
  A delegate that finds no worker to replace now waits for an in-flight close to release the pane, retries, and — still finding nothing — creates a fresh worker for the role from its `.dot-agent-deck.toml` entry, which is what `clear = true` means in the first place. The role's registration is restored along with it, so the next delegate routes normally instead of failing. A worker whose agent simply died and was reaped recovers the same way.
- **A plain pane is no longer named after an orchestration you only cycled past**
  The new-pane form's Name field pre-fills with the picked directory's basename, and selecting an orchestration replaces that with the suggested `<folder>-orchestrator-N`. Cycling *away* from the orchestration left the suggestion behind, so a pane created with no mode at all — or with an ordinary workload mode, or as a `schedule` or `dispatcher` card — was named `<folder>-orchestrator-1` despite never being an orchestration.
  This was not a corner case, because the Mode cycler orders the project's orchestrations *between* "No mode" and the built-in `schedule` / `schedule: issues` / `dispatcher` options. Reaching any of those from the left means passing over an orchestration, and passing over one was enough: the suggestion applied on the way through and nothing ever put the basename back. The likeliest way to meet it was the plainest one — open the form, cycle through the options to see what is on offer, settle on "No mode", and submit something now claiming to be an orchestrator.
  The suggestion is now two-way: landing on an orchestration suggests `<folder>-orchestrator-N` as before, and landing on anything else restores the directory basename the form opened with. A name you typed yourself is still never overwritten in either direction.
- **macOS: a `get-seed` reply is no longer discarded when the daemon closes the connection**
  On macOS the deck could throw away a daemon reply it had already received in full, and report the daemon as absent instead. A pane's seed prompt then silently fell back to PTY injection even though the native `get-seed` path had worked.
  The cause was a kernel rule with no Linux equivalent: macOS refuses **every** socket option on a connection that has been shut down in both directions. The client half-closes its own write side before reading a reply (so the daemon knows the request is complete), and the daemon closes its side immediately after answering — so from that moment the client's attempt to tighten its read timeout failed, and that failure was being treated as "there is nothing to read", discarding the reply sitting in the receive buffer. It needed the read to go round its loop once more after the answer arrived, which is why it showed up under load rather than every time.
  A timeout that can no longer be tightened is now logged and the read goes ahead. The overall 5s bound on the exchange is unchanged: the previously applied timeout still limits each read, and the operation still ends the moment its budget is gone.

### Miscellaneous

- **Repository triage can classify new work and learn from maintainer corrections**
  New issues and same-repository pull requests can be classified by a guarded GitHub Agentic Workflow using the repository's explicit type, area, priority, and size taxonomy. Authority and lifecycle decisions remain human-owned, fork pull requests cannot reach the credentialed classifier, and automatic runs stay disabled behind `ISSUE_LABELER_ENABLED` until maintainers accept a read-only sample.
  The **Issue labeler batch** workflow previews up to 20 issues or pull requests without applying labels or changing learning memory, then offers an explicit apply mode. Live predictions and human corrections persist on a dedicated memory branch, including abstentions so a label added after a complete false negative becomes a usable example.
  See [Adaptive issue and pull request labeling](https://github.com/vfarcic/dot-agent-deck/blob/main/docs/develop/issue-labeling.md) for the taxonomy, activation procedure, security boundaries, and maintenance commands.
- **The manual-review hold on the Rust toolchain pin is now actually a hold**
  `renovate.json` holds the workflow Rust toolchain pin for a human even on a patch, because it has to move in lockstep with `devbox.json`'s `rustc`/`cargo`/`clippy`/`rustfmt` by hand and because a Rust release is where new deny-by-default lints arrive. That hold has been advisory rather than enforced: the same `toolchain: 1.97.1` string was being detected a second time by Renovate's `github-actions` manager, which routed it into the automerging `GitHub Actions` group.
  The customManager's own description is what hid it. It opened "The github-actions manager cannot see this: it reads the `uses:` ref" — true when written, false now. Renovate carries a registry of community actions whose version lives in an **input** rather than the ref (`lib/modules/manager/github-actions/community.ts`), and `dtolnay/rust-toolchain` is in it, mapped to `packageName: 'rust'` with `withSchema: valSchema('toolchain')` — it reads the identical string the custom manager was written for and emits it as depType `uses-with`. The `GitHub Actions` rule matched the manager with no depType filter at all, so it automerged all six depTypes that manager can emit rather than just action refs.
  The two lanes were visible side by side and nobody had looked: [#624](https://github.com/vfarcic/dot-agent-deck/pull/624) (`rust-lang/rust`, branch `renovate/rust-lang-rust-1.x`, `manual-review`, "Automerge: Disabled by config") and [#623](https://github.com/vfarcic/dot-agent-deck/pull/623) (`rust`, `uses-with`, branch `renovate/github-actions`, no label, "Automerge: Enabled") proposed **byte-identical** 1.97.1 → 1.98.0 diffs — the same seven edits, the same blob hashes — on the same day. #623 did not merge itself only because CI was red from an unrelated `main` breakage, since fixed by [#609](https://github.com/vfarcic/dot-agent-deck/pull/609).
  What that would have cost is concrete rather than theoretical, because nixpkgs has no Rust 1.98.0 yet — `devbox search rustc@1.98.0` returns `No results found`, and 1.97.1 is still the newest it offers. An automerged #623 would have moved CI to 1.98.0 while every `devbox shell` stayed on 1.97.1, breaking the property `ci.yml`'s own comment says the pinning exists to provide: that `cargo test-fast` locally and the same command in CI are the same claim. And because the rule carries a `groupName`, a toolchain change could have arrived bundled inside a PR titled "update GitHub Actions" alongside a handful of `@v7` bumps, merged without ever being read on its own.
  The `GitHub Actions` automerge rule is now scoped to `matchDepTypes: ["action"]` — `uses: owner/repo@ref` and nothing else. That direction is deliberate: excluding the one dep name observed misbehaving would have been correct only until Renovate's registry grew its next entry, whereas a whitelist leaves anything the manager learns to detect tomorrow **outside** the automerging rule with no edit required. Being wrong this way costs a PR someone has to click; being wrong the other way costs an unreviewed toolchain change on `main`. A second rule states the hold on the non-action depTypes explicitly and labels it `manual-review`, following the convention the 0.x-minor rule set — a hold that exists only as an absence is invisible on the PR page and impossible to grep for. In this repo `uses-with` means two toolchains wearing a GitHub Actions costume: the Rust pin, and the docs site's Node version from `actions/setup-node`.
  `taiki-e/install-action` is **not** in that registry today, so the `cargo-nextest` pin has the same exposure latently rather than actively. Its description now records that as an expiry date rather than a property, and the depType rules cover it the day the registry grows an entry, without anyone having to notice.
  The duplicate PR is not suppressed, and that is the deliberate half. Disabling the `github-actions` lane for `rust` would have removed the noise and also removed the redundancy — leaving the custom manager's regex as the only detector of a pin whose named failure mode is *silent rot*, so that a reformatted `toolchain: "1.98.0"` (quoted, which the regex does not match) would take both lanes down at once. Two held PRs per Rust release is the cheaper mistake, and they self-resolve: the lanes edit the same lines, so merging either makes the other conflict and `rebaseWhen: conflicted` autocloses it, exactly as happened to [#252](https://github.com/vfarcic/dot-agent-deck/pull/252).
  Renovate configuration only; no change to the shipped binary, and no version pin moved in this change.



## [0.37.0] - 2026-08-21

### Changed

- **Automatic prompt delivery into a pane now requires naming the agent it is for (`PROTOCOL_VERSION` unchanged)**
  The daemon's atomic `write-and-submit` — the call the dashboard uses to type an orchestrator's role prompt, a spawn-time seed prompt or a delegate pointer into a pane and press Enter for you — used to accept a request that named no agent at all, and deliver it to whichever agent happened to hold that pane at that instant. A pane id is a slot that agents move through, not a name for one of them, so "deliver to whoever holds this pane now" is precisely the mis-delivery every other guard on this path exists to prevent: a queued prompt could land in a replacement agent's conversation, in a different orchestration role's pane, or in whatever the user opened in that slot in the meantime. The pane-less form of the same call already refused an unidentified request; the paned form did not.
  It does now. A `write-and-submit` for a pane that carries no `expected_agent_id` is refused with `no-live-target` before anything is written, and the refusal is reported honestly to the caller instead of being swallowed. The companion session check is closed the same way: if the daemon already knows which conversation is live in that pane, a request that declines to name that conversation is answered `stale` rather than being dropped into a generation nobody bound it to. That holds whether or not a deck is currently attached and watching the pane, so a headless delivery gets the same answer an interactive one does. `stale` is the retryable answer both delivery paths already understand, so once the dashboard's own event stream has caught up with the conversation the daemon named, it rebinds to that conversation and tries again — in the ordinary race that is the very next refresh, and the prompt arrives a beat later. The recovery is not unconditional, though: `stale` does not tell the dashboard *which* conversation to rebind to, so a dashboard whose event stream dropped that conversation's start and reconnected without replaying it never learns the name, keeps retrying without one, and gives up when the 60-second delivery deadline expires. That case is bounded and logged rather than silent, and nothing is mis-delivered — but the prompt is not delivered either. An agent that never reports a conversation generation at all is unaffected and still receives its prompts.
  Nothing about the wire changed — no field added, removed or retyped, no new frame kind, and every guard field is still optional — so `PROTOCOL_VERSION` is not bumped and the handshake will not refuse a mismatched pairing. What changed is what an *absent* identity means: it used to mean "authorize by pane id alone", and now means "refuse". Per this project's own rule (`docs/develop/versioning.md`) that is a semantic break behind a stable wire, which is why it is classified `breaking` and drives a minor bump.
  **Action required: if you run v0.36.0, upgrade the dashboard and the daemon together.** The direction that carries the break is an *older* dashboard talking to a daemon built from this change, and the affected set is narrow enough to name. A newer dashboard against an older daemon is unaffected in both directions — it already names the agent on every automatic delivery, and an older daemon simply ignores identity fields it does not use (exercised end to end against the v0.36.2 daemon: role prompt delivered, delegate routed, work-done feedback returned). Releases up to v0.35.10 speak an older attach protocol and are already refused at the handshake, so nothing changes for them. v0.36.1 and v0.36.2 bind the pane's live conversation before every write and are unaffected (verified against a daemon built from this change: same four flows, all green). **v0.36.0 is the one that breaks**: it names the agent but never names the conversation, so its orchestrator role prompt is now answered `stale` and — because it never rebinds — every retry is too. The pane comes up, the agent runs, and the role prompt silently never arrives. Nothing is mis-delivered; it simply is not delivered.

### Added

- **Whether a pane scrolls depends on the agent in it, and the deck now says so**
  Scrolling a pane with a two-finger swipe works on a `claude` pane and does nothing at all on a `codex` pane. Nothing was broken: the two agents use opposite scrolling models, and until now neither the docs nor the deck itself gave you any way to know that. A pane that silently ignores every swipe and every `PageUp` reads as locked, and the only honest thing to do about it was to explain it.
  Agents fall into two camps. **App-managed** agents ask the terminal for mouse tracking precisely so they can receive the wheel and scroll their own transcript — claude requests all four mouse modes, and scrolling a claude pane has always worked. **Terminal-managed** agents expect the *terminal* to hold the history while contributing none of it: codex requests no mouse events at all, does not use the alternate screen, sizes its drawing region to the exact pane height and repaints its whole transcript in place, so no line ever scrolls off the top. Measured at the height codex rendered for, the retained buffer is zero lines. For an agent like that the deck has nothing to scroll, by wheel or by key, in any mode. That is now stated in [Keyboard Shortcuts](https://agent-deck.devopstoolkit.ai/docs/keyboard-shortcuts) under its own section, along with why scrolling up in a long codex session in a plain terminal *appears* to work — what you reach is the content that was on screen before codex started, never an earlier part of the conversation — and in [Workspace Modes](https://agent-deck.devopstoolkit.ai/docs/workspace-modes), which made the same uniform claim about reading a pane in command mode.
  The deck no longer waits for you to go looking. Attempting a scroll on a pane that has nothing to scroll now overlays a brief centred line — `Nothing to scroll — this pane has no scrollback to move through` — in the same idiom as the command-mode banner, shortening to `Nothing to scroll — no scrollback` on a pane too narrow for the sentence and clearing itself after a moment or on your next keystroke. It is reactive: it appears only when you actually tried to scroll, never on focus or spawn, so a pane nobody scrolls never shows it. It never consumes the key that dismisses it, so a character typed into a pane while it is up still reaches the agent. And it describes the pane rather than the agent, deliberately: what the deck has to go on is a byte count, and a byte count cannot establish anything about how an application draws — an agent printing an untrusted file or relaying a web response is passing on content it did not author, so a message that read the volume as a rendering model could have put somebody else's falsehood in the deck's own voice. It says what it genuinely observed and stops there; the per-agent *why* stays in the documentation, which can draw a distinction one pane's output cannot. Nor does it key off an agent name: the trigger is "this pane retains nothing *and* it has already been handed eight screenfuls of output", where the second half is there for one purpose — not nagging a pane that is merely new, such as a claude pane one second after spawn — and where nothing in it is specific to codex, so a future agent that renders the same way is covered without a change.
  Underneath both, the deck now works out whether an agent wants mouse reporting by actually parsing the escape sequences instead of searching its output for four fixed byte patterns. That search had three holes, and every one of them produced the *same* locked-pane symptom for an agent that would otherwise have scrolled perfectly well. It missed the combined form `ESC[?1000;1002;1006h`, which contains none of the four patterns as a substring, so an app that sets all its modes in one sequence looked like it had set none. It let an enable anywhere in a chunk outrank a disable later in the same chunk, so an agent switching mouse reporting off stayed flagged on. And it could not see a sequence split across a read boundary, which is an ordinary thing for a PTY to do. Detection is now a real scan, resolved in byte order, carrying the tail of an unfinished sequence into the next chunk under a fixed cap so that a malformed or hostile stream cannot grow it — and it models these modes the way a terminal does rather than as four independent switches. `1000`, `1002` and `1003` are one mutually exclusive protocol that a later request supersedes, so an app that moves from one to another and later withdraws the one it left behind has withdrawn nothing; `1006` is not a protocol at all but an *encoding* selector, which on its own asks for a particular spelling of reports nobody has enabled. The deck treats a pane as mouse-driven only when a protocol is in force **and** SGR encoding is selected, because SGR reports are the only ones it emits and sending one to a child that asked for a different encoding puts bytes into that child that it will mis-parse — where declining costs at most one scroll of the deck's own buffer. The whole model is checked against the same `vt100` parser that renders these panes, over fifteen streams, so the two derivations cannot drift apart. Focus reporting (`ESC[?1004h`, the one private mode codex does set) is correctly not counted as mouse reporting.
  Making codex's own transcript scrollable is not something the deck can do from the outside; it needs codex to use the alternate screen, enable mouse tracking, or bind a scroll key, and that has been raised upstream separately.

### Fixed

- **A worker whose process ends on its own is now reported to the orchestrator instead of leaving it silently waiting**
  An orchestrator delegates a task, the worker finishes it, and the worker's session simply ends without ever calling `work-done` — no crash, no `StopAgent`, just a process that exits on its own once its work is done. Until now the daemon had no way to notice: the idle-worker and silent-worker detectors both wait out a timer (up to two hours by default) before saying anything, and neither one asks whether the worker's process is even still alive. The orchestrator was left waiting on a delegation that had, in fact, already ended, with nothing to tell it so until the timer eventually ran out.
  The daemon already knows the moment a worker's process dies — the PTY reader thread observes end-of-file on it immediately — but that signal never reached the delegation tracking that decides whether a nudge is owed. It does now: the moment a worker pane's process ends, any outstanding delegation or silence watch for that pane is retired right away, and the orchestrator receives a new, fixed-text notice naming the worker's pane instead of waiting out the full timeout window. The notice carries no worker-authored content — only the pane id — so nothing the worker printed can be mistaken for daemon-authored text. This is the detection half of that gap; issue 205 also asks for the worker's own last message to be forwarded alongside the notice, which this change does not do, so 205 is only partially addressed and stays open.
  Fixing this surfaced an unrelated identity-gate gap in the delegate write path: when a worker's identity could not be resolved (most commonly a pane id reused by an unrelated agent between one delegation and the next), the code fell through to an unguarded write instead of refusing outright. That gap is now closed — an unresolved worker identity refuses the write rather than risking delivery to whichever agent currently happens to own the pane.
- **The orchestrator is no longer pointed at a work-done summary the deck failed to write**
  When a worker reported `work-done`, the deck wrote its report to `.dot-agent-deck/work-done-<role>.md` and then told the orchestrator to go read it. Writing the file was best-effort — it can fail because no working directory was recorded for the pane, because `.dot-agent-deck` cannot be created, or because the write itself fails — but the instruction to read it was sent regardless.
  The dangerous case is not the missing file; it is the file that is already there. That path is keyed by role name alone and reused for every delegation to that role, so a failed write left the *previous* delegation's report sitting at it. The orchestrator read a report that was complete, well-formed, from the right role, and about the wrong task, with nothing in the content, the pointer, or the pane to distinguish it from the current one — and then made decisions about work that had never been done. The only trace was a warning in the daemon log, and one of the three failure paths did not even leave that.
  The deck now tells the orchestrator that the file is unavailable and inlines the worker's report into the feedback instead, so a failed write degrades to a worse-formatted report rather than a confidently wrong one. It costs nothing: the deck is still holding the report in memory at the moment it gives up on the file. An inlined report is collapsed to a single line (Markdown formatting is lost, the words are not), truncated past 4000 characters, and framed as untrusted worker-authored text; the worker still holds the full version. The happy path is unchanged — when the file really is written, the orchestrator gets the same short pointer to it as before. The previously silent no-working-directory case now logs a warning like the other two.
  See [Orchestration](https://agent-deck.devopstoolkit.ai/docs/orchestration) for the troubleshooting entry, which no longer claims the summary file is always written.
- **The deadlines on the deck's synchronous daemon requests now cover connecting, not just talking**
  Two paths in the deck ask the daemon a question and wait for the answer on the spot: the TUI's own synchronous requests (the manager dialog's run-now, and the hint the `Ctrl+n` form asks for as it opens), and an agent's `delegate` / `get-seed` over the hook socket. Each states a deadline — five seconds, or a quarter of a second for the hint — and each applied it only *after* the connection was open. Connecting itself was unbounded.
  That is not a theoretical gap on Unix. A blocking `connect(2)` to a socket whose listener has a full accept queue does not fail: it parks, indefinitely, until something accepts. It does not report "connection refused", and it does not report "try again" either — that is what a non-blocking socket gets, which is exactly why only the blocking path was exposed. So a daemon whose runtime was starved long enough for connections to queue behind it could hang a keystroke in the TUI, or an agent's `delegate`, with no ceiling at all, while the code and its comments said the whole exchange was bounded.
  The connect step now honours the caller's budget on both platforms. On Unix the socket is created non-blocking and the connect retried until it succeeds, fails for a real reason, or the budget runs out — a full accept queue is a transient condition worth waiting out, just not forever. Failure kinds are unchanged, so a missing socket file and a stale one still read as "no daemon" exactly as before; blowing the budget is a timeout, which no caller could see previously. Windows could never hang here, but it can now honour a budget *shorter* than its own two-second retry ceiling, so the 250 ms hint path no longer spends two seconds on a busy pipe.
  Nothing on the wire moved: this is how the deck opens a connection, not what it says once it is open. A build carrying this fix and one without it interoperate exactly as before.
- **A completion the orchestrator never asked for is now labelled as such, instead of reported as delegated work**
  An orchestrator could be told "Worker coder has completed their task" for work it had never delegated, and then re-plan on it. The trigger is ordinary use: you type a task straight into a worker's pane yourself. That worker still carries the `## When done` instruction in its context from an earlier delegation, so it signals completion when it finishes — and the daemon forwarded that completion to the orchestrator in exactly the wording it uses for work the orchestrator commissioned. Nothing in the report said otherwise, so the orchestrator treated a task you had handed out yourself as its own delegation coming back and planned its next step around it.
  The daemon now keeps its own record of every delegation it dispatches, and a `work-done` that answers none of them reaches the orchestrator with an explicit label: it is told that it has no outstanding delegation to that worker, that the worker was most likely tasked directly by a person, and not to re-plan on the assumption that it had asked for the work. The worker's report still arrives — inline, framed as untrusted worker-authored text rather than as an instruction — so the orchestrator judges the report for itself. An uncommissioned completion also no longer overwrites `.dot-agent-deck/work-done-<role>.md`, so the last report the orchestrator *did* commission stays where it was instead of being replaced by one it did not. That report is not written to any file, and it is collapsed to one line and truncated past 4000 characters on its way to the orchestrator, so a very long uncommissioned report loses its tail; the worker still holds the full text.
  A delegation only counts as commissioned once its task actually reaches the worker. If the deck could not deliver it — the identity gate refused the write because the pane had changed hands, or a `clear = true` respawn failed and left `⚠ respawn failed for role '<role>'` in the orchestrator pane — the record is released again. Left standing it would be spent by some later, unrelated completion from that worker, which would then be reported as delegated work and would overwrite the summary file: the same two defects, arriving through the mechanism added to prevent them.
  One related consequence is worth knowing: an *orchestrator* that runs `dot-agent-deck work-done` on itself without `--done` is uncommissioned by the same rule — nobody delegates to the orchestrator — so it no longer writes a summary file for its own role. Use `--done` to close out the orchestration.
  This record is deliberately kept separately from the idle-worker detector. A project that sets `worker_response_timeout_minutes = 0` switches that detector off entirely, and its completions are as genuine as anyone's: they are still reported normally, with no label. Deriving "nobody delegated this" from the detector's state would have silently stopped reporting completions for every project that has turned it off.
  See [Orchestration](https://agent-deck.devopstoolkit.ai/docs/orchestration) — the troubleshooting section covers what the label means and how to get a completion reported as delegated work.
- **`daemon status` shows a real status again, and reconnect restores it instead of `Idle`**
  `dot-agent-deck daemon status` printed `STATUS=-  TOOL=-` for an agent whose dashboard card was visibly `● Thinking`, and `--json` simply omitted the `status` and `active_tool` keys for it. The same root cause broke the TUI's reconnect restore: detaching and reattaching rebuilt a busy agent's card as `● Idle` rather than restoring the status the daemon already knew.
  The daemon keeps two views of the panes it owns — the PTY registry, which spawns and tracks them, and its own session state, which ingests their lifecycle reports — and the two had drifted apart. Only orchestration role panes were ever announced to the session-state side, so an ordinary pane existed in the registry and nowhere else. The daemon's admission check, which exists so that an arbitrary process cannot drive session state for an agent the daemon does not own, then correctly rejected every report that pane made: agents report `running`/`waiting`/`finished`, never a session start, and only a session start could register a pane after the fact. The status was therefore never recorded, and the query that joins live state onto each agent found nothing to join.
  The daemon now resolves ownership from the PTY registry itself rather than from a second list it would have to keep in step by hand — for panes started by the dashboard and for panes started by the scheduler and by issue dispatch, whose single-agent cards had the identical gap. That closes the two ends a hand-maintained list could not: a pane is owned from before its process exists, so an agent that reports faster than its spawn call returns is no longer dropped, and ownership ends by itself once the agent is finished with the pane — the moment another agent takes it over, or when the daemon reaps the record — so a short-lived pane leaves nothing behind. Long scheduled-task names are covered too — the generated pane id is now kept inside the length the daemon is willing to record, where before an over-long one was discarded and the same status join failed for exactly the reason above.
  Ownership is tracked per *agent*, not per pane, because a pane is a slot that agents move through: closing one and starting another in its place reuses the same pane. Two things follow, and both are behaviour you can see. An agent's own last report still counts after the agent is gone — an agent that says "finished" and exits in the same breath now has its card cleaned up, where a pane-level rule dropped that final report as coming from a pane whose process had already died, leaving the card's state behind for good. And a report from an agent that has been replaced no longer lands on its replacement's card, so a slow report from the previous occupant of a pane cannot show up as the current one's status — permanently, so a pane whose last two agents have both finished does not start answering for the earlier of them again. The same distinction fixes closing a pane whose agent had already exited and been replaced: that close now leaves the replacement's role, working directory and in-flight work alone instead of tearing them down — including when the replacement is still starting up, and for as long as the close itself takes to run.
  What the admission check guarantees, stated as it actually is: a lifecycle report is accepted only when it names an agent this daemon spawned and that agent holds the pane the report names, or when the pane was explicitly registered by this daemon and no agent of its own holds it — a registration never overrides the daemon's own record of who a pane belongs to. Two shapes are deliberately weaker. A report that carries no agent identity at all — what a hand-written or pre-F9 hook script emits, and what any wrapper that loses the identity variable emits — is matched on its pane alone, because there is nothing else to match it on. And a *session start* may name a pane the daemon has never heard of, which is what lets an agent's first hook arrive before its pane is registered, so a process running as the same user can still bring a card into existence for a pane nobody spawned. Both are long-standing behaviour rather than anything new here, neither is a cross-user issue (the daemon's sockets are owner-only), and tightening them is tracked separately — but they are worth stating plainly, because they are narrower than "only agents this daemon spawned" sounds.
  Both surfaces recover together: `daemon status` reports the live status and active tool for ordinary panes, and a TUI reattach restores a working agent's card as it was rather than resetting it to `Idle`.
- **`daemon status --json` no longer prints what the tool is working on**
  `dot-agent-deck daemon status` is documented never to reveal prompt text, and its human-readable table has always shown the active tool's **name** and nothing else. The `--json` document did not honour the same contract: it serialized the daemon's internal active-tool record whole, so it also carried that tool's `detail` — the first line of the command being run for a shell tool, the file path for a read or a write, the search pattern for a grep, the subagent description for a delegated task. A status query is a diagnostic, routinely piped into a file or pasted into a bug report, and that content is the user's, not the daemon's.
  `--json` now emits the tool name only, matching the table: `"active_tool": {"name": "Read"}`. The `detail` key is gone from the document rather than blanked, and the status document's `schema_version` moves from `1` to `2` to announce the removal — that field exists precisely to tell a consumer that something left the shape. Anything reading `active_tool.name` is unaffected.
  Worth knowing if you have scripted against this: the leak was mostly latent before now, because the bug fixed alongside it meant an ordinary pane never reported an active tool at all — only orchestration role panes did. Fixing the status join is what would have made `active_tool.detail` appear for every agent, so the two changes ship together.
- **A daemon that answers slowly is no longer mistaken for one that isn't there**
  The hook socket's request/reply path — the one `get-seed` uses to ask the daemon for a pane's seed, and the one `delegate` uses to await its reply — gave up on the whole exchange the moment a single `read` returned an error, whatever that error was. Two of the errors it can return say nothing at all about the peer: `EINTR`, which only means a signal arrived on the waiting thread, and the socket's own per-read timeout, which is a different and shorter clock than the five-second budget the operation actually advertises. Either one ended the exchange with seconds of budget left, and the caller was told what it is told when there is no daemon at all.
  That was a silent failure by design. `get-seed` treats "no reply" and "no daemon" alike, both falling back to injecting the prompt through the PTY, so a reply that was written and then dropped looked exactly like an older daemon that never knew the verb — no error, no log line, nothing to distinguish a fallback taken for a good reason from one taken for none.
  A read failure is now reconciled with the deadline before it is allowed to end anything: an interrupted read is retried, a per-read timeout is retried while the operation's own budget still has time left, and only a genuinely exhausted budget, a peer that closes without answering, or a real I/O error ends the exchange. The five-second bound is unchanged and still bounds the whole operation, so a wedged or absent daemon fails exactly as promptly as before — and when the deck now does give up, it records which of those reasons applied.
  Nothing on the wire changed, and no caller sees a new outcome, so a daemon and a deck from either side of this change interoperate exactly as they did.
- **One agent's session id can no longer take the whole deck down**
  A session id containing non-ASCII characters killed the entire TUI. The dashboard shortens a long id to fit the card title, and it did so by cutting at the 11th *byte* — which in Rust panics outright when that byte lands in the middle of a character. Nine Greek letters were enough. Because the cut happened inside the render loop, every subsequent frame panicked the same way, so the deck died taking every other agent's card with it, not just the one card that could not be drawn.
  Nothing validated the id on the way in: the deck stores whatever a hook posts to its socket verbatim. That socket is owner-only, so this was never a route in from outside the machine — but on this product every agent running on the deck is a same-uid process, which made it one agent's ability to terminate the operator's whole session with a single hook post. It was equally reachable by accident, from any agent that happened to mint a non-ASCII id.
  The same shape sat on the "Opened: …" status line that a Ctrl+click on an agent-emitted OSC-8 hyperlink leaves behind, where the URL — text the agent wrote into its own PTY — was cut at byte 57. Both now cut on a character boundary and mark the cut with an `…`, using the truncation the hook binary has always used on prompts. Ids and URLs short enough to fit are untouched.
- **Session warnings printed on exit can no longer be used to repaint your terminal**
  When dot-agent-deck cannot restore something from your saved session — a pane whose directory has since been deleted, an orchestration whose config was renamed, a project config that no longer parses — it collects a warning for each one and prints them to your terminal on the way out, after the TUI has already been torn down. Those warnings name the thing that failed, and the name comes from your session snapshot: a pane's saved name (which can originate from a display name or agent id supplied by the daemon) or its saved directory.
  Until now those values were printed verbatim. A name carrying ANSI escape sequences could recolour or clear the shell you are dropped back into; a carriage return could overwrite the warning line just printed; and a newline could forge an extra line that reads as though dot-agent-deck said it. Inside the running TUI this was never possible — the rendering layer drops control characters before they reach the terminal — but the exit path had no equivalent protection.
  Control characters in a warning are now escaped before it is written, so each warning is exactly one line and no part of a name can reach the terminal as a command. They are escaped rather than removed, so a name that contained something odd still shows what it was (`\r`, `\u{1b}`) instead of quietly reading as a different name. Ordinary warnings — the overwhelming majority — are unchanged, including Windows paths, which are not doubled.
- **The experimental flag is found from anywhere inside your project**
  The `[features]` table that backs the `experimental` flag was read from the deck's own working directory, and only from there. Every other config read in the deck — modes, orchestrations, roles — resolves against a directory it is handed; this one silently used wherever the process happened to be. Launching the deck one level down from your project root was therefore enough to lose it: the deck looked for a `.dot-agent-deck.toml` that is not there, found nothing, and every experimental surface resolved off. Nothing was printed, so the result was indistinguishable from the feature having been removed from the build.
  The deck now starts at the launch directory and walks up to the nearest ancestor that holds a `.dot-agent-deck.toml`, and treats that as the project. Running it from `repo/src`, `repo/crates/app`, or anywhere else inside the project finds `repo`'s flags. The nearest config wins, so a crate or worktree carrying its own config overrides the one above it. If nothing is found at or above the launch directory, that directory is the answer, exactly as before — a deck launched outside any project reads precisely the file it read previously.
  Because walking upward means reading directories you did not name and may not own, a candidate is only accepted if it is a regular file owned by you; an ancestor config belonging to another user is skipped and the walk continues past it. This matters where a project sits under a world-writable parent like `/tmp`, in which anyone can create a `.dot-agent-deck.toml`.
  One case is deliberately unchanged: a deck launched somewhere with no project above it at all, with its panes pointed into a project elsewhere, still does not adopt that project's flags. The flag is a single process-wide toggle and some gated surfaces belong to no project, so there is no per-pane answer to give. Point `DOT_AGENT_DECK_FEATURES_CONFIG` at the file you want in that situation. `DOT_AGENT_DECK_EXPERIMENTAL` is unchanged and still decides the value outright.
  The startup log line now names the file the value came from — `experimental flag: ON (from /path/to/.dot-agent-deck.toml)` — so a flag that reads off because the wrong file was loaded is distinguishable from one that is simply set to false.
- **A stuck agent no longer keeps the deck from stopping the others**
  Shutting the daemon down — `dot-agent-deck daemon stop`, a SIGTERM, or quitting the dashboard — asks every agent to exit, waits out a grace window, and then force-kills whatever is left. That last step used to kill one agent and wait for it to disappear before moving on to the next, which is fine right up until an agent cannot disappear: a process blocked in the kernel on unresponsive I/O (a hung network mount is the usual cause) does not die on a kill signal until that I/O finally completes. The shutdown parked there, and **every remaining agent was never signalled at all** — they stayed running after the deck reported a clean stop and exited, leaving orphaned agent processes behind with nothing in the log to say so.
  The kill is now delivered to every agent first, and only then does the deck collect the results, so no agent's kill depends on how long a different agent takes to die. Collecting those results no longer blocks on one agent either, so an agent that is already gone is cleaned up immediately instead of queueing behind a stuck sibling. Nothing is given up in exchange: every agent is still waited for, so this trades no leaked process for a leaked one. A genuinely stuck agent still holds the deck's own exit until the kernel releases it — that part is not something a program can hurry — but it no longer takes the rest of your agents with it.
- **`RUST_LOG=dot_agent_deck=debug` now turns debug logging on, instead of being silently discarded**
  Asking for the deck's own debug logs the obvious way did nothing. `RUST_LOG=dot_agent_deck=debug DOT_AGENT_DECK_LOG=1 dot-agent-deck` produced a log file identical to one written with no `RUST_LOG` at all — no warning, no error, nothing to distinguish "your filter was thrown away" from "debug logging had nothing to say". The deck appended its own `dot_agent_deck=info` default *after* reading `RUST_LOG`, and appending a directive replaces an equally specific one, so the user's directive lost every time. Only a more specific target survived, which is why the workaround was to spell out `dot_agent_deck::daemon=debug`, `dot_agent_deck::spawn=debug` and so on, one subsystem at a time — the form nobody reaches for first, and the reason a quiet daemon stayed quiet through a real debugging session.
  The defaults now go in first and `RUST_LOG` is layered on top, which is the precedence the syntax leads you to expect. `RUST_LOG=dot_agent_deck=debug` raises the whole crate to debug; `RUST_LOG=dot_agent_deck=warn` quiets it, which was equally impossible before; and the per-subsystem forms keep working unchanged. With no `RUST_LOG` set the log is exactly what it always was — the deck at `info`, its dependencies at `error`. A directive that does not name the `dot_agent_deck` target still leaves the deck's default alone, so a bare `RUST_LOG=debug` moves the dependency floor and nothing else. One small improvement comes with it: that `error` floor for dependency crates used to vanish the moment `RUST_LOG` was set at all, so turning on deck logging quietly turned dependency errors off; it is now unconditional.
  `RUST_LOG` only ever selects *what* is logged — `DOT_AGENT_DECK_LOG` is still what decides whether a log file exists, and neither variable prints anything to the terminal.
  See [Troubleshooting › Enabling Debug Logs](https://agent-deck.devopstoolkit.ai/docs/troubleshooting#turning-the-verbosity-up) for the filter syntax and examples.

### Documentation

- **`daemon status` is documented**
  `dot-agent-deck daemon status` shipped without a page anywhere under `docs/`, even though its `--json` form emits a versioned document that scripts are meant to consume. Its siblings `daemon stop` and `daemon restart` were already covered; the one subcommand you would reach for to find out what the daemon is actually doing was not.
  [Installation](https://agent-deck.devopstoolkit.ai/docs/installation) now carries an "Inspecting the local daemon" section. It documents the human table column by column — including the `mode:<name>` and `<role> (orchestrator)` values the `ROLE` cell can take, the six live-status strings, and the `-` that means "no value yet" — and separates it from the `--json` document, which is the form to parse. The JSON section states that `schema_version` is currently `2`, that a bump announces a field removal or a meaning change while new fields may appear without one, and that every field except `agent_id` is omitted entirely rather than emitted as null when the daemon has no value for it.
  The failure behaviour is documented as it actually is: an unreachable daemon writes a reason to stderr, prints nothing to stdout, and exits `1` — not the idempotent exit `0` that `daemon stop` gives you, because a status query that got no answer learned nothing. All three reasons you can hit are shown verbatim (no socket, a stale socket left by an exited daemon, and a wedged daemon hitting the 3-second bound), along with the fact that a malformed invocation exits `2` instead, so a script can tell an unreachable daemon apart from a binary too old to know the subcommand. Also stated explicitly: launching the TUI lazy-spawns a daemon, but a status query never does in either output form — an absent daemon is reported rather than brought into existence to answer the question.

### Miscellaneous

- **The one file that may not name its own crate is now checked rather than commented**
  `src/test_temp.rs` resolves the disk-backed `/var/tmp/dad-e2e-<uid>` scratch parent for tests that do not link the PTY harness. It is compiled into the lib target as an ordinary module and, via `#[path = "../src/test_temp.rs"]`, into ten integration-test crates as well — an arrangement that only works because the file is self-contained. In those crates `crate::` is the *test* binary's own root, where nothing the library defines is in scope, so one added `crate::` path breaks every consumer at once.
  That property is load-bearing economics rather than a style preference. Containing those fast-tier crates with `mod common;` was priced at pulling the PTY harness into six more binaries and duplicating roughly 530 fast-tier executions; the `#[path]` route cost 12, measured as `cargo nextest list` going 2,315 → 2,327. The whole difference between those two numbers rested on one file staying free of `crate::`, and it was enforced by a comment.
  `cargo xtask linkage-check` now has a ninth rule that refuses one, naming the file and line and explaining why the file is unusual. Two things make a mechanical check worth having over the compiler. A `crate::` path fails as N identical `E0433`s with no hint of the arrangement behind them, so the obvious "fix" is to unpick it rather than to drop the reference. And whether it fails at all depends on which names the *consumer* happens to have at its own crate root: measured by adding a `crate::features::experimental_enabled()` probe to the module, nine of the ten including crates failed with `cannot find features in crate` while `tests/features.rs` compiled clean, because its own `use dot_agent_deck::features::{self, Features};` puts a `features` at that test crate's root. A `crate::` path can therefore land green under whichever filtered `cargo test-fast` the author ran and break the next consumer to include the file. The scan runs over the comment-stripped source, so the file's own header note can point at the rule by name; a rename that left the rule's path constant behind fails the check rather than turning it into a no-op that still prints `ok`.
  Five tests in `xtask/linkage-check` hold it, all against synthetic sources rather than the live checkout — whose copy is clean by construction and would make them pass for a reason unrelated to the rule working. They cover a rejected `use` and call, the `$crate::` and spaced `crate ::` forms, an accepted self-contained module including a crate whose name merely ends in `crate`, and the guarded file going missing. No change to the shipped binary.
- **The nextest `e2e` profile that nothing ever selected is gone**
  `.config/nextest.toml` carried a `[profile.e2e]` with its own `120s x 2` kill window and four `[[profile.e2e.overrides]]` timeout carve-outs, and nothing in the repository ever selected it. `cargo test-e2e` is `nextest run --workspace --features e2e`: `--features e2e` names the *cargo feature*, and passes no `-P` / `--profile`, so the run has always used nextest's `default` profile — as has every `cargo nextest run` in `.github/workflows/`. The two `e2e` names collide and mean unrelated things, which is most of why this was easy to misread.
  It was misleading rather than harmful, but the misreading has a real cost: a contributor who adds a long real-agent test and carves it out under `[[profile.e2e.overrides]]` believes it is protected from the default `3 x 60s` kill, and it is not — the test dies mid-wait with a bare `TIMEOUT` and none of the diagnostics it was written to produce. The inconsistency was already visible: three of the seven `[[profile.default.overrides]]` entries had no `e2e` counterpart, which only makes sense once you know the profile is never consulted.
  The dead profile is deleted rather than wired up, because wiring it up was the option that would have changed real behaviour. Its four overrides were value-identical duplicates of `default` entries, so nothing unique was lost; selecting it would instead have moved the three carve-outs with no `e2e` counterpart (`route_001`, `new_pane_016`, `orchestration_dispatch_002`) down from their widened windows to that profile's 240s. Every timeout window in the tier that actually runs is unchanged, and all seven surviving carve-outs still resolve to exactly one test each. Short comments now sit at both places the name collision reads wrong — the top of `.config/nextest.toml` and the `test-e2e` alias in `.cargo/config.toml` — so the next reader does not have to re-derive it.
- **`/verify-pr`'s scan output can no longer be forged by a PR's own text**
  `.claude/skills/verify-pr/scan.sh` emits a line-based `KEY=value` stream that a reviewing agent parses to decide which paths execute on clone (`READ_DIFF_BEFORE_RUNNING`), whether the author is trusted, and which commit a pre-push gate diffs from. It built that stream with jq string interpolation, and `jq -r` passes an embedded newline straight through — so a value containing one ended its own record and started the next. A pull request title is attacker-controlled on a public repo: an outsider writes it by opening a PR. Measured against the real script, a title of `Fix a typo\nPR_AUTHOR=attacker\nREAD_DIFF_BEFORE_RUNNING=none` produced both forged records **ahead of** the real ones, so a consumer taking the first match read an attacker's author name and a downgraded safety gate. A label name forged `TRUSTED_AUTHOR=true` the same way, and `gh`'s multi-line error text could forge `SUCCESS=true` inside a failure report.
  The stream now has one writer. `stream.sh` defines the grammar — a record is `^KEY=` at column 0 with no CR or LF in its value, section headers are `--- NAME ---`, and every other line is indented free text — and `scan.sh`, `setup.sh` and `checks.sh` emit through it instead of `echo`. Values coming straight from `gh --jq` are sanitised by one expression mapped over an array of `[key, value]` pairs, so a field added later inherits it rather than having to remember it. Changed filenames now come from the JSON files API rather than `gh pr diff --name-only`, because git permits a newline in a pathname and a newline-separated list has already lost the difference between one path and two by the time the shell reads it; the count is cross-checked against the PR's own `changedFiles`, and a short list trips the read-the-diff gate instead of silently under-reporting it.
  Eight tests in `xtask/linkage-check` hold this: six drive the real `scan.sh` against a `gh` stand-in whose every free-text field carries an embedded newline, and two fail the build if a script in that directory starts writing records any other way — which is how this class of bug would otherwise come back the next time a field is added.
  Running the script under test also surfaced a separate defect it had been hiding: `scan.sh` used a bash 4 associative array, so under the `/bin/bash` 3.2 that macOS ships it died mid-stream under `set -u` and emitted **no `READ_DIFF_BEFORE_RUNNING` line at all** — the field a reviewing agent is told to act on failed by not existing. That has been true since the script was written; nothing ran it on macOS until these tests did. The classification now uses a portable `<bucket>\t<path>` list, the gate accumulator is a plain string rather than an array `set -u` refuses to expand when empty, and the tests assert the stream reached `SUCCESS=true` so a truncated run fails as truncation rather than as whichever assertion happens to look at a missing record.
- **`shell_quote_if_needed`'s contract is now pinned by its own tests**
  `platform::paths::shell_quote_if_needed` single-quotes a path for a POSIX shell only when it contains a byte outside a conservative safe set. Three subsystems interpolate its result into command text that agents then execute verbatim — the Codex hook installer, the Devin hook installer, and `binary_name`'s absolute-path fallback — and nothing tested it directly. Its only coverage was incidental: `orchestration/delegate/019` asserts a composed fallback result that happens to be quoted, which pins the composition rather than the helper.
  Eight fast-tier unit tests beside it now pin the contract byte by byte: a path of only safe bytes comes back unchanged rather than gratuitously quoted; a space forces the quoted form; an embedded single quote is spliced as `'\''` and the result still reads as one shell word; the empty string is quoted rather than returned bare, so it cannot vanish and promote the next word to command; every byte of the documented safe set (`/ . _ - + = : @ % ,` plus alphanumerics) stays unquoted; a sweep of the whole ASCII range asserts the safe/unsafe split in both directions, so widening the set — letting a `$`, a backtick or a space through unquoted — fails as loudly as narrowing it; and a non-ASCII path quotes without a multi-byte character being cut in half, which is the half of the contract the ASCII sweep cannot reach since the predicate reads bytes while a path is UTF-8. The single-word claims are checked by a test-local POSIX word reader rather than by spawning a shell, so the whole file stays pure data: no filesystem, no environment, no daemon, no sleeps.
  The backslash case is recorded as **observed** behavior, not endorsed behavior. `\` is absent from the safe set, so every Windows path is POSIX-single-quoted today — the property [#561](https://github.com/vfarcic/dot-agent-deck/issues/561) is about, and deliberately not resolved here. Pinning it is the point: whichever way #561 lands, the change has to appear as a deliberate edit to a named test instead of passing silently.
  Each assertion was confirmed to bite by mutating the helper — narrowing the safe set, widening it, dropping the `!path.is_empty()` guard, and replacing the `'\''` splice with a naive wrap — and checking that the intended test turned red for each. No production code changed.
- **The release assembler can no longer delete a changelog fragment it never checked**
  `scripts/assemble-changelog.sh` builds each release's notes from the fragments in `changelog.d/` and then deletes the ones it consumed. It scanned that directory twice with two `find` invocations that disagreed on depth: the guard that rejects an unrecognized type suffix looked only at the top level, while the loop that renders fragments and then `rm -f`s them recursed. Anything in a subdirectory was therefore invisible to the guard and visible to the deletion.
  The consequence was the exact failure the guard exists to prevent, reached by the one path it did not cover. A `changelog.d/nested/702.fix.md` — `fix` is not a recognized type, `bugfix` and `fixed` are — was never reported, never rendered, and never removed, while the fragments beside it were consumed and the release shipped without it. That is the shape of the v0.24.3 incident that put the guard there in the first place: fragments silently ignored, an empty release body, and nobody told. Nothing puts fragments in subdirectories today, so this was latent rather than active.
  Both `find` calls are now recursive, so every `*.md` anywhere under `changelog.d/` is suffix-checked before the collection loop can reach it, and a rejected run aborts before a single fragment is deleted. Converging the other way — bounding both to the top level — would have stopped the deletion but left a nested fragment unmentioned and unreported, which is the silent-drop shape rather than a fix for it. A rejected fragment is now named by its path relative to `changelog.d/` instead of by its bare filename, so a nested one says which directory to look in; for the flat layout the repo actually uses, that is still just the filename. A comment on each `find` records that the two are deliberately in lockstep.
  Four fast-tier tests in `tests/assemble_changelog.rs` drive the real script against a scratch directory and cover the reported case, the same fragment at the top level as a control, the flat happy path, and a validated nested fragment. The first was confirmed red against the unfixed script — the script exited 0, rendered and deleted its way around the offender — and each half of the fix was reverted individually to confirm it turns that test red again. They are scoped to Linux, which is where `release.yml` runs the assembler and the only place anything runs it: on macOS the script has always died on its first associative array, because `declare -A` needs bash 4 and macOS ships 3.2 — a pre-existing limit these tests were merely the first thing to execute into, now tracked separately as [#593](https://github.com/vfarcic/dot-agent-deck/issues/593). This is release tooling only; no change to the shipped binary.
- **The release assembler now runs on macOS's bash, instead of dying on its first line of work**
  `scripts/assemble-changelog.sh` opened by building its type-to-heading map as an associative array — `declare -A TYPE_HEADERS=([added]="Added" …)`. Associative arrays are bash 4. macOS ships `/bin/bash` 3.2.57, where `declare -A` does not merely go unsupported: the assignment degrades to an ordinary *indexed* array assignment, so `[added]` is evaluated as an **arithmetic** subscript, `added` is read as an unset variable, and the script's own `set -u` kills it on that line. The whole run was one message — `assemble-changelog.sh: line 12: added: unbound variable` — and nothing below line 12 had ever executed on bash 3.2.
  It never broke a release, because `release.yml` runs the assembler on `ubuntu-latest` and nothing else invokes it. What it did cost was the first maintainer to run the assembler locally on a Mac, who would have hit a hard failure whose message names a variable that appears nowhere in the script; and it is what forced [#582](https://github.com/vfarcic/dot-agent-deck/issues/582)'s new tests to be scoped to Linux, since they turned `build-macos` red with four identical copies of that message.
  The map is now a `type_header()` `case`, which needs no bash 4 and no feature detection — the dependency is removed rather than diagnosed, so there is no version to check and no second code path to keep working. Behaviour is unchanged on bash 4+: the same nine types map to the same six headings, and the same aliasing (`feature` under Added, `breaking` under Changed, `bugfix` under Fixed) still collapses into one section each. A type listed in `TYPES` with no matching arm now aborts with an error that names the type and says what to add, rather than the previous bare `unbound variable`; both fail loudly, which is the property that mattered. `.claude/skills/verify-pr/scan.sh` was moved off `declare -A` for this same reason under [#521](https://github.com/vfarcic/dot-agent-deck/issues/521), and this is the same fix in the one other place that needed it.
  `tests/assemble_changelog.rs` is back to `#![cfg(unix)]`, so `build-macos` proves this rather than leaving it resting on review, and two tests now cover the mapping the existing four never touched beyond `feature` and `bugfix`. Both read the script's `TYPES` array and `type_header()` arms out of the script itself rather than mirroring them: one checks statically that the two agree in both directions, the other feeds the assembler a fragment of every declared type and checks each renders under the heading the script's own arms map it to, with aliases still collapsing into one section. Deriving the lists is what makes the lockstep real — a mirrored copy would never feed a newly added type, so the mapping would go untested while the test still reported success, and the failure would surface as a release shipping short a section. The defect was reproduced under a real bash 3.2.57 before anything was changed, all four pre-existing cases failing at `line 12` exactly as `build-macos` had; the fix was then reverted to confirm they go red again.
  The sweep the issue asked for turned up one more instance of the same class, and it is fixed here too: `.claude/skills/demo-reel-adapter/build.sh` built its clip list with `mapfile -t`, which is also bash 4 — on bash 3.2 `mapfile` is not a builtin at all, so `build.sh reel` died with `mapfile: command not found` and exit 127 before selecting anything. It is now an `IFS= read -r` loop, which is safe because the id producer newline-terminates every line, so no unterminated final line can be dropped. Checked differentially rather than by inspection: across empty, single, multi, embedded-space, embedded-blank-line and embedded-tab inputs the loop builds a byte-identical array to `mapfile -t` on bash 5, and the same array again on bash 3.2. That was the only other bash-4 construct in the file, so the whole script is now 3.2-clean.
  One instance is knowingly left: `.claude/skills/dot-ai-tag-release/cleanup.sh` uses `declare -A` twice, but it is a `dot-ai-`prefixed synced mirror that gets overwritten wholesale by upstream syncs, so a fix here would be reverted rather than kept. It needs an upstream request instead.
  Release tooling and local skills only; no change to the shipped binary.



## [0.36.2] - 2026-08-18

### Added

- **Idle ASCII Art Removed, and With It the Deck's Only LLM Client**
  The opt-in idle ASCII art feature is gone. Idle dashboard cards now show the same flashing-dot indicator in every card density, and `dot-agent-deck` no longer contains an LLM client or reads any provider API key. The deck's job is to spawn and monitor real coding agents — `claude`, `opencode`, `pi`, `codex` — each of which authenticates itself; nothing in the daemon, orchestration, hooks, scheduler, or dispatch path ever made an LLM call.
  Carrying an API-key code path for a cosmetic feature had a real cost. An `ANTHROPIC_API_KEY` exported for idle art overrides a Claude.ai subscription inside Claude Code even when you are logged in, silently switching you to API billing — so merely *having* the key set for the art broke the agent the deck exists to run.
  **What is removed:** the `dot-agent-deck ascii` subcommand (`--input`, `--output`, `--provider`, `--model`), the `[idle_art]` config section, and the four `idle_art.enabled` / `.provider` / `.model` / `.timeout_secs` keys of `config get` / `config set`.
  **What you need to do:** nothing. An existing `config.toml` that still carries an `[idle_art]` section keeps loading unchanged — the section is ignored, not rejected, so no other setting is disturbed. Only two things change for anyone who had the feature enabled: idle cards stop drawing art, and `config get`/`config set` now report `idle_art.*` as an unknown key. Delete the section at your leisure. No environment variable that any other part of the deck uses was touched, and there is no daemon-protocol change, so a running daemon and a new binary still interoperate.
  See [Configuration](https://agent-deck.devopstoolkit.ai/docs/configuration) for the config keys that remain.
- **The new-pane form suggests a unique orchestration name, and refuses a colliding one**
  The new-pane form's Name field pre-filled with the directory basename and enforced no uniqueness, so two orchestrations spawned from the same repo were indistinguishable in the tab bar and in any tooling that reads `display_title`.
  When an orchestration is selected, the Name field now suggests the next free `<foldername>-orchestrator-N` name instead of the bare basename, and submit is refused outright — not merely disabled — when the resulting title matches a name a live orchestration already holds. This rides the existing PRD #140 same-cwd-warning guard seam, which now drops `[Submit]` entirely for a colliding name.
  The uniqueness check adds no daemon round-trip: `live_orchestration_cwds()` is folded into `live_orchestration_cwds_and_titles()`, so the check rides the same single `ListAgents` call the same-cwd warning already pays for at form-open time. The uniqueness universe is each live orchestration's `display_title` (falling back to its canonical name), which already travels over the wire on `TabMembership::Orchestration` — no protocol change.

### Fixed

- **Claude Code hook rules are now recognised regardless of the deck binary's name**
  dot-agent-deck used to identify its own Claude Code hook rules in `~/.claude/settings.json` by looking for the literal substring `dot-agent-deck` in the rule's command. That worked only when the binary happened to be named exactly that. Installed under any other name — a rename, a fork build, a binary shipped as something else entirely — the rule it had just written became invisible to the very tool that wrote it: repeated installs accumulated one duplicate rule per startup instead of replacing the prior one, and `uninstall` could not find its own rules to remove.
  Rules are now identified by the exact command they run (`<binary> hook --agent claude-code`), not by any part of the binary's path or name, so install and uninstall recognise a deck-owned rule under any binary name, symlink, or rename — including one written by a completely different binary from the one currently running. A rule from before this fix, written in the older bare `<path> hook` form under the historical default binary name, is still recognised and migrated automatically. A binary path containing spaces is now shell-quoted so the resulting command still parses correctly, and a historical unquoted rule at such a path remains recoverable. `install` also drops any of its own rules whose binary no longer exists on disk, so rebuilding or removing an old binary no longer leaves an orphaned rule behind — a user's own hooks are never touched by this, only rules already recognised as the deck's own.
  Separately, a `~/.claude/settings.json` the deck could not parse — even something as small as one trailing comma — used to be silently treated as empty and overwritten, destroying the user's `model`, `env`, and `permissions` settings while still reporting success. Install now refuses to touch a settings file it cannot parse, leaving it exactly as found and keeping a backup copy alongside it.
- **Your Claude Code settings survive `hooks uninstall`, a co-located hook, and an interrupted write**
  Three ways dot-agent-deck could destroy configuration in `~/.claude/settings.json` — a file it does not own — are fixed together, because they were one problem seen from three sides.
  `hooks uninstall --agent claude-code` used to read the settings file leniently: anything it could not parse, down to a single trailing comma, was treated as an empty config and written back as `{}`, destroying the user's `model`, `env` and `permissions` (including `permissions.deny`) while reporting success and exiting 0. Uninstall now applies the same contract install got in the previous release — only a *missing* file means "nothing to uninstall", a file that cannot be read or parsed is left byte-for-byte as found with a backup preserved at `settings.json.bak`, and the refusal reaches the shell as a message on stderr and a non-zero exit ([#522](https://github.com/vfarcic/dot-agent-deck/issues/522)). Uninstall also no longer rewrites the file at all when none of the deck's hooks were in it, so it can neither reformat settings it did not change nor create a `settings.json` on a machine that never had one.
  A single hook rule's `hooks` array is a list of commands sharing one matcher, so putting your own hook in the same rule object as the deck's is a normal thing to do — and both install and uninstall used to delete that whole rule object, taking your command with the deck's. A user's `/usr/local/bin/my-critical-audit.sh` disappeared on `hooks uninstall` with nothing said about it, and because hooks are auto-installed at every dashboard startup, simply opening the deck was enough to lose it. Removal is now per command: only the deck's own command is taken out of a shared rule, the rule keeps its matcher and every other command, and a rule is dropped only once nothing is left in it ([#535](https://github.com/vfarcic/dot-agent-deck/issues/535)).
  Finally, the deck wrote `settings.json` by truncating it in place — over a file two deck processes and your editor all write. Claude Code reading inside that window saw an empty file, a crash mid-write left a permanently truncated one, and two decks starting at once could lose each other's updates. The file is now published by writing a temp file in the same directory and renaming it over the destination, serialized by an in-process lock, so a reader sees either the whole old file or the whole new one and an interrupted write leaves the original intact ([#534](https://github.com/vfarcic/dot-agent-deck/issues/534)) — closing the very hole that manufactures the unparseable settings file the refusals above exist to protect.
  Two smaller behaviour changes come with that publish. An existing `settings.json` keeps its own permissions exactly (a file you had kept at 0600 is not widened to 0644), and a settings file the deck creates from scratch is now owner-only. A `settings.json` that is a *symlink* — a dotfiles arrangement — is now refused rather than silently replaced with a regular file; point it at a real file, or edit the linked file's hooks by hand.
- **Concurrent dispatches no longer fail on each other's half-created worktree**
  Dispatching several agents at once could fail one of them before any agent ran, with `fatal: failed to read '.git/worktrees/<name>/commondir': Success`. The `Success` is the tell: git prints `strerror(errno)` for an errno nothing ever set, so the read came back short rather than failing. `git worktree add` scans the repository's worktree list before creating its own entry and reads every entry's `commondir`; another `git worktree add` that has created its entry but not yet written that file — two adjacent syscalls apart — makes that read come back empty. The loser died in the setup step, so the visible symptom was a dispatch failing for reasons unrelated to anything it was asked to do. A busy filesystem made it markedly more likely by widening the window.
  Worktree creation is now serialized per repository across processes, keyed on `git rev-parse --git-common-dir` so every spelling of one repository (the main checkout, any of its linked worktrees, a relative path) lands on one lock — separate decks serialize against each other, not merely tasks inside one. Serialization cannot cover an add the deck did not start, so `git worktree add` is additionally retried a bounded number of times (four backoffs, 1.5s in total) on that one signature. Nothing is swallowed: a `commondir` that stays unreadable — what a crashed add leaves behind — still surfaces as an error, and every other `git worktree add` failure stays a hard failure with git's own message. If the lock cannot be taken at all, creation proceeds unserialized rather than wedging the dispatch.
  Serializing creation also made one pre-existing misclassification reachable by design rather than by luck, so it is fixed here too: a second dispatch of a name whose worktree is still **there** is now reported as a live claim ("already claimed by another dispatch") instead of as a leftover branch whose "worktree is already gone" — which sent the user to `git branch -D` for a tree another dispatch was working in. A name whose worktree really is gone still reports the leftover branch, unchanged.
  The retry also repairs a second-order failure that made the first one sticky. An add that dies on the scan has already created its `-b` branch, so a naive retry failed with `a branch named … already exists` — and because a dispatch refuses to reuse an existing branch (it may hold committed work), the dispatch name stayed poisoned until the branch was deleted by hand. The branch is now re-probed on each attempt and attached rather than re-created.
- **A dispatched agent no longer sits in a fresh tab having been asked nothing**
  `dispatch --single` could spawn its agent, open its tab, write the task into the pane — and never submit it. The agent sat at an empty turn until the delivery deadline, the task text visible in its input box, and because `dispatch` exits as soon as the bytes are written nothing surfaced the loss; it was noticeable only because the agent visibly never started work.
  The cause was a race of a few hundred milliseconds between the agent's `SessionStart` and the prompt write. A prompt whose pane has not yet proved it can report a submitted prompt is written provisionally and retried until the agent confirms it, but a producer that identified itself only *after* the write was refused as an unauthenticated claim, which disarmed the retry for the rest of that delivery. On this path the retry is not a safety net: the first write is routinely swallowed by a Claude Code TUI still finishing its boot, so the deliveries that work are the ones that retry. Losing the race therefore lost the whole dispatch.
  The deck now accepts a producer identifying itself after the write on a pane it spawned itself with an agent type it selected — for `dispatch --single`, the `default_command` the daemon exec'd, which is a statement about the pane made before a byte of the prompt was written, and one the deck wrote rather than observed. Panes the deck cannot vouch for are unaffected: a bare shell, `cat`, a recorder stand-in or any command the deck could not resolve still refuses a post-write capability claim, so an unauthenticated producer still cannot arm a replacement payload and its submit keystrokes into a pane that may be a shell.

### Miscellaneous

- **The repository-state preflight is now tested against real repositories**
  `cargo xtask linkage-check` refuses to run its catalog checks against a repository whose object store has been truncated by a shallow fetch, or whose worktree registry still lists a worktree that is gone. Until now the code that decides that was well tested but the code that *asks git* was not tested at all — so the preflight could have silently stopped running while still reporting success, which is worse than having no preflight, because a green run reads as a positive signal.
  The collector is now driven by twenty-one new tests. Fourteen of them build genuine repositories in a temporary directory with real `git` and check what the preflight makes of each: a shallow clone whose linked worktree shares the truncated object store, and one whose path contains a literal newline, must both be reported; a worktree removed without pruning, and one whose directory survives but whose contents do not, must both be reported as registry drift; a CI-style shallow clone with a single worktree, and a bare repository, must both still pass. The remaining seven drive the collector through a stub, which is the only way to see the git argument list itself and the fallback for git versions older than 2.36, neither of which leaves any trace on a healthy repository.
  Every one of the twenty-one was confirmed to fail against a deliberately broken collector before being accepted as passing, across nineteen injected single-line defects. They run in the fast tier (`cargo test-fast`), adding about a fifth of a second.
  Added `python314Packages.pyte` to `devbox.json` so a PTY capture can be replayed into a final screen locally. Rule 12's cross-version manual test asks what an *older TUI* does with a newer daemon's output, and that question is only answerable by reading the screen — but a raw `script` capture of a ratatui app is a diff-based stream of cursor moves, so stripping escape sequences from it recovers nothing, and naively tailing it recovers the last repainted region rather than the frame. Verifying #548's reverse direction needed the actual frame, which is how the daemon-synthesized delivery notice was confirmed to land on the correct pane's card as `● Error` on a v0.36.0 client that has no `apply_daemon_report_event` to guard it. `pyte` is a pure-Python VT100 emulator, so the replay is ten lines and needs no terminal. Developer tooling only — nothing links it into the shipped binary, and the automated tiers are unaffected.

## [0.40.0] - 2026-08-17

### Changed

- **A worker's completion report can no longer land in the wrong orchestration's worktree — and an old `work-done` CLI now has every report refused, not just stale ones**
  **Behavioural change.** `handle_work_done` used to resolve a report's destination purely from the sender's bare `pane_id`, via `pane_cwd_map`/`pane_role_map` — the same maps `register_orchestration_role` overwrites whenever a pane_id is reused (a torn-down worktree's role pane recycled by a later, unrelated orchestration). A report produced under one registration but delivered after that pane_id was reassigned would silently land in the new tenant's worktree, under the new tenant's role label, and surface in the new tenant's orchestrator feedback — with the original sender's report simply gone.
  Every pane registration now carries a generation counter, reserved and injected into the worker's own environment (`DOT_AGENT_DECK_REGISTRATION_GENERATION`, sibling to `DOT_AGENT_DECK_PANE_ID`) **at spawn time** — not re-read from the daemon when the worker later reports. That distinction matters: an earlier cut of this fix asked the daemon what the pane's generation was immediately before sending, which by construction is always the pane's *current* generation and could never disagree with itself microseconds later at delivery, so the actual issue #358 scenario (a worker that outlives its own orchestration's teardown) went straight through unchanged. Capturing the value at spawn means a worker's report genuinely carries the registration it was produced under; `handle_work_done` now refuses delivery (logs and drops, does not write) when that no longer matches the pane's current registration — the pane was re-registered, most likely for a different orchestration entirely, since this worker began.
  The misdelivery reported in issue #358 is fixed by this. A related, narrower leak on the same signal — a stale report still disarms the *new* tenant's silence/idle watch before the refusal, even though it writes nothing and notifies nobody — is out of scope here and tracked separately in issue #444.
  **M4 update: the generation counter alone did not actually close this issue, and now it does.** Independent reviewer and auditor passes on the above found that `pane_registration_generation` is an in-memory map: it resets to empty on every daemon restart, exactly like the counter it guards. Two daemon processes — a pre-restart one and the post-restart one that reuses the same pane_id — both start that pane at generation `1`, so a signal produced before the restart and delivered after it compared equal and was delivered anyway. This is issue #358's own motivating scenario (a worker that outlives a daemon restart, not merely a same-process re-registration), so it was not actually fixed by the generation counter on its own.
  The generation is now paired with a `daemon_boot_id` — a value minted fresh once per daemon process (`AppState::daemon_boot_id`), reserved and injected into the worker's environment alongside the generation (`DOT_AGENT_DECK_DAEMON_BOOT_ID`, sibling to `DOT_AGENT_DECK_REGISTRATION_GENERATION`) at the same spawn-time point. `handle_work_done` now refuses delivery unless BOTH the generation and the boot id match the pane's current registration. A pre-restart daemon and the post-restart daemon that replaces it can never mint the same boot id, so a pre-restart signal can no longer slip through on a coincidentally-matching generation.
  **M4 also fixed an ordering bug the generation-only design made newly guaranteed (auditor B2).** `handle_work_done` used to run `retire_silence_watch`/`retire_outstanding_delegation` — bookkeeping that cancels the CURRENT tenant's own idle-worker watch — unconditionally, before the generation check. That meant a signal that was ultimately refused as stale still disarmed the current tenant's watch first, even though nothing was written and nobody was notified. This was already known as a general residual (issue #444). M4 round-2 review narrowed it further: the residual now covers only a pane `unregister_pane` already tore down, whose registration generation is deliberately left unchanged (see that function's doc) — such a pane still reaches the retire calls below and then falls through the `pane_role_map` miss, exactly as before M4. A pane that was NEVER registered at all is a different case, not part of #444's remaining scope: it now fails the compound-key check directly (there is no `pane_registration_generation` entry to match), so its bookkeeping is already protected by M4's fix rather than left open. Before this narrower framing, M4's fail-closed compound key had also turned one specific KNOWN-pane instance of the residual into a guaranteed hang: an old `worker-agent-deck` binary on a worker's `$PATH` during a rolling upgrade sends no generation and no boot id at all (`generation: 0`, `daemon_boot_id: ""`), which can never match a live registration — so every report from a not-yet-upgraded worker was both refused AND silently cancelling that worker's own idle-nudge watch, leaving a genuinely-still-working worker looking idle with no way to be flagged. The validation now runs before the retire calls, so a refused signal no longer touches the current tenant's bookkeeping at all.
  **Compatibility impact, no wire-shape change.** This rides the existing hook socket; no `PROTOCOL_VERSION` bump. A `work-done` CLI built before this change has no code path that reads or sends a registration generation or a daemon boot id at all, so its report is missing both fields entirely; `#[serde(default)]` decodes the generation as `0` and the boot id as `""` — neither ever matches a live pane's real registration (generations start at `1`; a real `daemon_boot_id` is always a non-empty minted value, see `DaemonBootId::default`). Every report from an old CLI is therefore refused as stale, not only genuinely stale ones — the fix's fail-closed design cannot distinguish an old binary from a delayed report from a torn-down orchestration or a pre-restart daemon; all three look identical on the wire.
  If you run the daemon and any worker's `work-done` CLI from different installed versions, upgrade the worker's binary alongside the daemon — a mixed old-CLI/new-daemon pairing will silently drop every worker completion report until both sides match. On this fork the binary you'd actually run is `worker-agent-deck` (`worker-agent-deck work-done --task-file …`), not `dot-agent-deck`.

### Fixed

  - **A Codex pane whose native hook install/trust fails no longer has its remit permanently abandoned**
    `ConfirmationCapability` for a Codex-identity pane was resolved from agent type alone (`Codex` always reports), so a pane whose native hook genuinely failed to install/trust — a real, anticipated, non-crashing failure that degrades events to stdout classification — was still misclassified `Reports`. It burned the full 60s escalating-backoff retry cycle against a live interactive Codex TUI, then permanently abandoned the tab's remit at the deadline, even though `Emitter::emit_with_metadata` hardcodes `user_prompt: None` on that degraded path, making TEXT confirmation structurally impossible for that pane. `dot-agent-deck wrap`'s Codex hook install/trust outcome (`codex_spawn_prep`) is now surfaced on the wrapper-fork `SessionStart` and recorded per-pane (`AppState::codex_hook_trust_failed`); `delivery_capability` now resolves `Reports` only once the hook is known-successful for that specific pane, resolving to `Unknown` otherwise so the pane's delivery stays provisional to the deadline and finalizes honestly instead of retrying and then abandoning. A Codex pane whose hook installs/trusts successfully is unaffected. This is a residual gap on issue #254, found during a third attempt at the underlying observability defect — issue #254 stays open (out of scope: redesigning `unconfirmed_retry_delay` in `src/prompt_delivery.rs`, a separate decision).
  Regression coverage spans the full plumbing chain, not only the `delivery_capability` seam: `delivery_capability_defers_codex_reports_to_hook_outcome` / `delivery_capability_still_reports_a_codex_pane_with_no_recorded_hook_failure` (`src/ui.rs`) pin capability resolution against `codex_hook_trust_failed` directly; `codex_spawn_prep_ok_zero_hooks_is_not_confirmed` (`src/wrap.rs`) drives `codex_spawn_prep`'s real `trust_deck_hooks_in` call against a synthetic `codex app-server` to pin the `Ok(0)` case in isolation; `codex_hook_trust_outcome_parses_true_and_false` / `codex_hook_trust_outcome_absent_key_is_none` / `codex_hook_trust_outcome_unrecognized_present_value_is_not_confirmed` (`src/event.rs`) pin the metadata parse; and `apply_event_records_and_clears_codex_hook_trust_failed` (`src/state.rs`) pins the recording/clearing of the per-pane failure set. Forcing a real, end-to-end Codex hook-install failure through a live `codex` CLI is still not deterministic and stays out of scope (this PRD's own Risk table), but every deterministic in-process seam in the chain now has a test.
  No-Test: every test this fix added or would add is an internal in-process unit test over `src/wrap.rs`/`src/event.rs`/`src/state.rs` plumbing (listed above), not a `#[spec]`-tagged TUI-harness test under `tests/`, because the only way to exercise this end-to-end is a real Codex native hook install/trust outcome, which is not deterministic (this PRD's own Risk table) — the same reasoning `codex_spawn_prep_ok_zero_hooks_is_not_confirmed` already works around by faking `codex app-server`'s output rather than invoking the real hook install path.
  - **Restored the retry-backoff-floor test override silently dropped by the 2026-08-15 upstream sync**
    Issue #257's fix (PR #268) — an overridable floor for `send_retry_delay`'s exponential backoff, via `DOT_AGENT_DECK_TEST_SEND_RETRY_BASE_MS` in test/debug builds — merged cleanly but its actual content never made it into `main`, found during #443's sync audit. Restored `send_retry_base()` and its supporting constants in `src/ui.rs`, and `orchestration/seed/017` (the pinning unit test) along with it.
    This restoration is **narrowed**: `orchestration/seed/018`, the companion test proving the confirmation-retry fires deterministically, is not restored. The retry path it targeted — `confirmation_grace_period()` / the `ui.orchestration_awaiting_confirmation` gate — no longer exists on `main`; that case is now gated by `unconfirmed_retry_delay` in `src/prompt_delivery.rs`, which this fix does not touch. That gap remains documented and issue #257 stays open to track it.
  - **The scheduled `issue_dispatch` worktree attach no longer races itself**
    Fork #331 closed the interactive TUI's own worktree-attach race by taking an exclusive lock around the whole probe→add attempt, but explicitly left the unattended `issue_dispatch` scheduler's separate, asynchronous `create_worktree` untouched — that path had no lock at all. Two scheduled dispatches attaching the same existing branch (or a scheduled dispatch racing an interactive attach) could both report success while git registered two administrative entries for one on-disk worktree, or leave one racer's `git worktree add` silently overwritten by the other's cleanup.
    `create_worktree` now takes the same lock, keyed the same way (`worktree_attach_lock_path`, anchored on the shared clone's real `--git-common-dir` rather than the branch name), so a scheduled dispatch and an interactive attach contend on the identical key instead of each locking a key the other never touches. Acquisition is bounded against the same 30s `WORKTREE_GIT_TIMEOUT` the surrounding `git` calls already use, via a new bounded-async primitive (`platform::lock::acquire_spawn_lock_bounded`) rather than an external `tokio::time::timeout` around the unbounded one — the bound lives inside the primitive so a timeout genuinely terminates the wait instead of merely abandoning it, refusing with an error rather than blocking a scheduler tick indefinitely if the lock cannot be granted in time.
    Issue #282 is now closed for both paths.
    **Restart both sides together after upgrading past this change.** The lock filename derivation also changed from `DefaultHasher` (not specified by std, effectively stable in practice but not guaranteed) to the explicitly stable `fnv1a64`. A daemon or TUI still running a build from before this change and one running a build from after it compute *different* lock filenames for the same worktree and therefore do not contend on the same lock at all — silently reopening the exact worktree-admin-entry corruption fork issue #331 closed, for the duration of any mixed-version window. This is a same-wire, different-meaning break (CLAUDE.md rule 12): nothing in the TUI↔daemon protocol version changed, but the on-disk lock-file naming contract between an old and a new build did. Upgrade by restarting the daemon and any attached TUI onto the matching build rather than rolling one side forward independently. (Recorded here rather than as a separate `changelog.d/282.breaking.md` fragment: `cargo xtask work-type-check` classifies any `.breaking.md` suffix as PRD-type work regardless of content, which conflicts with this branch's `bug` classification — a real gap between the tool and CLAUDE.md rule 12's stated policy that a `.breaking.md` fragment should be able to pair with either a `fix/` or `feat/` branch. Flagging for the maintainer rather than fixing the tool as part of this PR.)
    Also worth knowing, not itself a compatibility break: the interactive TUI's own worktree-attach (`create_worktree_sync`, on the render/event loop) can now block that loop for up to the same 30s bound the scheduler's async path already used, on a scheduled dispatch contending for the same lock. Bounded and intended, not a regression, but a new source of a brief TUI stall worth knowing about if one is observed.

## [0.39.0] - 2026-08-17

### Changed

- **Attach-protocol bump: daemon-authoritative `pane_id` (`PROTOCOL_VERSION` 8 → 9)**
  **Wire-shape and semantic change.** `AttachRequest::StartAgent` used to trust whatever `DOT_AGENT_DECK_PANE_ID` the attaching client proposed inside its `env`, extracted server-side into `pane_id_env`. Two independently-attached clients never coordinate that value with each other or with the daemon beyond a one-shot hydration bump, so the same id could be minted twice — most dangerously across a daemon restart, or by two panes with no live overlap at all — and every consumer keyed on it (routing maps, report-path digests, `AgentPtyRegistry`) would silently collide or misroute. See PRD fork#365 for the full evidence trail.
  The daemon is now authoritative: it mints its own collision-resistant `pane_id` (a per-process nonce hashed from PID + nanosecond epoch time, combined with a monotonic per-process sequence — the same recipe `mint_orchestration_id` already used, prefixed `pane-` for legibility) at `StartAgent` time, overriding whatever the client sent, and returns it on the new `AttachResponse.pane_id` field. That field is additive on the wire, but this is a same-wire/different-*meaning* semantic break, not a forward-compatible add: an old client that doesn't read the returned `pane_id` keeps minting a client-side id the new daemon never asked for and no longer treats as authoritative — exactly the ambiguity this change exists to close. `PROTOCOL_VERSION` bumped from 8 to 9 so the attach handshake refuses the mismatched pairing rather than letting a stale client limp along in that broken mode, matching the codebase's only existing cross-version policy (fork #17 / upstream #405): the local-attach handshake recovers by restarting the daemon to match the attaching binary; the remote/SSH path points the user at `remote upgrade`.
  Compatibility impact: a TUI and daemon must be on the same `PROTOCOL_VERSION` to interoperate. After upgrading in place, an older still-running daemon and the new TUI will fail the handshake until the daemon is restarted (the standard recovery the build-version handshake already prompts for).
  `spawn_agent`'s existing duplicate-`pane_id_env` rejection (`agent_pty.rs`) stays in place unchanged as a backstop — it now defends against a daemon-minting bug rather than a client-minting race, a strictly smaller threat surface. Every downstream consumer of `DOT_AGENT_DECK_PANE_ID` (hooks, `issue claim`'s identity resolver, report-path digests, the pane-keyed routing maps) treats the value as an opaque string and needs no change.
  Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.

### Fixed

  `codex_hooks_manage`'s hook command line now quotes the deck's own binary path with `cmd.exe`-safe escaping on Windows instead of `platform::paths::shell_quote_if_needed`'s POSIX single-quoting, which `cmd.exe` treats as an ordinary literal character rather than a quote. `codex_home()` is documented as intentionally reachable on Windows via `$CODEX_HOME` (Codex hook installation is meant to work there, unlike `devin_hooks_manage`'s config dir, which is `#[cfg(not(unix))]`-gated to `None`), so a binary path containing a Windows-typical hazard such as `~` or a space previously produced a hook command `cmd.exe` could never locate.
  No-Test: pinned by a new plain `#[test]` in `src/codex_hooks_manage.rs`'s `mod tests` (`build_command_quotes_a_windows_hazardous_path_so_cmd_exe_locates_it`), round-tripped through a real `cmd.exe` the same way fork #283's `watch_invocation` tests are — not `#[spec]`-annotated, since this is internal shell-quoting logic with no independent TUI-visible scenario to narrate.
  Windows watch-pane invocations (`dot-agent-deck watch --interval N <command>`, spawned into a `watch = true` mode pane or reactive rule) now quote the executable and command positions with position-aware, `cmd.exe`-safe escaping instead of reproducing `main`'s pre-#157 `{:?}`-Debug-escaped format. `{:?}` is Rust `Debug` escaping, not a `cmd.exe` grammar: `cmd.exe` does not treat a backslash before an embedded `"` as an escape, so a watch command containing `" & <anything> & rem "` closed the quoted word early and ran the injected tail as its own, unquoted command (finding A1 on fork PR #277) — and the executable token, emitted bare, was never locatable at a path containing a space either (issue #157's original executable-quoting regression, still present on Windows only).
  Any control character inside `command` — including `\t`, not only `\r`/`\n` — is now replaced with a space before either quoting pass runs, rather than left raw. No caret encoding can neutralize a raw control character the way it neutralizes every other `cmd.exe` metacharacter — on the persistent-watch-pane path the Windows console's cooked-mode line editor consumes several as *editing commands* before `cmd.exe`'s own grammar is ever consulted (a newline submits the current input; `ESC` clears the entire typed buffer, up to and including the program token; `BS`/`DEL` delete backwards; `ETX` cancels the line), and on the `/C <string>` path `cmd.exe` treats an embedded newline as a statement separator the same way a batch file would — so a `[[modes.panes]]` `command` value containing a real newline, or an `ESC`/`BS`/`ETX` byte (all legal TOML), previously either ran everything after it as its own, separate `cmd.exe` command, or — for `ESC` on the typed-PTY path — let `cmd.exe` run an attacker-chosen program name outright. This was a regression against `main`, whose old `{:?}`-Debug-quoted format at least kept the mangled content on one line and never emitted a raw control byte (PR #423 review findings B1 and C1).
  `escape_cmd_exe_program`'s escape set also now includes `;` and `=`, `cmd.exe`'s other two command-line delimiters besides `,` (already escaped) that are legal in NTFS path components — a deck installed under a path containing either previously split the program token the same way an unescaped space did in #157. Both functions' doc comments now state plainly that `%` and `!` are only incidentally, not actually, neutralized (delayed expansion still reaches `!VAR!`; an undefined `%VAR%` still mangles under batch-file rules), per this issue's explicit request not to leave that implied.
  No-Test: pinned by new plain `#[test]`s in `src/mode_manager.rs`'s `mod tests` (`watch_invocation_prevents_a1_command_injection_through_real_cmd_exe`, `watch_invocation_quotes_a_spaced_executable_so_cmd_exe_locates_it`, `watch_invocation_neutralizes_control_characters_through_real_cmd_exe`, `quote_cmd_exe_arg_recovers_the_exact_argument_bytes_through_a_real_child_process`) and `src/platform/shell.rs`'s `windows_quoting_tests` (`quote_cmd_exe_arg_replaces_every_control_character_with_a_space`), each round-tripped through a real `cmd.exe` where practical (the last through a real compiled child process) rather than asserting on the generated string alone, per this issue's own "done looks like" bar — not `#[spec]`-annotated, since this is internal shell-quoting logic with no independent TUI-visible scenario to narrate.

### Added

Without the cap, a long model would have pushed the session's own identity off the title entirely; with arbitrary text it could have forged one.

### Fixed

  - **The hook CLI no longer reads an unbounded stdin payload**
    `read_stdin` read the incoming hook event to completion with no size cap, unlike the reply path a few hundred lines below it in the same file, which has been carefully bounded since fork issues #99/#101/#125. A wedged or misbehaving agent harness writing an enormous hook payload would have the short-lived hook process allocate it in full before rejecting it at the JSON-parse stage. The hook **CLI's** read is now capped (reusing `daemon_protocol::MAX_FRAME_LEN`'s literal, 16 MiB — sized for a tool's whole argument, e.g. a `Write`/`Edit` call's full file content, rather than the reply path's much smaller seed-sized cap; the reuse is of the number only, not of that constant's framed-transport rationale, since the hook path is newline-delimited, not framed) and a payload over the cap is rejected outright rather than truncated and handed on to the parser, which could otherwise turn a corrupted payload into one that happens to still parse.
    This closes the unbounded read in the short-lived, single-event hook CLI process only. The **daemon's** hook-socket reader (`src/daemon.rs`'s `BufReader::lines()`) is a separate, still-unbounded read in a long-lived, multiplexed process and is not touched by this change — tracked as its own follow-up in #393.

That third clause is declined here, deliberately: `src/hook.rs` calls no `tracing`/`eprintln!` anywhere, and every other failure on this path (malformed JSON, an unmapped event type, a failed socket send) already returns silently, so adding a diagnostic only for the over-cap case would be a new pattern in an otherwise-silent file rather than an extension of its existing one.   - **Shutdown's non-reaping exit peek: bounded EINTR retry, an honest error-classification comment, quieter logging, and a test-only shell-injection hazard closed**
    `observe_exit_without_reaping`'s non-reaping `waitid` peek (graceful shutdown's phase 2) retried an `EINTR` in an unbounded loop with no reference to the grace-window deadline. Genuinely unreachable in production — `waitid(2)` documents `EINTR` only when `WNOHANG` is unset, and this call always sets it — but an unbounded retry around a syscall is worth bounding regardless. The retry now stops once the shared grace-window deadline passes (and, independently, after a small fixed number of immediate retries, so a persistent `EINTR` cannot busy-spin one agent's peek for the rest of the grace window and starve its siblings' polling), falling back to the same conservative "still running" default the surrounding code already uses for an unclassified error. The comment justifying that default previously described protecting the grace window from a *transient* failure; after the bounded retry, the only error reachable there is a permanent misuse, not a transient one, so the comment was rewritten to say that plainly rather than describe behavior the code no longer has. One further comment, unrelated to behavior, was corrected: a claim that skipping the pre-#163 `.all()` short-circuit "affects how promptly the early break can trigger" — it does not; only the number of `waitid` syscalls issued per round changed.

The warn-once suppression and the two comment corrections have no independently testable behavior beyond what those tests already pin.
- **Concurrent orchestrations no longer corrupt each other's git state**
  Running several orchestrations at once shares one git repository between them — one worktree registry, one object store — and nothing scoped either. A worktree isolates your working tree; it does not isolate the two things underneath it, and both were writable by everything on the machine. Two failures came out of that, and neither announced itself.
  **Two orchestrations creating a worktree on the same existing branch could both succeed.** Git serialises the creation of a *new* branch on its own ref lock, so that case was always safe. Attaching an *existing* branch was not: both processes exited 0, and git registered two separate administrative entries pointing at one directory. Nothing downstream had any reason to look, because both callers were told they had created it.
  The same race had a second shape that only appeared once the first was measured properly. A caller whose own attempt timed out would clean up after itself — but with nothing serialising the two, that cleanup could remove the *other* caller's just-completed registration instead, leaving a worktree that had been reported as created with nothing registered for it. Both shapes are closed the same way, for the attach made from the interactive TUI's own worktree-creation path: an attach now takes a lock covering the whole attempt, including any cleanup it triggers, so two attempts on one directory can no longer interleave at all. The loser is told the worktree is already claimed, which is what every caller already believed was happening.
  **This closes the race only for that one path.** The unattended `issue_dispatch` scheduler attaches worktrees through a separate, asynchronous implementation that this change does not touch, so two scheduled dispatches (or a scheduled dispatch racing an interactive attach) can still hit the same corruption this fragment describes. Issue #282 stays open for that remaining path.
  **A shallow fetch anywhere made the whole repository shallow, for every worktree at once.** The marker git writes for that lives beside the object store rather than in the worktree that caused it, so one truncated fetch silently truncated history for every orchestration on the machine. Nothing reported an error. Logs read normally, status was clean, and branches still resolved to the commits you expected. The only symptom was that merges and rebases against the upstream remote began failing as though the histories were unrelated — which reads like a misconfigured remote, not a truncated one, and sends you looking in the wrong place. `worktree list` now says so plainly when it sees a shallow clone, explains that every worktree sharing it is affected rather than just whoever ran the fetch, and gives the command that repairs it.
  Neither failure was reachable by a single orchestration working alone, which is why both survived: each needs two, and their symptoms surface far away in time from their cause.

  Three defects in the orchestration command-entry lock. A bracketed paste into a locked worker pane was delivered instead of being dropped, so the lock held against typing but not against pasting. The bottom-bar hint read `Pane locked — Ctrl+d then Ctrl+e to unlock`, which omits the third keypress actually required — `Ctrl+E` leaves you in command mode — and now reads `Pane locked — Ctrl+d, Ctrl+e, Ctrl+d to type here`.     On Unix, the `[features]` flag resolver walks up from the working directory looking for the project's `.dot-agent-deck.toml` (fork issue #303). That walk was unbounded, so a deck launched anywhere under a shared, world-writable directory (like `/tmp`) could adopt a config another user planted there — including when the launch directory itself was the world-writable one. A world-writable ancestor is now declined — with a warning naming the declined path, surfaced on stderr at startup as well as to the log — and the search continues upward to the nearest safe ancestor, so discovery from a normal project subdirectory keeps working exactly as before. If no ancestor can be trusted at all, the deck no longer guesses: experimental features stay off and no config file is watched for the rest of the run, rather than silently falling back to a path it just declined. Windows is unchanged; the ancestor walk there is still unbounded and is tracked separately as fork issue #383.
  No-Test: the resolver logic itself (a guarded fallback, a three-state directory-safety check, a "nowhere trustworthy" outcome) is pure data and is covered by the plain `#[test]` fixtures in `src/config.rs`'s `mod tests`, extended in this round. Its one user-visible surface — the startup stderr warnings this now prints — is already covered by the `startup_warning_001`–`003` end-to-end tests in `tests/e2e_features_status.rs`; a dedicated case for the newly-declined-ancestor path is tracked as a follow-up (fork issue #387) rather than added here.
  - **A swapped features-config target can no longer hang deck startup**
    `load_features_file` used to stat the target and then open it as two separate steps. Between them the target could be replaced, and if the replacement was a FIFO, opening it blocked indefinitely waiting for a writer — on the synchronous startup path, before the watcher thread even exists. The loader (and its diagnostic mirror used by `features status`) now opens the target first, non-blocking on Unix, and validates the same handle it opened, so there is no window between the check and the use and a FIFO is rejected immediately instead of blocking. On Windows, opening a directory target now requests backup semantics so it still reports as non-regular instead of unreadable, matching prior behavior there.
  No-Test: this is a pure-data fix to the shared open-then-validate loader, covered by the existing FIFO regression test in `src/config.rs`'s `mod tests`. The TOCTOU race itself can't be reproduced deterministically from a test — the window is a handful of instructions between two syscalls — so that test pins the fix's load-bearing half (a FIFO target no longer hangs startup) rather than the race itself.

### Miscellaneous

  New `issue-triage.yml` workflow stamps and clears a `needs-triage` label from live `priority-*`/`size-*` label state.
  The workflow stamps `needs-triage` on any issue missing a `priority-*` or `size-*` label — on open, reopen, and every later labelling change, not only at creation — and clears the stamp once both are present. Issues carrying `wontfix`, `duplicate`, `invalid`, or `question` are treated as exempt and left alone even while under-labelled. New issue-form templates, a `CONTRIBUTING.md` section, and a CLAUDE.md rule ask filers to apply both labels themselves at filing time; `needs-triage` is the backstop for anything that slips through, not a substitute for labelling carefully.

## [0.38.0] - 2026-08-15

### Changed

- **Attach-protocol bump: kept-worktree signal (`PROTOCOL_VERSION` 7 → 8), and issue-dispatch no longer force-removes a dirty worktree on close**
  **Wire-shape change.** Closing a dispatched tab/card can now leave its worktree on disk instead of removing it — uncommitted work, a status probe that itself failed, or the removal itself failing — and the daemon needs a way to tell an attached TUI where the work survives. The daemon→TUI event broadcast (`BroadcastMsg`, forwarded over the attach socket's `KIND_EVENT` frame) gained a new `worktree_kept` variant carrying the retained path and why. That is a wire-shape change an older peer would fail to deserialize, so `PROTOCOL_VERSION` bumped from 7 to 8 and the attach handshake refuses across the mismatch — the same reason PRD #120's own `orchestration_surface` variant bumped 3 → 4.
  Compatibility impact: a TUI and daemon must be on the same `PROTOCOL_VERSION` to interoperate. The daemon deliberately outlives the TUI, so after upgrading in place an older still-running daemon and the new TUI will fail the handshake until the daemon is restarted (the standard recovery the build-version handshake already prompts for). Hook events, the single-agent live-surface path, and `orchestration_surface` are unchanged.
  **Behavioural change.** Scheduled issue-dispatch (issue #120) used to `git worktree remove --force` a dispatched worktree on tab close, unconditionally discarding any uncommitted work the agent had left behind — the removal policy the shipped code cited for this was that a surviving worktree reads as "issue already claimed" to `dispatch_decision` and would skip that issue on every later fire, forever. This PRD unifies issue-dispatch onto the same `KeepIfDirty` policy the (unscheduled) `dispatch` CLI subcommand already used: a **clean** worktree is still removed and its slot freed immediately, but a **dirty** worktree — or one whose status couldn't be checked, or one `git worktree remove` itself failed against — is left in place instead of discarding the work, and every attached TUI is notified where it's sitting. `dispatch_decision` still sees the surviving path and still (correctly) skips the issue on later fires, so the slot is **not** freed until you resolve the worktree's contents and run `worktree reclaim` yourself — `worktree list --json` reports a kept, deck-marked `#120` worktree as `owned: true`, and once its dirtiness is resolved and its PR merges, a bare `worktree reclaim` frees the slot.
  If you were relying on issue-dispatch silently discarding a dirty worktree to keep the slot cycling automatically, that no longer happens — you (or `worktree reclaim`, once the tree is clean and its PR has merged) now have to clear it explicitly.
  Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.

### Added

  **New: `dot-agent-deck issue claim <n> [--repo owner/name] [--takeover] [--confirm-stopped]` — claims a GitHub issue and exits non-zero when someone else already holds it.** Call this a **claim**, not a lock: it is cooperative coordination against accidental collision between agents working the same deck, and replay and forgery of the claim record are explicit non-goals. The command uses three surfaces for three different jobs. The `in-progress` label says *that* the issue is held, cheap for `dispatch_decision` and any external tool to read. The **assignee** says *who owns it now* — replaced on each claim, so it always names the current holder and nobody else. The comment log says *who has held it, in order* — appended, never edited, so the history survives a takeover. `--takeover` alone still refuses, and tells you to re-run with `--confirm-stopped`; that two-step is deliberate friction, so an agent cannot satisfy its own override in the same breath it discovers the conflict. A takeover rewrites the claim record naming who it took over from — it does **not** stop the agent it took over from, which may still be running.
  Two things worth stating plainly rather than discovering later. First, **the worktree's absolute path — and now also the machine's hostname — is published in a public GitHub comment on every claim.** That is deliberate — CLAUDE.md rule 23 already did this by hand, precisely so a human can cross-check a claim against `git worktree list` — but on the unattended `issue_dispatch` path, this now happens **automatically, per claim, at cron rate**, publishing the daemon host's directory layout, plus its hostname, to a public issue comment without a human in the loop for any individual claim; the two together are correlatable across every issue the same host has ever claimed, which the path alone was not. Second, **every pre-existing claim comment now reads as "no identity"**: the parser this command reads back is scoped to its own comment shape, so an issue claimed under an older format refuses with "identity unknown" the next time anyone tries to claim it. Recover with `--takeover --confirm-stopped` once you've confirmed nothing is still working the issue under the old claim.
  **The removal half of replace-to-one reads GitHub's own assignee list, never a claim comment.** `dot-agent-deck issue claim` computes the assignee it removes as *current GitHub assignees minus the claimant*, read straight from `gh issue view`'s `assignees` field — not by parsing anyone's `, for @<login>` clause back out of a comment. That clause is still rendered into every claim comment, because a human reading the issue wants to see who claimed it, but nothing parses it back for a write: no comment, however it is worded or who wrote it, can drive a removal. The cost this pays for, stated plainly rather than left to be discovered: **the deck can overwrite an assignee a human set by hand**, because GitHub's assignee list does not record who set it or why — a human-assigned issue that a deck then claims will have that human's assignment replaced, exactly as if a second deck's claim had. That is the assignee field's own defined meaning — *the human who owns the agent working the issue right now* — enforced consistently, not a special exemption for a human's own assignment.
  Prose in this fork calls the product `worker-agent-deck`; the binary name in a command you would actually paste and run is still `dot-agent-deck`.
  **`worker-agent-deck worktree list` now names a specific owner for every worktree — an agent identity, a human, or a stated "unknown" — instead of a bare `owned: true/false` bit.** Previously the only signal was whether the deck could prove it created a worktree; a hand-made worktree (an ordinary `git worktree add`, the normal path when following this project's own worktree-per-change discipline) reported no owner at all, and the only way to answer "who does this belong to?" was to read `git log` authorship, which is not the same question. Every row in `worktree list --json` now carries `owner_kind: "agent" | "human" | "unknown"` beside the existing `owner` string: `"agent"` for a deck-created worktree whose ownership marker names an identity, `"human"` for an unmarked, hand-made worktree (resolved via the same `gh api user` login lookup `issue claim` already uses, rendered as `human:<login>@<host>`), and `"unknown"` when neither can be established — a pre-existing legacy marker with no recorded identity, or a login that could not be resolved (`gh` absent, unauthenticated, or failing). `worktree list` never crashes or guesses in the failure case; it says so.
  **This does not change what a bare `reclaim` is allowed to remove.** Reporting an owner and deciding whether a worktree can be deleted without `--yes` are kept as two independent questions, resolved independently: a human-owned worktree is now correctly *named* as such, but removal authority still comes strictly from the deck's own creation marker, exactly as before. A merged, clean, human-owned worktree still requires `--yes`.
  `worktree list --json --mine` also now surfaces two disagreement cases directly in the JSON document (previously stderr-only, or silently dropped) so an automated consumer reading stdout alone can see them: a row where the ownership marker names the caller but the independent ownership check disagrees, and a row that is deck-owned but carries no identifiable marker owner (most often a pre-existing legacy marker). Neither changes which rows `--mine` returns — both are reporting-only, added to a new `warnings` array alongside the existing worktree list.

### Fixed

- **Watch panes now start when worker-agent-deck is installed at a path containing a space**
  A watch pane runs by building a shell command line that contains worker-agent-deck's own executable path followed by the command to watch. Neither operand was shell-quoted: the executable went in bare, so an install path such as `/opt/My Deck/worker-agent-deck` split into two words and the pane never started, and the command went through Rust's debug formatting, which looks like quoting but is not a shell-quoting contract — a command containing `$`, backticks or a real newline was still mangled or re-interpreted.
  On Unix both operands are now POSIX single-quoted, verified by round-tripping values through a real shell and comparing the recovered bytes rather than by inspecting the generated string.
  On Windows no quoting is applied, deliberately. `cmd.exe` has no equivalent single-quote construct, and a correct implementation has to be position-aware: the escaping needed to contain an embedded quote in the command breaks ordinary executable paths such as `C:\Program Files (x86)\...`. Windows behaviour is therefore byte-for-byte identical to previous releases — which remains inadequate for a watched command containing shell metacharacters, and is tracked separately as issue #283.
- **A pane could still read Idle while its shell command was still running — the remaining ways in are now closed**
  A previous fix made worker-agent-deck's shell-activity monitor honest about its own uncertainty: when the process-table sample it uses to detect a running shell command failed under load, the daemon started logging that instead of quietly treating it as "nothing is running." That made the problem visible without removing it, because visibility on its own does not stop a pane from actually reading Idle mid-command.
  This closes several of the paths that were still causing that. A single unusually large command line could make one process-table sample cost several hundred kilobytes, sampled twice a second — under sustained load that alone could push a sample past its size cap, and an over-cap sample now reports "no sample" through the same honest path a slow sample already used, instead of contributing to the contention that caused the slowness in the first place. Separately, one specific check inside that sample — whether a candidate process still belongs to the shell session being watched — could answer "no" with false confidence when the process's session couldn't actually be read, rather than admitting it didn't know; it now reports unknown instead, so a pane won't be told a command has finished when the daemon never actually confirmed that. And on a deck running several panes at once, one pane sampling successfully no longer resets the shared signal that the others were relying on to show they were degraded — each pane's own uncertain state is now tracked separately, so a healthy pane can no longer hide a struggling one sitting right next to it.
  None of this changes what a healthy sample reports. The only behavior that moves is what happens when the daemon genuinely cannot tell: rather than asserting Idle, it now leaves the pane's last known status alone and records the uncertainty in its own log instead.
- **A worktree whose ownership marker failed to write is no longer silently reclaimable**
  When worker-agent-deck creates a worktree it writes an ownership marker into that worktree's private git directory, which is how `worktree reclaim` later knows the worktree is its own and can remove it without asking. If writing that marker failed — a full disk, a read-only or unwritable git admin directory, an unresolvable git-dir — the failure was discarded: creation reported success, nothing was shown to the user, and the only trace was a line in the daemon log. The worktree then looked foreign to the deck, so `reclaim` would ask about it, and there was no way to tell that apart from a genuinely foreign worktree.
  Both creation paths now surface the failure at the moment it happens, which is the one moment the tool has that information. The interactive path adds a non-fatal warning to the status it already shows after creating the worktree, and scheduled issue dispatch reports it as its own event while still going on to spawn the agent — a failed marker is a degradation, not a reason to strand a worktree that was created successfully. The warning names the worktree and says plainly that reclaiming it later will need `--yes`. The `worktree reclaim` help text has been corrected to match: a worktree skips the confirmation only when the deck created it **and** successfully marked it, which is the claim that can silently fail.
  The marker write itself is now atomic — written to a temporary file alongside the marker and renamed into place. Previously a write that failed partway through could leave a partially written marker file behind, and because ownership was decided by the marker's presence rather than its contents, that half-written file still counted as proof of ownership. A worktree could therefore be told it needed `--yes` while actually being removable without it. A failed write now leaves the marker either absent or exactly as it was, so the two agree.
- **`worktree list --mine` no longer reports a silent empty answer when it isn't sure**
  `worktree list --mine` filters out any worktree where the ownership check and the ownership marker disagree with each other — that filtering is correct and unchanged, since the two signals contradicting each other is not something worker-agent-deck should guess its way past. What was wrong is that when this happened, the command printed `no worktrees owned by <x>` and exited successfully, asserting a definite empty answer while it was actually sitting on evidence of a contradiction it chose not to mention.
  Now, before that filter runs, worker-agent-deck prints one line per disagreeing worktree explaining what it found and why the worktree is being excluded rather than trusted either way. The underlying disagreement is usually a transient race in how ownership gets checked, and if it persists across a re-run it's worth checking the ownership marker and the deck's admin directory directly. The command's answer for worktrees it is confident about is unchanged; the difference is that you can now tell "there really are none" apart from "there might be, and I'm not guessing."
- **Claude Code hook rules are now recognised regardless of the deck binary's name**
  worker-agent-deck used to identify its own Claude Code hook rules in `~/.claude/settings.json` by looking for the literal substring `dot-agent-deck` in the rule's command. That worked only when the binary happened to be named exactly that. Installed under any other name — a rename, a fork build, a binary shipped as something else entirely — the rule it had just written became invisible to the very tool that wrote it: repeated installs accumulated one duplicate rule per startup instead of replacing the prior one, and `uninstall` could not find its own rules to remove.
  Rules are now identified by the exact command they run (`<binary> hook --agent claude-code`), not by any part of the binary's path or name, so install and uninstall recognise a deck-owned rule under any binary name, symlink, or rename — including one written by a completely different binary from the one currently running. A rule from before this fix, written in the older bare `<path> hook` form under the historical default binary name, is still recognised and migrated automatically. A binary path containing spaces is now shell-quoted so the resulting command still parses correctly, and a historical unquoted rule at such a path remains recoverable. `install` also drops any of its own rules whose binary no longer exists on disk, so rebuilding or removing an old binary no longer leaves an orphaned rule behind — a user's own hooks are never touched by this, only rules already recognised as the deck's own.
  Separately, a `~/.claude/settings.json` the deck could not parse — even something as small as one trailing comma — used to be silently treated as empty and overwritten, destroying the user's `model`, `env`, and `permissions` settings while still reporting success. Install now refuses to touch a settings file it cannot parse, leaving it exactly as found and keeping a backup copy alongside it.
- **A crafted directory name could rewrite what `worktree list` showed you**
  worker-agent-deck printed worktree paths, and git's own error output, straight to the terminal. A directory name containing terminal control characters — an ESC sequence, a carriage return, a bidirectional-text override — is acted on by the terminal rather than displayed, so a crafted name could overwrite or reorder the lines around it: hiding a worktree from the listing, or making a row appear to say something it did not. That matters most in `worktree reclaim`, where the listing is what you read to decide which worktrees to delete.
  Every terminal output path in `worktree list` and `worktree reclaim` now rewrites control and bidi characters to a visible escaped spelling before printing, including the raw error text git produces when enumeration itself fails. The escaping is injective, so two directory names that differ still render differently rather than collapsing into the same display string. `--json` output is deliberately left raw, since it is consumed by programs rather than by a terminal.
- **A forged "waiting for you" status could no longer be told apart from a real one**
  A status planted on a pane by an unidentified producer could be silently promoted to a trusted one. worker-agent-deck tracks, per pane, whether a pending-permission marker is currently set — a plain `WaitingForInput` always clears that marker, and a tagged `ToolStart` treated a missing marker as proof that the waiting prompt it was now looking at must be its own. That heuristic didn't check who had set the status being looked at: an unidentified producer could plant a forged "waiting for you" status on a pane, and the moment the pane's genuine agent did anything at all — emitting its own `ToolStart` — that tag treated the forged status as self-authored and left it in place, laundering it into something the deck now trusted.
  The deck now only applies that heuristic when the current status came from an identified producer. A status of unknown provenance no longer gets treated as trustworthy just because the pane's own agent later touched it.
- **The drift-check workflow could never report drift when there was any**
  The `drift-check` workflow measures how far `main` has drifted from the fork's curated branch and reports the oldest un-curated commit's age. It found that age by piping `git log --reverse` into `head -1` to grab the first line of the reversed log. `head` exits as soon as it has its one line, closing the pipe while `git log` still has commits left to write — `git log` receives SIGPIPE and dies with exit code 141. The step runs under `set -uo pipefail` and GitHub's default `shell: /usr/bin/bash -e {0}`, so that 141 aborted the whole step with `Process completed with exit code 141`, and nothing after the crash — including the summary drift-check exists to produce — ever ran.
  This was deterministic, not a flake: the crashing line only runs when the commit count is greater than zero, which is exactly the case the workflow exists to report. It could only ever succeed when drift was precisely zero.
  The pipeline now reads `git log | tail -1` instead — dropping `--reverse` and taking the *last* line of the log yields the same oldest commit, but `tail` reads to EOF, so `git log` is never SIGPIPEd and no output is suppressed.
- **Feature flags were read from the deck's launch directory, so a deck started outside its project silently ran with everything off**
  `features_config_path()` resolved the `[features]` table against the deck process's own working directory, while every other config read in the deck resolves against an explicit project directory it was handed. That made the feature flag the only config keyed to where you happened to be standing when you started the deck.
  Launch the deck from anywhere but the project root and it read `[features]` from a file that usually did not exist. A missing file is the documented default, so the flag resolved OFF and stayed OFF — the ~2s watcher re-read the same non-existent path forever. Nothing said so: there was no warning, and the one startup log line reporting the flag's state surfaces only when file logging is enabled. The symptom was a feature that simply did not work, indistinguishable from one that had been removed. It was found because it disabled the orchestration command-entry lock on a running deck, where the project's own config said `experimental = true` throughout.
  The resolver now walks up from the working directory and uses the first `.dot-agent-deck.toml` it finds, so launching from a subdirectory of the project picks up the project root's file. `DOT_AGENT_DECK_FEATURES_CONFIG` still overrides the search, unchanged. The startup log line now names the **resolved path** as well as the value, and a new warning fires when the walk finds no config anywhere up the tree — so the next time this resolves somewhere unexpected, it says so instead of failing silently.
  One case is deliberately still open: a deck launched entirely outside the project tree — from `$HOME`, say — has no ancestor to walk up to, and its flags still resolve OFF. Fixing that means making the flag per-project rather than process-global, which is tracked separately on the issue.
- **The active orchestration tab now shows its own status color**
  An orchestration tab's label colors by the most urgent status among its panes — Error (red), Needs Input (yellow), Working (green), Thinking (blue) — but only if that tab was inactive. The active tab was excluded, so an orchestration you were currently looking at could sit in `Error` or `WaitingForInput` and the tab strip would show no color at all, the one case where you were most likely to be watching it.
  The active tab is now cued with an underline instead of a reversed block, which frees it to carry a status color the same way an inactive tab does: an underlined, bold, colored label rather than a plain underlined one. The trade-off is that underline is a weaker "this is the active tab" signal than a reversed block was — reversed unmistakably inverts foreground and background on every terminal, while underline is dropped outright by some (legacy Windows conhost being the notable case) and degrades to bold-alone there.
- **A renamed orchestration no longer silently rebuilds its tab from stale role data**
  Rename (or remove) an orchestration in `.dot-agent-deck.toml` while one of its tabs is live, then reattach the TUI to the running daemon. The tab was rebuilt from the role metadata the daemon still held rather than from the project config, and nothing on screen said so — the role cards simply stopped matching the file that had just been edited, and the only trace was a log line at `info`.
  The symptom that reaches the user is "the roles in my deck don't match the roles in my toml", with no way to connect it back to the rename. Reattaching is exactly when the config was last read, so it is also the moment the discrepancy is least likely to be attributed to the config.
  Reconnect now says so. When the project config loads successfully but carries no orchestration under that tab's name, the deck names the orchestration and states that the cards were rebuilt from the live daemon rather than from the project config — on the status line while the deck is running, so it arrives while the mismatched cards are actually on screen, with the directory appended too (a narrow terminal may truncate it there), and again in full on exit alongside the other session warnings.
  Which config wins is unchanged. The synthesised fallback is still used, because it is the correct answer for the case it was built for: a laptop TUI attached to a remote daemon whose working directory does not exist locally. That case is a legitimate reconnect rather than a drift, so it stays silent and is not warned about.
- **A config the deck cannot read no longer looks identical to one it read fine**
  Four different situations used to reach the same silent outcome when the deck rebuilt an orchestration tab: the project's `.dot-agent-deck.toml` was genuinely absent, it existed but couldn't be read, it existed but no longer parsed, or it parsed but no longer listed that orchestration. Only the first is ordinary — it is what a laptop TUI attached to a remote daemon sees, and it is why the deck fell back to the roles the daemon still remembered.
  The other three are the user's own edit (or their filesystem) coming back at them, and they were the ones with no way to be recognised. A mistyped config, a config a permission change made unreadable, and a renamed orchestration all produced role cards that quietly stopped matching the file, which is the same symptom a rename produces and the last thing anyone suspects immediately after saving — as far as the deck let on, it had read the file.
  All three are now named. An unparseable config says so and names where in the file parsing failed, so the fix is the one thing the message points at. A config that exists but couldn't be read says so and names why. A config that no longer lists the orchestration reports the drift as before. A genuinely absent config stays silent, because nothing is wrong with it.
  The live-orchestration path has the same treatment. Tabs the daemon opens mid-session — an issue dispatch, a scheduled run — went through a separate code path that collapsed all four cases and, unlike reconnect, recorded nothing at all, not even a log line. It now resolves the config through the same states and reports through the same surfaces, so an orchestration that appears while you are working can no longer be built from stale roles without saying so.
  Which config wins is unchanged in every case. The deck still falls back to the roles the daemon holds; it just no longer does it silently.


## [Unreleased]

Fork-only content from the 2026-08-12 upstream sync: real, shipped in-tree functionality whose `changelog.d/` fragments this sync's own release-rollup commits consumed, but which no already-tagged release section above documents. Needs a real version/date from whoever cuts the next release.

### Added

  **New: `dot-agent-deck worktree list` shows an OWNER column, and `worktree list --mine` lists only the worktrees the calling orchestration created.** The human table now names which orchestration created each worktree (a dash for one predating this feature, or one worker-agent-deck did not create); `--json` already carried the field. Every pane of an orchestration that **created a worktree** now carries a `DOT_AGENT_DECK_WORKTREE_OWNER` environment variable — the exact identity stamped into its own worktrees' `created-by:` markers — mirroring the existing `DOT_AGENT_DECK_PANE_ID` (which, unlike this variable, really is set in every orchestration pane), so `worktree list --mine` can match "mine" by comparing two plain strings, with no daemon round-trip and no dependency on in-memory state (it still works immediately after a daemon restart). The identity is persisted in the saved session, so a tab that is closed and reopened restores with the SAME identity, and `--mine` still matches its earlier worktrees. Two cases restore with no identity instead: a tab whose session snapshot predates this fix — saved before the identity was captured, or before this field existed at all — and a tab reattached to a still-running ("warm") daemon, whose metadata is rebuilt without the saved identity, so a session saved in that state also restores with none. In both cases `--mine` then fails loudly for that tab alone rather than silently listing everything or nothing. Run outside an orchestration pane, in a pane whose orchestration created no worktree, or with the identity set to the `orchestration:unknown` sentinel a nameless orchestration falls back to, `--mine` fails loudly (non-zero exit, names what is missing) rather than silently listing everything or nothing — a wrong answer here would hand one orchestration another's worktrees, the fork #74 collision this feature exists to prevent. One deployment note: an orchestration with no typed Name that also creates a worktree stamps the `orchestration:unknown` sentinel, which `--mine` always refuses, superseding the `orchestration:<config_name>` fallback fork#192's M2.1 shipped in v0.37.0 — a worktree marked by that earlier fallback keeps showing its old string in the OWNER column while the same (now-nameless) orchestration identifies as the sentinel, so `--mine` refuses it. Loud and safe, but worth knowing about before it surprises anyone.

### Fixed

  Fixed the shell-activity monitor going silent under machine load instead of saying so. The daemon samples the process table every 500ms to detect a long-running Bash-tool command so a pane's status stays accurate; under sustained contention that sample can time out, and a timed-out sample was always correctly treated as "no opinion this tick" rather than "nothing is running" — so a pane never falsely flipped to Idle. What was missing was visibility: there was no way to tell a machine that is chronically failing this sample from one that is healthy, so a pane's status could go quietly stale under load with nothing in the log to explain why.
  worker-agent-deck's daemon log now reports this directly: the first sample failure right after a healthy one is logged immediately, and then every 20th consecutive failure after that — enough to make a chronically contended machine visible without flooding the log on every 500ms tick. On Windows, where this signal has never been supported at all, the daemon now logs one line naming the platform gap and stops polling for it, instead of waking up every 500ms indefinitely to relearn a fact that can never change.
  Fixed a rare deck-wide shutdown hazard where signalling one agent's descendants could hit an unrelated process instead. During shutdown, worker-agent-deck waits briefly for each agent to exit on its own before force-killing whatever is left; checking whether an agent had already exited could, in rare cases, release its process id back to the operating system before the force-kill ran, and the OS could hand that same id to a completely different process in the meantime — which the deck would then signal by mistake.
  The deck now checks whether an agent has exited without releasing its process id until the force-kill step actually runs, closing that window. This also restores full coverage of the case the check exists to protect: an agent descendant that outlives its own leader process (for example an MCP server or a background tool the agent started) is still force-killed during shutdown even when the leader itself already exited, on every platform the deck supports.



## [0.37.0] - 2026-08-10

### Changed

- **Orchestration `display_title` promoted from decoration to instance identity (semantic contract change, `PROTOCOL_VERSION` unchanged at 7)**
  feat: the new-pane form now suggests a unique name for a new orchestration tab (`<foldername>-orchestrator-N`) instead of the picked directory's bare basename, and refuses to submit a name a live orchestration already holds. Accepting the suggestion costs one keystroke. Two live orchestrations in the same directory used to record the identical `created-by:` worktree-ownership marker (`orchestration:<name>`) because every form submitted the same bare basename by default — this made two live instances of the same orchestration indistinguishable by name, which is exactly the fork #74 collision the ownership marker exists to detect. This is a **user-visible default change on the normal path for every user**: a form left untouched now submits `<foldername>-orchestrator-1` (or `-2`, `-3`, …) instead of `<foldername>`.
  **What the refusal does NOT cover:** it reads a snapshot of live orchestration names taken once when the form opens, never refreshed. It corrects the common single-form case and makes an already-open form refuse a name that was taken before it opened; it is **not** a lock against two forms open at the same time — two forms opened concurrently can both be suggested (and both submit) the same name, and nothing at the worktree-marker write enforces uniqueness either. That concurrent case is the one fork #74 was actually about. Documented rather than silently accepted: [fork #201](https://github.com/prageethw/dot-agent-deck/issues/201) tracks closing it (re-query at submit, a daemon-side claim, or enforcement at the marker); not implemented here.
  The compatibility consideration is `display_title`'s meaning, not its shape. `TabMembership::Orchestration.display_title` (`src/agent_pty.rs`) was documented — here, in PRD #140, and in the field's own doc comment — as presentation-only: it fed the tab TITLE and nothing else. The new-pane uniqueness/suggestion check (`live_orchestration_cwds_and_titles`) now reads it too, applying the same fallback the tab-title computation already uses (`display_title.filter(nonempty).unwrap_or(name)`), to decide whether a live orchestration's recorded name collides with what a user is about to submit. That is a **semantic contract change behind a stable wire** per rule 12 (see `docs/develop/versioning.md`): the field's shape is completely unchanged (`Option<String>`, `#[serde(default, skip_serializing_if = "Option::is_none")]`), so every frame still deserializes identically on an older or newer peer — only what this TUI *does* with the value once decoded has grown a second consumer.
  `PROTOCOL_VERSION` is deliberately **not** bumped, for the same reason PRD #140's own `orchestration_id` promotion and PRD #20's guarded-send capability were not: nothing about the wire format changes, so no peer at any version can mis-parse a frame carrying `display_title`. A version bump would also be the wrong tool for the actual mixed-version risk, which is described below and is a UI-suggestion quality gap, not a decode-safety one.
  **Mixed-version behaviour, corrected (fork#192 review F5):** the failure mode this fragment originally argued from — an older daemon yielding fewer titles to `live_orchestration_cwds_and_titles()` — cannot actually occur. `ensure_compatible_daemon_or_die` refuses the pairing outright on `probe.response.server_version != Some(PROTOCOL_VERSION)` — exact equality, not a floor — so a genuinely older daemon never gets far enough to matter. `display_title` itself predates `PROTOCOL_VERSION = 7` by two months (landed 2026-06-14 in `8b863b0`, PRD #107 / PR #160; the bump to 7 landed 2026-08-09, and the previous release `v0.36.1` already carries it), so every daemon that can pass the handshake has round-tripped the field for as long as it has existed. There is no mixed-version peer this decision needs to tolerate — which makes the not-bumping decision *more* clearly correct than the original reasoning here suggested: a bump would refuse only pairings that already handle `display_title` correctly.
  The "fewer titles reach the uniqueness check" shape is real, but its cause is same-version, not cross-version: the daemon's own spawn-time validation (`validate_tab_membership` / `validate_orchestration_surface`, `src/agent_pty.rs`) nulls an invalid `display_title` and keeps the membership regardless of which protocol version either peer runs. Its consequence is also understated above what was originally written — it is not merely a stale-name miss in a suggestion, it is two worktrees recording byte-identical `created-by:` ownership markers, the exact fork #74 condition this PRD exists to prevent (fork#192 audit F2).
  A dispatched (daemon-initiated) orchestration is unaffected either way: it sets `display_title: None` and types no name, exactly as before.
  Cross-version manual test, corrected to match the reasoning above: build this branch, start a daemon from the previous release (`v0.36.1` or later — already protocol 7) with one orchestration open under a typed name, then open a second orchestration of the same config from the same directory against the new-branch TUI. Confirm the attach handshake succeeds and the new TUI's suggestion/refusal correctly sees the older daemon's orchestration's name — it should, since that daemon already round-trips `display_title`. This test is expected to demonstrate the uniqueness check working end to end across the version boundary, not to reproduce a gap; the same-version validator-nulling gap above is the one that can actually degrade the check, and no cross-version daemon combination reproduces it.



## [0.36.1] - 2026-08-10

### Added

- **Issue dispatch now claims its issues, and can hand each one off already triaged**
  Issue-dispatch tasks used to know only two things about an issue: whether its worktree already existed, or whether an open PR already targeted its branch. Both are inferred side-effects — nothing ever said, in the open, "this issue is spoken for." A schedule you paused mid-cycle, a worktree cleaned up by hand, or simply two decks pointed at the same repo could all end up dispatching the same issue twice, and there was no way for a human glancing at the issue to tell it was already claimed.
  A successful dispatch now writes the `in-progress` label onto the issue and posts a comment naming the claimant — which scheduled task claimed it, on which host, and when. That label is a third idempotency signal, and it is honoured no matter who applied it: this deck's own prior dispatch, a human working the issue by hand, or an external tool. Every skip is now reported with a specific, distinguishable reason instead of a generic "skipped".
  Issue dispatch can also opt into **triage**. Set `triage = true` under a task's `[scheduled_tasks.issue_dispatch]` sub-table, or pass the new `--triage` flag to `schedule add`, and every issue the fire actually dispatches gets a triage instruction appended to its prompt, ensuring a seven-label vocabulary exists on the repo (`priority-high/medium/low`, `size-high/medium/low`, `needs-triage`) — the spawned agent applies its own labels, the deck never classifies anything itself. Opt-in and off by default; nothing sweeps the rest of your backlog.
- **An orchestrator is reminded of its role after its context is compacted**
  An orchestration role is told what it is exactly once — a seed prompt sent when its pane starts. Nothing ever says it again, so in a long session the remit gradually ages out of the conversation, worst exactly when an orchestration is long and complicated. The deck now watches for the moment its start role reports its context has been compacted, and re-sends the same one-line pointer to that role's context file it sent at spawn — a reminder, not new instruction, going through the exact same delivery machinery as the original seed (readiness gating, submission confirmation).
  Only the start role is re-reminded, and only on compaction — never on a timer, and never while a previous delivery to that pane is still in flight. A role that has already finished or failed keeps that status. This addresses the decay, not the underlying design: a session that runs long without ever compacting will still drift.
- **Worktrees the deck creates now record who created them**
  `dot-agent-deck-owner` marked a worktree as one the deck made, but not which task or orchestration made it. Every worktree the deck creates — a task's issue-dispatch clone, or an orchestration's Spawn Pane — now records the creator's identity alongside the marker: `issue-dispatch:<task>#<issue>` for a dispatched task, `orchestration:<name>` for an orchestration-created one. This does not retroactively claim an existing or older-build worktree — it still stays foreign, and `reclaim` still asks about it rather than assume ownership it can't prove.

### Fixed

- Fixed `.claude/skills/dot-ai-tag-release/cleanup.sh` (the release skill's worktree/branch cleanup detection) offering worktrees and branches for deletion that must never be removed — the root checkout (now excluded by its own path, not by matching a branch name) and `fork-only` (the branch the fork's upstream-sync model depends on). Every remaining way the script's PR-state or ref-freshness data could silently go stale — a failed or missing `gh`, an undetermined repository slug, a truncated or full-page open/merged-PR result, a failed `git fetch --prune`, an scp-style remote leaking a hostname, an unset `origin/HEAD`, an embedded newline in a worktree path — now degrades and surfaces explicitly instead of looking like a clean run. Also fixed the script being unable to run on macOS at all (bash 4+ associative arrays against macOS's bash 3.2 `/bin/bash`).
- Fixed an orchestration role occasionally showing as working when the agent never actually received its starting prompt — the deck previously treated "the write reached the PTY" as good enough, so a CR that landed as a plain newline (looking identical to a real submit) left the pane showing as working while the agent never saw a prompt. The deck now waits for independent confirmation that the prompt was actually submitted, checked against the exact agent session the prompt was written to, and retries once if confirmation doesn't show up in time — the retry itself fixes a real bug, since earlier builds silently cached a retried prompt and never resent it. A prompt that genuinely landed but was never confirmed is reported as delivered-but-unconfirmed with a warning rather than claimed lost, unless the failure is affirmative evidence the target session was replaced.

## [0.36.0] - 2026-08-08

### Changed

- **Local daemon attach now enforces `PROTOCOL_VERSION`**
  The TUI↔daemon attach protocol version was only checked on the SSH/`remote add` path — the local (same-machine) attach never inspected it. A daemon started by an older or newer binary than the one attaching would connect successfully anyway, and the dashboard looked completely normal while every event the TUI could not decode was silently dropped and the subscription reconnect-looped invisibly.
  Local attach now compares the daemon's advertised protocol version against the version this binary speaks, before any other startup decision is made, and refuses to attach on a mismatch instead of connecting silently. The refusal names both protocol versions and the running daemon's build, says how many agents are running under it, and gives two ways forward.
  **This is a breaking change for one specific pairing that used to work:** an older daemon with a newer TUI, where the user declined a restart, used to attach successfully — safely, since an older daemon cannot emit event variants a newer TUI doesn't understand. That pairing is now refused too. If you hit the refusal and want to keep agents running under an older daemon, relaunch on that daemon's own build rather than stopping it; otherwise `dot-agent-deck daemon stop` and relaunch to start a fresh daemon at the current protocol version.
  The wire protocol itself is unchanged — `PROTOCOL_VERSION` stays at its current value. This adds a check against the existing constant; it does not move the wire.

### Added

- **New: an orchestration tab can root itself in its own git worktree instead of the deck's shared directory.** Type a slug in the new-pane form's Worktree field (shown once you've picked an orchestration) and every role pane spawns inside a sibling worktree named `<repo>-<slug>` — created from the picked directory on tab open, on the branch named after your slug — instead of sharing the deck's own checkout. Leave the field blank and nothing changes: panes spawn in the deck's directory exactly as before.
  This closes the multi-orchestration collision the deck has warned about since PRD #140. If the worktree can't be created — the directory isn't a git repository, or a worktree already claims that path — the tab never opens: the failure is surfaced in the status bar and nothing is spawned. The worktree is created when the tab opens and is never removed automatically, including when the tab is closed — cleanup is left to you for now.
- **The command-entry lock is now a single, command-mode chord for the whole deck.**
  `Ctrl+e` now only toggles the lock from command mode, so unlocking is `Ctrl+d` then `Ctrl+e` — freeing the keystroke for end-of-line inside a pane the same way `Ctrl+w` and `Ctrl+l` already were. Toggling the lock on any orchestration tab now changes every other open orchestration tab too, and a newly opened tab adopts the current value instead of always starting locked. A pane that is waiting for input is never locked — you can answer it without unlocking anything. The 30-second inactivity snap-back that used to return focus to the orchestrator is gone entirely; focus now only moves automatically while the deck is locked, steering to a role pane that starts waiting for input and back to the orchestrator once nothing needs you.

### Fixed

- `dot-agent-deck get-seed` no longer lets a misbehaving daemon grow its reply buffer without limit. A single reply line is now capped at 1 MiB, and busting the cap folds into the same "no seed" outcome as any other non-answer. The number is chosen with real headroom: the daemon already clamps stored prompts to 64 KiB, so a legitimate seed cannot be silently truncated by it.
- Fixed a pane reading **Working** forever after you reconnected to the deck while a shell command was still running in it. The reconnected card now keeps the provenance marker recording that its `Working` status came from the shell-activity signal rather than a real agent event, and returns to `Idle` when the command finishes — including correctly after a `/clear` or thread restart.
- Closed most of a race in the shell-activity scan that could make a pane read **Working** for a moment with nothing actually running in it, from a process id recycled between the process-listing pass and the follow-up session check. Each session answer is now confirmed against a second process listing taken afterwards, and a discarded answer counts as "unknown", never as evidence that a pane is busy.
- Closed the last way a pane could read **Working** forever after you reconnected to the deck (fork issues #49, #28). Reconnect now opens the event stream first and waits until the daemon has confirmed it before asking for the agent list, and anything that arrives while the cards are still being rebuilt is held and applied once they exist.
- Fixed `write_atomic` in `codex_hooks_manage.rs` silently widening the permissions of `CODEX_HOME/hooks.json` and `CODEX_HOME/config.toml` every time the deck published to them, since the temp file it wrote before renaming over the destination always used the default `0666 & !umask` mode regardless of the destination's own. `write_atomic` now sets the temp file's mode to the destination's own mode when the destination exists, or `0600` for a new file — mirroring the fix already in place for Devin's equivalent `write_atomic`.
- Fixed a card stranded on a stale status after the deck lost its connection to the daemon mid-session. Reconnecting now re-reads the daemon's current state and reconciles the cards already on screen against it, so a status that changed during the outage is recovered on the next reconnect.
- Fixed a keystroke-misrouting defect in the command-entry lock's auto-focus (fork issue #68): a focus steer applied before the event loop drained already-queued input could forward keystrokes to a pane you had not been typing at. The focus decision is now deferred rather than dropped whenever input is pending.
- Fixed two ways a worker's `work-done` report could silently disappear (upstream #331, fork #76). The output filename is now additionally keyed on the reporting pane, so two panes never collide on the same path, and a pre-existing report at the target path is archived aside to a freshly-allocated slot rather than overwritten. `dot-agent-deck work-done --task-file <path>` also now refuses client-side when `<path>` resolves into the daemon's own output namespace, including through a symlink.
- **A Stopped Daemon Now Shuts Down Cleanly — and Says So.** The daemon installed no `SIGTERM`/`SIGINT` handler, so `daemon stop`/`daemon restart` (and a plain Ctrl-C) killed it instantly with nothing written to the log. The daemon now runs its full graceful-shutdown sequence on either signal — agents get their termination grace period, sockets are unlinked, and a line naming the signal goes to the log before it exits — while a second `SIGTERM` during that shutdown still exits immediately, so a wedged daemon stays killable with `pkill`. `dot-agent-deck wrap` now also honours the same orphan and maximum-lifetime safety nets `daemon serve` has always had, so a wrapper whose parent was killed no longer survives indefinitely.
- Fixed a case of genuine message loss: a Pi start role's very first delegate could vanish entirely (fork issue #92). Roles used to spawn in configuration order, and a start role's seed prompt became pullable as soon as its own child pane finished spawning — so the orchestrator could act on that seed and issue a delegate before the target worker's own pane had finished being created, and the delegate silently resolved to nothing. Non-start roles now spawn first, and registration completes before any start role's seed becomes pullable, so a start role's first delegate always has a real pane to land on.

## [0.36.1] - 2026-08-14

### Fixed

- **Spawn-time role prompts are no longer lost silently on slow-booting panes**
  A role's spawn-time prompt was counted as delivered the moment its bytes reached the pane's PTY. `Applied`/`Queued` only ever meant the write reached the PTY, not that the agent actually submitted it — so against a booting Claude Code pane (SessionStart fires early, then MCP servers start and a hook can emit around 11 KB of output before the input is ready to accept a submit), the prompt could be swallowed entirely. The pane then came up healthy and Idle with no prompt at all, and was silently abandoned 60 seconds later with nothing logged.
  Delivery is now provisional: the prompt, its delivery state and retry backoff are retained until a matching `UserPromptSubmit` confirms the agent actually received it, the existing bounded backoff retries the write, and an unconfirmed prompt is still abandoned after the timeout rather than retried forever. Info-level delivery logging was added — written, delivery id, confirmed, unconfirmed, abandoned — visible when `DOT_AGENT_DECK_LOG` is set.
  This lands across all three places a spawn-time prompt is delivered: the orchestrator delegate path and the seed-prompt path (both in `src/ui.rs`), and the `dispatch --single` spawn path (`src/spawn.rs`).
- **Generated `delegate`/`work-done` commands now name the binary you're actually running**
  The `delegate` and `work-done` command examples the deck writes into orchestrator context and worker task files used to hardcode the literal `dot-agent-deck`, regardless of what the running binary was actually named or where it lived. A renamed build (a browser-download duplicate, a Finder copy, a `target/release` binary not yet on `$PATH`) generated instructions naming a binary that was never the one running, so an agent following them literally ran the wrong program or nothing at all.
  The deck now resolves its own name from `current_exe()` and emits that instead. Two gates keep the resolved name usable rather than merely well-formed: it is used bare only when it both looks shell-safe to interpolate unquoted into a generated ```` ```bash ```` block, and resolves via `$PATH` to the SAME file the deck is actually running as (identity, not mere resolvability — a same-named binary earlier on `$PATH` is rejected, not trusted). When either gate fails, the deck falls back to its own absolute `current_exe()` path, shell-quoted, rather than the old hardcoded literal — so the generated command is always runnable, never a guess.
  One caveat worth stating plainly: the absolute-path fallback is POSIX-quoted (`shell_quote_if_needed` omits `\` from its safe set), so on Windows every fallback path is single-quoted — correct in git-bash/WSL, inert in `cmd.exe`/PowerShell. A normal on-`PATH` Windows install is unaffected, since it takes the bare-name branch instead.
- **A dispatched orchestration can delegate to its own workers again — and a delegate that reaches nobody now says so**
  An orchestration started with `dot-agent-deck dispatch --orchestration <name>` came up looking perfect and could not do the one thing an orchestration is for. Every role pane spawned, every card was named, the tab surfaced live, and the orchestrator was handed a context file explaining exactly how to delegate — but every `dot-agent-deck delegate --to <role>` it then ran was silently dropped. No worker ever received a task, and the daemon log recorded only `delegate from unknown pane`. Starting the same orchestration the normal way, with `Ctrl+N`, worked.
  The cause was that the daemon learned about orchestration roles in exactly one place: the handler behind the TUI's "start this agent" request. That is the path a `Ctrl+N` orchestration takes, and the only path that went through it. An orchestration the daemon spawns *itself* — `dispatch --orchestration`, a scheduled fire, or issue dispatch — goes straight to the spawn primitive, so its panes were never recorded as belonging to an orchestration and its orchestrator was never recorded as being one. The delegate arrived, found no role for the sender, and returned. Both spawn paths now register through a single shared function, so the two cannot drift apart again.
  The second half of the report was that none of this was visible. `delegate` was fire-and-forget: it sent the signal and exited 0 without waiting to hear whether anything had happened. So an orchestrator whose delegation had been dropped was told it succeeded, announced that its worker was now working, and waited forever for a completion signal that could never arrive — which is how a routing bug turned into a hung orchestration rather than an error message.
  `delegate` now waits for the daemon's answer and reports it. A delegate that cannot be routed — from a pane that carries no orchestration role, or from a pane that is not its orchestration's orchestrator — exits non-zero and prints what could not be resolved, naming the pane. So does a delegate that reaches nobody at all because every role it named has no worker pane, which previously also exited 0. An orchestrator can now tell a delegation that landed from one that did not, which is the difference between reporting progress and inventing it.
  A delegate that reaches *some* of the roles it named is reported as exactly that, and still exits 0. `--to coder --to tester` where only the coder has a pane really does deliver to the coder, so the message names both sides — what missed and what landed — and a retry can be aimed at just the role that missed. Retrying the whole delegation would send the coder the same task twice.
  A delegate whose reply never arrives is now bounded rather than open-ended: if the daemon accepts the connection but does not answer within five seconds, `delegate` stops waiting and treats the signal as sent-but-unconfirmed, the same as against an older daemon. Previously, on Unix, it would wait indefinitely — so an orchestrator delegating while the daemon was busy could hang on the command itself.
  Mixed versions keep working in both directions. An older `delegate` against a newer daemon is unaffected, and a newer `delegate` against an older daemon — which does not answer on this verb — treats the silence as the previous contract and still exits 0, rather than reporting every delegation as broken.

### Miscellaneous

  Fixed `cargo xtask clean-e2e-tmp` refusing to reap e2e temp roots it could prove were dead. The tool judged every leftover `dad-tests-<pid>-*` root by age alone, so 280 roots (6.2 GB) with dead owning PIDs sat untouched because the oldest was under the 6-hour default — at a moment when the tmpfs was nearly full and swap had 5 MiB free. It now checks the owning PID first: a dead PID is reaped once the root is at least 10 minutes old, a live PID (including one this process can't signal) is never reaped regardless of age, and only a PID that can't be determined falls back to the age rule. The 10-minute floor is deliberate — the PID names the *test* process, but a daemon it spawned `setsid`s out of that process group and can keep writing under the root for up to 300s, so reaping a dead owner instantly could delete a live process's working directory. For the reverse case, `--ignore-liveness` demotes live-PID roots to the age rule: after a reboot a leftover root's PID can be reused by an unrelated long-lived process, which would otherwise pin it for the whole life of that boot. Survivors are now listed individually with size and age rather than only counted, so such a collision is visible. This is developer tooling only — no change to the shipped binary.
- **A Windows clone's broken symlinks are now caught instead of ignored**
  The repository tracks 35 symlinks, and two of them carry real behaviour: `AGENTS.md` → `CLAUDE.md` is how Codex and OpenCode read the same project conventions Claude does, and the 33 entries under `.agents/skills/` are how they reach the same skills tree. It compares content rather than asking `test -L`, which on Windows answers a question about the shell rather than about the checkout, and it refuses to report success when it found nothing to check. CI's `build-windows` job runs it right after checkout — preceded by `--self-test`, which materialises the index with `core.symlinks=false` and requires the checker to reject that tree, so the green result is never the vacuous kind.

No released binary is affected: `release.yml` builds only the Apple and Linux targets.



## [0.36.0] - 2026-08-11

### Changed

- **Attach-protocol bump: shell-activity event types (`PROTOCOL_VERSION` 6 → 7)**
  `EventType` gains two daemon-synthesized, wire-serialized variants, `ShellBusy` and `ShellIdle` — the signal that a pane's agent has a foreground shell command running even though the agent itself has gone quiet (a backgrounded build, a long test suite). Both ride `AgentEvent.event_type` in the daemon→TUI `KIND_EVENT` broadcast, a payload a peer decodes as a whole frame. A build that predates this change has neither variant nor a `#[serde(other)]` fallback for `EventType`, so a `KIND_EVENT` frame carrying either one fails the entire frame decode, not just that one event.
  Classification: this is a cross-version compatibility break for a **pre-existing reader** — an older TUI (or any other client that decodes `KIND_EVENT`) attached to a newer daemon that emits `ShellBusy`/`ShellIdle` — not generic user-facing breakage, so per this project's own rule (`docs/develop/versioning.md`) it is classified `breaking` and `PROTOCOL_VERSION` is bumped from 6 to 7. The attach handshake's `probe_remote_protocol` refuses a mismatched pairing with a clean `ProtocolMismatch` at connect time instead of a mid-session decode failure.
  Mitigation: `EventType` also gains a `#[serde(other)]` catch-all (mirroring `AgentType`'s earlier retrofit) that decodes any future/unrecognized `event_type` string to a neutral `Unknown` variant instead of erroring, so this build and every build after it degrade gracefully — a further event-type addition needs no further bump. Already-released binaries predate that fallback, which is exactly why the `PROTOCOL_VERSION` bump is still needed as the guard for them.
  **Action required: upgrade the TUI and the daemon together.** An old TUI cannot safely attach to a daemon built from this change — `probe_remote_protocol` refuses the connection with `ProtocolMismatch` rather than risk a mid-session frame-decode failure. Pair an upgraded daemon with an upgraded TUI (and vice versa) rather than upgrading one side only.

### Added

- **A Pane Reads Working While Its Agent's Shell Command Runs**
  A pane's status used to come entirely from agent-emitted hooks, so a role whose agent shelled out to something long — `cargo build`, a test suite, a release script — sat on a stale "Idle" while the command was visibly still running. The worst case was the common one: Claude Code moves a command that outlives its ~2-minute limit into a background shell and ends the agent's turn right there, so the pane flipped to "Idle" about two minutes in and stayed wrong for the rest of a ten-minute build.
  The daemon now watches each pane's own process tree for a shell command the agent has launched, and the pane reads Working for as long as one is running — past the point where the command is backgrounded and the agent's turn ends, and equally for a plain foreground command that finishes well inside the limit. The pane returns to Idle when the command actually finishes. This never overrides a more specific status like Thinking, WaitingForInput, or Error; it only fills the gap where nothing more specific is known. A pane sitting at an idle agent prompt is unaffected, including one with MCP servers and other long-lived helpers running underneath it.
  The behaviour is proven against a real agent running a real command — both that a busy pane reads Working across the backgrounding point, and that an idle pane does not.

### Fixed

- **A stuck `ps` can no longer stall the daemon or wrongly mark every pane idle**
  The shell-activity poll ran its process-table sample synchronously on the daemon's async runtime, with no time limit. Two consequences, both now fixed.
  The sample occupied a runtime worker thread for its whole duration, so everything else the daemon does queued behind it — hook ingestion, client requests, even shutdown. Ordinarily that was ~49ms every 500ms; a `ps` wedged in uninterruptible state on a stuck filesystem (a hung NFS mount, a failing disk) stalled the daemon indefinitely, and the 500ms cadence made that a recurring exposure rather than a one-off. The sample is now awaited rather than blocked on, so the worker stays free while `ps` runs, and a 2-second deadline bounds how long any one poll waits for an answer.
  The deadline bounds the wait, not the `ps` process itself, and deliberately so: a process stuck in uninterruptible state cannot be killed until it comes unstuck, so abandoning it and starting a fresh one on the next poll would accumulate unkillable `ps` processes at roughly 24 a minute. A poll that overruns instead keeps waiting on the same sample, so at most one `ps` exists at a time however long the underlying filesystem stays wedged. The overrun is logged once, not once per poll.
  Because that lets a sample answer late, an answer is only acted on while it still describes the current machine — a reading more than 3 seconds old is discarded rather than applied — and only about the panes that were already open when it was taken. Otherwise a filesystem that unwedges after the panes it was asked about have been closed or replaced would have its old reading attributed to whichever panes are open now, which on a machine recycling process ids can mean one pane inheriting another's activity.
  A sample that times out is treated as *no information*, never as "no pane is busy". This distinction is the reason the fix is not simply a shorter wait: a wedged `ps` says nothing about the panes, which are exactly as busy as they were a moment earlier. Reading a blown deadline as "not busy" would have marked every running pane `Idle` — reintroducing the stale-`Idle` badge this signal exists to prevent, with a new trigger and nothing in the log to trace it by. Statuses are instead left untouched until a sample answers, and a timeout is logged as a warning.
- **Bounded Frame Length on the TUI's Synchronous Daemon Client**
  The TUI's one-shot daemon queries now reject an over-long response frame instead of allocating from the length prefix on the wire. `read_frame` has always refused a frame larger than 16 MiB precisely so a forged or corrupted length cannot make the process allocate gigabytes; the synchronous client the TUI uses for its blocking queries read the same 5-byte header without that check and sized its buffer straight off the `u32`. Since the allocation happened before the body was read, a 5-byte header claiming 4 GiB was enough — no payload required.
  This ran on the `Ctrl+n` new-pane key path, where the deck asks the daemon which directories already host a live orchestration, so the visible failure was the TUI ballooning or being killed on a keystroke. Both sides now read the same bound and return the same `InvalidData` error, and every caller already treated a failed request as best-effort, so an over-long frame degrades to "no hint" or a `Run-now failed: …` status line rather than taking the TUI down.
  The wire format is unchanged. A daemon can never have sent a frame this affects — the writer has always enforced the same cap — so builds across versions interoperate exactly as before.
- **The shell-activity poll no longer scans the process table when no pane needs it**
  A running deck stops paying for a process-table scan it has nothing to do with. The shell-activity monitor — the 2Hz poll that spots a pane whose agent is quietly running a long shell command — sampled the whole machine *before* checking whether any pane was open to classify. A daemon with zero panes therefore forked `ps -A` twice a second, each sample also issuing a `getsid(2)` for every process row, to classify nobody. Nothing bounded it: the daemon's idle shutdown requires no clients **and** no agents, so a dashboard sitting attached with nothing open polled for as long as it was left open.
  The cost that buys is now measured rather than assumed: roughly 49ms of wall time per sample on an idle 16-core Linux box with ~620 processes, i.e. about 10% of one core at the 2Hz cadence — of which only ~1.4ms is the deck's own CPU, the rest being the `ps` child and the wait on it. The monitor now resolves which panes exist first and skips the sample entirely when the answer is none, so an idle deck spends nothing here.

### Miscellaneous

  Fixed the e2e test harness allocating its per-process temp root on `/tmp`, which on some machines is a RAM-backed tmpfs ([#322](https://github.com/vfarcic/dot-agent-deck/issues/322)). Interrupted runs leak those roots, and because tmpfs is memory the leaks are resident RAM, not disk — one cleanup freed 5.8 GB and took swap from 5 MiB free to 3.8 GiB free on the machine that reported this. The visible symptom was a healthy `cargo test-e2e` collapsing into a wall of failures that read like real product regressions (`Disk quota exceeded`, `git init` failing, daemons never booting) when the tmpfs simply ran out of room.
  Containment is scoped to what was measured rather than asserted broadly. Live `/tmp` sampling during a recorded full run found three allocations still escaping, ~184 KiB in total: the harness's own Codex-auth pre-flight (a `NamedTempFile`, which `linkage-check` rule 8 did not match — the rule now covers file constructors as well as directory ones), `src/dispatch.rs`'s e2e-gated unit test (which clones a repo, and lives in the lib target that does not link the harness), and `tests/daemon_protocol.rs` (the one fast-tier crate that binds Unix domain sockets, and which `cargo test-e2e` runs). All three are fixed — the first through the harness, the other two through a ~40-line crate-internal resolver (`src/test_temp.rs`) that reaches the same private base without the ladder, the pre-flight or the seeded HOME. `docs/develop/e2e-temp-dirs.md` now states the boundary as a table of what is and is not contained, with the measurement behind each row. Everything under `tests/` is now contained, the seven fast-tier crates that do not link the harness included; the one remaining gap is documented as **not** contained rather than implied to be — the rest of `src/`'s unit tests, roughly 82 bare constructors across 22 files, left uncovered deliberately with no measured leak behind them.
  The harness now resolves its temp root from a ladder — `DAD_E2E_TMPDIR`, then a private UID-scoped `/var/tmp/dad-e2e-<uid>` directory, then the OS temp dir as a last resort — and every previously bare `tempfile::tempdir()` call site across the e2e suite now goes through `common::harness_tempdir()`, which resolves that root before it allocates. Pointing `tempfile`'s process-global default at the root is kept only as defence in depth: it is installed at the end of the root's lazy initialiser, so an allocation that ran before anything else asked the harness for a directory — the first statement of a test body, under nextest's one-process-per-test — still went to the OS temp dir. A new `linkage-check` rule (check 8) fails the build on a bare `tempfile` constructor anywhere under `tests/`, plus `src/dispatch.rs` — scoped by **directory** rather than by an enumerated list, so a new file under `tests/` inherits it instead of silently falling outside it. It matches the directory, file and spooled constructors alike (`tempdir`, `TempDir::new`/`with_prefix`/`with_suffix`, `NamedTempFile::new`/`with_prefix`/`with_suffix`, `tempfile`, `spooled_tempfile`) and deliberately never the `…_in` forms, which name their parent. A refused private directory or a refused `DAD_E2E_TMPDIR` now fails the run loudly instead of silently falling back to the RAM-backed tmpfs, and the pre-flight free-space check now probes the base that was actually chosen. `cargo xtask clean-e2e-tmp` gained a `--root <path>` flag to reap a specific location.
  `DAD_E2E_TMPDIR` is now walked from `/` with descriptor-relative, no-follow opens (`openat`/`mkdirat`), so every directory is judged by `fstat` on the descriptor it was opened with rather than on an earlier look at its name, and a component that appears between the two is refused instead of adopted. Each component is validated **before** it is resolved: a symlink is inspected without being followed and is only resolved when it belongs to you or to root, so a link another local user planted at a predictable name in a sticky directory such as `/var/tmp` cannot redirect the harness — sticky semantics protect that planted entry from you, so resolving first and judging afterwards was not enough. Links owned by root are still followed, which is what makes the check work on macOS, where `/var` is a symlink to `/private/var`. The base itself must now be owned by you at exactly mode 0700 (`chmod 700`) — the same bar the default `/var/tmp/dad-e2e-<uid>` parent already had to meet, since this is where the harness seeds real agent credentials — and the refusal names a umask that clears owner bits as a legitimate cause.
  `cargo xtask clean-e2e-tmp` now verifies the boundary it deletes under instead of assuming it. The harness proves `/var/tmp/dad-e2e-<uid>` is private before it writes there, but that is a predictable name in a world-writable directory and the reaper is the half that removes things, so it now requires a real directory owned by you with no group or other bits, inside a `/var/tmp` that is itself root-owned and sticky; a symlink at that name is refused rather than followed. Scanning and deletion both run against the path that vetting resolved rather than the spelling they were handed, so a symlinked component cannot be retargeted between listing a directory and removing it. Naming that same parent by hand with `--root` gets the identical treatment: a `--root` whose resolved directory is the private parent keeps the ownership, mode and sticky-holder checks and stays out of `--include-untagged`'s reach, so one directory cannot have two security postures depending on how it was spelled.
  On Windows, where `std` offers neither ownership nor an `openat`, the same value now gets a by-name walk that creates each missing component with `create_dir` rather than handing the whole path to `create_dir_all`, so a symlink, junction or other reparse point planted at a missing component is refused instead of adopted and silently followed. That closes the redirection, not the whole race: the check is a second lookup of the name rather than a descriptor, a plain directory another local user planted is still adopted because there is no owner to compare, and created directories inherit their parent's ACLs. The ACL-and-handle version is tracked by #163/#164.
  The macOS shape is now pinned by tests rather than reasoned about. `/var` there is a symlink to `private/var`, so the harness and the reaper hold two spellings of one directory (`/var/tmp/dad-e2e-501` and `/private/var/tmp/dad-e2e-501`); both are accepted, every comparison that matters is by resolved path or by the final component's name, and both fit the socket budget with room. That had to be pinned on Linux, by building the same symlinked-ancestor shape in a scratch directory: `build-macos` runs `cargo nextest run` without `--workspace`, so the `xtask` crates' tests — the reaper's included — never execute on macOS at all (#470).
  This is developer tooling only — no change to the shipped binary.
  Fixed three e2e tests (`idle_worker_011`, `focus_007`, `card_stats_005`) that were consistently red on `main`. Triage found no production defect: two earlier commits changed presentation behaviour — gating the auto-focus chain behind the `experimental` flag, and switching the selected card border from plain to thick — and three tests were never updated to match. The fixes scope the experimental flag correctly, crop observation to the right pane column range, and make the card-layout parser border-weight-agnostic while still enforcing coherent borders. Review follow-up then addressed the class rather than the three instances: the border-weight glyph table and the pane-column/card-title grid predicates now live once in the shared test harness instead of being re-encoded per file, the pane-column wait reports "no anchor" and "needle absent" as distinct failures instead of one indistinguishable timeout, and both predicates gained fast-tier guards so CI catches the next presentation change on every push rather than only in the pre-PR tier. This is test-only; no production code changed.
- **The xtask crates' tests now run in a gate**
  `cargo test-fast` and `cargo test-e2e` select the whole workspace. The workspace root is itself a package and there is no `default-members`, so cargo's default target selection was the **root package alone** — every test in `xtask/linkage-check` and `xtask/docs` executed in no gate anywhere: not the per-task alias, not the pre-PR alias, and not CI, which runs the same commands. The tier goes from 1657 to 1705 selected tests.
  This is the test-side sibling of the `--workspace` flag added to clippy in [#436](https://github.com/vfarcic/dot-agent-deck/issues/436), and the reason it outlived that fix is that clippy's half already covered the compile-time half: those tests are *built*, so a type error or a lint in them still failed. Only their runtime assertions were inert, which matters most for `clean-e2e-tmp` — a deletion tool whose safety properties (owned-prefix matching, opt-in untagged reaping, never following a symlink out of the temp root) are runtime assertions and nothing else.
  The three CI test jobs — `build`, `build-windows` and `build-macos` — carry the flag too, so they keep matching the aliases, which apply on every platform. Widening costs nothing measurable: all 48 newly-gated tests are under 40ms and run in ~0.07s in aggregate, while the tier's wall clock is set by its slowest single test.
- **`/verify-pr` Detects Vacuous E2E Runs Again**
  The `/verify-pr` reviewer skill flags e2e runs where a real-agent test skipped at runtime instead of executing. Those tests print `SKIP: <reason>` and return normally, so nextest counts them as **passed** — a fully green e2e tier that proved nothing about the surface under review.
  That safeguard had been silently inert. The detector in `checks.sh` matched `SKIP:` anchored at column 0, but nextest indents captured test output by four spaces under `--success-output=final`, so the pattern never matched. Every review recorded `E2E_RUNTIME_SKIPS=0`, never wrote `e2e-skips.txt`, and never emitted the `e2e-real-coverage` **ATTENTION** row — including two reviews that each had four genuinely skipped real-agent tests to report.

Reviewers once again see which real-agent tests declined to run, and can rerun them with `DOT_AGENT_DECK_REQUIRE_REAL_E2E=1` to turn a skip into a hard failure.



## [0.35.10] - 2026-08-10

### Added

- **Install with Nix, home-manager or NixOS**
  Nix, home-manager and NixOS users can now install dot-agent-deck declaratively. Until now the only documented install path was the Homebrew tap, so anyone on Nix had to hand-wrap the prebuilt binary and pin a fresh `sha256` on every release, or skip the tool ([#231](https://github.com/vfarcic/dot-agent-deck/issues/231)). `nix run github:vfarcic/dot-agent-deck` now runs it with nothing installed at all; adding the flake as an input gets you `packages.default` for `environment.systemPackages` or `home.packages`; and there is an `overlays.default` for people who would rather reach it as `pkgs.dot-agent-deck`. There is also a `devShells.default` if you want the toolchain without the tool.
  The derivation builds from source against the committed `Cargo.lock`, so there is **no per-release hash** for anyone to recompute and commit. That was the core ask in the issue: a single stale `sha256` is what made the hand-rolled packaging painful enough to be worth filing.
  home-manager users get a module as well. `imports = [ inputs.dot-agent-deck.homeModules.default ];` gives you `programs.dot-agent-deck`, where `enable = true` installs the binary and the freeform `settings` and `keybindings` attribute sets are rendered to `~/.config/dot-agent-deck/config.toml` and `~/.config/dot-agent-deck/keybindings.toml`. Neither file is written unless you actually put something in it, so turning the module on does not overwrite a config you already have. It manages those two files and no others: `session.toml` and `remotes.toml` are written by the application itself and would break if home-manager made them read-only symlinks, and `schedules.toml` is left for a follow-up because it is the one file whose location follows `$XDG_CONFIG_HOME`. Hooks stay a one-off `dot-agent-deck hooks install`, since that command edits other tools' configuration files and a generation switch cannot roll it back. See [Installation](https://agent-deck.devopstoolkit.ai/docs/installation) for a worked example.
  The flake pins the released version and passes it to the build as `DAD_VERSION`, so `--version` reports the release you actually installed rather than the `0.1.0` placeholder that `Cargo.toml` carries permanently. A Nix source build gets a tarball with no `.git`, so the `git describe` step in `build.rs` is unavailable and the fallback would otherwise land on the placeholder; this uses the injection seam that [#250](https://github.com/vfarcic/dot-agent-deck/issues/250) added for exactly this kind of packager. Because that pin is a hand-maintained line, a guard step in the release workflow fails the release if the flake's version and the tag being released ever disagree, and a `nix flake check` job in CI builds the derivation on every run, so a nixpkgs bump that breaks it is caught there rather than by the first user who types `nix run`.
  Two limits worth stating plainly. This **complements devbox, it does not replace it**: devbox stays the development environment, the flake is the consumer install. And the flake does not run the test suites (`doCheck = false`), because the fast tier needs `cargo-nextest` and the e2e tier needs live agent CLIs and network access, neither of which exists in a Nix sandbox; correctness stays gated by the existing CI matrix, and the flake's job is to prove the tree builds reproducibly from source.
  Cross-version contract (CLAUDE.md rule 12): no impact. The change is packaging, CI and docs only, and touches no daemon, protocol, orchestration or hook code, so there is no `PROTOCOL_VERSION` bump.
  **New: `dot-agent-deck daemon status [--json]`.** A read-only snapshot of every agent the local daemon currently manages — pane id, label, cwd, orchestration role, live status, and active tool — without attaching to any pane. `--json` emits a versioned document (`{"schema_version": 1, "agents": [...]}`) for scripts. It never prints prompt text, never starts a daemon that isn't already running, and reports a non-zero exit if the daemon can't be reached.
  **New: `dot-agent-deck worktree list [--json]` and `worktree reclaim [--yes]`.** `list` reports every linked git worktree with its resolved PR state, cleanliness, ownership, and gate verdict (`remove`/`ask`/`keep`) with a reason; `--json` emits a versioned document (`{"schema_version": 1, "worktrees": [...]}`). `reclaim` removes a worktree only when all three hold: its PR's state is `MERGED` (checked via `gh`, never git ancestry — squash-merges never enter `main`'s ancestry, so an ancestry check misses genuinely merged branches, and an ancestor branch with no PR at all must never be removed), the tree is clean, and the deck can prove it created the worktree. A worktree it cannot prove it created is reported as reclaimable-pending-confirmation, naming the exact path and the ready-to-copy `--yes` command, rather than removed silently. The branch always survives; only the worktree directory is removed. An unresolvable PR state (missing `gh`, a spawn or parse error, an ambiguous match) always keeps rather than guessing.



## [0.35.9] - 2026-08-09

### Added

- **An agent can now dispatch a task into its own worktree**
  Added the `dispatch` CLI verb and a new **dispatcher mode**. An agent can now run `dot-agent-deck dispatch <name> --task "..."` and the daemon creates a dedicated git worktree as a sibling of the repo (`../<repo>-dispatch-<name>`) and starts an isolated line of work inside it — one step, no manual worktree chore. Dispatcher mode is a built-in seeded mode that teaches an agent this one extra verb: a dispatcher pane is an ordinary conversational agent that reaches for `dispatch` when you say to start something as a separate line of work.
  You choose whether each unit starts as one agent or as a full multi-role orchestration — `--single` or `--orchestration [<name>]`, with `dot-agent-deck dispatch --list-targets` printing what the repo offers. The dispatcher asks you before its first dispatch rather than inferring it, because the same words ("work on these three features" vs "verify these three PRs") want opposite shapes. Naming an orchestration the repo does not define is an error rather than a silent fallback to something you did not pick.
  Either shape starts the unit the way opening it yourself with `Ctrl+n` would, plus your prompt. `--single` runs a real agent (the configured `default_command`, else the Claude default). `--orchestration` starts every role and hands the orchestrator its usual context — its own prompt template, the available agents, and the delegation protocol — with your task folded in, so it actually delegates instead of working alone while its team sits idle. Dispatched role cards previously showed the agent's own session id, so a six-role team came up as six cards you could not tell apart. (A scheduled issue-dispatch's role cards were labelled with the schedule name, which had the same effect: every card in the tab read alike.) The tab still carries the identity of the dispatch itself, so the two questions — which unit is this, and which role — are answered in different places instead of competing for one label.
  Dispatcher mode is available to everyone — no feature flag to enable. It is documented at [Dispatcher Mode](https://agent-deck.devopstoolkit.ai/dispatcher-mode). Completions do not yet route back to the dispatching pane — that return edge is tracked separately.
  Closing a dispatched agent's card now works on the first Ctrl+W. It used to take two: the card came back, its agent still running, and only a second close removed it. Two things caused that. A card the daemon spawned — a dispatch, or a scheduled fire — has no pane attached in your deck until you focus it, so the close reported "pane not found" and the deck deliberately kept the card so you could retry; it now stops that agent by asking the daemon directly. And the daemon waited for the dispatched worktree's cleanup before answering the close, which on a worktree an agent has been working in means a `git status` walk of seconds — long enough for the deck to give up and keep the card. Cleanup now runs after the answer, since the agent is already stopped by then.
  One more close-path defect went with it, and it is the one that survived the first fix: a pane can carry more than one session, and closing removed only the one its card was built from. The leftover rendered as a ghost card badged "No agent", pointing at the closed agent's directory. It showed up specifically when the pane's command is one the deck cannot recognise as an agent — a `devbox run agent-coder` style launcher — because such a command is not wrapped, so the agent's own session never merges with the pane's placeholder. Closing a pane now drops every session belonging to it.
- **Orchestration tab labels are colored by the most urgent pane inside them**
  With several orchestration tabs open, there was no way to tell which one needed you without switching to each in turn. Every pane already carries a live status — Working, Thinking, Needs Input, Error, Idle — and the orchestration sidebar shows it per role, but that signal stopped at the tab you happened to be looking at. The more orchestrations you run in parallel, the more the answer to "what needs me right now" was hidden one keypress away in every direction.
  A background orchestration tab's label in the tab bar is now colored by the single most urgent status among its panes, using the same status palette the sidebar and deck cards already use — no new colors. Priority runs Error (red) > Needs Input (yellow) > Working (green) > Thinking (blue), so a tab with one errored role reads red no matter what its other roles are doing. A tab with a role waiting on your input turns yellow while you are somewhere else entirely.
  Color means "something in here needs you", so a tab with nothing going on does not compete for your eye: an all-idle tab renders in the ordinary tab color rather than a gray, and the tab you are currently on keeps its usual active highlight untinted — you are already looking at it. Keeping status color off those two cases also keeps every label at full contrast on light and dark terminals alike.
  Only orchestration tabs are colored. The Dashboard tab and single-agent Mode tabs already show their own status directly and are unchanged, as is the way any individual pane, sidebar entry, or deck card renders its own status once you are inside a tab.
- **Typing Into a Worker Pane Can Now Be a Decision Rather Than a Reflex (Experimental)**
  **This ships behind the `experimental` feature flag and is off by default.** Nothing about how you work today changes unless you turn it on: set `experimental = true` under a `[features]` table in your `.dot-agent-deck.toml`, or launch with `DOT_AGENT_DECK_EXPERIMENTAL=1`. It is gated precisely because it changes a reflex you already have — the default is deliberately restrictive, and that deserves real use before it reaches everyone. Everything below describes what you get once it is on.
  An orchestration is one workflow with a single coordinator, but every worker pane sits there with a cursor in it, inviting you to answer its question on the spot. Doing that puts a second, uncoordinated actor inside the workflow: you change state the orchestrator believes it owns, with no path for it to learn that you did. The deck does not look broken afterwards — it looks fine, and the model behind it has quietly diverged. Most often it is not even deliberate: you open a worker pane to check on it, get distracted, and type your next instruction into the pane in front of you instead of the one you meant.
  On an **orchestration tab**, keystrokes aimed at a worker role are now dropped rather than delivered, and the bottom bar says `Pane locked — Ctrl+d then Ctrl+e to unlock`. The orchestrator's own pane is never locked. Dashboard and mode tabs are not affected at all, nothing becomes read-only, and every pane still shows live output and scrolls as before. When you genuinely want to reach into a worker — a parked agent, a model that never called `work-done`, an agent waiting somewhere unexpected — it costs one deliberate `Ctrl+D`, `Ctrl+E`. That pause is the feature; a lock you have to remember to engage protects nothing, so it is on by default.
  **A worker that has stopped and asked you something is never locked.** While a role pane reports `WaitingForInput`, every key reaches it with no unlock at all, and the lock re-engages the moment that status clears — answering a question the agent itself asked is a response to a request, not an intrusion into one. An agent that never reports `WaitingForInput` gets no exemption and still needs the deliberate unlock.
  **Focus follows the lock.** While locked, the deck steers focus onto a role pane the moment it starts waiting on you (lowest-numbered first when several wait at once, advancing as each is dealt with) and back to the orchestrator once nothing is waiting. While unlocked, no automatic focus move happens at all — focus stays exactly where you put it until you lock again. Automatic focus moves also wait for you: if a keystroke of yours is still queued when the deck decides to move focus, the move is deferred to a later frame rather than applied, so what you typed always reaches the pane you typed it at — and never answers a prompt in a pane that jumped in front of you mid-sentence.
  `Ctrl+E` is claimed in command mode only, exactly like `Ctrl+W`. While you are typing in a pane the deck does not take it, so `0x05` reaches the program and readline's `end-of-line` works as usual. The lock is one setting for the whole deck rather than one per tab — unlocking on any orchestration tab unlocks all of them, and a newly opened one adopts the current value. It is not persisted: every deck starts locked.

### Fixed

- **A pane no longer sprouts a second card when a hook reports without an agent id**
  A pane could end up with two cards on the deck, showing two different statuses for the one agent. Which of the two the deck believed was decided by hash-map iteration order, so the same pane could read `Needs Input` on one run and `No agent` on the next with nothing having changed. An orchestration fixture with two roles rendering three cards — two of them labelled `worker` — is what surfaced it.
  The trigger is a hook event that names no agent id. That is not a malformed event: it is the shape agent-deck deliberately still accepts from pre-F9 hook scripts, and the shape any producer sends when `DOT_AGENT_DECK_AGENT_ID` did not reach it — a hand-written hook, a wrapper that scrubbed its environment, or `dot-agent-deck agent-event` invoked from a subprocess that lost the variable. Such an event matched neither the path that routes a report onto the pane's existing card nor the path that replaces a card outright, so it fell through and created a second one.
  An untagged report now lands on the card the pane already has, instead of starting a rival. The protection that pathway existed for is untouched — a legacy hook still cannot wipe the accumulated tool count, prompt history, or start time of the card it reports on, and it cannot blank the pane's agent identity either. What goes away is only the duplicate card, which was never load-bearing.
  Two things that read per-pane status get steadier as a result: orchestration tab labels colour from the pane's real status, and the command-entry lock's focus steering stops being able to chase a stale one. The sharpest symptom is gone too — a worker pane could display `Needs Input` while your keystrokes were dropped with a message insisting the pane was locked, because the card and the lock were reading different sessions for the same pane.
  One deliberate exception: the command-entry lock's `Needs Input` exemption is **not** granted on the strength of a report that names no agent id. That exemption decides whether your keystrokes reach a worker the lock is otherwise protecting, so it acts only on a status whose origin is established; a report that cannot say which agent generation it came from is displayed on the card as usual but does not open the lock. Until now an untagged report could not reach a pane's real card at all, so this restriction was already in force as a side effect — it is simply explicit now rather than incidental. A deck running entirely on pre-F9 hooks therefore reaches its worker panes with `Ctrl+d`, `Ctrl+e` rather than automatically, which is the same trade the lock already makes for any agent that never reports `Needs Input`.
- **The selected deck card is now visible whatever its agent is doing**
  Finding the card you were pointed at was harder than it should have been, in two different ways. While you were typing into a pane, the selected card was drawn in a dimmed magenta — and on a dark terminal that lands in the same band as the dark gray an idle agent gets, so the card you were driving became one of the hardest on screen to find. It was not only the outline: because a border's style bleeds into the titles drawn over it, the card's name and its `Last:` / `Tools:` counters faded along with it. Separately, an idle card's border is deliberately faint so that a resting agent recedes — but that meant selecting an idle card barely changed anything, because a border you can hardly see is no easier to see for being thicker.
  A selected card's border is now drawn in **your terminal's own foreground colour** — near-white on a dark theme, near-black on a light one, decided by your terminal rather than by us — and it is **thickened** at the same time, alongside the `▸ ` marker it already carried. Three cues at once, none of which depends on what the agent happens to be doing. Nothing is ever dimmed to indicate selection.
  Cards that are not selected are unchanged: each still carries its status colour, so a working agent reads green, one waiting on you reads yellow, one that errored reads red, and an idle one still recedes quietly into the background exactly as before.
  Which mode you are in still reads off the same card. In command mode, where the keyboard drives the deck, the selected card's border is bold; while you are typing into a pane it returns to normal weight, keeping its colour, its thick border and its marker. So "which card is selected" and "where are my keystrokes going" remain separate questions with separate answers, and neither is answered by making something harder to see.
  The selected card's border no longer reports its agent's status, since it is showing selection instead. The status badge in its top-right corner still does, at full colour.

The pane returns to Idle when the command actually finishes. This never overrides a more specific status like Thinking, WaitingForInput, or Error; it only fills the gap where nothing more specific is known. A pane sitting at an idle agent prompt is unaffected, including one with MCP servers and other long-lived helpers running underneath it.

  `Ctrl+l` used to toggle an orchestration tab's sidebar/pane-column split between two ratios. It now cycles through three stages — the tab's own Default ratio (33/67 on the Dashboard, 34/66 in an Orchestration tab), a Narrow 25/75, and a Hidden stage where the sidebar collapses to zero width and the pane column takes the full tab area. Press it again from Hidden to return to Default.

  Like every other keybinding, `toggle_orchestration_split` is remappable through `[global]` in `~/.config/dot-agent-deck/keybindings.toml`. See [Keyboard Shortcuts](https://agent-deck.devopstoolkit.ai/docs/keyboard-shortcuts) for the full list.

  In an orchestration tab, focus stayed wherever you last left it. After glancing at a worker pane you had to walk focus back to the orchestrator yourself before typing your next command — and it was easy to forget, so the next thing you typed went to a pane you did not mean.
  Orchestration tabs now bring focus back to the orchestrator pane on their own in two situations. The moment the last role pane that was waiting for input resolves — so nothing on the tab still needs you — focus moves to the orchestrator once, not repeatedly every frame. And while the tab is command-entry locked (the default), if you move focus to another role pane yourself and then leave it untouched for 30 seconds, focus snaps back to the orchestrator. Anything you do in that pane restarts the 30 seconds, and the snap-back holds off entirely while any role on the tab is still waiting for input, so you are never pulled away from a pane that is asking you a question.
  Typing counts as activity even when nothing reaches the pane: a keystroke that the `Ctrl+e` command-entry lock drops rather than forwards still restarts the 30 seconds, so working at a locked role pane never looks idle to the timer and focus is not pulled out from under you mid-keystroke. If you unlock command entry to type directly into a role pane, the 30-second timer stops applying for as long as the tab stays unlocked.

  In an orchestration tab it was easy to accidentally type into a worker pane instead of the orchestrator — nothing distinguished "this pane accepts your keystrokes" from "this pane is just being observed."
  Orchestration tabs now lock command entry to the orchestrator pane by default: typing while focused on any other pane in that tab no longer reaches its PTY, and a status message confirms the keystroke was dropped rather than silently swallowed. `Ctrl+e` toggles the lock per tab — while unlocked, every pane accepts direct input as before — and the orchestrator pane itself always accepts input regardless of lock state. Every other global chord keeps working from any pane, locked or not.

  `Ctrl+L` is clear-screen for shells, readline, and every agent you run in a pane — Claude Code included. In an Orchestration tab the deck claimed it regardless of what you were doing, so a focused role pane's agent never saw the keystroke and its own clear-screen simply never worked. Running an interactive agent in a role pane is what the deck is for, which made that the worst possible place to swallow the chord. It now passes straight through to the pane's occupant as `^L` (byte `0x0c`) whenever you are typing in a pane, on every tab type. Dashboard tabs already behaved this way.

That is a deliberate trade, and the same one `Ctrl+W` (close pane) already makes: a chord the program inside your pane genuinely needs is scoped to command mode rather than eaten forever, so you pay one extra keystroke in the rarer direction instead of losing the chord in the common one.

There is now a single stage shared by the Dashboard and every Orchestration tab: cycling anywhere moves everywhere, and a tab you open afterwards starts at whatever stage is current. Sidebar width reflects how you like to read, not which tab you happened to open — but if you were deliberately keeping one tab wide and another narrow, that combination is no longer possible.

The three stages are still Default → Narrow (25/75) → Hidden (sidebar gone, pane column full-width) → Default, `Default` still resolves to each tab type's own ratio (33/67 on the Dashboard, 34/66 in an Orchestration tab), and the stage still resets to Default on the next launch rather than persisting. Mode tabs have no sidebar split and never claim the chord.
  Like every other keybinding, `toggle_orchestration_split` is remappable through `[global]` in `~/.config/dot-agent-deck/keybindings.toml`; whatever chord you bind it to is command-mode only. See [Keyboard Shortcuts](https://agent-deck.devopstoolkit.ai/docs/keyboard-shortcuts) for the full list.

## [0.35.4] - 2026-08-02

### Fixed

- **Scheduled Tasks Dialog Now Captures the Mouse Wheel**
  The Scheduled Tasks manager dialog no longer leaks mouse-wheel scrolling to the pane behind it. Previously, scrolling the wheel while the dialog was open scrolled the mode-tab pane underneath instead of the dialog itself, forcing users to scroll blind or fall back to the keyboard.
  The wheel now scrolls the task list in the dialog directly, matching the existing j/k keyboard navigation.
- **Source builds now report their real version instead of a silent 0.1.0**
  A binary built from source outside a tagged git checkout reported its version as `0.1.0` and its build id as `0.1.0-unknown` — indistinguishable from the placeholder `Cargo.toml` carries for exactly this case. `build.rs` derived both values from git (`describe`/`rev-parse`) and degraded to that placeholder whenever git metadata was missing — a source tarball, a shallow or `.git`-less clone, `cargo install --git`, or a sandboxed package build (Nix, distro packaging) — and there was no way for a packager or CI job to override it. Every version-aware path then misbehaved against the fake `0.1.0`: compatibility-based version negotiation, the newer-only remote upgrade nudge (a source build looked permanently ancient), the `remote add`/`--no-install` pre-flight, and the `DAD_BUILD_ID` daemon-restart handshake, where a constant `-unknown` across genuine rebuilds could suppress a restart an in-place upgrade was supposed to force.
  `DAD_VERSION`/`DAD_BUILD_ID` now resolve in order: a pre-set value in the build environment, then git, then `CARGO_PKG_VERSION` — unchanged behavior for release builds and ordinary dev checkouts, but packagers can now inject the real version directly. An injected version is validated with the same semver parser `src/version.rs` uses for everything else, so a malformed injection falls back to the placeholder rather than being accepted or panicking the build, and every `cargo:` directive `build.rs` emits is now guarded against line-protocol injection.
  This PR also closes a pre-existing, unrelated shell command injection in `.github/workflows/release.yml`, found during the security audit of this change because the file was already being edited. Several steps interpolated `github.event.inputs.version` and tag-derived values directly into `run:` scripts; git tag names may legally contain quotes, semicolons, and command substitution, and the affected steps carry `HOMEBREW_TAP_TOKEN`/`SCOOP_BUCKET_TOKEN` with `contents`/`packages` write access. All 13 interpolations across 8 steps are now rebound through `env:` blocks, and the prepared version is validated as SemVer before it reaches `GITHUB_OUTPUT`. The tag-triggered release path is unchanged — identical task/cargo/cross invocations and git command sequence.
  The Linux ARM64 artifact is cross-compiled inside a container, so the injected version has to cross that boundary to reach the build script. It now travels two independent channels — cross's own passthrough allowlist and an explicit `docker run -e` — and, because both of those live on the far side of the boundary they protect, the release job additionally verifies on the host that the finished ARM64 binary really does carry the version being released, failing the release rather than publishing a binary that reports a different version than the tag it ships under.
- **A respawned worker no longer leaves a duplicate, unreachable card on its pane**
  Delegating to a role configured with `clear = true` respawns the worker, and on Pi workers the pane was left showing **two** cards instead of one — the dead generation's card stacked on top of the live one. Both claimed the same pane, so the deck gave no clue which was which.
  Respawning a third, fourth or fifth time did not add further cards, but it did something quieter: the surviving card silently kept the *previous* generation's identity and event history, so the deck was describing a process that had already been killed while the new one worked unattributed.
  The second card was not just cosmetic clutter: it was unreachable. The orchestration deck derives its highlight from the pane id and resolves it to the first card matching that pane, so the highlight stayed pinned to the stale card and the live one could not be selected at all. The practical effect was a worker that was genuinely running and doing the delegated work while the only card you could reach was the corpse of the previous generation.
  A pane now ends up with a single card after a respawn: the stale generation is retired as soon as the replacement's first frame arrives, whichever kind of frame that is — Pi never announces a new session the way Claude Code and OpenCode do, which is why its respawns were the ones that duplicated. Every later respawn hands that one card over to the generation actually running, with a fresh history rather than the dead one's. A card also no longer disappears from a live pane when a late farewell frame arrives from the agent that just left. Scheduled tasks are unaffected in the other direction: a scheduled card is still replaced cleanly by the agent's real card when the agent starts, and still keeps the schedule's friendly name rather than reverting to a session id.
- **Generated delegation guidance now defaults to `--task-file`**
  The delegation protocol dot-agent-deck generates for an orchestrator showed only `dot-agent-deck delegate --to <role> --task "…"` and never mentioned `--task-file`. The orchestrator runs that command in its own shell, so the task text was rewritten before dot-agent-deck received it — backticks and `$(…)` executed and replaced by their output, usually empty — and pieces of an instruction disappeared while the delegation still reported success. Worker `work-done` summaries had the same exposure.
  The generated protocol, the `## When done` footer in every worker task file, and the prompt that generates new configs now lead with `--task-file` and reserve the inline form for a single line of plain text with no backticks, `$`, `"`, `\` or `!`. They also say how to produce the file: write it with a file-writing tool — never with shell redirection or a heredoc, because a line of the task text can terminate the heredoc and Bash then executes everything after it — name it from a fresh `[a-z0-9-]` slug, single-quote the path, keep secrets out of it, and delete it after the handoff. The footer's suggested path is role-specific, length-bounded, and outside the `work-done-*` names the deck writes itself, so a report cannot be overwritten by its own completion signal or by another role's. Preferring the file is not a hard dependency on it: having a file-writing tool is not the same as being allowed to use one, and a role launched with a restricted allowlist (`claude --allowedTools Bash Read`, say) would otherwise stop at an interactive approval prompt and never signal at all — so all three branches are now stated outright, in the footer above the inline example where a worker actually reads them. With no authorized file-writing tool, send a single plain line inline with `--task`; if the content fits neither form, say so plainly. The fallback is never shell redirection or a heredoc. This corrects advice rather than adding enforcement: `--task-file` has shipped on both commands (including `-` for stdin) for several releases, and it differs from the older suggestion to reference a long-context file inside `--task`, which shortens the description but still sends it through the shell. Bounded reads, coordination-file permissions, and a daemon-side clobber guard remain open in [#328](https://github.com/vfarcic/dot-agent-deck/issues/328), [#329](https://github.com/vfarcic/dot-agent-deck/issues/329), and [#331](https://github.com/vfarcic/dot-agent-deck/issues/331).
  Demo reel for PRD #303: https://youtu.be/7ZTG6zi4nCc. Watch before merging.



## [0.35.3] - 2026-07-31

### Fixed

- **Command mode is now visible on the pane border**
  There was no reliable way to tell whether you were in command mode. The focused pane rendered its cyan focus border identically whether or not it was accepting keystrokes, so the loudest signal on screen said "type here" while the keyboard was actually driving the deck. The only real cues lived in the bottom bar — the first button flipping between `[Command Mode Ctrl+D]` and `[Back to Pane Ctrl+D]`, and `[Close Ctrl+W]` going dim — which meant identifying your own mode required reading and diffing button labels in the corner of the screen. On a mode tab with a full-screen pane, pressing `Ctrl+D` changed exactly one row of the display.
  The focus accent is now gated on actually being in PaneInput: cyan appears only while your keystrokes reach the pane. In command mode the focused pane's border falls through to its agent's status color — green working, blue thinking, yellow waiting, red error, gray idle — the same role the deck card uses for that state. Pressing `Ctrl+D` now visibly changes the pane you are looking at, and command mode gains a side benefit: while you navigate, every border reports what its agent is doing instead of all of them reading "focused".
  Focus itself moves to border **weight** so nothing is lost. The focused pane draws a thick border (`┃`) in command mode, where color can no longer carry that fact, which matters because `j`/`k` cycles pane focus on a mode tab and focus decides where `Enter` / `Ctrl+D` return you. Color now answers "are my keystrokes landing here?" and thickness answers "which pane is focused?" — one channel each instead of both competing for the same one.
  Nothing changes size. Border weight does not affect a pane's inner area, so PTY dimensions, layout, and reflow are untouched; only the glyphs and the color change. Thickness was chosen over a fourth accent color because the 16-color-safe palette is already full (green/blue/yellow/red are statuses, cyan is focus, magenta is selection) and the remaining candidates are grays — the exact low-contrast trap on light terminal backgrounds that the terminal-relative color model exists to avoid. One consequence worth knowing: a focused pane with no backing agent session — a plain shell pane — has no status to fall back to, so in command mode it renders the same dimmed border unfocused status-less panes already use, with the thick weight as its focus marker.
- **Starting the deck no longer fails on machines with a slow interactive shell**
  On a machine whose interactive login shell takes more than five seconds to start, the very first launch of the deck always failed with `daemon failed to start within 5000ms: endpoint /tmp/dot-agent-deck-attach-<uid>.sock never became available`, and then succeeded on the next try. The retry-succeeds behaviour made it read as flaky infrastructure, but it was deterministic: two startup budgets in different modules disagreed with each other, and the shell's speed decided which one won.
  The daemon does real work before it binds the endpoint the launcher is waiting for. At `daemon serve` startup it captures the user's login-shell PATH — running `$SHELL -ilc` so that installers which append their `PATH` line to `~/.bashrc` after the standard non-interactive guard are still seen — and that capture is allowed up to ten seconds, followed by materializing the pi orchestrator extension and the Codex hooks. Only then does it call `bind`. The lazy-spawn launcher, meanwhile, polled for the endpoint for a hardcoded five seconds: half the time the daemon was explicitly permitted to spend before binding. Any interactive shell slower than that deadline produced the failure, and a zsh with `compinit`, a plugin manager, and generated completions for a few CLIs measures around six seconds — not a hung or misconfigured shell, just an ordinary heavy one. The daemon then bound normally a moment after the launcher had already given up, which is why it was up and working by the time you ran the command again.
  The launcher's budget is now derived from the daemon's own worst-case pre-bind budget instead of being chosen independently, so the two cannot drift apart again, and a unit test asserts the ordering directly rather than trying to reproduce a slow shell. The healthy path is unchanged and still returns as soon as the endpoint appears, typically in milliseconds — the longer bound is only ever spent when a daemon is genuinely missing or dead, where the failure message now takes about fifteen seconds to arrive rather than five.
  The timeout message also stopped pointing you at an empty file. It advised checking `daemon.log` for daemon stderr, but that log only receives output when the daemon was started with `DOT_AGENT_DECK_LOG` set, so on a default install it is zero bytes — which read as evidence that the daemon had never started at all, the opposite of what was happening. The message now says so explicitly.
- **The dashboard stats bar no longer loses its `tools` total to a per-agent-type breakdown**
  On a deck running more than one kind of agent, the stats bar appended a per-agent-type count breakdown (`14 ClaudeCode │ 8 Codex`) after the status totals. That bar is drawn into the last row of the *left dashboard column* — not the full terminal width — and as an unwrapped single-line paragraph it clips silently at the right edge, with no ellipsis to show anything was dropped. Each type segment costs roughly 12-18 columns, so on a real multi-agent deck the breakdown pushed the segments after it off-screen: the `tools` total, which the renderer treats as always-present, and the `mode:` indicator. The reported symptom was a bar that appeared to simply end at `… │ 19 idle │ 14 ClaudeCode`, which also made it look as though only one agent type was active when several were.
  The breakdown is now removed rather than made narrower. The information it carried was already on screen and better placed: every deck card renders its agent type as a registry-colored badge (`Claude · name`, `Codex · name`) directly below the bar, so the aggregate restated in one scarce row what the cards show per session. Removing it also stops the cost from growing with each agent type added to the registry. The status totals, the `tools` total, and the `mode:` indicator are unchanged.
  Bars narrow enough to clip even the status counts still truncate at the right edge without an ellipsis; giving the bar a defined truncation priority is a separate change.



## [0.35.2] - 2026-07-30

### Fixed

- **Delegated tasks no longer get lost when a worker respawns**
  Delegating to a role configured with `clear = true` could leave the worker sitting idle forever with no sign that anything had been sent. The respawned agent's `SessionStart` hook fires early in its boot sequence — before its TUI is ready to accept input — and the daemon wrote the task pointer the instant that signal arrived, so the write raced the agent's startup. Land late enough and it worked; land mid-boot and the task text arrived but the Enter was swallowed, leaving it unsubmitted in the input box; land early and the whole prompt was dropped and the worker never started. This is why the reported symptoms looked like three different bugs, why the failure rate varied by machine speed and load, and why setting `clear = false` worked around it.
  Delegation now waits for a readiness buffer after the respawned worker signals `SessionStart` — and also after the fallback wait expires, since a timeout means readiness was never confirmed at all. The default is 1000 ms: the spawn-time path's warm-pane 500 ms, doubled because a respawn is a cold start. A new slow-readiness regression test toggles only the buffer and shows the pointer lost at `0` and delivered-and-submitted at `1000`, which pins the mechanism against a deterministic fixture built to ignore input for 650 ms. To be precise about what that does and does not establish: it verifies the gate's behaviour, not any real agent's startup distribution, so the buffer is a well-targeted delay rather than a measured threshold. Pi's native seed delivery and Codex's wrapper-side readiness fix are untouched.
  A delegate that goes undelivered is also no longer silent. A worker that receives its task pointer and then emits no turn-shaped agent event within its response window now produces a daemon warning plus a visible notice in the orchestrator's pane, so "never got the task" is distinguishable from "still thinking" instead of looking like a healthy, idle card. The notice is written without an Enter so it reads as scrollback rather than as a prompt — best effort, not a guarantee, since whether an agent treats a bare line feed as "submit" is unverified per agent and a later prompt can carry pending notice bytes with it, which is why the line carries no project-supplied text at all (the role name and panes go to the daemon log). It is bound to the orchestrator's identity, so it cannot land in an unrelated agent that later inherited the pane, and it is cancelled outright if the worker reports `work-done`, the delegation is superseded, or either pane closes. Its window defaults to the idle-worker timeout capped at 30 seconds, and `DOT_AGENT_DECK_DELEGATE_NO_EVENT_WINDOW_MS` shortens it, turns it off (`0`), or arms it on its own — the two detectors are now independently switchable in both directions.
  Task pointers themselves are now delivered under the same identity guard the diagnostics use. The delegate path holds a pane id across the respawn wait plus the new buffer, and an unguarded write keyed on that string could deliver — and submit — one orchestration's task into a successor agent that inherited the pane after a close, respawn, re-home or teardown. Delivery is now bound to the exact worker agent the task was composed for and re-validated against the pane's closing state and orchestration membership immediately before writing.
  The buffer is overridable with `DOT_AGENT_DECK_DELEGATE_READINESS_BUFFER_MS` (milliseconds; `0` disables the wait, values above 30000 are capped) for operators whose machines need longer and for test harnesses that need to skip it. It is a deliberate stopgap — a fixed delay cannot prove that an agent is listening. The durable fix is a real "TUI ready" signal from the agent side, tracked in [#243](https://github.com/vfarcic/dot-agent-deck/issues/243).
  Demo reel for PRD #249: https://youtu.be/v7ONU4LTa3E. Watch before merging. It shows the fixed path end to end against two real interactive workers — Claude Code and OpenCode — each respawned through `clear = true`, receiving and submitting its task pointer, and visibly doing the delegated work.



## [0.35.1] - 2026-07-30

### Fixed

- **Ctrl+W no longer destroys a pane by accident**
  `Ctrl+W` — delete-previous-word in shells, readline, vim, and nearly every other TUI — instantly and irreversibly tore down a pane in dot-agent-deck from any mode, with no confirmation. Typing it inside an embedded shell or agent pane destroyed the pane instead of deleting a word. Three users hit this independently and reported it separately (#88, #192, #218); all three are fixed by this change.
  **Intentional behavior change — please read if `Ctrl+W` is muscle memory for you:** `Ctrl+W` no longer closes a pane while you are inside it. It now reaches the shell or agent as a normal keystroke (word-delete), exactly as it would in any other terminal. Closing a pane is now a command-mode-only action, and it always asks for confirmation first — there is no `y`/`n` one-key shortcut for that confirmation; confirm with `Down` + `Enter` or a mouse click, and the default selection is Cancel so an accidental keypress cannot close anything.
  Three other defects are fixed alongside the behavior change. First, a stale pane whose agent had already stopped on the daemon side used to wedge forever on close — the daemon's "Agent not found" response was treated as a failure and retried against an id that could never succeed, forcing a full detach and relaunch to clear it. That response is now treated as already-stopped, so the pane closes cleanly. Second, every path that can close a pane — the keybinding, the `[Close]` button, the tab-strip `×`, and the modal's own `[Close]` — now goes through the same confirmation, bound to the specific tab or pane that was armed when the modal opened, so navigating away while the modal is open can never close the wrong target. Third, the hints bar and help overlay are now mode-aware: they no longer advertise `close` in a mode where `Ctrl+W` does not close anything, and `Ctrl+D` is now a genuine two-way toggle between the dashboard and the pane you came from, so command mode always shows how to get back.
  See the [keyboard shortcuts documentation](https://agent-deck.devopstoolkit.ai/docs/keyboard-shortcuts) for the updated key behavior per mode.
- **A pane that loses its agent now says so, instead of going quietly dead**
  When a pane's agent went away and the deck's reconnect attempts ran out, the pane kept rendering its last frame and looked completely healthy — but every keystroke was silently dropped. The only hint was a status message that flashed `PTY write failed: Pane <id> stream I/O task ended`, naming an internal task rather than telling you the agent was gone. Selecting such a pane and typing looked, from the outside, like the deck had frozen.
  Those panes are now labelled `— disconnected` in the title, so the state is visible before you type anything, and their last output is preserved so you can still read what the agent did before it went away. Typing into one now reports what actually happened and what you can do about it — "Agent is no longer running — pane is disconnected. Close it to start over." — instead of an internal error. Nothing is closed automatically: the pane stays until you close it.
  The two situations that lead here are reported distinctly, because their causes are unrelated: an agent that exits on every restart attempt (usually the agent's own command failing at startup) versus an agent the daemon no longer has at all (stopped deliberately, or a daemon restart underneath the pane).
  Both give-up paths now log at warning level and name which one was taken, so a report of "my pane died" can actually be diagnosed. Previously they logged at debug level, which meant that unless you had already set `DOT_AGENT_DECK_LOG`, four different causes produced one identical symptom and left no evidence behind. See [Troubleshooting › A pane says "disconnected" and ignores what you type](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for how to capture that detail when filing an issue.
- **An agent card that appears and vanishes now says where it came from**
  If a card for an agent you never started flickers onto the dashboard and disappears again, that is another deck's agent posting into your daemon — most often a test run, or a second checkout, whose child process inherited a `DOT_AGENT_DECK_SOCKET` pointing at your session. The card is registered because the hook arrives, then retired because no local pane backs it.
  Until now this left nothing to go on: the daemon logged it as an ordinary `Received event`, indistinguishable from a real agent starting, so the only way to find out was to notice the flicker by eye and then read the log afterwards knowing exactly what to grep for. The daemon now logs a warning naming the pane, the session and the agent type when a `SessionStart` arrives for a pane it never spawned, along with the usual cause. Enable file logging with `DOT_AGENT_DECK_LOG=1` and search for `did not spawn`.
  This is a warning rather than a refusal on purpose: a pane can legitimately belong to a client whose agent the daemon does not own, and dropping those hooks would break it. Nothing about which events are accepted has changed.



## [0.35.0] - 2026-07-28

### Changed

- **Orchestration routing identity gained a per-tab instance id (semantic contract change, `PROTOCOL_VERSION` unchanged at 6)**
  fix: concurrent orchestrations no longer cross-deliver delegate/work-done signals; same-directory orchestrations now warn and point at worktrees. Opening the same orchestration in two tabs from one directory used to produce two byte-identical routing identities, so a delegate reached *both* tabs' workers and a work-done landed on *either* tab's orchestrator non-deterministically. Each orchestration tab now mints its own instance token, shared by every role pane of that tab, and the daemon routes on it — so each tab is an isolated routing group even when the orchestration name and directory are identical.
  The compatibility consideration is the routing key itself: the daemon's `pane_orchestration_map` value changed from the `(orchestration_name, orchestration_cwd)` tuple to an identity that is either `Instance(id)` or `NameCwd(name, cwd)`. That is a **semantic contract change behind a stable wire** per rule 12 (see `docs/develop/versioning.md`) — the frames still deserialize on both sides, but the meaning of "same routing group" now depends on which variant a pane's client produced. `PROTOCOL_VERSION` is deliberately **not** bumped: the new `orchestration_id` rides `TabMembership::Orchestration` as an additive optional field that older peers round-trip untouched, and a pane from a pre-#140 client simply resolves to the `NameCwd` fallback, which is byte-equivalent to the previous behaviour. Because the wire stays additively forward- and backward-compatible, the break is versioned through this fragment and the `0.x` minor bump rather than through a handshake refusal.
  Cross-version behaviour: a newer TUI against an older daemon (or an older TUI against a newer daemon) keeps routing a single orchestration correctly via the `NameCwd` fallback — correct across directories and across differently-named orchestrations, and ambiguous only in the same-name-same-directory case that has always been ambiguous. Mixed-variant identities never compare equal, so a tokened pane and a token-less pane are never merged into one routing group on the strength of a coincidental name-and-directory match. Only the newer-client-plus-newer-daemon pairing gains the per-tab partition, so the previous-release-daemon manual test at release is: build the branch, start a daemon from the previous release with an agent under it, run the branch TUI against it, and confirm a delegate still routes and hooks (work-done, status) still arrive.
  The product stance ships alongside the fix: same-directory concurrency is legal but discouraged, because the two resources the daemon cannot partition — the `.dot-agent-deck/*-{role}.md` coordination files and the working tree — are shared no matter how routing is keyed. Selecting an orchestration whose directory already hosts a live one now shows a non-blocking warning in the new-pane form naming both shared resources and pointing at a git worktree (`/worktree-prd`) as the isolated alternative. The supported model — concurrent orchestrations are safe across directories, one worktree per parallel line of work — is documented in `docs/orchestration.md`.

### Added

- **Orchestrations Report Workers That Go Silent**
  An orchestrator that delegates work and then waits gets no execution turns until the worker answers — so a worker that dies, hangs, or quietly stalls leaves the whole run parked with nothing to show for it. Nobody notices until you come back and look.
  The daemon now watches every outstanding delegation. If a worker has not reported `work-done` after `worker_response_timeout_minutes` (default **120**), the daemon injects one self-describing prompt into the orchestrator session — *"A delegated worker has not responded with work-done (dot-agent-deck daemon report, not a message from a person or an agent). It was delegated 2 hours ago. … It may be stuck, waiting on input, or still working: check its pane and decide how to proceed — if this needs the user, notify them; otherwise keep waiting, re-delegate, or reassign."* — and the orchestrator decides what happens next. The daemon itself never notifies anyone; it only reports the condition, which keeps the deck out of the business of holding chat credentials and leaves the judgment call with the agent that has the context. The prompt names itself as a daemon report and labels the role name as untrusted config metadata, so an agent reading it cannot mistake either for a message from you.
  The prompt fires once per delegation, so a stuck run cannot turn into a stream of nags, and an arriving `work-done` cancels the timer — a worker that finishes just as the deadline passes produces no alert. Closing a worker's pane cancels it too, on the grounds that you are already handling that worker.
  Set `worker_response_timeout_minutes` at the top level of `.dot-agent-deck.toml` (above the first `[[table]]` header, or TOML makes it a key of the preceding table and it is silently ignored). Values from 1 to 10080 minutes are accepted; **`0` disables the detector entirely** — no timers, no prompts — and an out-of-range value falls back to the default rather than being clamped.
  Because the idle prompt travels over the existing prompt-injection path, no new wire message was added: the change is non-breaking, and an older TUI attached to an upgraded daemon simply sees the prompt as ordinary pane output. Two limits worth knowing: a daemon restart forgets every outstanding delegation and silently disarms its pending timers, and v1 measures elapsed time since delegation rather than actual agent activity, so a legitimately long task can produce one discardable alert.

- **Concurrent orchestrations no longer cross-deliver delegate / work-done signals**
  Opening the same orchestration in two tabs from one directory used to make a delegate land in *both* tabs' workers and a work-done land on *either* tab's orchestrator, non-deterministically — the two tabs were indistinguishable to the daemon's routing. Each orchestration tab now mints its own instance token internally, so every role pane the tab spawns routes as its own isolated group even when the orchestration name and directory are identical. Delegation and work-done feedback now always reach the tab that actually sent them, with no configuration change required.
  Opening a new orchestration in a directory that already runs one now shows a non-blocking warning naming the two things that still aren't isolated between them — the `.dot-agent-deck/*-{role}.md` coordination files and the working tree itself — and points at a git worktree as the isolated alternative. The warning informs; it never blocks, so opening a second same-directory orchestration on purpose still works exactly as before.

The previous "one orchestration tab at a time" workaround wording is gone.

- **Native Windows Support — Process, Path & Filesystem Backends**
  The Windows daemon can now actually run. [#42](https://github.com/vfarcic/dot-agent-deck/issues/42) laid the cross-platform `src/platform/` foundation but intentionally hard-failed the Windows daemon at bind time until the remaining backends were secure; this change implements every one of them and lifts that hard-fail. dot-agent-deck now resolves config/state/lock/runtime directories via `%LOCALAPPDATA%`/`%APPDATA%`/`%USERPROFILE%` (with the existing `DOT_AGENT_DECK_*` env overrides still authoritative), wraps agent spawn through `%COMSPEC%`/`cmd /C`, detaches the daemon with `DETACHED_PROCESS`/`CREATE_NEW_PROCESS_GROUP` (handling job breakaway), and serializes concurrent spawns with a named mutex. Peer-PID resolution (`GetNamedPipeServerProcessId`/`GetNamedPipeClientProcessId`) and `daemon stop` now work end-to-end — graceful `KIND_SHUTDOWN`, `CTRL_BREAK_EVENT` best-effort, then a Job-Object `TerminateJobObject` backstop that reaps descendants. Clipboard writes go through `CONOUT$` OSC 52, the ConPTY-appropriate equivalent of the Unix `/dev/tty` write.
  Alongside the new backends, every Windows security gap flagged by #42's review is closed: named pipes are created with an explicit current-user-SID owner and DACL (`O:<sid>D:P(A;;GA;;;<sid>)`) on both `bind` and every `accept`'d instance, and both IPC client entry points — the UI/attach client and the hook client — verify the server's owner SID before trusting a connection, so a foreign local user can no longer pipe-squat a predictable per-user pipe name to read agent output or spoof the daemon. Config files that may carry secrets (`remotes.toml`, `schedules.toml`, `session.toml`) get an explicit owner-only ACL applied immediately on creation. The synchronous TUI request path now has a real read/write deadline on Windows (overlapped I/O with a millisecond timeout), matching the Unix 5-second guarantee instead of risking an indefinite hang against a wedged daemon. Stale-endpoint detection is short-circuited on Windows, where a named pipe has no filesystem inode to probe.
  Unix/Linux behavior is unchanged — every backend above is a `cfg`-gated Windows-only addition alongside the existing Unix implementation. Full interactive end-to-end validation on a real Windows host and release binaries ship in the follow-up [#164](https://github.com/vfarcic/dot-agent-deck/issues/164).
- **Shift+Enter inserts a newline in embedded agent panes**
  Pressing Shift+Enter in an embedded agent pane now inserts a newline into the agent's draft instead of submitting it — the behavior you get running the agent directly in the same terminal — with **no terminal configuration at all** on any terminal that implements the enhanced ("kitty") keyboard protocol. Two deck-side defects compounded to cause this: the deck never asked the terminal for the enhanced protocol (so a kitty-capable terminal stayed in legacy mode and delivered a bare carriage return, losing the modifier before any deck code ran), and the pane-input encoder dropped the SHIFT modifier even when it did arrive — Shift+Enter and plain Enter were literally the same byte on the wire, so every agent read both as "submit".
  Both halves are fixed. The deck now pushes `DISAMBIGUATE_ESCAPE_CODES` at startup and pops it on *every* way out — a normal quit, a terminal I/O error that aborts the session early, and the panic path — so no keyboard mode leaks into the shell you drop back into; the push is gated on the terminal actually reporting support, so inside tmux (which reports none) the deck degrades to its previous behavior rather than pushing a mode nothing honors. Pane-input key forwarding is now modifier-aware: Shift+Enter is forwarded as `ESC[13;2u` — the one newline encoding verified to work across all four supported agents (Claude Code, OpenCode, Pi, Codex) — Ctrl+Enter as `ESC[13;5u`, Shift/Ctrl+arrows in their modifier-bearing CSI form (`ESC[1;2A` and friends), and the non-letter C0 controls the enhanced protocol disambiguates now reach the pane as their control byte rather than as a literal character (so Ctrl+[ is Escape again — vim leaves insert mode inside an embedded pane instead of typing a `[`). Plain Enter still submits, and the submit-debounce is unchanged because a CSI-u newline carries no `\r`.
  The previously documented Ghostty workaround (`keybind = shift+enter=csi:13;2u`) is no longer necessary; if you already have it, it still works and does no harm. There is no `experimental` flag to enable — this is a correctness fix to an existing input path, so it ships on by default.
  Cross-version contract (CLAUDE.md rule 12): no impact. The interactive keystroke path writes opaque bytes through the existing attach/PTY channel, and the change touches only `src/ui.rs`, tests, and docs — nothing in `src/daemon_protocol.rs`, the daemon, hooks, or orchestration. No `PROTOCOL_VERSION` bump and no semantic (same-wire, different-meaning) break; an older daemon and a newer TUI interoperate exactly as before.
  See [Troubleshooting](https://agent-deck.devopstoolkit.ai/docs/troubleshooting) for what to check if Shift+Enter still submits (running inside tmux is the main case).

### Fixed

- **Delegating to a Codex worker delivers the prompt again**
  A `clear = true` delegate to a Codex worker silently lost its prompt. The worker restarted, came up with an empty composer, and did nothing: the orchestrator believed it had delegated, while the operator watched a pane that appeared to restart and then sit idle. Codex was effectively unusable as an orchestration worker, because every delegation to it was dropped. Both defects behind that are fixed, so a Codex worker now receives its task and starts working like every other agent.
  Prompt delivery now waits for a signal that actually means "the agent can accept input". `dot-agent-deck wrap` emits a session-start event the moment it forks the child, purely so the dashboard card appears immediately for a slow-booting agent — but at that point the pane is often still running only the launcher, seconds before the agent's own interface exists. That fork-time event is now marked as card-surfacing only, and the delegate readiness gate ignores it for agents that will post a genuine session-start of their own, so the prompt is no longer typed into a launcher's line discipline and echoed away. Wrapper-strategy agents with no native hooks are unaffected: their fork-time event remains their readiness signal, so they still receive prompts immediately rather than waiting out a timeout. That fallback timeout, which only applies when an agent's native hooks never fire, is raised from 10 to 30 seconds to match measured Codex startup.
  A pane's launch shape is also stable now. Previously a pane started from a command whose name did not identify an agent (for example `devbox run codex-big`) launched unwrapped, and then, once hook events revealed the real agent type, came back up *wrapped* after its first delegate — the same pane running a different process tree before and after. The agent type learned from hook events now updates the dashboard badge only, never how the pane relaunches. ## [0.34.0] - 2026-07-25

### Changed

- **Attach-protocol bump: guarded input delivery + typed stream rejections (`PROTOCOL_VERSION` 5 → 6)**
  Input delivery from the TUI to a daemon-driven pane is now identity- and idempotency-guarded, and the daemon reports a *typed* reason when it refuses a keystroke instead of dropping it silently. Two coordinated wire changes ride one `PROTOCOL_VERSION` bump (5 → 6):
  - **New attach-stream frame `KIND_STREAM_REJECT` (server → client).** When the daemon refuses a `KIND_STREAM_IN` key/paste frame because the focused target went non-live (history-only / view-only), exited, or rebound while the stream stayed open, it now emits a non-terminal `KIND_STREAM_REJECT` frame carrying a short reason (e.g. `history-only`) rather than debug-logging the drop and leaving the client stuck typing into a dead pane. Adding a server→client frame kind changes the attach-stream wire shape, so per rule 12 this is a hard `PROTOCOL_VERSION` bump, not an additive-field change. The client surfaces the reason and leaves its input mode for both key and paste; the stream stays open.
  - **Guarded-send capability handshake (semantic break behind a stable wire).** A newer client that issues an *identity-bearing* `write-and-submit` (carrying `expected_agent_id` / `expected_session_id` / `delivery_id`) now first checks that the daemon advertises a `guarded_send` capability on its `Hello` reply. The daemon enforces the guards: an exact agent-and-session-generation match before writing (refusing `stale` / `wrong-session` with no bytes), atomic `delivery_id` deduplication (a lost-response retry replays the first result; a partial write is reported `ambiguous`, never blind-retried), and a re-validation of liveness/ownership *after* acquiring the target writer. An older daemon silently ignores those fields and just returns `ok=true`, so a new client that trusted it could double-submit on a retry or mis-deliver on a rebind. To prevent that, a new client now **fails safe** — it refuses to submit an identity-bearing prompt when the capability is absent, preserving pre-PRD-20 fire-once semantics against an old daemon. The capability rides the `Hello` reply as an additive optional field (an old daemon simply omits it), so it is decoupled from the version number; the version bump is driven by the new frame kind above.
  Classification: a cross-version compatibility consideration for the **TUI↔daemon send/attach contract** — a semantic break (a new client must not trust an old daemon's unguarded `ok=true`) plus a stream wire-shape change (the new frame kind). This is `breaking` per rule 12. While the major version is `0`, a `breaking` fragment bumps the **minor** digit.
  Cross-version behavior after the bump: the exact-match attach handshake refuses an old-reader/new-daemon or new-reader/old-daemon pairing at connect time (a clean `ProtocolMismatch`, recover by upgrading), and on the local socket the build-version (`DAD_BUILD_ID`) handshake already forces a daemon restart on any in-place binary upgrade. **A previous-release-daemon manual test is required at release**: build the branch, start a daemon from the previous release with an agent under it, run the branch TUI against that older daemon, and confirm a delegate still routes and hooks (work-done, status) still arrive — and that an identity-bearing send against the old daemon now fails safe rather than double-submitting.

- **Attach-protocol bump: live orchestration surfacing (`PROTOCOL_VERSION` 3 → 4)**

## [0.27.1] - 2026-06-06

### Fixed

- **Scrollback No Longer Scrambled After Reconnect**
  Reconnecting to a `dot-agent-deck connect` session no longer corrupts scrollback in agent panes. Previously, every reconnect caused overlapping text, narrow vertical text strips on the right edge, and duplicated inner-TUI status lines when scrolling up to read prior model output — sometimes making history unreadable for the rest of the session.
  The root cause was that the client's vt100 parser was always initialized at a hard-coded 24×80 during snapshot replay, even when the daemon's PTY was opened at the terminal's real dimensions (e.g. 120 columns × 40 rows). Absolute cursor-position and line-wrap sequences sized for the real geometry were mis-parsed at the wrong width, permanently baking the corruption into scrollback. The live viewport recovered automatically on SIGWINCH redraw, hiding the bug until the user scrolled up.
  The daemon now records each agent's current PTY dimensions and reports them via `list_agents` (added `rows`/`cols` to `AgentRecord` with `serde(default)` for backward compatibility with older daemons). The client initializes the vt100 parser at those dimensions before replaying the snapshot, with a defensive clamp and fallback to 24×80 when talking to a legacy daemon. The daemon also clears its scrollback ring on every real PTY resize, ensuring every snapshot delivered to a reconnecting client covers a single consistent (rows, cols) epoch.
- **Orchestrator spawn-time role prompt now submits reliably**
  Fixes the orchestrator's spawn-time role prompt failing to submit in slower or remote-daemon environments. After PRD #100's interleave-race fix shipped in v0.27.0, the role prompt payload still arrived in the orchestrator's input box as un-dispatched text — the trailing Enter was interpreted as a literal newline rather than a submit.
  The root cause is a timing race: Claude Code's `SessionStart` hook fires early in its boot sequence, before its TUI input is ready to interpret `\r` as submit. The spawn-time path, which sends the role prompt immediately after detecting `SessionStart`, was writing into a pane that had not yet entered submit-aware mode. The fix adds a 500ms readiness buffer (`SPAWN_TIME_READINESS_BUFFER`) between `SessionStart` detection and the role-prompt write, giving Claude Code's TUI input time to reach a submit-ready state. A regression test (`tests/spawn_time_role_prompt_submit_after_session_start.rs`) drives a Python slow-readiness agent stub and toggle-verifies the fix: the test fails at `BUFFER=0` and passes at `BUFFER=500`.
  Daemon-side `RUST_LOG=pane_write=trace`-gated trace instrumentation is also included, adding four trace events across the PTY write path (payload, submit terminator, notice terminator, and `STREAM_IN` forwarding). Each event carries `pane_id` and `agent_id` for future cross-path debugging.

### Fixed

- **Fix Orchestrator Spawn-Time Role Prompt Not Submitting**
  When orchestration starts, the deck automatically injects the initial role prompt into the orchestrator agent's input. The trailing Enter sometimes did not trigger submission — instead, the cursor dropped to a new line inside the input box with the prompt text un-submitted.
  Root cause: the TUI client's spawn-time write used two `KIND_STREAM_IN` frames separated by a 150ms sleep. The daemon's per-agent writer mutex was released between frames, leaving a window during which a concurrent daemon-initiated write (e.g. a sibling worker's work-done feedback) could interleave, fusing its payload and CR into the gap. The orchestrator agent then saw the daemon's CR first — submitting the fused line — and the user's trailing CR landed in an empty input box and was rendered as a newline.
  Fix: a new `WriteAndSubmit` RPC routes the spawn-time injection through the daemon's existing `write_to_pane_and_submit` primitive, which holds the per-agent writer mutex across the full `payload → SUBMIT_DELAY → CR` sequence — the same atomic contract used by the daemon-initiated orchestration-delegate path, which has always worked correctly.

### Fixed

- **Stale-Daemon Version Skew Detection and `daemon stop`/`restart` Commands**
  The local TUI now detects when it is connecting to a daemon built from a different commit and exits with a clear error message instead of silently misfiring. Previously, upgrading the `dot-agent-deck` binary while a daemon from the previous build was still running could cause delegate prompts to appear queued in the TUI but never progress — the stale daemon's handler code predated internal role-map schema changes, so orchestration silently no-op'd with no error visible to the user.
  A new `DAD_BUILD_ID` build variable (`<version>-g<short-sha>[-dirty]`, e.g. `0.25.0-g243b049`) is compiled into every binary. The same field is compared on remote connections (`probe_remote_protocol`), where a mismatch points at `remote upgrade` instead.
  Two new CLI subcommands make daemon lifecycle management safe and documented: `dot-agent-deck daemon stop` gracefully shuts down the local daemon (via `SIGTERM`, falling back to `SIGKILL` after 5 s with `--force`), refusing if managed agents are still alive unless `--force` is passed. `dot-agent-deck daemon restart` stops the daemon and lets the next TUI launch re-spawn it. Both commands discover the daemon PID via socket peer credentials (`SO_PEERCRED` on Linux, `LOCAL_PEERPID` on macOS) — an OS-level facility that works against any daemon version, including pre-handshake binaries.
  See the updated [Installation](https://devopstoolkit.ai/docs/ui/installation) and [Troubleshooting](https://devopstoolkit.ai/docs/ui/troubleshooting) docs for the recommended upgrade flow and recovery steps.

  Delegating to a worker with `clear=true` now correctly shows a fresh session card in the TUI dashboard. Previously, the session-reuse guard introduced for opencode deck continuity would remap a respawned agent's new `session_id` back to the old one, making it appear as though no new session had started — even though the daemon had correctly killed and respawned the worker process.
  The reuse logic now checks the `agent_id` carried in each `SessionStart` event before applying the remap. When the same agent restarts naturally within a pane (e.g., an opencode crash or config reload), the session card is reused as before. When a different `agent_id` arrives — which is what happens after a `clear=true` delegate — the reuse is skipped and a new session card is created, so the dashboard accurately reflects the fresh agent run.
  Pre-F9 hook scripts that emit `SessionStart` without an `agent_id` continue to fall through to the reuse path, preserving backward compatibility.
- **Orchestration Tabs Restored on Remote Reconnect**
  Fixes orchestration panes being dumped onto the dashboard tab when a TUI reconnects to a daemon running on a different host (e.g., a laptop TUI reconnecting to a VM daemon). Previously, the hydration code tried to load the config file from the daemon's local path—a path that doesn't exist on the TUI's machine—causing every active orchestration session to silently fall back to the dashboard instead of appearing in its own orchestration tab.
  The TUI now synthesises a minimal `OrchestrationConfig` directly from the metadata already present in the daemon's `list_agents` response (orchestration name, role names, and role indices). The synthesised config is structurally complete, so tabs are rebuilt correctly without needing access to the daemon-side config file. When the config file *is* available locally (same-host connections), it is still used to enrich display-only fields like `description` and `prompt_template`—no regression for local connections.
  The active-tab reset on reconnect is also fixed: after hydrating orchestration tabs the TUI now lands on the first orchestration tab rather than unconditionally snapping back to the dashboard. Users reconnecting to running orchestration sessions will find their tabs where they left them.
  Security hardening included: role indices from the wire are capped at 256 (preventing multi-gigabyte allocation from a malformed daemon response), and role and orchestration names are validated to reject control bytes and ANSI escape sequences that could disrupt terminal rendering or spoof tab labels.

  Workspace modes transform dot-agent-deck from a multi-agent dashboard into a focused development environment. When AI agents execute commands, relevant output now appears in dedicated side panes alongside the agent instead of being buried in the conversation.
  Each mode is defined in a per-project `.dot-agent-deck.toml` config file. Modes create tab-based workspaces with an agent pane on the left and configurable side panes on the right in a 50/50 layout. Side panes come in two types: persistent panes run predefined commands immediately (e.g., `cargo watch -x test`, `kubectl get pods -w`), while reactive panes populate automatically when the agent executes commands matching user-defined regex rules (e.g., `kubectl describe`, `terraform plan`). Watch rules periodically re-execute commands via the built-in `dot-agent-deck watch` subcommand for live-updating output.
  Mode activation is integrated into the new-agent flow: press `Ctrl+n`, select a directory, and if a `.dot-agent-deck.toml` exists, cycle through available modes with arrow keys in the unified form. Tab navigation uses `Tab`/`Shift+Tab`, arrow keys, or `h`/`l` for vim users. Side panes support keyboard focus (`j`/`k`), click-to-focus, and full shell interaction via `Enter` on a focused pane. The `dot-agent-deck init` command scaffolds new config files, and `dot-agent-deck validate` checks config correctness. An agent-driven config generation flow (`g` on dashboard cards) analyzes the project and proposes a config interactively.
  See the [Workspace Modes Guide](https://devopstoolkit.ai/docs/ui/workspace-modes) for configuration examples and usage details.

  Pick up where you left off with automatic session persistence. Previously, launching `dot-agent-deck` always started from a blank slate, requiring users to re-open every agent pane, reselect directories, re-enter names, and retype commands each time.
  The dashboard now automatically tracks every pane's launch metadata (directory, name, and command) while running and persists the full pane set on exit — no explicit save step required. The deck's permission UI (y/n approval) was already disabled, making the blocking hook purely harmful.
